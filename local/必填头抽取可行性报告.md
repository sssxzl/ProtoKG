# F 阶段：RFC 源产「必填头」可行性报告（附三条负结果）

> 日期：2026-11-05
> 目标：让 `required_headers` 桶（**当前 100% 来自骨架**）有 RFC 源来源 ⇒ 纯净度提升，
> 且必填头直接决定种子报文是否被服务器接受 ⇒ 对 fuzzing 效果的影响**量级大于状态名**。
> 脚本：`local/_pilot_required_headers.py`（确定性）、`local/_pilot_required_headers_llm.py`（LLM）

| 路线 | 可行性 | 实测 |

## 1. 负结果一：确定性路线不可行（三条证据）

### 1.1 句级路线：语义混淆 + 误报

扫 RFC 里的规范性句（MUST/SHALL + 头名）：

| 协议 | 抽到的头 | 问题 |
|---|---|---|
| rtsp | Cache-Control / Content-Length / Proxy-Require | ★ **全是误报**（可选头、代理头），骨架版的 CSeq/Session/Transport **一个都没抽到** |
| sip | 17 个（含 Min-Expires / WWW-Authenticate / Retry-After / Content-Type…） | ★ **大量是响应头或条件必填** |
| smtp | Resent-From / Return-Path | 条件必填，非消息级 |

⇒ 覆盖率：rtsp **0/3**、sip 3/8。

### 1.2 根因：RFC 的必填性用**指代句式**表达，正则抓不到

RFC 2326 里 **不存在** `CSeq MUST ...` 这类表述。实测：

- 第 2825 行（§12.10 CSeq 节内）：`This field MUST be present in all requests and responses`
  ⇒ 句子里**没有头名**（只有 "This field"）⇒ 正则必然漏。

⇒ ★ **这是"必填头"这类语义知识与"状态转移表"的结构性差异**：
状态转移表是**结构化的**（表格 ⇒ 可确定性解析），
而必填性是**散在散文里的指代句**（⇒ 必须读上下文）。

### 1.3 节级路线（标题里的头名 + 节内规范句）：部分可行，但收紧后反而变差

| 口径 | rtsp | sip |
|---|---:|---:|
| 节级（不加量词约束） | 3 个 | **17 个（覆盖 6/8=75%）** |
| 节级 + 「所有请求」量词 | 4 个（覆盖 **1/3**） | 17 个（覆盖 **3/8=37.5%**） |

⇒ ★ 收紧后**覆盖率下降**（sip 75%→37.5%）、**误报仍在**
（句级路线不受量词约束 ⇒ Cache-Control / Content-Type 等仍被收进来）
⇒ **两条路线的语义不一致，无法靠规则对齐** ⇒ 判定为不可行。

## 2. LLM 路线：可行（并暴露一个更深的发现）

`local/_pilot_required_headers_llm.py`：把形态层的 `table` + `normative` 块喂 LLM，
注入**已知头名列表**做约束，要求只收「所有请求都必带」的头并给出 RFC 证据句。

| 协议 | 候选块 | 抽出 | 覆盖率 | **误报** |
|---|---:|---:|---:|---:|
| **sip** | 312 | 6 | **6/8 = 75.0%** | **0** ✔ |
| rtsp | 45 | 2 | 1/3 = 33.3% | 1（`Require`，证据是 `Require R req. all` ⇒ ABNF 碎片 ⇒ 误报） |

### 2.1 ★ 副产物：骨架版的 `required_headers` **语义分层有问题**

rtsp 骨架版 = `CSeq` / `Session` / `Transport`，三者**不同层级**：

| 头 | 实际层级 | RFC 依据 |
|---|---|---|
| `CSeq` | **消息级**（每个请求都带） | §12.10 "MUST be present in all requests and responses" |
| `Session` | **响应级 → 对话延续头**（服务器返回、客户端在后续请求回带） | §12.37 |
| `Transport` | **方法级**（仅 SETUP 必带） | §10.4 |

⇒ 骨架版把三者**一律按「每方法必带」**投影 ⇒ 骨架对每个方法都加 `Session`/`Transport`
⇒ ★ 生成的报文**带上了本不该带的头** ⇒ 与 RFC 语义不符。

⇒ **LLM 抽法（严格消息级）反而更正确** ⇒ 这也解释了 rtsp 覆盖率只有 1/3：
**不是 LLM 漏抽，而是骨架版的「3 个」本身就不都是消息级必填。**

⇒ ★ **这意味着 F2（用 RFC 源替代骨架版）会改变种子报文构成**（`Session`/`Transport`
不再对每个方法必带）⇒ 这是**语义纠正**，方向正确，但**会改种子** ⇒ 必须重立基线。

## 4. 落地设计（分两步）

### F1（安全，零产物变化）：RFC 源抽消息级必填头 → **并集投影**

- 新增 aspect `required_header_global`（**消息级**）；
- LLM 抽取（注入已知头名列表 + 「所有请求都必带」口径 + 证据句）；
- **投影进现有 `required_headers` 桶（并集）**，骨架那份**保留**；
- ⇒ **种子逐字节不变**；但论文可报告「RFC 源**独立**抽到 X 个消息级必填头，
  与骨架版交集 Y、差集 Z（且 Z 为骨架版的语义误置项）」。

### F2（★ 经实测**重新定义**）：从「替代骨架」改为「**独立复核**」

> ⚠️ **原设想已被实测推翻**（2026-11-05 交叉校验，`local/_crosscheck_required_headers.py`）：
> 原设想 F2 = 「用 RFC 源那份**替代**骨架那份 + 按消息级/方法级分层」。**实测不成立**：

| 实测项 | 结果 | 推翻了什么 |
|---|---|---|
| 骨架的 `required_headers` 是什么层级？ | **方法级**（rtsp：SETUP 带 `Transport`；PLAY/PAUSE/TEARDOWN 带 `Session`；DESCRIBE/OPTIONS 只带 `CSeq`） | ❌「骨架把三者一律按每方法必带投影」 |
| 报文里是否带上了不该带的头？ | **没有** —— 取值池有真实值（`Session: 12345678`、`Transport: RTP/AVP/TCP;unicast;interleaved=2-3`） | ❌「报文带上本不该带的头 ⇒ 种子废掉」 |
| RFC 源抽的消息级 ⊆ 骨架方法级并集？ | **是，零缺口零误报**（rtsp `CSeq`；sip 6 个） | ❌「两者是替代关系」 |
| 「替代 / 叠加」的增量？ | **0**（RFC 抽到的全被骨架覆盖） | ❌「F2 有增量」 |

⇒ ⇒ ★ **F2 的真正价值不是「替代」，而是「独立复核」**：
RFC 源从 RFC 原文**独立**抽出的消息级必填头，与骨架那份**一致**（零缺口），
且骨架多出的头**恰好是方法级专属**（rtsp `Session`/`Transport`；sip `Contact`/`Event`）
⇒ **证明骨架这一维经得起 RFC 独立复核**
⇒ 这是「RFC 单源纯净度」的**正面证据**，而不是「骨架是污染源」的负面判断。

**交叉校验结果**（`local/required_headers_crosscheck.json`）：

| 协议 | RFC 源独立抽出（消息级） | 交集 | 骨架独有（方法级专属） | 判定 |
|---|---|---|---|---|
| rtsp | `CSeq` | 1 | `Session`(5 个方法) / `Transport`(SETUP) | ✅ 一致 |
| sip | `CSeq, Call-ID, From, Max-Forwards, To, Via` | **6** | `Contact`(REGISTER) / `Event`(SUBSCRIBE) | ✅ 一致 |
| smtp | （行命令协议无头字段概念） | — | — | ✅ 适用性豁免 |

**落地（F1 已完成）**：RFC 源的消息级必填头作为 **aspect=required_header_global** 留在中枢
（**不进任何 bundle 桶** ⇒ 产物逐字节不变），跨校验脚本可复现该结论。

**若仍要做「替代」**：需先把「消息级 / 方法级」在 bundle 里显式分层，再逐协议比对新旧报文
⇒ **仍需端到端 ChataFL 验证**才知收益；当前实测增量 0 ⇒ **优先级低**。

## 5. 不可计算 / 未覆盖项（诚实声明）

- 本轮**未修改任何生产代码**（纯试点 + 报告）⇒ 护栏基线未受影响；
- ★ **LLM 抽出的必填头未经人工标注核验**：sip 的 6 个与骨架版交集且零误报（较强证据），
  但 rtsp 只有 1 个交集 + 1 个明显误报 ⇒ **准确率未测**（无人工真值）⇒ 不可计算；
- sip 的 75% 覆盖率里，未抽到的 2 个（`Contact` / `Event`）**恰恰是方法级**头
  （`Contact` 仅 REGISTER 必带、`Event` 仅 SUBSCRIBE 必带）⇒ ★ **这反证了
  「消息级 vs 方法级」分层是必要的**，而不是 LLM 漏抽；
- 未做**多温度重复**，LLM 抖动未估计；
- 试点只跑了 rtsp / sip，**smtp 的 LLM 路线未跑**（smtp 无头字段概念 ⇒ 不适用）。
