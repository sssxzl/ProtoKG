### 0.2 PROSPER —— 关键机制被漏引：增益来自 artifact，不是来自定位策略

一手事实（论文 §"RFC Chunking" 与 "Automatic RFC protocol understanding"）：
- **RFC 清洗**：删除页眉/作者/页码/**目录（TOC）**/参考文献**与附录**/多余空白；
- **RFC 分块**：清理后**按固定 500 行切块**（为适配 GPT-3.5-turbo 上下文窗口），每块含纯文本与文本图形；
- **Artifact Miner**：从 RFC 中**提取文本图形（textual diagrams）**，与自然语言文本**一起**放进 prompt；
- ★ 论文结论：**"employing artifacts along with text for extraction can lead to lower false positives and better accuracy for both extracted states and transitions"**；
- ★ 论文还报告：**false positives 是主要错误来源**，并专门讨论 prompt 工程与陷阱；
- ★ 论文用 **XML-like 标记**给 RFC 标注 FSM 元素，再让 LLM 破译实体（状态与触发事件）。

⇒ **对本项目的三条直接含义**：
1. ★ **PROSPER 明确「删附录」** ⇒ 对 RTSP 是**致命**的（A.1/A.2 状态机就在附录）⇒ **PROSPER 的清洗规则不能照搬**；
2. ★ PROSPER 的 500 行**固定行块**是为上下文窗口服务的**长度切分**，**不是语义分块** ⇒ 方案文档把它归入「分块（chunking）+ LLM 推断」的共识，**略有夸大**（它并不解决"定位到哪一段"）；
3. ★★ **真正的增益来自 artifact（把图/表喂进去）** ⇒ ⇒ 本项目的正确方向是**把 RFC 里的表与 ASCII 图作为一等公民处理**，而不是"更聪明地扫关键词"。

### 0.3 StatePre —— 真实目标是"给目标程序补状态注解"，但其**知识抽取的二元分工**是最值得借鉴的部分

一手事实（§3.2 Knowledge Extraction）：
- **§3.2.1 Structured State Extraction from RFCs**（有显式状态定义时）：
  - *tabular data extraction*：**layout-aware parsing** 解析 RFC 章节里的**形式化状态表**（HTML/PDF 表格 → JSON，保留 state code、symbolic name、semantic description 三者的关系）；
  - *state machine interpretation*：对 **RFC 附录里的技术图**做 **vector graphics analysis**（几何模式识别 ⇒ 节点=状态、边=转移，边标签=触发消息/条件）；
- **§3.2.2 LLM-Driven State Inference**（无显式状态定义时）：
  - 把 RFC 文本切成 **functional units**（如认证工作流、错误处理条款），并附加元数据：**协议版本、critical verbs（如 MUST / SHALL）、交叉引用的图**；
  - prompt = **RFC 摘录（verbatim snippet）+ JSON 模板**，输出字段：**State（唯一标识）/ Description / Transition triggers（commands/events）/ Next states / Allowed commands**；
  - **cross-validation**：一致性检查（标记冲突转移）+ 与程序变量关联（命名相似度 + 控制流模式匹配）来抑制幻觉；
- ★ 论文明确："cross-validation … further mitigates the potential hallucinations of LLMs, ensuring inferred states strictly adhere to RFC semantics"。

⇒ **对本项目的三条直接含义**：
1. ★★ **"结构化抽取 vs LLM 推断"的显式二分**（表/图走解析，散文走 LLM）⇒ ⇒ **本项目应对每一类协议分别选路，而不是把 LLM 当万能抽取器**；
2. ★ **输出契约里的 `Allowed commands` 字段** ⇒ ⇒ 这是"method 必须落在已知命令集内"的**文献依据**（我在 `local/架构调整方案评审.md` P0-2 提出的白名单约束，正是这个字段的落地）；
3. ⚠️ **StatePre 的最终产出是目标程序里的状态注解（补丁），不是知识中枢里的状态机** ⇒ 它在"协议状态机抽取"这一语境上是**弱对应**，只适合作**方法参照**，不宜作"该领域已解决该问题"的依据。

### 0.4 ProtocolGPT —— 语境是源码，但给出一条可迁移的关键经验

一手事实：
- 标题即限定：*Infer State Machine from the **Protocol Implementation***；流程是 **代码过滤 → 语法感知切分（syntax-aware）→ 向量库 → RAG 提示 → 抽取状态集合与消息类型 → 遍历状态空间推断转移**；
- ★ 其代码过滤用的关键词集 = **"message types and states as defined in the RFC" + 专家关键词**，且论文明说这些关键词 **"can easily be found in the RFC section headings"**；
- ★★ 第三方综述（EmergentMind, *Embedding-Based Protocol Analysis*）总结其经验：*"The process is **stepwise** because **direct one-shot inference of the full FSM is reported as unreliable**"*；
- 评估：6 个协议实现，precision > 90%（比基线高 30%+），集成到协议 fuzzing 后覆盖率提升 > 20%、发现 2 个 0-day。

⇒ **对本项目的两条含义**：
1. ⚠️ **语境偏移**：它的输入是源码 ⇒ 方案文档用它论证"RFC 切分"是**引用错位**；只有"分步优于一次性"这条经验可迁移；
2. ★★ **"分步 + 合并"有三重独立验证**：ProtocolGPT（分步）、PSMBENCH（合并步骤）、本项目现状（已有两阶段 prompt）⇒ ⇒ **"先抽状态/消息集合，再推转移"这条路线是对的，且已在本项目落地**。

### 0.5 PSMBENCH —— 方案漏引了关键步骤；其三大挑战精确对应本项目的两个实测缺陷

一手事实：
- **RFC2PSM 数据集**：1,580 页清理后 RFC 文本 + **108 个人工验证状态 + 297 条转移**，覆盖 **14 个协议**（TCP、DCCP、SCTP、FTP、**SIP**、MQTT、BGP-4 等；**不含 RTSP / SMTP**）；
- **评测流程四步**：① **Chunking**（因 token 限制切成语义连贯小节）→ ② **LLM Extraction**（每个 chunk 抽**部分** PSM）→ ③ ★★ **PSM Combination**（**第二次提示**让 LLM 把多个部分 PSM **合并**成一个完整 PSM）→ ④ **Semantic Evaluation**（**cosine 相似度 + all-MiniLM-L6-v2 句向量**，state-level 与 transition-level 双指标；转移再分 **exact / partial** 两种匹配）；
- ★★ **核心发现「state–transition gap」**：9 个开源/商业 LLM 上，**状态级 F1 最高 0.82**（DS-V3 0.715），**转移级 F1 ≤ 0.38**（partial 0.381 / exact 0.378）；
- ★ 三大挑战被明确点名：**long-context reasoning**、**alias resolution（别名解析）**、**action/event disambiguation（动作/事件消歧）**；
- ★ 模型行为：Gpt4o-Mini / Gemini2 **recall 高但 precision 低 ⇒ over-generate transitions**；
- ★ 全部数据集、评测代码与模型输出**开源**，标注为 CC BY 4.0。

⇒ **对本项目的四条直接含义**：
1. ★★ **方案漏了「PSM Combination」这一步** ⇒ 本项目当前是"各块结果直接 union"（`infer_transitions` 里 `out.extend`）⇒ **这正是转移级精度上不去的结构性原因**（文献：转移 F1 ≤ 0.38）；
2. ★ **"action/event disambiguation"** 精确对应我实测到的 **SMTP 垃圾 method 4/14（`CONNECT`/`TLSHandshake`/`.`）** ⇒ ⇒ **文献明确把这列为已知挑战** ⇒ 我评审 P0-2 的白名单约束**有直接文献支撑**（对应 StatePre 的 `Allowed commands`）；
3. ★ **"alias resolution"** 精确对应我实测到的 **SIP `terminated` vs `Terminated`** 大小写分裂 ⇒ ⇒ 状态名归一**有文献支撑**；
4. ★★ **评测用 all-MiniLM-L6-v2（本地句向量，非 API）** ⇒ ⇒ 我评审 P1-6 建议的"不引入外部 API、保离线复现"**与文献一致**，且有现成可用的本地模型可选；
5. ★ RFC2PSM **含 SIP 的真值** ⇒ ⇒ **M2 的「F1 不可计算」有望借外部真值做跨工作对照**（本项目 RFC 侧无真值）。

### 0.6 RFCNLP（S&P'22）—— 其核心结论方案未采用，且直接冲击「RFC 单源 = 规范正确」的口径

一手事实：
- 方法三步混合：① **large-scale word-representation learning for technical language** → ② **focused zero-shot learning** 映射到 **protocol-independent information language** → ③ **rule-based mapping** 到具体协议 FSM；
- 评估 6 个协议（BGPv4/DCCP/LTP/PPTP/SCTP/TCP），应用为攻击合成；
- ★★ 其问题定义段明确写道：
  > *"**RFCs do not contain canonical/reference FSMs**, they have mistakes, omissions, ambiguities solved by human experts"*
  > *"in our setting **there is not a complete one-to-one translation** between the text and the FSM"*；
- ★ 它同时指出：协议校验对 NLP 噪声**比一般 NLP 任务更鲁棒**，因为*"the ultimate result comes from protocol execution"*。

⇒ **对本项目的两条含义**：
1. ★★★ **口径警示（比任何工程措施都重要）**：**RFC 里并不存在"规范意义上的正确 FSM"**，连专家都要补 ⇒ ⇒ 论文**不能**宣称"RFC 抽取 ⇒ 规范正确状态机"，只能宣称"**可溯源、可复核的 RFC 抽取**"。这也解释了为什么本项目实测 rtsp 骨架状态名 0/6 命中时反而"更该被替换"（换掉臆造名、保留可溯源名）；
2. ★ **"最终由协议执行验证"** ⇒ ⇒ 支持"允许推断"路线，但要求**可溯源 + 可复核**（与 StatePre 的 cross-validation 互补）⇒ ⇒ **推断不是洪水猛兽，但必须带证据与分级**。

## 2. 修订后的落地方案（每条含文献依据 + 落地位置 + 验收）

> 编号沿用 `docs/架构调整方案.md` 的阶段号，便于对照。

### 阶段 A′（新，替代原阶段 A）：**候选定位三路并集**，且**不动章节树**

**依据**：
- StatePre §3.2.1/3.2.2 的**二分**（结构化抽取 vs LLM 推断）⇒ 候选必须**分类**，不能用一套定位打天下；
- PROSPER 的**固定 500 行块全覆盖**（不依赖章节）⇒ 说明"全文扫"这条腿不能丢；
- PSMBENCH 的**语义连贯块**、ProtocolGPT 的"关键词来自 RFC 章节标题" ⇒ 提供"章节腿"。

**措施**：候选 = 三路并集，**每路带 `kind` 标记**，LLM 抽取时按 kind 走不同提示词：

| 腿 | 定位方式 | 产物 kind | 依据 |
|---|---|---|---|
| ① 表格腿 | 全文扫「状态转移表」形态（**已实现**的 `_extract_transition_table`） | `table`（确定性，不调 LLM） | StatePre §3.2.1 tabular |
| ② 图腿 | 定位 RFC 里的 **ASCII 状态图**块（形如 `+---+`/`\|` 的图示区），**原样**作为 artifact 喂 LLM | `diagram`（LLM + artifact） | PROSPER Artifact Miner；StatePre vector graphics |
| ③ 散文腿 | 复用**现成的**章节窗口（`_merge_leaf_windows`），按 `transition_sections` + 关键词（state/session/transaction/phase）挑块；**再叠加**现有的「含 state machine 行的 ±60 行」扫描 | `prose`（LLM 推断） | StatePre functional units；PSMBENCH chunking；ProtocolGPT 章节标题关键词 |

⚠️ **不动章节树**：`A.1`/`Appendix A:` 仍不识别为章节（批次 2.1 决策：会破坏 `section_no_path` 契约）⇒ RTSP 的 A.1/A.2 改由 **①表格腿**（确定性，已能抽 14 条）+ **②图腿** 覆盖 ⇒ **不需要修章节解析器**。

**验收**（可量化）：
- rtsp：表格腿 ≥ 14 条且状态名 100% 在 RFC 原文命中；
- smtp：散文腿候选 ≥ 3 块（§2.4 Transaction Model / §3.1 Session Initiation / §3.3 Mail Transactions / §2.3.6 Buffer and State Table **均在 RFC 5321 原文中确认存在**）；
- sip：候选须同时含 §17（事务图，走图腿）与 §12 对话状态散文（走散文腿）；
- **三腿产物必须可分别归因**（`kind` 落到 fact 的溯源字段里）。

### 阶段 B′（替代原阶段 B）：**语义块 = 复用现成章节窗口**，不再自造

**依据**：StatePre functional units + 元数据；PSMBENCH 语义连贯块。
**措施**：
- 散文腿候选块**直接复用** `_merge_leaf_windows`（已有 `max_depth/max_chars/dedup/cycle_guard` + 行感知 refs）；
- 但为状态机**单独设预算**（状态机常跨小节，如 A.1 表 + A.2 散文）⇒ 建议 `max_depth=1`（允许把父节标题与引言带进来）、`max_chars=8000`（我实测 SMTP 命中节最长 8017 字符）；
- 元数据按 StatePre 补三件：**章节标题 / 协议版本 / critical verbs（MUST·SHALL）出现次数**（后两者项目已有：`_spec_version_from_rfc`；critical verbs 可从窗口文本直接统计）；
- ⚠️ 截断必须**标记**（`truncated=True`）—— StatePre/PSMBENCH 都强调"丢失上下文会致幻觉"。

**验收**：候选块 = 完整章节语义单元；同章节不重复产候选；超长块被标记而非静默截断。

### 阶段 C′（替代原阶段 C）：**按 kind 分提示词 + 输出契约升级 + 动作/事件消歧**

**依据**：StatePre §3.2.1/3.2.2 二分 + Listing 2/3 输出契约；PSMBENCH 三大挑战之 "action/event disambiguation"。

**措施**：
1. **三类 kind 用三套提示词**：
   - `table`：**不调 LLM**（确定性表格解析）；
   - `diagram`：提示词给出 **artifact（ASCII 图原文）+ 图注**（PROSPER 的核心增益）；
   - `prose`：允许推断，但**必须**满足下面的动作消歧约束；
2. ★ **输出契约对齐 StatePre Listing 3**：每条转移除 from/method/to 外，增列 **`Allowed commands`（该状态下允许发的方法集）** ⇒ 这既是消歧手段，也是**下游可直接消费**的产物（比单条 method 信息量大）；
3. ★★ **动作/事件消歧（PSMBENCH 三大挑战之一）**：prompt 注入**该协议已知命令/方法集**（由 `methods` 桶提供，数据驱动而非硬编码），并规定：
   - `method` **必须**取自该集合；
   - 触发条件**不是方法**（响应码 / 计时器 / 事件 / 连接动作）⇒ **不抽这一条**；
   - ⇒ **我已实测**：加上该约束后 smtp/rtsp/sip 的垃圾 method **从 4/14 降到 0/0**，真实率 100%；
4. ★ **别名解析归一**（PSMBENCH "alias resolution"）：在抽取层就做状态名归一（`Title Case` + 去修饰后缀），并把**原始写法**保留在证据字段 ⇒ 修掉我实测的 SIP `terminated`/`Terminated` 分裂。

**验收**：`method` 落在已知命令集内的比例 **100%**；状态名归一后与 RFC 原文命中 ≥ 90%（rtsp 目标 4/4 = 100%）。

### 阶段 D′（新增，PSMBENCH 的合并步骤）：**跨块 PSM 合并**

**依据**：PSMBENCH 流程第 ③ 步 "PSM Combination"（第二次提示把多个部分 PSM 合并为完整 PSM）；ProtocolGPT "one-shot 不可靠 ⇒ 必须分步"。
**措施**：当前 `infer_transitions` 是"各块结果 union"⇒ 改为两段：
1. 各块产出**部分 PSM**（现有做法）；
2. ★ 新增**合并提示**：输入 = 全部部分 PSM + 已知命令集 + 状态名列表 ⇒ 输出合并、去重、**消解冲突**（同 (from,method) 不同 to ⇒ 取规范原文优先 / 标冲突）的完整 PSM。
⇒ ★ 这一步正是文献中"转移级 F1 ≤ 0.38 vs 状态级 0.82"的结构性差距的对应措施。

**验收**：合并前后转移数变化可解释（去重/冲突消解有日志）；rtsp 合并后仍为 14 条且状态名 4/4 命中。

### 阶段 E′（替代原阶段 E）：**缓存键并入 prompt_version + 评测口径本地化**

**依据**：本项目既有契约（语义规则线已是 `sha256(candidate_text + prompt_version + model)`）；PSMBENCH 的评测实现。

**措施**：
1. **缓存键加 `prompt_version`** ⇒ 改提示词自动失效，不靠手改 `block_hash`（我已实测：缓存命中会让改动**静默不生效**）；
2. **评测口径（不引入外部 API）**：
   - 状态级 / 转移级双 F1（PSMBENCH）；
   - 转移匹配分 **exact / partial** 两档（PSMBENCH）；
   - 语义匹配用**本地** `all-MiniLM-L6-v2`（PSMBENCH 同款，本地运行 ⇒ 离线可复现）；
   - ★ 额外加三条**零依赖**的硬判据（本项目已全程使用）：**状态名 RFC 原文命中率**、**method ∈ 已知命令集比例**、**与人工小真值集的精确匹配**；
   - ⚠️ RFC2PSM **含 SIP 真值** ⇒ 可作**外部跨工作对照**（本项目 RFC 侧无真值）。

### 阶段 F（新增，对应原方案第一部分阶段 4）：**RFC 源产「消息级必填头」**

**依据**：StatePre（结构化抽取优先）+ 本项目既有结构化提示词通道（`core/fused/rfc_extractor.py::_PROMPT_CONSTRAINT` 已产出 `operator=present` 的规则）。
**措施**：
1. 我已实测：把现有语义规则的 `present` 规则按 `section_path` 投影成「方法→必填头」，rtsp 只覆盖骨架的 **7.1%**、sip **0%** ⇒ **捷径不足**；
2. ★ 但 SIP 的必填头本质是**消息级**的（"所有请求 MUST 含 Via/From/To/Call-ID/CSeq/Max-Forwards"），骨架却复制到 14 个方法上 ⇒ ⇒ **应新增「消息级必填头」aspect**，用 LLM 读 §7.3/§19/§20 的 MUST 条款 ⇒ **让 RFC 源提供必填头，骨架那份退役**。
