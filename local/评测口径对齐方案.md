> 用户决策（2026-11-03）：「后期等调试都结束，最后验证效果也按照他们的指标和方式来」
> 本文档 = 把这句话落成**可执行的评测设计**。
> 前置依赖：批次 2.5 的跨源污染修复（D21）—— 否则真值与投影都带污染。

## 0. 为什么必须「按他们的口径」

三篇论文报的是**三个正交维度**，我们此前一个都没量：

| 维度 | 谁报的 | 口径 | 我们现状 |
|---|---|---|---|
| **E1 抽取准确率** | FlowFSM / SpecGPT | 转换级 P/R/F1（人工真值） | ❌ **没有**（无真值 ⇒ 算不出） |
| **E2 生成物有效率** | SemFuzz | test-case validity（可编码 + 可发送） | ❌ 没有（只有 G1/G2，维度不同） |
| **E3 动作序列消融** | SemFuzz | 完整 vs `w/oAction` | ⚠ 有机制（⑤ 层），**但用 G2 量 ⇒ 口径错配** |
| **E4 漏洞** | SemFuzz | 规则驱动预言机 | ❌ 没做 |
| **E5 覆盖广度** | **前人都没有** | 状态/边/方法覆盖 | ⚠ 我们有 G1/G2（不是覆盖率） |

⇒ **E1 是让前人无法把我们排除在外的一维**；**E2/E3 是让我们的 ⑤ 层价值可被验证的两维**。

## 1. E1 抽取准确率（对齐 SpecGPT / FlowFSM）

### 1.1 计数单位与匹配规则（**照 SpecGPT 原文**）

SpecGPT 原文：
> "a state machine transition is considered correct only if the states match exactly, and both
> the condition and action spans overlap beyond a specified threshold, which we set as 0.75"

⇒ 我们采用**同样的四元组 + 同样的 0.75 阈值**：

```
T = (S_init, A, C, S_next)
匹配条件：S_init 与 S_next **严格相等**
         且 span_overlap(A_pred, A_gold) ≥ 0.75
         且 span_overlap(C_pred, C_gold) ≥ 0.75
span_overlap(x, y) = |交集词数| / min(|x|, |y|)      ← 短者归一
```

### 1.2 真值（ground truth）怎么来 —— **不用 210 人时**

SpecGPT 用了 **210+ 人时**标注 3GPP 规范。**我们走另一条路**：

| 步骤 | 做法 | 工时 |
|---|---|---|
| ① **机器初稿** | 用**确定性抽取器**（`rfc_extractor._extract_transition_table`，全文扫状态转移表）直接产出候选四元组 | 0（已有） |
| ② **人工复核** | 人工逐条核对「机器初稿 vs RFC 原文」，标记 TP/FP/FN | **1–3 人时**（RTSP 客户端状态机量级） |
| ③ **补漏** | 人工扫原文，补机器漏掉的转移 | 同上 |
| ④ **争议仲裁** | 同一处 RFC 有歧义 ⇒ 记为「不计分」，并登记 | 少量 |

⚠ **实测基础**：RTSP RFC 2326 附录 A.1 的状态转移表，**确定性抽取已能抽 14 条、与原文逐条一致**
（批次 2.1 的成果）⇒ 步骤 ① 的质量足够做初稿。
⚠ **扩展**：服务端散文状态机 + SIP ASCII 图（批次 P1 待办）⇒ 真值范围随之扩展。

### 1.3 报什么（**两个数都报，避免被质疑挑口径**）

| 指标 | 口径 | 对标 |
|---|---|---|
| **F1@0.75**（主口径） | SpecGPT 口径：状态严格相等 + span 重叠 ≥0.75 | SpecGPT 91.14（NAS） |
| **F1-strict**（辅口径） | 状态 + 动作**全等**（不含条件重叠容差） | FlowFSM 的人工严格核对风格 |
| 分量准确率 | action 准确率 / condition 准确率 / 目标态准确率 | SpecGPT 的分量报法（86.41 / 92.94） |

⚠ **同时报两个口径的理由**：SpecGPT 的 0.75 重叠**放宽**了条件匹配的容忍度，
若只报宽口径，会被质疑「你的条件匹配太松」；若只报严口径，又会低估。
⇒ **报区间（F1-strict ~ F1@0.75）比报单点更可信**。

### 1.4 必须先做的前置修正

⚠ **跨协议规则必须先修**（D21-F1）：RTSP 规则库 3/5 条是 SIP 的 RFC 3261
⇒ 若不修，`legal_boundary` 投影出来的约束是错的 ⇒ **E1/E4 的真值与投影都不可信**。

## 2. E2 test-case validity（对齐 SemFuzz 的 87%）

### 2.1 SemFuzz 的原文定义

> "The accuracy of test cases (𝒯) is determined by their syntactic validity; a test case is
> deemed correct if it can be properly encoded and successfully sent."

⇒ **两个条件**：① 可编码为协议报文 ② 可成功发送。

### 2.2 我们的实现

| 条件 | 我们的现成资产 | 要补的 |
|---|---|---|
| ① 可编码 | `core/fused/raw_writer`（写 .raw）+ `bundle` 的字段渲染 | ✅ 已有；补一个「编码器不抛异常且报文非空」的判定 |
| ② 可发送 | ChatAFL/VM 实验链路：`local/_replay_seed.py`、`local/_smoke_client.py`、`_smoke_req.json` | 需要一个**批量回放器**：把种子逐条发到目标环境，记录「发送成功 / 收到合法响应」 |

⚠ **口径细节（SemFuzz 最容易被误读的地方，必须照做）**：
- SemFuzz 的 **87%** 是 **4 个协议准确率的**「宏平均」，不是 5,940 条上的整体比例
  （它报的「1,271 条」是**每协议平均条数**）
- ⇒ 我们报的时候**必须同时写清楚**：分子分母各是什么、宏平均还是微平均
- ⚠ 这正是我们上一轮「G2 绝对数下降被误读成质量改善」的同款陷阱

### 2.3 报什么

```
test_case_validity = 有效条数 / 总条数
  有效 = 可编码 ∧ 可发送 ∧ 目标返回**协议合法**响应（非 5xx/非连接错误）
分层报：base 层 / ⑤层（mutation 层）分别报
```
⚠ SemFuzz 的分层是 `base` / `mutation`（对应我们的基准层 / ⑤层）⇒ **正好可比**。

## 3. E3 动作序列消融（复现 SemFuzz 的 36%→87% 对照）

### 3.1 这是**决定性实验**

我们批次 1 的结论是「价值指标（G2 / SemFuzz「36%→87%」）未兑现」。
⚠ 现在查明：**那是因为拿 G2（不可播会话占比）去对标 SemFuzz 的 test-case validity（可编码可发送率）** ⇒ **口径错配**。

⇒ **E3 用正确口径重做这个对照**，就能回答「我们的 ⑤ 层到底有没有用」。

### 3.2 对照设计（照 SemFuzz）

| 组 | 配置 | 对应 SemFuzz |
|---|---|---|
| **完整** | 含 ⑤ 层 action_seq 变异 | SemFuzz |
| **w/oAction** | 关 ⑤ 层（`--layers edge_cover,generic_danger,vuln_boundary,canonical`） | w/oAction |

⇒ 指标 = **E2 的 test-case validity**（不是 G2）
⇒ **预期**（若我们的 action_seq 与 SemFuzz 同机制有效）：完整组 validity 显著高于 w/oAction 组

⚠ **诚实预判**：SemFuzz 的增益高度不均（TLS 79→6、IPv6 91→22 崩最狠，HTTP 88→70 较轻）。
⇒ 我们**应当分协议/分层报**，不能只报一个总均值。

### 3.3 我们比 SemFuzz 多一个维度

SemFuzz 只做了「模块开/关」。我们可以做**三档消融**（批次 2.3/2.4 已建好）：

| 档 | 知识来源 | 对应 SemFuzz |
|---|---|---|
| 规范单源 | RFC | （SemFuzz 无对应） |
| +实现侧 | + 源码分析 | （SemFuzz 无对应） |
| +观测侧 | + 真实流量 | （SemFuzz 无对应） |

⇒ **这是我们的差异化点**：SemFuzz 的知识只有「规范 + LLM 推断」，
而我们能回答「**多源异构知识对生成物有效率的边际贡献是多少**」。

## 4. E4 漏洞（SemFuzz 的终点）—— 可选，放在最后

- 前提：E1 真值 + 规则按协议过滤（否则预言机判据是错的）
- 机制：**规则驱动**的响应比对（实际响应 ≠ 预期响应）⇒ 我们已有
  `response_expectation` 投影，只需接上比对器
- ⚠ 我们是**黑盒**（live555 目标）⇒ 与 SemFuzz 同处境
- ⚠ 预期：短期内难出 CVE（我们没有插桩、没有 CVE 提交流程）⇒ **不作为主指标**

## 5. E5 覆盖广度（我们独有，前人没做）

| 指标 | 定义 | 分层 |
|---|---|---|
| 状态覆盖 | 种子能到达的状态数 / RFC 状态机状态数 | 规范 / +实现 / +观测 |
| 边覆盖 | 种子能走过的转移数 / 转移总数 | 同上 |
| 方法覆盖 | 种子用到的协议方法数 / 方法全集 | 同上 |
| 资源覆盖 | 种子覆盖的可播流数 / 可播流总数 | — |

⚠ 真值来自 RFC 原文（状态机表）⇒ 可机器构建 ⇒ **不需要人工标注**
⇒ **E5 是唯一可以立刻做、且零人工成本的维度** ⇒ 建议作为 E1 之前的「热身」。

## 6. 执行顺序（含依赖与人工投入）

```
阶段 0（零人工，1 天）  跨协议污染修复（D21-F1/F2）+ 重标定基线
        ↓
阶段 1（零人工，1 天）  E5 覆盖广度：真值机建 + 三档消融报告
        ↓
阶段 2（★ 唯一需人工，1–3 人时）  E1 真值：机器初稿 + 人工复核
        ↓
阶段 3（1 天）           E2 可发送率判定器（批量回放器）
        ↓
阶段 4（★ 决定性，0.5 天）  E3 消融：完整 vs w/oAction（用 E2 口径）
        ↓
阶段 5（可选）           E4 漏洞预言机
```

⇒ **总计约 4 天 + 1–3 人时人工**
⇒ 对比参考：SpecGPT 标注 210+ 人时、SemFuzz 28 人时 ⇒ **我们用「机器初稿 + 人工复核」把成本压到 1/100 量级**
⇒ ★ **这本身就是论文的一个方法学贡献**：「用确定性抽取做真值初稿，人工只做复核」

## 7. 论文里的指标呈现建议（一张表）

| 维度 | 我们的报法 | 对标 | 前人有吗 |
|---|---|---|---|
| **E1 抽取准确率** | F1@0.75 + F1-strict（区间），分量准确率 | SpecGPT 91.14 / FlowFSM 85.71 | ✅ 有，我们补上 |
| **E2 生成物有效率** | test-case validity（可编码+可发送），**分层 + 注明宏/微平均** | SemFuzz 87% | ✅ 有，我们补上 |
| **E3 动作序列消融** | 完整 vs w/oAction，用 E2 口径；**再叠加三档源消融** | SemFuzz 36%→87% | ⚠ SemFuzz 只有前一半 |
| **E4 漏洞** | 规则驱动预言机（可选） | SemFuzz 10/16、4 CVE | ✅ 有 |
| **E5 覆盖广度** | 状态/边/方法覆盖 × 三档源消融 | **前人全都没有** | ★ 我们的新维度 |
| **E6 知识准入台账** | 每桶 {class, owner_source, count} ⇒ 单源实验可自证纯净 | **前人全都没有** | ★ 我们的新维度（可审计性） |

⇒ ★ **E5 + E6 + 「三档源消融」是我们相对三篇前人的差异化**：
前人只做「规范 → 状态机 → 种子」的单线流水线；
**我们是「规范 / 实现 / 观测 / 专家 / 漏洞」五源可归因的融合框架**，
并把「每条知识从哪来」做成**机器可审计**的台账。

## 8. 一句话总结

> 调试阶段先把**知识本身**做对（抽取准确率 E1 + 覆盖广度 E5）；
> 收尾阶段再把**效果**按前人口径量出来（E2 可发送率、E3 消融），
> 并用我们独有的 **E5 覆盖广度 + E6 知识台账 + 三档源消融** 立住差异化。
>
> ⚠ 前提：跨源污染必须先修（D21）—— 否则 E1 的真值与 E2 的样本都带污染，
> 量出来的数字对谁都没有意义。
