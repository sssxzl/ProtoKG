## 二、记录的问题（**未改任何代码**）

### 🔴 问题 1：RFC 抽不到**服务器方向**的消息类型 ⇒ 状态机断裂 ⇒ 种子覆盖度崩塌

**现象**：
| | 骨架里 | bundle 里 | 种子 |
|---|---:|---:|---:|
| 状态机边 | 6 | **3** | — |
| 报文实例 | 6 | **3** | — |
| 产出种子 | — | — | **1 条** |

被裁的 3 条边全用**服务器方法**：`DHCPOFFER` / `DHCPACK` / `DHCPNAK`。

**根因链**（实测逐层定位）：

```
① RFC 2131 §4.3 只有 5 个**客户端**消息的小节
   （4.3.1 DISCOVER / 4.3.2 REQUEST / 4.3.3 DECLINE / 4.3.4 RELEASE / 4.3.5 INFORM）
   ⇒ **服务器消息（OFFER/ACK/NAK）没有独立小节** ——
      它们只在 §3.1 的**散文**里被提及（"Each server may respond with a DHCPOFFER…"）
② ⇒ 标题式抽取拿不到它们 ⇒ RFC 方法集只有 5 个
③ ⇒ 骨架闸「方法必须在最终 methods 桶里」⇒ 把 3 条服务器边裁掉
④ ⇒ Init --DHCPDISCOVER--> Selecting 之后**没有出边**（Selecting--DHCPOFFER--> 被裁）
⑤ ⇒ 贪心游走只能覆盖 1 条边 ⇒ **只产出 1 条种子**
```

**量化影响**（实测对比）：

| 状态机 | 种子数 | 内容 |
|---|---:|---|
| 当前（3 条边） | **1** | `[DHCPDISCOVER]` |
| 完整（6 条边） | **2** | `[DISCOVER, OFFER, REQUEST, ACK, RELEASE]`（**完整黄金路径**）+ `[DISCOVER, OFFER, REQUEST, NAK]` |

⇒ **这是当前最严重的问题**：种子从「完整会话」退化成「单报文」。

**可能的修法（供判断，未实施）**：
- **A**：走 **LLM 散文抽取**（`infer_transitions` 的思路）——RFC §3.1 的散文里
  明写「client broadcasts DHCPDISCOVER → server responds DHCPOFFER → …」
  ⇒ LLM 能抽出完整状态机。但 DHCP RFC 里**没有 "state machine" 字样**
  ⇒ 现有 `_RE_STATE_MACHINE_HINT` 命中 0 ⇒ 候选块定位不到（需另找定位方式）。
- **B**：放宽骨架闸 —— 允许骨架里的方法即使不在 RFC 方法集里也保留
  （但会破坏「RFC 单源纯净度」主张：OFFER/ACK/NAK 确实是 RFC 定义的，
  只是抽取器没抓到 ⇒ 放宽闸是**合理的**，不是污染）。
- **C**：把服务器消息加进 `profile.seedgen.required_headers` 之类的**配置层**声明
  （绕过闸），但那样就不是「RFC 抽取的」了。

### 🟠 问题 2：DHCP 选项**没有取值** ⇒ 选项区全空

**现象**：中枢 `headers` 桶里有 **37 个选项布局**（code + 长度，✅ 抽到了），
但**所有选项的 `values` 都是 `None`** ⇒ 报文的 `msg.headers` 里没有选项
⇒ 渲染时选项区只有 `0x00` 填充 + 末尾 `0xff`。

**根因**：RFC 2132 只定义选项的 **code 与长度**，**不给具体取值样本**
（取值要靠协议语义推导，如 Subnet Mask = 客户端掩码）。

**判定**：**知识缺口，不是代码 bug**。选项的取值属「实现/场景知识」，
RFC 单源拿不到 ⇒ 与 `precondition`/`session_header` 同类。

**影响**：DHCP 的**选项变异**（⑤ 层 value-pool 变异）无从下手
⇒ 二进制协议目前只能变异**固定头字段**。

### 🟡 问题 3：选项区**偏移**在 `vend` 末尾（@300）而非 cookie 之后（@240）

**现象**：布局里 `vend`（BOOTP vendor 区，64 字节 @236）与 `magic_cookie`
（4 字节 @236）**重叠** ⇒ 渲染出的总长 = 300 ⇒ 选项区从 **@300** 开始。
但 RFC 2132 §2 规定：选项紧跟 **vendor 区的开头**（cookie 之后）⇒ 正确是 **@240**。

**当前不影响**（因为没有选项值要写 ⇒ 只多 60 字节 0 填充）；
**一旦有选项值**（问题 2 解决后）⇒ 选项会**偏移 60 字节** ⇒ 目标解析失败。

**根因**：位域图（RFC 1542）把 `vend` 画成 64 字节的 vendor 区，
而 DHCP（RFC 2132）把选项放在 vendor 区的**前 4 字节之后** ⇒
**两个 RFC 的布局语义不同**，位域图无法表达「区内的子结构」。

### ⚪ 问题 4：`gen_binary_layout.py` 每次运行都**累加** note 文本

profile.json 的 `note` 字段被重复追加同一句话（已累积 5 次）。
**不影响功能**，但让配置文件膨胀 ⇒ 需去重（幂等写）。
