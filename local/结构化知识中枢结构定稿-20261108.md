# 结构化知识中枢：结构定稿

> 2026-11-08 · **结构定稿**（不含数据；数据待框架落地后填充）
> 定位：「**针对目标协议的知识分类进行存储**；多个异构知识源抽出关于协议的知识，存入对应的位置。」
> 前置：`local/结构化知识中枢设计-v2-20261108.md`（v2 设计稿，本文档是其结构定稿）

---

## 〇、定稿的三条不变式

| # | 不变式 | 含义 |
|---|---|---|
| **I1** | **分类是第一维，源是第二维** | 存放位置由「知识的性质」决定，**不由来源决定** |
| **I2** | **同一槽位可有多源 claim** | 规范形式（RFC）与观测形式（traffic）是**同一知识点的不同证据**，不是两类知识 |
| **I3** | **源只作 provenance，不作特例** | 中枢**没有**「某源恒允许/恒禁止」的概念；允许与否由 `source_set` 统一判定 |

★ I2 修正了此前「method_sequence 只能由 traffic 给」的错误认识：
它**不是**「只能来自某源」，而是「**同一槽位上规范证据与观测证据并存**」。

## 一、目录结构（定稿）

```
derived/per_source/<协议>/
│
├── index/                              ← ★ 跨分类的全局索引
│   ├── entities.jsonl                  ← 实体主表（协议里有哪些东西）
│   └── slots.json                      ← 槽位填充统计（每槽位多少条/来自哪些源）
│
├── A_structure/                        ← 协议结构：有什么
│   └── structure.jsonl
├── B_interaction/                      ← 交互行为：怎么连
│   └── interaction.jsonl
├── C_constraints/                      ← 约束规则：必须/不许怎样
│   └── constraints.jsonl
├── D_construction/                     ← 构造渲染：怎么写出来
│   └── construction.jsonl
├── E_observation/                      ← 观测实现：实际什么样
│   └── observation.jsonl
├── F_security/                         ← 安全漏洞：哪里可能出错
│   └── security.jsonl
│
├── ledger.json                         ← ★ 纯度台账（分类 × 源 × 允许状态）
├── provenance.json                     ← 源清单与各源本次贡献（可溯源入口）
└── build_meta.json                     ← 构建元信息（build_id / schema_version / 时间 / 各源 build_id）
```

### 为什么是「每分类一个文件」而不是「每槽位一个文件」

| | 每分类一文件（**定稿**） | 每槽位一文件 |
|---|---|---|
| 读取「一个分类的全部知识」 | ✅ **一次读** | ❌ 读 N 次 |
| 读取「某槽位」 | 过滤 `slot` 字段 | ✅ 直接读 |
| 文件数 | **6 + 3**（可控） | ~25 |
| 槽位 schema 校验 | 需按 slot 分支校验 | ✅ 单一 |

⇒ **定稿：每分类一个文件**，`slot` 作为记录内的必填字段，`index/slots.json` 提供按槽位的统计索引。

## 三、记录结构（**全分类统一 schema**）

分类之间**共用一套记录结构** ⇒ 通用处理代码不需要分类分支。

```jsonl
{
  "record_id": "sip:B_interaction:transitions:sip:rel:register:idle->registered",
  "protocol": "sip",
  "category": "B_interaction",
  "slot": "transitions",
  "entity": {
    "entity_id": "sip:relation:register:idle->registered",
    "type": "relation",
    "name": "Idle → Registered via REGISTER",
    "canonical_name": "Idle→Registered",
    "aliases": [],
    "participants": [
      {"role": "source", "entity_id": "sip:state:idle"},
      {"role": "via",    "entity_id": "sip:method:register"},
      {"role": "target", "entity_id": "sip:state:registered"}
    ]
  },
  "condition": {"type": "always"},
  "claims": [
    {"claim_id": "c_8519af82",
     "owner": "rfc",
     "value": {"type": "text", "data": "Registered"},
     "epistemic": "normative",
     "evidence": [{"source": "rfc", "file": "rfc3261.txt", "line": 9019,
                   "span": "the client transitions to the Registered state"}],
     "confidence": "high",
     "extracted_at": "2026-11-08T16:23:39Z"}
  ],
  "resolution": {
    "strategy": "consensus",
    "decided": "2026-11-08T16:23:39Z",
    "winners": {"value": "c_8519af82"},
    "reason": "only claim"
  }
}
```

### 字段语义

| 字段 | 作用 | 约束 |
|---|---|---|
| `record_id` | 记录主键 | `{protocol}:{category}:{slot}:{entity_id}` |
| `category` / `slot` | **存放位置**（第一维） | 必须在 `knowledge_slots.json` 中登记 |
| `entity` | **知识的主体** | 指向 `index/entities.jsonl` 的 `entity_id` |
| `entity.participants` | **关系型槽位**的端点（source/via/target） | 关系类槽位必填 |
| `condition` | 生效条件 | 现在恒 `always`（预留维度） |
| `claims[]` | **各源的证据**（第二维） | ≥1 条；每条带 `owner`/`evidence`/`epistemic` |
| `epistemic` | **证据强度** | `normative`(规范要求) / `informative`(规范提及) / `observed`(实测) / `inferred`(推导) |
| `resolution` | **多源裁决结果** | 由 `resolution_semantics` 决定；**必填**（即使只有一条 claim） |

★ **`epistemic` 是「信息 vs 知识」的判据**：
`normative` + `observed` 的区分，让论文能声明「这条是协议规定的，那条是我们观测到的」。

## 四、实体主表（`index/entities.jsonl`）

实体**跨分类**（`INVITE` 同时出现在 A/B/C），所以主表独立于分类目录。

```jsonl
{"entity_id": "sip:method:invite",
 "protocol": "sip",
 "type": "method",                 // method|header|status|state|relation|timer|param|role|option
 "name": "INVITE",
 "canonical_name": "INVITE",
 "aliases": ["invite", "Invite"],
 "subtype": "request",             // 协议特有子类（可空）
 "evidence": [{"owner": "rfc", "file": "rfc3261.txt", "line": 1562}],
 "mentions": 34}
```

★ **作用**：
1. 事实/关系/规则/图**全部引用同一主键** ⇒ 四套视图自动对齐；
2. 「这个实体在中枢里有什么」⇒ 一次索引查询（跨分类聚合）；
3. 图节点直接用 `entity_id` ⇒ 图与中枢天然对齐；
4. `index/slots.json` 可生成「**实体 × 分类**矩阵」诊断表。

## 五、落位协议（源 → 分类槽位）

```
① 源抽取器产出 claim：
   {slot, entity_ref, value, epistemic, evidence, confidence}

② 中枢按 **slot → (category, slot)** 的确定性映射表落位
   （映射表在 knowledge_slots.json 中登记，抽取器不需要知道分类）

③ 同一 (entity_id, slot) 若已有其它源的 claim：
   ⇒ 并入 claims[]
   ⇒ 按 resolution_semantics 裁决（默认 consensus）
   ⇒ 把裁决写进 resolution（**必填**，即使只有一条 claim）

④ 落盘后更新：
   index/entities.jsonl   （新实体则登记）
   index/slots.json       （各槽位计数 + 源分布）
   ledger.json            （分类 × 源 × 允许状态）
   provenance.json        （各源本次贡献）
```

★ **关键**：源**不写目录**，只写**槽位** ⇒
- 加新源 ⇒ 只改抽取器，中枢结构不动；
- 换协议 ⇒ 只换 kb，分类与槽位契约不动。

## 六、契约文件（schema 目录）

```
fused_hub/schema/
├── aspect_registry.json        ← 已有：实体有哪些属性（23 个 aspect）
├── knowledge_slots.json        ← ★ 新增：分类 + 槽位契约（中枢的存放位置表）
└── graph_schema.json           ← 已有：图结构（节点/边类型 + 遍历配置）
```

### `knowledge_slots.json` 结构

```json
{
  "version": "1.0",
  "categories": [
    {
      "id": "B_interaction",
      "name": "交互行为",
      "question": "协议怎么用（东西之间怎么连）",
      "file": "B_interaction/interaction.jsonl",
      "slots": [
        {"name": "transitions",
         "aspects": ["target_state"],
         "entity_types": ["relation"],
         "value_type": "text",
         "requires_participants": true,
         "resolution": "consensus",
         "cardinality": "one"},
        {"name": "sequences",
         "aspects": ["method_sequence"],
         "entity_types": ["relation"],
         "value_type": "text",
         "requires_participants": true,
         "resolution": "consensus",
         "cardinality": "one"}
      ]
    }
  ],
  "aspect_map": {
    "target_state":      {"category": "B_interaction", "slot": "transitions"},
    "method_sequence":   {"category": "B_interaction", "slot": "sequences"},
    "message_instance":  {"category": "B_interaction", "slot": "instances"},
    "definition":        {"category": "A_structure",    "slot": "by_entity_type"},
    "required_headers":  {"category": "C_constraints",  "slot": "required_headers"},
    "legal_boundary":    {"category": "C_constraints",  "slot": "value_constraints"},
    "binary_layout":     {"category": "D_construction", "slot": "layout"}
  }
}
```

★ **与 `aspect_registry.json` 正交**：
- `aspect_registry` = 属性清单（23 个 aspect）
- `knowledge_slots` = **存放位置表**（aspect → 分类 + 槽位）
⇒ 迁移时用 `aspect_map` 一次性重排，**现有抽取器几乎不用改**（只改落盘位置）。

## 九、三个待决项（结构层面，不是数据层面）

| # | 待决 | 选项 | 影响 |
|---|---|---|---|
| **1** | `syntax`（字段语法）归 A 还是 D | (a) A 结构 (b) D 构造 | 只影响槽位归属，不影响目录结构 |
| **2** | `value_enum` 拆分 | 规范值 ⇒ A；实测样本 ⇒ E | **需新增 `E_observation/observed_samples` 槽位**（结构已预留） |
| **3** | `definition` 的槽位粒度 | (a) 按实体类型分槽（`methods`/`headers`/`statuses`）<br>(b) 单一 `definitions` 槽位 | (a) 更细但槽位多；(b) 简单但查询要按 entity.type 过滤<br>⇒ **建议 (a)**，因为 A 类本来就是「按实体类型组织」的 |

★ 三项都**不影响顶层目录结构**（6 分类 + index + 3 个元数据文件）⇒ 结构可以先定死。

## 十、与现状的差距（结构层面）

| 现状 | 定稿 | 差距 |
|---|---|---|
| `facts/<aspect>.jsonl`（11~16 个文件） | `A_*/`…`F_*/`（6 个文件） | 文件数减少，**按知识语义聚合** |
| 实体藏在 `fact_key.subject.name` | `index/entities.jsonl` 主表 + `entity_id` 引用 | **新增一层索引** |
| 关系塞在 `subject.qualifiers` | `entity.participants[]` | 结构化但**同一个模型** |
| `authority` 在 claim 里 | 同上 + `ledger.json` 逐类统计 | **新增可审计台账** |
| 语义四库在 `rfc/semantic/rules.jsonl` | 并入 `C_constraints/` | **消除两套体系** |
| 无 `build_meta` / `provenance` | 新增 | 溯源链闭合 |
| 图自己造节点名 | 图节点用 `entity_id` | 图与中枢对齐 |

## 十一、定稿后的结构一览（一张图）

```
                 ┌──────────────────────────────────────┐
   知识源        │  中枢（按目标协议的知识分类存储）         │
  ┌────────┐    │                                      │
  │ rfc    │    │  index/  entities.jsonl  slots.json   │  ← 跨分类索引
  │ traffic│───▶│  ├─ A_structure/     有什么           │
  │ source │    │  ├─ B_interaction/   怎么连           │
  │ expert │───▶│  ├─ C_constraints/   必须/不许怎样     │
  │ vuln   │    │  ├─ D_construction/  怎么写出来       │
  └────────┘    │  ├─ E_observation/   实际什么样       │
                 │  ├─ F_security/      哪里可能出错     │
                 │  ledger.json  provenance.json  build_meta.json

                              │
```

★ **源 → 槽位 → 分类**：源只提供 claim，落位由 `aspect_map` 决定；

★ **分类 → 消费**：bundle 从分类聚合，不再直接读 aspect 文件。
