## 1. 先修正三条既有认知（避免重复论证）

### 1.1 「服务端状态机 A.2 是散文，表格抽不到」——**证伪**

RFC 2326 原文 4421–4435 行：

```
      state           message received  next state
      Init            SETUP             Ready
                      TEARDOWN          Init
      Ready           PLAY              Playing
                      SETUP             Ready
                      TEARDOWN          Init
                      RECORD            Recording
      Playing         PLAY              Playing
                      PAUSE             Ready
                      TEARDOWN          Init
                      SETUP             Playing
      Recording       RECORD            Recording
                      PAUSE             Ready
                      TEARDOWN          Init
                      SETUP             Recording
```

⇒ A.2 **也是定宽表格**；且其 14 条边与 A.1 客户端表**逐条相同**。
⇒ 「补齐服务端散文状态机」这条 LLM 路线在 RTSP 上**收益为零**（抽出来也是同一套）。

### 1.2 「RTSP 状态机需要 LLM 补服务端」——**证伪**

| 抽取方式 | 条数 | 与 A.1 是否一致 |
|---|---|---|
| 确定性 `_extract_transition_table` | 14 | — |
| LLM 通道 G（缓存 `derived/source_blocks/rtsp.transitions.json`） | 14 | **14/14 逐条一致** |

⇒ RTSP 状态机：**LLM 零增量**。

### 1.3 「58 → 17 是因为服务端状态机缺失」——**归因修正**

历史测量「开 `enable_transitions` ⇒ transitions 38 → 12、种子 58 → 17」的真实机制：

1. `profile.allowed_methods` = 8 个方法，**不含 `RECORD`**；
2. RFC 源那 14 条边里有 **2 条用 `RECORD`** ⇒ 被裁到 12 条；
3. 骨架那 38 条边的方法全在白名单内 ⇒ 白名单**对骨架无影响**；
4. 于是「38 → 12」是**用 RFC 源替换骨架**造成的覆盖下降，**与服务端散文无关**。

⇒ 旧归因（服务端散文缺失）**错**；真因是「用更小的一套替换了更大的另一套」。

## 2. 根因链（三层，均已定位到代码行）

### 2.1 提示词层：SIP 状态名被硬塞给所有协议

`core/fused/source_autoseeder.py`：

- 第 182–183 行：`引导 LLM 围绕协议真实方法/会话流程枚举「语义化状态」（Idle/Registered/Invited/Confirmed），而非响应码（200/401/404）或认证中间态（Trying/Unauthorized）`
- 第 203 行：`状态名用语义化命名（如 Idle/Registered/Invited/Confirmed），`

⇒ 这四个名字正是 **SIP 的状态名**，被当作通用范例写进提示词 ⇒ LLM 给 **RTSP** 也编出同一套 `Idle/Registered/Confirmed/Invited/Paused/Terminated`。

### 2.2 骨架层：携带 source 派生知识，却被当「跨实验复用资产」

`fused_hub/targets/rtsp/skeleton.json`：

```json
"note": "协议骨架（跨实验复用）：……由 source + traffic 源抽取 ⇒ 固化为资产……",
"origin": {"source": ["message_instance", "target_state"],
           "traffic": ["existence", "method_sequence", "occurrence", "value_enum"]}
```

⇒ `target_state` 桶的 origin 是 **`source` 源**（证据摘要 `source.autoseeder.transition.Idle.OPTIONS.Idle`）。

### 2.3 组装层：骨架「恒允许」⇒ RFC 单源实验也混入源码侧状态机

`core/fused/downstream/rag_seedgen.py` 第 968–969 行：

```python
# ★ 协议骨架恒允许（跨实验复用的协议结构，不是源派生知识）
_allowed.add(SKELETON_AUTHORITY)
```

⇒ **注释里的前提与事实不符**（骨架实为 source/traffic 派生）⇒ 即使 `--sources rfc`，那 38 条 SIP 式状态机**仍然进中枢、仍然进 prompt**。

### 2.4 择一层：实现与文档意图相反

- 第 1170–1171 行注释：默认采用**协议骨架**那套（为保持产物不变）
- 第 1172 行注释：后期 LLM 判别时**只需替换 `_select_active_transitions()`**
- 批次 2.1 原始措辞：**「源派生优先、骨架兜底」**
- 实际实现（`_select_active_transitions`）：`chosen = by_source.get(SKELETON_AUTHORITY) or []` ⇒ **骨架优先**

## 3. 零成本诊断：状态名在 RFC 原文的命中率

| 协议 | 骨架(profile)状态名命中率 | RFC 源状态名命中率 |
|---|---|---|
| **rtsp** | **0/6 = 0%**（Confirmed/Idle/Invited/Paused/Registered/Terminated） | **4/4 = 100%**（Init/Playing/Ready/Recording） |
| sip | 4/8 = 50%（Active/Idle/InCall/Registered 查无） | 7/7 = 100%（含 1 处大小写分裂 `terminated`） |
| smtp | 2/9 = 22%（Greeted/Transferring/Authenticated/Secured/Completed/Closed/Idle 查无） | —（RFC 无状态机可依） |

⇒ **RTSP 的骨架状态机 100% 是外来的**（SIP 式命名），完全不属于 RTSP 规范。

## 4. 对照实验（真调 LLM：4 组 × 3 次 = 12 次调用）

### 4.1 设计（只差 prompt 的 `[状态机转移]` 一节 ⇒ 归因干净）

| 组 | transitions | 说明 |
|---|---|---|
| **A 现状** | 骨架 38 条 | 6 个状态名 0/6 命中 RFC 原文 |
| **B RFC 原生** | RFC 源 14 条（不裁白名单） | 4/4 命中；对应 `--sources rfc` 口径 |
| **C RFC 被裁** | RFC 源 14 条裁 `allowed_methods` 后 12 条 | 复现历史 58→17 的口径 |
| **D 合并** | 骨架 38 ∪ RFC 14 = 52 条 | 两套状态名并存 |

### 4.2 结果

| 组 | raw | kept | 落位率 | 跨源污染 |
|---|---:|---:|---:|---:|
| A 现状（骨架38） | 19.67 | **16.33** | 100% | 0% |
| B RFC14原生（不裁） | 20.00 | 10.67 | 100% | 0% |
| C RFC14裁后 | 20.00 | 7.67 | 100% | 0% |
| D 合并52 | 19.67 | **2.00** | 100% | 0% |

⚠️ **`kept` 不是质量指标** —— 它衡量「本系统自己的校验器裁掉了多少」，而校验器用的就是**被测对象自己的**状态机 ⇒ 自证循环。必须用外部真值评判。

### 4.3 外部真值重算（真值 = RFC 2326 A.1+A.2 共 14 条边，逐行核对原文）

| 组 | R 召回（raw 中合法率） | **P 精确（kept 中合法率）** | 种子用到的**非法状态名** |
|---|---:|---:|---|
| A 现状（骨架38） | **0.0%** | **0.0%** | 6 个（全错：Idle/Registered/…） |
| B RFC14原生 | 93.3% | **100%** | 0 |
| C RFC14裁后 | 98.3% | **100%** | 0 |
| D 合并52 | **0.0%** | **0.0%** | 6 个 |

### 4.4 结论解读

1. **现状（A 组）的 RTSP 种子在状态机维度全军覆没（0%）** —— 不是「少一点」，是「全错」：
   LLM 完全照抄 prompt 里的骨架状态名（落位率 100%），而那些状态名 RTSP 根本没有。
2. **B/C 组把精确率从 0% 提到 100%**，代价是种子数 16.33 → 10.67 / 7.67。
   ⇒ **用 5–6 个「本来就不合法」的种子，换 100% 合法率 ⇒ 净收益为正。**
3. **B 优于 C**（种子多 3 个，召回略低 5pp）⇒ 推荐 **B**（不裁 `allowed_methods`），
   且它正好是 `--sources rfc` 的既有语义（源码侧白名单不裁剪规范知识）。
4. **D 合并必须否决**：两套状态名并存 ⇒ LLM 在两套间摇摆 ⇒ 精确率/召回率**双 0**，种子几乎全被校验器杀掉。

## 5. SIP / SMTP 的补充诊断

- **SIP**：RFC 源 14 条（确定性 0 条 ⇒ LLM 是唯一来源）。状态名 7/7 命中 RFC 3261，
  但存在 **1 处大小写分裂**（`terminated` vs `Terminated`）⇒ `_normalize_state` 只对
  全大写做 title()，**小写不归一** ⇒ 状态名分裂。
  ⚠️ 且其边的 `method` 字段多为**事件**而非真实 SIP 方法
  （`Timer F` / `provisional response` / `2xx` / `300-699`，仅 `ACK` 是方法）
  ⇒ **不能用于推导 `state_changing`（方法→状态映射）**，对种子生成的直接价值受限。
- **SMTP**：RFC 5321/5322 里**没有 "state machine" 表述** ⇒ LLM 候选段落 0 个 ⇒ 通道不可用。
  骨架那 9 个状态名只有 2 个（Envelope/Recipients）在 RFC 原文命中 ⇒ 属协议外知识。
