## 1. 先修正三条既有认知（避免重复论证）

### 1.1 「服务端状态机 A.2 是散文，表格抽不到」——**证伪**

RFC 2326 原文 4421–4435 行：

```
      state           message received  next state
      Init            SETUP             Ready
                      TEARDOWN          Init
      Ready           PLAY              Playing
                      SETUP             Ready
                      TEARDOWN          Init
                      RECORD            Recording
      Playing         PLAY              Playing
                      PAUSE             Ready
                      TEARDOWN          Init
                      SETUP             Playing
      Recording       RECORD            Recording
                      PAUSE             Ready
                      TEARDOWN          Init
                      SETUP             Recording
```

⇒ A.2 **也是定宽表格**；且其 14 条边与 A.1 客户端表**逐条相同**。
⇒ 「补齐服务端散文状态机」这条 LLM 路线在 RTSP 上**收益为零**（抽出来也是同一套）。

### 1.2 「RTSP 状态机需要 LLM 补服务端」——**证伪**

| 抽取方式 | 条数 | 与 A.1 是否一致 |
|---|---|---|
| 确定性 `_extract_transition_table` | 14 | — |
| LLM 通道 G（缓存 `derived/source_blocks/rtsp.transitions.json`） | 14 | **14/14 逐条一致** |

⇒ RTSP 状态机：**LLM 零增量**。

### 1.3 「58 → 17 是因为服务端状态机缺失」——**归因修正**

历史测量「开 `enable_transitions` ⇒ transitions 38 → 12、种子 58 → 17」的真实机制：

1. `profile.allowed_methods` = 8 个方法，**不含 `RECORD`**；
2. RFC 源那 14 条边里有 **2 条用 `RECORD`** ⇒ 被裁到 12 条；
3. 骨架那 38 条边的方法全在白名单内 ⇒ 白名单**对骨架无影响**；
4. 于是「38 → 12」是**用 RFC 源替换骨架**造成的覆盖下降，**与服务端散文无关**。

⇒ 旧归因（服务端散文缺失）**错**；真因是「用更小的一套替换了更大的另一套」。

## 3. 零成本诊断：状态名在 RFC 原文的命中率

| 协议 | 骨架(profile)状态名命中率 | RFC 源状态名命中率 |
|---|---|---|
| **rtsp** | **0/6 = 0%**（Confirmed/Idle/Invited/Paused/Registered/Terminated） | **4/4 = 100%**（Init/Playing/Ready/Recording） |
| sip | 4/8 = 50%（Active/Idle/InCall/Registered 查无） | 7/7 = 100%（含 1 处大小写分裂 `terminated`） |
| smtp | 2/9 = 22%（Greeted/Transferring/Authenticated/Secured/Completed/Closed/Idle 查无） | —（RFC 无状态机可依） |

⇒ **RTSP 的骨架状态机 100% 是外来的**（SIP 式命名），完全不属于 RTSP 规范。

## 4. 对照实验（真调 LLM：4 组 × 3 次 = 12 次调用）

### 4.1 设计（只差 prompt 的 `[状态机转移]` 一节 ⇒ 归因干净）

| 组 | transitions | 说明 |
|---|---|---|
| **A 现状** | 骨架 38 条 | 6 个状态名 0/6 命中 RFC 原文 |
| **B RFC 原生** | RFC 源 14 条（不裁白名单） | 4/4 命中；对应 `--sources rfc` 口径 |
| **C RFC 被裁** | RFC 源 14 条裁 `allowed_methods` 后 12 条 | 复现历史 58→17 的口径 |
| **D 合并** | 骨架 38 ∪ RFC 14 = 52 条 | 两套状态名并存 |

### 4.2 结果

| 组 | raw | kept | 落位率 | 跨源污染 |
|---|---:|---:|---:|---:|
| A 现状（骨架38） | 19.67 | **16.33** | 100% | 0% |
| B RFC14原生（不裁） | 20.00 | 10.67 | 100% | 0% |
| C RFC14裁后 | 20.00 | 7.67 | 100% | 0% |
| D 合并52 | 19.67 | **2.00** | 100% | 0% |

⚠️ **`kept` 不是质量指标** —— 它衡量「本系统自己的校验器裁掉了多少」，而校验器用的就是**被测对象自己的**状态机 ⇒ 自证循环。必须用外部真值评判。

### 4.3 外部真值重算（真值 = RFC 2326 A.1+A.2 共 14 条边，逐行核对原文）

| 组 | R 召回（raw 中合法率） | **P 精确（kept 中合法率）** | 种子用到的**非法状态名** |
|---|---:|---:|---|
| A 现状（骨架38） | **0.0%** | **0.0%** | 6 个（全错：Idle/Registered/…） |
| B RFC14原生 | 93.3% | **100%** | 0 |
| C RFC14裁后 | 98.3% | **100%** | 0 |
| D 合并52 | **0.0%** | **0.0%** | 6 个 |

### 4.4 结论解读

1. **现状（A 组）的 RTSP 种子在状态机维度全军覆没（0%）** —— 不是「少一点」，是「全错」：
   LLM 完全照抄 prompt 里的骨架状态名（落位率 100%），而那些状态名 RTSP 根本没有。
2. **B/C 组把精确率从 0% 提到 100%**，代价是种子数 16.33 → 10.67 / 7.67。
   ⇒ **用 5–6 个「本来就不合法」的种子，换 100% 合法率 ⇒ 净收益为正。**
3. **B 优于 C**（种子多 3 个，召回略低 5pp）⇒ 推荐 **B**（不裁 `allowed_methods`），
   且它正好是 `--sources rfc` 的既有语义（源码侧白名单不裁剪规范知识）。
4. **D 合并必须否决**：两套状态名并存 ⇒ LLM 在两套间摇摆 ⇒ 精确率/召回率**双 0**，种子几乎全被校验器杀掉。

## 5. SIP / SMTP 的补充诊断

- **SIP**：RFC 源 14 条（确定性 0 条 ⇒ LLM 是唯一来源）。状态名 7/7 命中 RFC 3261，
  但存在 **1 处大小写分裂**（`terminated` vs `Terminated`）⇒ `_normalize_state` 只对
  全大写做 title()，**小写不归一** ⇒ 状态名分裂。
  ⚠️ 且其边的 `method` 字段多为**事件**而非真实 SIP 方法
  （`Timer F` / `provisional response` / `2xx` / `300-699`，仅 `ACK` 是方法）
  ⇒ **不能用于推导 `state_changing`（方法→状态映射）**，对种子生成的直接价值受限。
- **SMTP**：RFC 5321/5322 里**没有 "state machine" 表述** ⇒ LLM 候选段落 0 个 ⇒ 通道不可用。
  骨架那 9 个状态名只有 2 个（Envelope/Recipients）在 RFC 原文命中 ⇒ 属协议外知识。

## 7. 后续三条**负结果**（2026-11-05 01:30~09:50 实测，避免下轮重复论证）

> 这三条都是「看起来该做、实测做不了」的方向。**省下的不是时间，是几轮 LLM 调用和一次基线重立。**

### 7.1 「修 `source_autoseeder` 提示词」——**实测无效，否决**

`core/fused/source_autoseeder.py:202-204` 的状态锚点提示词确实硬塞了 SIP 的状态名范例：

```
"请围绕上述方法枚举「语义化」状态（如空闲/已注册/通话建立/通话中/通话结束），"
"状态名用语义化命名（如 Idle/Registered/Invited/Confirmed），"
```

⇒ 三版提示词在同一批真实代码块上的对照（`local/_pilot_source_prompt.py`，rtsp）：

| 版本 | 状态数 | RFC 原文命中 | 命中率 |
|---|---:|---:|---:|
| 旧（现状：硬编码 SIP 范例） | 20 | 4/20 | **20%** |
| 严版（宁缺勿滥：找不到标识就不产出） | 1 | 0/1 | 产出**崩塌** |
| 中间版（给**来源约束**，不给名字清单） | 29 | 7/29 | **24%** |

**结论**：
1. 命中率几乎不改善（20% → 24%，且分母从 20 涨到 29）；
2. 「宁缺勿滥」版直接崩塌（只产出 1 个、还是整句话）⇒ 不可用；
3. ★ **提示词设计经验：给 LLM 任何具体名字（正例或反例）都可能被照抄**
   ⇒ 正确做法是约束**来源**（代码里的标识 / 本协议自己的术语），而不是列举名字；
4. ★ **根本原因不在提示词**：live555 的 RTSP 实现源码里**零个规范会话状态名**
   （`Init/Ready/Playing/Recording` 全不命中，命中的只有 `Initialize`/`isInitial401`
   这类无关词）⇒ **源码逆向在本质上产不出规范状态机** ⇒ 改提示词改不出规范名。

⇒ **正解是架构性的**（已落地）：规范状态机只能来自 **RFC 源**，消费端用**择一**
（`rfc` 优先）而不是让各源PK。提示词改造只值当「防止复发」的保险，
且需连带修**缓存键缺陷**（见 7.4）。

### 7.2 「骨架按 `origin` 受 `source_set` 约束」——**会掏空 sip/smtp，否决**

骨架 `skeleton.json` 的 `target_state` origin 实为 `source` 源，而
`rag_seedgen.py:968` 让骨架「恒允许」⇒ RFC 单源实验确实混入了源码侧状态机。
看似是纯净度漏洞，但只读模拟（`local/_sim_purity_skeleton.py`，RFC 单源口径）：

| 协议 | A 现状 | B 排除骨架 target_state 后 | 该协议 RFC 源可抽 |
|---|---|---|---|
| rtsp | 14 条 / 确定性层 15 种子 | **14 条 / 15 种子（不变）** | 14 条 ✔ |
| sip | 51 条 / 45 种子 | **0 条 / 0 种子** | 14 条（未启用） |
| smtp | 64 条 / 56 种子 | **0 条 / 0 种子** | **0 条**（RFC 无 state machine） |

⇒ **排除会让 sip / smtp 的确定性层直接归零**（smtp 无 RFC 状态机可依，无解）
⇒ **不可行**。
⇒ **正确形态是「分层 + 标注」而非「排除」**：中枢本就有 `transitions_by_source`
（批次 2.3 设计）可按源分组 ⇒ 论文/消融直接用它区分「规范原生」与「实现级推断」。
⇒ 决策：**保持分层，不排除**。

### 7.3 「给 sip 开 `enable_transitions`」——**会产出 `METHOD` 垃圾报文，否决**

sip 的 RFC 源 14 条（§17 ASCII 图，LLM 抽）里，**只有 1 条用真实 SIP 方法**（ACK），
其余 9 个 method 值全是**事件/响应码**：`Timer F` / `Timer I fires` / `Timer J fires` /
`Timer K` / `2xx` / `300-699` / `provisional response` / `final response` /
`response with status code from 300-699`。

⇒ 用它跑 `edge_cover`，生成的报文方法名是 **`METHOD`（占位符）** ⇒ 完全不可用。

⇒ ★ **新判据（可迁移）**：**RFC 状态机能否驱动种子生成，取决于其转移表的
「触发列」是不是方法名**：
- RTSP A.1/A.2：触发列 = 方法名（SETUP/PLAY/PAUSE/RECORD/TEARDOWN）✔
- SIP §17：触发列 = 事件 / 响应码 ✘

### 7.4 附带发现：状态机 LLM 的**缓存键不含提示词版本**（缺陷，未修）

`core/fused/source_autoseeder.py` 的 `infer_source_facts` 按
`md5(code_blocks)` 命中 `derived/source_blocks/<协议>.state.json`；
`rfc_extractor.py::infer_transitions` 按 `sha256(候选段落 hash 拼接)` 命中
`*.transitions.json` ⇒ **两者都不含 prompt_version**。

⇒ ★ **改了提示词但缓存命中 ⇒ 改动静默不生效**（与语义规则那条线的
`sha256(candidate_text + prompt_version + model)` 契约不一致）。
⇒ 本轮做提示词对照试点时**必须绕过缓存重跑**，否则会得出「改了没用」的假结论。
（未修：修它需给缓存键加版本位 ⇒ 会使既有缓存失效 ⇒ 触发一次全量重抽。）
