## ★ v4 增补（2026-10-25 晚）：执行量控制口径的裁决

> **v4 不推翻 v1–v3 的任何归因**，只做一件事：**裁决「执行量是否为混淆因子」**，
> 并给出**有效的控制口径**。结论：**覆盖率优势在控制执行量后依然成立**，
> 故污染归因**不削弱**覆盖率结论。

### v4.1 ★ 裁决：4 条独立路径一致，protorag 10/10 全胜，无反转

**背景**：覆盖率是「执行量」的结果量。两组 `execs_done` 相差数倍
（aflnet 侧 protorag 只跑基线的 77%；chatafl 侧 protorag 跑了基线的 129%），
故必须做执行量控制。

#### ⚠ 已被否决的口径：「每百万次执行的覆盖率」（cvg / (execs/1e6)）

覆盖率对执行量是**饱和递减曲线**（边际收益递减），故该比值**对同一容器随执行量单调下降**——
它度量的是「到目前为止的平均」，**不是效率**。同一容器、同样的种子，只是跑得更久
（实测，`rq1_2_norm_bias.csv`）：

| 容器 | 预算 (execs) | cov (%) | cvg/(execs/1e6) |
|---|---|---|---|
| seed_reuse_chatafl_r1 | 83 484 | 9.820 | **117.628** |
| seed_reuse_chatafl_r1 | 166 967 | 10.010 | **59.952** |
| seed_reuse_chatafl_r1 | 250 450 | 10.010 | **39.968** |
| seed_reuse_chatafl_r1 | 333 934 | 10.050 | **30.096** |

→ 同容器比值降 **3.9 倍**。故用它比较「跑得多」与「跑得少」的两组，
**必然系统性偏袒跑得少的一组**：chatafl 侧 protorag 执行量高 → 比值被压低；
aflnet 侧 protorag 执行量低 → 比值被抬高。**方向相反的同一个偏差。**

### v4.2 挂起与执行量的关系（澄清一个流传中的错误解释）

曾有解释称「chatafl 侧 protorag 的更多执行量是挂着停顿换来的」。**实测方向相反**：

| 关系（chatafl 侧 10 容器） | 相关系数 |
|---|---|
| `unique_hangs` vs `execs_done` | **r = −0.377**（弱负相关） |
| `paths_total` vs `execs_done` | **r = +0.827**（强正相关） |

- `execs` 最高的容器 = `protorag_r3`（execs 500 012，**hangs 仅 3**）
- `hangs` 最高的容器 = `seed_reuse_r4`（hangs 220，**execs 最低 305 814**）
→ 挂起阻塞 1000 ms timeout 是**负贡献**，挂起多的容器执行反而少；
  执行量差异的主因是 **paths_total（队列规模）**，不是挂起。
→ 且挂起阻塞总量极小：220 × 1 s = 0.061 h，占 24 h 的 **0.255%**，
  解释不了 21%~29% 的执行量差异。

### v4.2.1 ★ 补充（2026-10-25 晚）：两组 chatafl 容器的**启动时刻相差 73.7 分钟**

VM 直读 `fuzzer_stats.start_time` 实测：

| Fuzzer | 组 | start_time（r1） | 首行延迟 | 队列规模 |
|---|---|---|---|---|
| chatafl | seed_reuse | 1792812238 | 90 s (1.5 min) | 1511 |
| chatafl | protorag | 1792816673 | 482 s (8.0 min) | 2516 |
| aflnet | seed_reuse | 1792811377 | 6 s (0.1 min) | 1544 |
| aflnet | protorag | 1792811377 | 18 s (0.3 min) | 1402 |

组间错位（protorag 相对 seed_reuse，同 fuzzer 同 rep）：
```
chatafl  启动错位 = [4435, 4365, 4490, 4379, 4453] s  → 均值 4424 s = 73.7 分钟
chatafl  结束错位 = [4804, 4818, 5203, 4665, 4774] s  → 均值 4853 s = 80.9 分钟
aflnet   启动错位 = [0, 1, 1, 1, 1] s                → 均值    1 s =  0.0 分钟
aflnet   结束错位 = [−180, −139, −96, 37, −97] s       → 均值  −95 s = −1.6 分钟
```

**成因**（源码事实）：`afl-fuzz.c` 中 `start_time = get_cur_time()` 位于 **10707 行**，
而 `enrich_testcases()` 位于 **10687 行**、且 `read_testcases()` 在 **10689 行** ——
即**LLM 富集全部完成后才记录 start_time 并开始正式 fuzzing**。
chatafl 侧 protorag 的 50 条基础种子要富集成 1294 条（LLM 调用量远大于基线组 161 条），
因此启动被推迟约 74 分钟；aflnet 无 `enrich_testcases()` → 两组几乎同时启动。

**影响评估（关键：结论不受影响）**
- 每个容器的 `rel_hours` 都以**自身首行为 t0** 归零（实测 20/20 容器 min(rel_hours)=0）→
  **时序分析、时间-阈值口径、崩溃首现时刻全部对启动错位免疫** ✅
- **等执行预算口径以累计执行数为轴，与墙钟无关** → 同样免疫 ✅
- 各容器实际 fuzzing 时长均为 **23.9 ~ 24.1 h**（实测 20/20），**无一方被缩短** ✅
- → **chatafl 半侧的「唯一变量不成立」结论进一步加固**：两组不仅语料被污染，
  连**正式 fuzzing 的起止墙钟窗口都相差 74~81 分钟**。
  任何「同一时段内对比」的表述在该半侧都不成立。
→ ★ **论文表述纪律新增一条**：chatafl 半侧不得写「同一 24 小时窗口内」，
应写「各自 24 h fuzzing（起始墙钟相差约 74 min）」。

## 2. 机制（镜像内代码事实）

ChatAFL 在选定协议后**无条件**调用 `enrich_testcases()`：

```
afl-fuzz.c:10681   if (protocol_selected) {
afl-fuzz.c:10687       enrich_testcases();      ← ★ 无条件调用，chat-llm.c 中零 getenv
afl-fuzz.c:10689   read_testcases();            ← ★ 在 enrich 之后
```

- `enrich_testcases()` → 对每条种子枚举消息类型子集 → `enrich_sequence()`
  （`chat-llm.c:929`）→ `chat_with_llm()`（`chat-llm.c:47`）
- LLM 端点**硬编码** `http://192.168.37.1:18080/chat/completions`，模型 `deepseek-chat`
- 成功则写回 `in_dir/enriched_<i>_<原文件名>`
- ★ `chat-llm.c` 中 `getenv` 命中数 = **0** → **没有任何环境变量开关**

**失败路径（干净退出的关键）**：`chat_with_llm` 返回 NULL → `enrich_sequence` 返回
NULL → `afl-fuzz.c:2725-2726` `if (client_request_answer == NULL) continue;`
→ **不写任何 enhanced 文件**。

## 3. 实测污染数据

| `rq2_seed_reuse_aflnet_r1` | — | 7 | **0** | **0 / 1335** |

### 3.1 ★ 污染方向因组而异（关键发现）

AFL 用 `scandir(in_dir, &nl, NULL, alphasort)` 按**文件名字母序**入队：

| 组 | 种子名形态 | 增强种名形态 | 字母序 | 结果 |
|---|---|---|---|---|
| `protorag` | `01_…`（数字前缀） | `enriched_0_…`（字母 e） | `0-9 < e` | 原始种**在前**（id:000000–000049），增强种在后 |
| `seed_reuse` | `rtsp_requests_…`（字母 r） | `enriched_0_…`（字母 e） | `e < r` | 增强种**在前**，**7 条原始种被挤到 id:000161–000167（队列末尾）** |

→ 同一次「增强」事件，对两组的影响方向**相反**。

### 3.2 宿主语料目录是干净的

`/home/zxy/rq2_seeds/protorag` 恰 **50** 个 `.raw` → **污染只发生在容器内的
`/seeds_work` 副本**，语料上传环节无问题。

### 3.3 LLM 端点可达性随时间变化

- 11:09 启动时**可达** → 写入 1294 条增强种子
- 事后实测**不可达**（宿主与容器均 `Connection refused`）

→ ★ **不能依赖「现在恰好连不上」**。必须用**机制性**手段保证任意时刻启动都不被增强。

## 4. 影响面分析

### 4.1 受影响的指标

| 指标 | 影响 | 原因 |
|---|---|---|
| **初始种子规模** | 严重 | 1344 vs 168（而非 50 vs 7） |
| **初始路径数**（`paths_total` 首行） | 严重 | RQ1.2 实测 `protorag_chatafl` 首行 = **1344**（= 增强后种子数）→ **污染的独立指纹** |
| **队列初始规模 / 校准成本** | 严重 | 校准阶段要处理 1344 个输入 |
| **分支覆盖 %（绝对值）** | 中等 | 覆盖被「更多且更脏的初始种子」抬高 |
| **`chat_times`（运行时 LLM 交互）** | 严重 | RQ1.2 实测 `protorag_chatafl_r1` 的 `chat_times` 从 0 增长到 **64** → 运行时 stall-chat 生效 |

### 4.2 不受影响的项

镜像、fuzzer 参数串、运行时长、rep 数、容器资源配置 —— **均未改变**。

### 4.3 ★ 对「组内相对比较」的污染

ChatAFL 行的组内比较（`protorag` vs `seed_reuse`）**混淆了两个因素**：
「种子来源」与「初始种子规模」。因为 1344 vs 168 不只是 50 vs 7 的放大，
还包含 **LLM 生成的低质量种子**。

→ **ChatAFL 行的相对比较只能作为方向性参考，不作主结论。**

## 5. RQ1.2 结论的表述纪律（论文正文 / 表注 / 实验记录三处一致）

### 5.1 表 4 表注（建议文字，可直接使用）

> ⚠ 本表 ChatAFL 两行含 ChatAFL 运行时 LLM 种子富集污染：ChatAFL 在 `protocol_selected`
> 时无条件调用 `enrich_testcases()`（`afl-fuzz.c:10687`，早于 `read_testcases()`），
> 把 LLM 增强后的种子**回写进初始种子目录**并成为初始队列成员。
> 实测 `protorag_chatafl` 的初始队列条目为 **1344** 条（50 条 ProtoRAG 种子 +
> **1294** 条 LLM 增强种），`seed_reuse_chatafl` 为 **168** 条（7 + **161** 条 LLM 增强种），
> 增强种中约 **95%** 含明显 LLM 自然语言文本。
> ★ **该污染源自 ChatAFL 的 fuzzer 内置 LLM 功能，两组同等受影响**
> （`orig:enriched*` 占比 96.28% vs 95.83%），**不是 ProtoRAG 引入的** ——
> 两个输入语料目录本身均不含 `enriched_`、不含散文（0/50、0/7）。
> **AFLNet 两行未受污染**（AFLNet 无 LLM 逻辑，实测 `orig:enriched*` = 0、无 LLM 调用），
> 故 RQ1.2 结论以 AFLNet 两行为准，ChatAFL 两行降级为辅证。
> ★ 覆盖率指标本身**不受该污染影响**：等执行预算与时间-阈值两种口径下 protorag 均 10/10 占优
> （详见 v4.1）；ChatAFL 两行降级的理由**仅是崩溃样本混入 LLM 文本、不可作真实漏洞证据**。

### 5.2 论文正文表述

1. RQ1.2 的结论**以 AFLNet 两行为准**（唯一变量是种子来源，50 vs 7，未受污染）；
2. ChatAFL 两行**降级为辅证**并附污染说明 ——
   ★ 降级理由**仅是崩溃样本混入 LLM 散文、不可作真实漏洞证据**，
   **不是覆盖率指标不可靠**（覆盖率在等执行预算与时间-阈值两种口径下均为 protorag 占优，v4.1）；
3. 覆盖率结论可表述为「**在相同或更少的执行量下取得更高分支覆盖，且更早达到同等覆盖门槛**」
   （aflnet 半侧 protorag 仅用基线 **77%** 的执行量即达到更高覆盖；见 v4.1）；
4. ★ **崩溃数不得作为方法优劣判据**：晚发（最早 9.20 h）、概率性、方差极大
   （sd 6.38 / 19.39）、受 `execs_done` 量级放大，且 chatafl 侧两组崩溃输入均含 LLM 散文；
5. ★ **必须同时说明 RQ1.2 与 RQ3 的 chatafl 行不可直接横向比较**
