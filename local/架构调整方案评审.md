## 0. 总体可行性判断

### 0.1 结论

**值得实施，但必须按本文的 3 处设计修正 + 2 个前置条件执行；按现方案原样实施会产生回归。**

- **问题识别准确**：方案指出的两个问题（骨架是跨源污染源、状态机定位过窄）**均经实测复现**，不是误判；
- **方向正确**：「先强能力、后去兜底」的推进顺序是对的，且有文献支撑（PROSPER / StatePre / PSMBENCH 的 chunking+LLM 共识）；
- **两处关键设计有缺陷**：① 阶段 A 若按「替换」实施会让 **RTSP 状态机从 14 条退化到 5 条**（实测）；② 阶段 C 的「允许推断」不加命令白名单会产生 **29% 垃圾 method**（实测），最终变成种子里的假命令报文；
- **一处代价被低估**：删骨架后不是「种子变少」，而是 **sip/smtp 的确定性层直接归零**（实测）；
- **两处前置条件缺失**：现有章节树**不认字母编号附录**（`A.1` 解析为 `None`）；`required_headers` 与骨架走同一物化路径，删骨架会连带删掉它。

### 0.2 实测证据速览

| 方案论断 | 实测结果 | 判定 |
|---|---|---|
| 骨架是跨源污染源 | `required_headers`/`message_instances`/`method_sequences`/`occurrence` **100% 来自 profile** | ✅ 成立 |
| SMTP 候选定位命中 0 段 | 0 段（`_RE_STATE_MACHINE_HINT` 只匹配 "state machine"） | ✅ 成立 |
| 阶段 C「允许推断」能让 SMTP 从 0 到有 | 0 → **54 条**，method 71% 是真实命令 | ✅ 成立（**但需加白名单约束**） |
| 阶段 A「RTSP/SIP 候选不减少」 | 按章节树定位，RTSP 只命中 §3.4/§12.37/§14.5，**A.1/A.2 全漏** | ❌ **不成立** |
| 删骨架后「种子变少、覆盖下降」 | sip/smtp 确定性层 **45→0 / 56→0 条** | ⚠️ **低估** |
| 阶段 4「从 RFC 抽取必填头」 | present 规则投影仅覆盖骨架的 **rtsp 7.1% / sip 0%** | ⚠️ **需新增抽取能力** |

### 0.3 适用条件（满足才建议实施）

1. **论文口径**明确「RFC 单源 = 仅用 RFC 源抽取所得知识」，并**显式声明**哪些维度属协议结构声明（必填头/方法白名单）而非 RFC 抽取产物；
2. 愿意承担种子规模下降的代价（rtsp 已从 91 → 37；若再删骨架，sip/smtp 会归零 ⇒ **必须先补 RFC 源的对应抽取能力**）；
3. **先修章节树的附录支持**（否则 RTSP 退化，见 P0-1）；
4. 评测（阶段 D）**不引入外部向量模型/API**，以保离线复现性；
5. 有一轮「能力就绪」门禁：RFC 源在该协议的 `transitions` 条数 ≥ 骨架版的 80% 且 method 真实率 ≥ 95%，才允许进入删骨架阶段。

## 1. 分项评估

### 1.1 技术实现难度

| 阶段 | 难度 | 说明 |
|---|---|---|
| 骨架 阶段 1（关物化） | **低** | 现有 `--exclude-skeleton-dims` 已等价 ⇒ 主要是改默认值 |
| 骨架 阶段 2（移除特权） | **低** | 删 `_allowed.add(SKELETON_AUTHORITY)` 与兜底分支 |
| 骨架 阶段 3（物理清除） | **低** | 删文件与函数；⚠️ 但 `kb/` 有只读位，删除需 PowerShell 清只读位 |
| 骨架 阶段 4（必填头脱钩） | **高** | 我实测 `present` 规则投影只覆盖 7.1%/0% ⇒ **需新增「消息级必填头」抽取**，非简单改标注 |
| 状态机 阶段 A（定位扩展） | **中** | 章节树已有（`SectionNode`/`SectionHead`）；⚠️ 但**不认字母附录**（P0-1） |
| 状态机 阶段 B（语义块） | **中** | 整节入块 ⇒ 块变大 ⇒ 需上下文预算控制 |
| 状态机 阶段 C（prompt 升级） | **低** | 改提示词；**但必须加命令白名单约束**（P0-2） |
| 状态机 阶段 D（语义匹配评测） | **高** | 引入 embedding/向量模型 ⇒ 新依赖 + 离线复现风险（P1-6） |

### 1.2 依赖与兼容性

- **已有依赖可复用**：章节树（`core/fused/rfc_extractor.py:405+`）、`SectionNode.body_lines/body_line_nos`（行感知）、LLM 客户端、磁盘缓存、护栏与基线脚本 ⇒ 方案不需要引入新的框架；
- **硬依赖顺序**：阶段 E（缓存失效）**必须**在阶段 A/B/C 之后，且缓存键要显式含 `prompt_version`（P1-5）；
- **兼容性风险点**：
  - `required_headers` 与骨架共用物化路径 ⇒ **阶段 1/3/4 存在耦合**（P1-9）；
  - 下游 `edge_cover`/`generic_danger` 依赖 `transitions` 与 `message_instances` ⇒ 删骨架后 smtp 的 `edge_cover` 从 6 → 0；
  - `profile.json` 的 `seedgen.required_headers` 是**唯一**的必填头来源 ⇒ 删骨架前必须先有替代来源。

### 1.3 性能影响

| 项 | 影响 | 量级 |
|---|---|---|
| LLM 成本 | 候选从「关键词行 ±60 行」变「整节」⇒ 块变大 | SMTP 实测 21 个候选章节（最长 8017 字符）⇒ 单次调用 token 上升约 1 个量级 |
| 构建时间 | 阶段 E 三协议重抽（缓存失效） | 约 3 协议 × 10~20 块 × LLM 往返 ⇒ 分钟级，可接受 |
| 运行时 | 消费端不受影响（择一 + 对齐已就位） | 无 |
| 中枢体积 | 删骨架后 facts 减少 145/169/368 条/协议 | 中枢变小 ⇒ **查询更快** |

### 1.4 维护成本

- **净收益**：删掉「profile 伪装成来源」这个特例 ⇒ `_allowed.add(SKELETON_AUTHORITY)` 的注释与实现不一致问题消失（当前注释称「跨实验复用的协议结构」，实际含 traffic/source 派生维度）；
- **新增成本**：`authority` 语义从 5 源变「5 源 + required_headers 单独标注」⇒ 知识台账（`knowledge_ledger`）与纯净度审计脚本要同步适配；
- **长期收益**：不再需要「骨架 vs 源」的双口径解释 ⇒ 论文的纯净度论证链条更短。

## 2. 问题与隐患清单

> 影响程度：**高** = 会导致结论错误/回归/论文口径被质疑；**中** = 会导致返工或口径模糊；**低** = 工程卫生问题。

### P0-1 【高】章节树不认字母编号附录 ⇒ 阶段 A 按方案实施会让 RTSP 退化

- **问题**：方案阶段 A/B 要求「复用现有章节切分」定位状态机章节，但 `core/fused/rfc_extractor.py::_parse_heading_shape` **只解析数字编号**：
  | 输入 | 解析结果 |
  |---|---|
  | `10.4  SETUP` | ✅ level=2, number='10.4' |
  | `2.3.6.  Buffer and State Table` | ✅ level=3 |
  | `3.1.  Session Initiation` | ✅ level=2 |
  | **`A.1 Client State Machine`** | ❌ **None** |
  | **`Appendix A: RTSP Protocol State Machines`** | ❌ **None** |
- **触发条件**：阶段 A 用章节树**替换**（而非并入）现有的「关键词行 ±60 行」定位 ⇒ RTSP 唯一权威的状态机章节（A.1 客户端表 / A.2 服务端表）不会进候选。
- **实测影响**：按「章节标题 + 状态/会话/事务/阶段关键词」定位，RTSP 只命中 §3.4 Session Identifiers、§12.37 Session、§14.5 Playing media into an existing session ⇒ 抽出 **5 条**（状态名 RFC 命中 4/5），而**现有实现是 14 条、状态名 4/4 命中、method 5/5 真实** ⇒ **权威转移 14 → 5，是净退化**。
  ⚠️ 归因边界：该退化在我的**试点脚本**上复现（脚本正则只匹配数字编号），**不等于现方案必然如此**；但它证明「章节树能覆盖 RTSP 状态机章节」这一前提**当前不成立**。
- **影响程度**：**高**（阶段 A 的验收标准「SMTP 命中且 RTSP/SIP 候选不减少」按现状**不可达成**）
- **建议改进**：
  1. **前置修复**：扩展 `_parse_heading_shape` 支持 `A.1` / `B.2` 形式的字母附录编号与 `Appendix X:` 标题（并补对应单元测试）；
  2. **阶段 A 改为「并集」而非「替换」**：候选 = 「现有正文关键词扫描（能抓到 A.1/A.2）」∪「章节树定位（能抓到 SMTP 的 Transaction Model）」⇒ 两类协议都覆盖，且不丢 RTSP 的权威表；
  3. 验收标准改为可量化：RTSP 候选命中集合**必须包含 A.1 与 A.2**。

### P0-2 【高】阶段 C「允许推断」缺命令白名单约束 ⇒ 29% 垃圾 method ⇒ 种子含假命令

- **问题**：方案阶段 C 把 prompt 从「只抽明确写出的转移、不要推测」改为「从文本推断状态与转移」，**未约束 `method` 必须是该协议真实方法/命令**。
- **触发条件**：阶段 C 实施后，LLM 会把「触发条件」而非「方法」写进 `method` 字段，或把协议内部动作当命令。
- **实测影响**（SMTP，方案阶段 A 的章节定位 + 阶段 C 的 prompt）：
  | method 全表 | 真实命令 | 垃圾 |
  |---|---|---|
  | 14 个 | 10 个 | **4 个：`.` / `CONNECT` / `TLSHandshake` / `TLSHandshakeComplete`（29%）** |
  ⇒ 这些会**直接变成报文里的方法名**。⚠️ 这与已实测的 SIP 失败模式**同构**：SIP 的 RFC 状态机触发列是事件（`Timer F`/`2xx`）⇒ `edge_cover` 生成 `METHOD` 占位符请求。
  ⇒ **本次修正**（我已实测有效）：prompt 里给出**已知命令/方法列表**并要求 method 必须取自该表、触发条件不在表内则不抽 ⇒
  | 协议 | 转移 | method 真实率 | 垃圾 |
  |---|---:|---:|---:|
  | smtp | 33 | **9/9 = 100%** | **0** |
  | rtsp | 5（受 P0-1 影响） | 4/4 = 100% | 0 |
  | sip | 14 | 4/4 = 100% | 0 |
- **影响程度**：**高**（垃圾 method ⇒ 种子含不存在的命令 ⇒ ChataFL 重放必失败 ⇒ 直接损伤模糊测试有效性）
- **建议改进**：阶段 C 的 prompt 增补第 2 条硬约束「`method` 必须取自已知命令列表；触发条件非方法（响应码/计时器/事件）则不抽」，并把「已知命令列表」由 `methods` 桶注入（数据驱动，非硬编码）。

### P0-3 【高】删骨架的代价被低估：sip/smtp 确定性层不是「变少」而是**归零**

- **问题**：方案第一部分原则 2 写「删骨架后 4 个维度走默认值兜底，种子变少、覆盖下降」。
- **触发条件**：阶段 2 移除骨架特权后，RFC 单源态下 `transitions` 只剩 RFC 源产出。
- **实测影响**（RFC 单源口径，仅剔除骨架的 `target_state`）：
  | 协议 | 现状 transitions / 确定性层 | 排除骨架后 | 该协议 RFC 源可抽 |
  |---|---|---|---|
  | rtsp | 14 条 / 15 条种子 | 14 条 / 15 条（不变） | 14 ✔ |
  | **sip** | 51 条 / **45 条** | **0 条 / 0 条** | 14（但触发列非方法名，不可用） |
  | **smtp** | 64 条 / **56 条** | **0 条 / 0 条** | **0**（RFC 无 state machine 表述） |
  ⇒ ⚠️ **确定性层归零 ⇒ `edge_cover` 与 `generic_danger` 两层同时失效** ⇒ 只剩 `canonical` + `vuln_boundary` + `action_seq`。
  ⇒ 现有生产 prompt 的第 2 条硬性规则是「状态转移要合法（参考 [状态机转移]）」⇒ **状态机为空时该指令自相矛盾**。
- **影响程度**：**高**（sip/smtp 的种子会塌陷到不可用于状态机模糊测试的程度）
- **建议改进**：
  1. 阶段 1 改为**逐维度开关**（`--exclude-skeleton-dims` 已有该能力），先只关 `target_state`（收益最大、代价可控），`message_instance`/`method_sequence`/`occurrence` 延后；
  2. **门禁**：进入「删骨架」阶段前，先用阶段 A~C 的升级能力把 sip/smtp 的 RFC 源 `transitions` 补到「≥ 骨架版 80% 且 method 真实率 ≥ 95%」，否则**不允许删**；
  3. 阶段 2 的验收标准补一条：**每个协议的确定性层种子数 ≥ 删骨架前的 50%**。

### P0-4 【中高】「允许推断」与「RFC 单源纯净度」主张冲突，论文口径需显式处理

- **问题**：推断出的状态名有相当比例**不在 RFC 原文**（SMTP 实测 11 个状态里仅 5 个命中 = 45%）；且 `section_path`/`evidence` 无法覆盖推断出来的边 ⇒ **溯源链断裂**。
- **触发条件**：阶段 C 允许推断后，SMTP/SIP 的状态机成为「部分规范原生 + 部分推断」。
- **影响程度**：**中高**（论文若声称「RFC 单源纯净」而状态机里含大量推断名与无溯源的边 ⇒ 审稿人会质疑）
- **建议改进**：
  1. 给 `transitions` 增加**来源分级标记**：`native`（规范原文可溯源）/ `inferred`（推断）；现有 `evidence.source_anchor` 只对 native 有值 ⇒ 推断条目必须显式标 `evidence_kind=inferred`；
  2. 论文口径改为「**RFC 抽取 + 规范内推断**」，并单独报告 native 占比；
  3. 阶段 D 的评测**必须分 native / inferred 两组**报 F1，否则数字会被推断条目稀释而失真。

### P1-5 【中】缓存键不含 `prompt_version` ⇒ 阶段 E 的「缓存失效」脆弱且易静默失效

- **问题**：状态机 LLM 的缓存键只有 `md5(code_blocks)`（`source_autoseeder`）与段落 hash 拼接（`rfc_extractor`），**不含提示词版本** ⇒ 改 prompt 但缓存命中 ⇒ **改动静默不生效**。
- **触发条件**：阶段 C 改 prompt 后直接构建 ⇒ 命中旧缓存 ⇒ 以为升级了其实没有（**这正是本项目已有的坑**）。
- **实测证据**：本轮做提示词对照试点时**必须绕过缓存重跑**，否则会得出「改了没用」的假结论。
- **影响程度**：**中**（阶段 E 的验收会误判为成功）
- **建议改进**：阶段 E 显式把 `prompt_version` 并入缓存键（与语义规则那条线已有的 `sha256(candidate_text + prompt_version + model)` 契约对齐），并让缓存文件记录版本；版本变更即自动失效，不靠手改 `block_hash`。

### P1-6 【中】阶段 D 的「语义模糊匹配」引入新依赖，威胁离线复现性

- **问题**：方案引用 PSMBENCH 的 cosine 语义匹配 ⇒ 需 embedding 模型（本地或 API）。
- **触发条件**：阶段 D 实施。
- **影响程度**：**中**（若用 API：凭据管理 + 网络依赖 + 不可复现；本地模型：新增模型文件与推理依赖）
- **建议改进**：优先用**零新依赖**的可审计判据组合：① 状态名在 RFC 原文命中率（我已全程使用）；② method ∈ 真实命令集比例；③ 与人工小真值集的精确匹配；④ 仅当 ①~③ 不足时再考虑本地句向量。**不建议用外部 API**。

### P1-7 【中】SMTP 的「状态机」与 RTSP 的不同构 ⇒ 同一桶内语义混淆

- **问题**：SMTP 抽出的 (from, method, to) 语义是「命令序列阶段推进」（Greeting→Mail→Recipients→Data），而 RTSP 是「会话状态转移」（Init→Ready→Playing）。同放一个 `transitions` 桶，下游 `edge_cover`/`generic_danger` 的假设（from/to 是可停留的状态）不再成立。
- **触发条件**：阶段 C 完成后三协议状态机混用。
- **影响程度**：**中**（语义正确性受损，且难以在论文里说清）
- **建议改进**：给 transition 增加 `kind` 字段（`session_state` / `command_sequence`），下游按 kind 分别处理；或对 SMTP 只保留 `command_sequence` 并在论文中单列。

### P1-8 【中高】阶段 4「从 RFC 抽取必填头」缺少可行性验证，工作量被低估

- **问题**：方案认为 `required_headers` 可「改走从 RFC 抽取」。我实测了最省事的路径（把语义规则里 `operator=present` 的规则按 `section_path` 绑到方法）：
  | 协议 | 骨架「方法-必填头」对 | RFC 投影对 | 覆盖 |
  |---|---:|---:|---:|
  | rtsp | 14 | 1 | **7.1%** |
  | sip | 86 | 0 | **0%** |
- **实测同时揭示了正确形态**：SIP 的必填头是**消息级**的（"所有请求 MUST 含 Via/From/To/Call-ID/CSeq/Max-Forwards"），骨架却把它复制到 14 个方法上 ⇒ RFC 源可以抽，但要按**消息级**抽（新增 aspect），而不是方法级。
- **影响程度**：**中高**（阶段 4 若按「改标注」做，等于把必填头继续伪装成「非 RFC 来源」；若按「从 RFC 抽」做，工作量比方案设想大）
- **建议改进**：阶段 4 拆成两步：4a 新增「**消息级必填头**」抽取（可复用现有语义规则 LLM 通道与结构化提示词）；4b 再把 `required_headers` 桶的来源标注改为 `rfc` 或 `protocol_declared`（**显式区分**，不伪装）。

### P1-9 【中】`required_headers` 与骨架共用物化路径 ⇒ 阶段 1/3/4 存在耦合

- **问题**：`_materialize_skeleton` 与 `_materialize_required_headers` 是构建脚本里的**两个独立函数**，但 required_headers 也标 `authority=profile` ⇒ 阶段 3「删除骨架源目录定义/来源维度表」时极易连带删掉 required_headers 的定位。
- **触发条件**：阶段 3 的物理清除。
- **影响程度**：**中**（删除范围含糊，可能误删或返工）
- **建议改进**：阶段 3 前**先把 required_headers 的物化路径独立出来**（独立源目录 + 独立 authority 常量），再执行清除；并在阶段 3 的验收里加「`grep skeleton` 无残留 **且** `required_headers` 仍能物化」两条。

### P2-10 【低】缺可执行的回滚定义

- **问题**：方案写「可回滚——每阶段先记录基线，保证可回退」，但未定义回滚点形态。
- **建议改进**：每阶段一个 git tag（如 `stage1-skeleton-off`）+ 每阶段的种子 MD5 快照落盘 `local/`（复用现有 `local/baseline_p0_seeds.md5` 格式）。

### P2-11 【低中】候选块变大 ⇒ LLM 成本与截断风险上升

- **问题**：整节入块，SMTP 实测最长 8017 字符；RFC 章节可远超 10k 字符 ⇒ 截断会丢尾部状态信息。
- **建议改进**：设块大小上限（建议 8k 字符）+ 超长章节按二级标题再切分；并在块元数据里记录「是否被截断」。

### P2-12 【低】并发与竞态

- **问题**：阶段 E 三协议重抽若并发写同一缓存目录，存在写竞态；现有缓存写入未做原子替换（先写临时文件再 rename 可解）。
- **建议改进**：缓存写入改原子替换（`tmp + os.replace`）；若并发，缓存文件名带协议名即可隔离。

### P2-13 【中】可观测性：推断条目缺溯源字段

- **问题**：推断出的状态/转移没有 `evidence.source_anchor` ⇒ 无法回指 RFC 原文 ⇒ 论文的可追溯性论证会缺口。
- **建议改进**：推断条目至少记录「推断依据的章节路径 + 该章节的字符区间」，与 native 条目的 `source_anchor` 同构，便于人工复核。

### P2-14 【中】测试缺口：新定位逻辑与新抽取口径缺少单元测试

- **问题**：方案有验收标准，但未列单元测试。
- **建议改进**：补 4 类测试：① 章节解析支持字母附录（`A.1`）与 `Appendix X:`；② 候选去重（同章节不重复产候选）；③ 块大小上限；④ method 真实率守门（白名单外 method 计数 = 0，作为回归断言）。

### P2-15 【低】安全与权限：方案本身无外部输入面

- **问题**：本方案改动不引入新的外部输入面 ⇒ 注入/越权风险低。唯一需要注意的是阶段 D 若引入外部 API ⇒ 凭据管理与出网策略需评估。
- **建议改进**：评测一律本地模型；确有 API 需求时按项目既有凭据规范（`.env` + 不落盘）管理，禁止把密钥写入代码或报告。

### P2-16 【中】缺「能力就绪」客观门禁 ⇒ 推进顺序可能空转

- **问题**：方案规定「先强能力后去兜底」，但没定义「强能力已达成」的判据 ⇒ 可能状态机升级效果不佳却仍进入删骨架阶段。
- **建议改进**：设量化门禁（建议）：`RFC 源 transitions 条数 ≥ 骨架版 × 80%` **且** `method 真实率 ≥ 95%` **且** `native 状态名 RFC 原文命中率 ≥ 90%` ⇒ 三者全过才允许进入第一部分阶段 2。
