## 二、记录的问题（按严重度）

### 🔴 问题 ①（**必须改代码**）：`raw_writers` 无二进制协议派发 ⇒ `.raw` 不是 DHCP 报文

**现象**：生成的 `.raw` 只有 14 字节：

```
DHCPDISCOVER\r\n
```

而真正的 DHCP 报文应是 **236 字节 BOOTP 固定头**（op/htype/hlen/hops/xid/secs/flags/
ciaddr/yiaddr/siaddr/giaddr/chaddr/sname/file + magic cookie 0x63825363 + 选项 TLV）。

**根因**：`core/raw_writers.py::seedcorpus_to_raw()` 的派发只有
RTSP / TCP / DNS / HTTP / 「其他」（走 `expert_note/request_format.json` 的**文本** `key=value` 模板）。
profile 存在 ⇒ 走 `_render_from_profile()` ⇒ 只支持 `request_line` / `header_line`
两个**文本行模板**（占位符仅 `{method}/{url}/{version}/{argument}` 与 `{key}/{value}`）。

⇒ **二进制协议（字段布局 / 字节序 / padding / 定长字段）无法用配置表达**。
这是**能力缺口**，不是配置错误。

**影响**：DHCP 的种子**对 fuzzer 无效**（目标不会接受）。

**修法建议（待你决定）**：
- **A**：给 `raw_format` 增加「二进制布局」段（如 `binary_fields: [{name, offset, length, endian}]`），
  在 `_render_from_profile` 里加一条分支 —— 改动 `raw_writers.py`，**不动模型代码**；
- **B**：新增一个 `raw_writers` 的 DHCP 专用 writer（类似 `_rtsp_to_raw`）；
- **C**：本轮先不修，DHCP 只做「抽取→中枢」验证，不产出可 fuzz 的种子。

### 🟠 问题 ②（配置可解，但需改一行代码）：协议名大小写校验

**现象**：`scripts/build_hub.py --protocol dhcpv4` 与 `--protocol DHCPv4` **双向都失败**：

```
[错误] 协议 'dhcpv4' 不在 kb/ 下（可用: DHCPv4, rtsp, sip, smtp）
```

**根因**（`build_hub.py:1329-1330`）：

```python
known = {p.name for p in paths.kb_root().iterdir() if p.is_dir()}   # 区分大小写
if protocol.lower() not in known:                                    # 折叠大小写
    print("... 不在 kb/ 下 ...")
```

⇒ 一边**折叠**、一边**不折叠** ⇒ 目录名含大写字母的协议**永远过不了**。
（`paths.kb_source_dir()` 用 `protocol.lower()`，Windows 上大小写不敏感 ⇒ 实际能读到文件，
只是被这道字符串校验拦住。）

**当前绕过**：`local/_dhcp_build.py` 给 `kb_root()` 加了「小写别名」，
**其余流程完全走真实代码**（已实测：抽取/质量闸/映射/物化/落盘/状态机全部正常）。

**修法建议**：`known` 改成 `{p.name.lower() for p in ...}`（一行）。

### 🟡 问题 ③（配置层）：章节号撞车 ⇒ 方法集混入 `NVT`

**现象**：RFC 源抽出的 6 个方法里有一个 **`NVT`**（不是 DHCP 消息类型）：

```
['DHCPDECLINE', 'DHCPDISCOVER', 'DHCPINFORM', 'DHCPRELEASE', 'DHCPREQUEST', 'NVT']
```

**根因**：`rfc_config.method_sections = ["4.3"]` 是**全局**的、**不分文件**。
36 份 RFC 的章节号大面积重号（每份都有 §1–§8，语义各异）⇒
`rfc6607.txt` 的 §4.3 也被当成「消息定义章」⇒ 抽出 `NVT`。

**溯源**（`evidence_summary` 生效了，能精确定位）：

```
NVT        rfc:DHCPv4.method.nvt@file:rfc6607.txt#@414
BOOTREQUEST rfc:DHCPv4.field.bootrequest@file:rfc1542.txt#@80
Message     rfc:DHCPv4.field.message@file:rfc2132.txt#@1570
```

**修法建议**（二选一，均需改代码）：
- **A**：给 `rfc_config` 增加**按文件限定**的章节配置（如 `sections_by_file: {"rfc2131.txt": {...}}`）；
- **B**：把 `method_sections` 精确到 `4.3.1`–`4.3.5`（仍是全局，撞车概率降低但不为零）。

---

### 🟡 问题 ④（配置层）：`headers` 桶全是**误抽的章节标题**，没有真字段

**现象**：中枢 `headers` 桶的 36 个键：

```
Applicability / Authentication / Bibliography / Compatibility / Configuration /
Context / DHCP / DHCPACK / Example / Format / Implementation / Summary / URL …
```

⇒ **一个都不是** DHCP 选项或 BOOTP 字段。

**根因**：RFC 2132 的选项是「小节标题 + ASCII 图」形态（`3.1. Pad Option`），
**没有 ABNF** ⇒ 现有 ABNF 通道抽不到（实测**全协议 0 个 ABNF 字段**）；
而「编号+标题」通道把**章节标题**当成了字段名。

**连带影响**：`_apply_instance_fields` 的 `known_fields` 来自 headers 桶
⇒ BOOTP 字段不在其中 ⇒ 实例字段**全部**被当「未知字段」⇒ 走 argument 分支
⇒ 报文头全丢、argument 变成 `op` 的值（`DHCPDISCOVER 1`）。

**当前绕过**：骨架里补了 16 个 BOOTP 字段的 `syntax` facts ⇒ headers 桶认识它们
⇒ 字段分流恢复正常（实测 13 个字段全进 `msg.headers`，argument 空）。

**长期修法建议**：为「编号+标题」通道加**停用词/语义过滤**（`Introduction`/`Bibliography`/
`Context`/`Summary`/`Example`/`Format`/`Compatibility` 等不是字段名），
或为 RFC 2132 这类「选项表」形态加专用通道。

---

### 🟡 问题 ⑤（已记录，不阻塞）：DHCP RFC 里**没有 "state machine" 字样**

**现象**：`infer_transitions` 的候选定位靠全文扫 `state\s+machines?`
⇒ 36 份 DHCP RFC **命中 0** ⇒ LLM 状态机通道无从下手 ⇒ transitions=0
⇒ seedgen 报「无状态机转移，无法生成种子」。

**当前绕过**：骨架手工提供 6 条状态机边（从 RFC 2131 §3.1 的 ASCII 时序图提炼）。

**修法建议**：把候选定位从「扫关键词」扩到「扫**消息名表**」（如 DHCP 的
`DHCPDISCOVER`/`DHCPOFFER`/… 在 §3.1 出现 ⇒ 该节即状态机描述）。

---

### ⚪ 问题 ⑥（已知，不修）：二进制协议下 `required_headers` 不适用

`profile.seedgen.required_headers = {}`（DHCP 无文本头）⇒
B2 新增的**必填头覆盖守卫**会因「transitions 里的方法没有必填头条目」而告警。
实测 rtsp/sip/smtp 无此问题（它们的 `header_line` 非空）⇒ 守卫判据
（`raw_format.header_line` 非空）对 DHCP **正确豁免** ✅。
