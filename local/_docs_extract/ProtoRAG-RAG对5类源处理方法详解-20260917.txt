摘要
本文是 ProtoRAG 协议感知模糊测试框架中「RAG 模块」的技术详解文档。
ProtoRAG 在种子生成与变异阶段,把 5 类异构知识库源统一映射为 5 段 RAG context,rfc / source / traffic / vuln / edge 五段各自独立检索,每段最多 800 字符,五段合计 4000 字符预算喂给 LLM。这种「5 段分层」设计让 LLM 在每次种子生成时都能同时看到规范主源、源码/接口辅助、真实流量模式、历史漏洞模式、专家边缘注释五类互补信号。
为了让 5 段 RAG 的输入干净可靠,ProtoRAG 在 KB 文件入库阶段引入「内容驱动分类 + 5 类 source_family」机制:依据 30 条支持证据 + 27 条排斥证据对每个 KB 文件打分,并以 7 档决策 (A1/A2/B1/B2/B3/C/D) 决定自动通过、LLM 仲裁还是人工复核。在 KB 文件被分类到对应 family 后,由 8 个 per-format extractor (RFC / traffic_pcap / traffic_raw / ndjson / csv / vuln / expert_notes / api_doc / header_def / error_table) 分别抽取为 ProtocolNorm,并通过 source_layer facet 标记其归属段。
本文围绕三个阶段展开:抽取阶段 (5 类源各自的处理算法)、合成阶段 (5 段 RAG 拼装与字符预算)、校验阶段 (JointConstraint 协议无关联合校验)。全文 50+ KB,以公式 + 代码片段 + 实测数据三结合的方式描述算法细节,可直接作为论文 Method 章节的素材使用。
一、引言：为什么对知识库源做差异化处理
1.1 协议模糊测试对知识的需求是异构的
协议模糊测试 (Protocol Fuzzing) 在 AFLNet 体系下需要把种子消息发送给被测服务器并观察响应。LLM-guided 协议模糊测试进一步把 LLM 作为「种子构造器」,提示词中需要包含协议的语法、状态机、必填字段、典型消息序列、历史漏洞模式等。ProtoRAG 在 KB (Knowledge Base) 中维护三类输入源:
原始资料:协议 RFC、源码 header 定义、OpenAPI / Swagger 文档、错误码表
实测数据:fuzzing 会话抓包 (pcap / pcapng / ndjson / CSV)、客户端 / 服务端日志
先验知识:历史 CVE / AVD 漏洞条目、专家 ## hint 注释
这三类资料各自的语义角色不同:RFC 是权威规范源、pcap 是真实流量样本、CVE 是已知攻击模式、专家注释是经验补丁。如果用「单一 retriever + 单一拼接」方式把所有源一股脑扔给 LLM,会出现三个问题:
(1) 规范主源被噪声稀释
RFC 文档通常 100KB+ (实测 rtsp/rfc2326.txt=190.4KB、tcp/rfc793.txt=168.7KB、dns/rfc1035.txt=119.7KB),而单条 CVE 条目可能只有 2KB。如果不按 source 切片,真实流量样本中的字节级特征会挤占 RFC 章节文本的 token 配额,LLM 反而看不清 method 语义。
(2) 源类型错配导致格式冲突
pcap 字节魔数 0xD4C3B2A1、PDF 头 %PDF-、HTML 标签密度 > 30%、JSONL 逐行 JSON,这些格式特征在文本类 (RFC/CVE/Spec/Expert) 出现时是「不该有」的;反之文本类特征 (MUST/SHOULD/Authors' Addresses/CVE-YYYY-NNNN) 在二进制或流量样本中出现也是异常。ProtoRAG 用 28 条排斥证据 (-2.5/-2.0/-0.5 三档) 显式压制「格式错配」误判。
(3) 源缺失与降级
如果某协议 KB 没有真实流量样本 (例如首次接入的私有协议),traffic 段必须退化为 "(none)";如果 CVE 库没有该协议的条目,vuln 段降级为空。ProtoRAG 用 (none) / (no spec graph) 等显式占位符标记缺源,而不是用「强行凑数」降低后续 LLM prompt 的可信度。

二、5 类源的形式化定义
ProtoRAG 在两处使用「5」这个数字:
5 段 Layered RAG (rag/rag_context.py::_LAYERED_SEGMENTS):rfc / source / traffic / vuln / edge — 这 5 段是「喂给 LLM 的视角切片」
5 类 source_family (core/classifier/evidence_profile.py::FAMILIES):rfc / traffic / vuln / expert_note / source — 这 5 类是「KB 文件的分类标签」
两者关系:5 类 family 是「分类维度」(每个 KB 文件打 1 个 family 标签);5 段 RAG 是「组装维度」(spec graph 里的 entity 按 source_layer facet 归入 5 段,每段独立检索后拼装给 LLM)。cve 在分类层有专属 family,在组装层与 vuln 段融合 (因为两者都提供历史漏洞信号);spec_doc / expert_note 在分类层独立,在组装层合入 source 段和 edge 段。

2.1 5 段 RAG 的语义优先级
5 段在 spec_graph 查图与 LLM 拼装中按以下优先级排序 (JointConstraint.DEFAULT_LAYER_PRIORITY):
rfc > expert_notes > header_def > error_table > source > traffic_pcap > traffic_raw > fuzz_history > log_file > vuln > api_doc
前三段 (rfc / expert_notes / header_def) 是「静态规范」,第四段 (source) 是「实现细节」,traffic 两段是「实测模式」,vuln 是「历史漏洞」,api_doc 是「规范摘要」。LLM prompt 中 5 段按 (rfc > source > traffic > vuln > edge) 顺序拼装,理由:rfc 规范定义 method 语义、source 提供实现层 header 定义、traffic 展示真实用法、vuln 暴露已知攻击模式、edge 给出专家补丁建议。
2.2 闭环反馈源与 KB 5 段的边界
有两类 source 不进入 KB 5 段 pathgen 拼装路径,而是闭环反馈源:
fuzz_history:stage3 AFLNet 跑出的会话历史,仅在 stage4 重抽规范时使用
log_file:服务端 / 客户端运行时日志,仅在 stage4 重抽规范时使用
这两个 source_layer 在 extractor_dispatcher.py 中显式 skip (SkipReason.LOG_FILE / SkipReason.FUZZ_HISTORY),在 rag_context.py::_FEEDBACK_SOURCES 中独立处理 (build_feedback_rag_context)。闭环反馈源与 KB 5 段是「写时」与「读时」的对偶:KB 5 段是「写时固化」(boot 阶段预抽好),闭环反馈是「读时即时」(运行时按需调 LLM 重抽)。
三、内容驱动分类机制
3.1 设计目标
KB 文件分类器的输入是任意一个待入库文件,输出是 ClassIR {family, confidence, evidence, format_type, secondary}。设计目标:
(1) 单标签稳定:同格式文件 (RFC 文本、pcap、JSON) 在 28 条规则下应得到一致标签
(2) 边界可解释:每条 evidence 给出 rule_id + weight + level,人工复核可见
(3) 决策可分档:7 档 (A1/A2/B1/B2/B3/C/D) 覆盖「自动通过 → LLM 仲裁 → 人工复核 → 阻塞」全光谱
(4) 缓存友好:content_hash → tier 的 LRU 缓存减少重复分类
3.2 三步流程
完整流程由 3 个 step 串成:
# Step 1: format_type 探测 (ir_normalize.detect_format)  - 二进制魔数 (pcap: 0xD4C3B2A1, pcapng: 0x0A0D0D0A)  - 结构特征 (HTML 标签密度 > 30%, JSONL 逐行)  - 文本指纹 (RFC 2119 关键字 / OpenAPI 版本字符串 / CVE 编号)# → 9 种 format: rfc / pcap / pcapng / ndjson / csv / json / html / markdown / binary# Step 2: 内容驱动打分 (scoring.score_families)  - 对 5 类 family 各跑 SUPPORT_EVIDENCE + NEGATIVE_EVIDENCE 规则集  - raw[family] = Σ support_weight - Σ |negative_weight|  - score_abs[family] = clip(raw / (Σ support_weight × 1.05), 0, 1)  - 证据数分档封顶: 0→0, 1→0.5, 2→0.7, ≥3 不封顶  - score_rel[family] = score_abs / max(score_abs)# Step 3: 7 档决策 (scoring.decide)  - 主标签 abs ≥ 0.65 且 margin OK → A1 (单标签自动通过)  - 主标签 abs ≥ 0.65 且有副标签 → A2 (多标签自动通过)  - 主标签 abs < 0.65 → LLM 仲裁 → B1/B2/B3  - 规则冲突 (并列 top_rel=1.0) → C (人工复核)  - 解析失败 / 极低置信 → D (阻塞入库)
3.3 打分公式
raw[family] 是 family 的「加权证据净值」,公式如下:
raw[f] = (Σ support_weight[f] × hit)       - (Σ |negative_weight[f]| × neg_hit)score_abs[f] = clip( raw[f] / ( Σ_{r∈SUPPORT_F} LEVEL_WEIGHTS[r.level] × 1.05 ), 0, 1 )score_rel[f] = score_abs[f] / max_{g∈FAMILIES}( score_abs[g] )

3.6 抽样与反馈闭环
为了不让分类器「固化」错判,ProtoRAG 在每个 batch 抽取完成后跑一次抽样复核:
每个 family 随机抽 5% 的 ClassIR,用 ground-truth 标签对照
误判的 ClassIR 进入「人工标注集」,作为下一轮 LLM few-shot prompt 的示例
LRU 缓存按 content_hash 复用上轮结果 (缓存命中率实测 ~70% 重复文件场景)
四、抽取阶段:5 类源各自的处理方法
KB 文件经过分类后,被分发到对应 extractor。每个 extractor 实现 BaseExtractor.extract(file_path, protocol) 接口,产出 list[ProtocolNorm]。每个 norm 含 5 元组 (kind, name, content, source, facets, kb_source_type, extraction_method)。facets 用于后续查图定位。
4.1 RFC 规范主源 (rfc family)
4.1.1 输入与产出
输入:kb/spec/<proto>/rfcXXXX.txt 纯文本 (RFC 2326 = 190.4KB,RFC 793 = 168.7KB,RFC 1035 = 119.7KB)。产出:ProtocolNorm 列表,典型 kind 分布 = method / state / field / transition / actor 五类。
4.1.2 算法:5+1 启发式 + LLM 兜底
RFC 抽取复用 E 方案 (core/extractors/rfc.py),分两阶段:
# 阶段 1: 章节切分 (RfcSectionParser)sections = RfcSectionParser().parse(text, source=file_path.name)#  按 RFC 章节编号 (^N.\s+Title) 切;每节含 title + body# 阶段 2: 5+1 启发式 (RuleBasedExtractor.extract_from_sections)for section in sections:    # 5 启发式: 大写 method 名 (SETUP/PLAY/...)    #          RFC 2119 关键字上下文 (MUST/SHOULD/MAY/SHALL)    #          request line 模式 (METHOD rtsp://...)    #          response 模式 (RTSP/1.0 NNN ...)    #          header 定义模式 (Header-Name: required|optional pattern)    norms += rule_extractor.extract_from_sections(protocol, sections)# 阶段 3 (+1): LLM 兜底if llm is not None and not isinstance(llm, StubLLMClient):    # rule 抽到 ≥1 method → LLM 只补 field/state/transition 三类    # rule 抽 0 → LLM 兜底抽 4 类 (method+field+state+transition)    include_method = (len(rule_norms) == 0)    llm_norms = LLMExtractor(llm, parser,                              include_method=include_method).extract_from_sections(protocol, sections)    norms.extend(llm_norms)
4.1.3 实测数据
RTSP 协议 (RFC 2326) 在 rfc_mode='llm' 默认模式下抽到 26420 条 norm,state_machine 4 states / 26 transitions。rfc_mode='heuristic' 显式降级路径只抽 ~11 条 norm (仅启发式部分)。
4.1.4 输出 facets
RFC 产出的 norm 通常带 facets = ["rfc_method_def", "rfc_section:N", "protocol:"+protocol],方便 LLM prompt 按「章节定位」召回。

4.2.2 pcap 抽取算法 (TrafficPcapExtractor._do_extract)
scapy 解析 pcap → 过滤 RTSP 端口 (554/8554) → 抽取 method / response / CSeq / transport。算法分 5 步:
packets = rdpcap(str(file_path))   # scapy 解析for pkt in packets:    # 1) 抽 TCP/UDP layer + payload bytes    if pkt.haslayer(TCP):        sport, dport = int(tcp.sport), int(tcp.dport); payload = bytes(tcp.payload)    elif pkt.haslayer(UDP):        sport, dport = int(udp.sport), int(udp.dport); payload = bytes(udp.payload)    else: continue    # 2) 端口过滤 (只保留 RTSP 端口)    if sport not in RTSP_PORTS and dport not in RTSP_PORTS: continue    # 3) 抽 method (regex: ^(OPTIONS|SETUP|PLAY|...)\s)    m_req = _RTSP_REQUEST.match(payload)    if m_req: method_count[m_req.group(1)] += 1    # 4) 抽 response code (regex: ^RTSP/1.\d\s+(\d{3})\s)    elif m_resp: response_codes.append(int(m_resp.group(1)))# 输出 5 类 norm:# ① 每 method 1 条 message norm (kind=message, facets=traffic_method_seq)# ② 1 条 state_machine norm (method → method 转移序列)# ③ 1 条 field norm (CSeq 出现频次, facets=traffic_field_freq)# ④ 1 条 protocol norm (TCP/UDP 分布, facets=traffic_protocol_overview)# ⑤ 1 条 actor norm (RTSP server port 出现, facets=traffic_actor)
4.2.3 ndjson / csv 算法差异
ndjson 走 Elasticsearch Wireshark JSON,逐行 json.loads 拿 layers.rtsp.rtsp.request_method / response_code / request_url;CSV 走 Wireshark 列名 (rtsp.method / rtsp.status / rtsp.url / rtsp.session),只处理含 rtsp.method 列的 RTSP 控制 CSV,rtp.csv 直接返 [] 不抽。
4.2.4 关键设计:不抽字段级条目
traffic 抽取只统计 method 频次 + 状态序列 + 字段共现计数,不生成「每个 method 的必填字段」这样的「字段级条目」。原因是真实流量的字段值是「实际客户端用什么」,不能当作「规范定义」。字段必填的权威信息由 RFC 段 (4.1) 提供,traffic 段只补充「真实用法概率分布」。

4.3.2 占位符翻译规则
trigger.requests 字段含 12 类占位符,实测触发过的全部翻译为 {{xxx}} 形式供运行时注入:
_PLACEHOLDER_PATTERNS = [    # Session 类 (RTSP-001 关键 — multi-Session 保留 N)    (re.compile(r"<SESSION_FROM_SETUP_(\d+)>"), r"{{session_id_\1}}"),    (re.compile(r"<SESSION_FROM_STEP_(\d+)>"), r"{{session_id_\1}}"),    (re.compile(r"<SESSION>"), "{{session_id}}"),    # Content-Length 自增    (re.compile(r"<AUTO>"), "{{auto_length}}"),    # URI resource    (re.compile(r"<PAYLOAD>"), "{{resource}}"),    # payload 大小 (raw / base64 / 普通 bytes)    (re.compile(r"<PAYLOAD_(\d+)_BYTES_RAW>"), r"{{payload_\1b_raw}}"),    (re.compile(r"<PAYLOAD_(\d+)_BYTES_BASE64>"), r"{{payload_\1b_b64}}"),    (re.compile(r"<PAYLOAD_(\d+)_BYTES>"), r"{{payload_\1b}}"),    # payload 语义    (re.compile(r"<PAYLOAD_INTEGER_OVERFLOW>"), "{{payload_int_overflow}}"),    (re.compile(r"<PAYLOAD_HEXSTREAM>"), "{{payload_hexstream}}"),    (re.compile(r"<LONG_PAYLOAD_(\d+)>"), r"{{long_payload_\1}}"),    # playlist URL    (re.compile(r"<PLAYLIST_ITEM_URL_(\d+)>"), r"{{playlist_url_\1}}"),    # repeat 次数    (re.compile(r"<REPEAT_(\d+)_TIMES>"), r"{{repeat_\1}}"),]
4.3.3 CVE 描述符删除策略 (本次修订)
trigger.requests 中有 8 条 CVE 描述符 (<HARDCODED_PASSWORD>、<MALFORMED_VALUE>、<EXTVLCOPT_INJECTION> 等)。此次修订后,描述符整段删除 (替换为空字符串),不进 .raw;同时在 build_vuln_graph 时把描述符展开成自然语言说明写入 seed entity.content,让 LLM 看到「要构造什么类型的畸形值」而非「用什么字面值」。原因:hardcode 成字面值 (如 "MALFORMED") → server 收到合法字符串,不触发 CVE,种子看似无占位符但实际坏。
4.3.4 双写产物
vuln extractor 同时产出两个数据结构:
ProtocolNorm (kind=vuln_seed) → norms.jsonl → spec_graph 5 段 RAG 基本元数据
VulnSeed (trigger_requests 翻译后) → build_vuln_graph → RAG 多步序列 + mutation_hints
双写是「同一输入、两个消费侧」的设计:spec_graph 让 5 段 RAG 通用检索可用,vuln_graph 让历史漏洞专属检索 (trigger / mutation_hints) 可用。
4.4 规范摘要 / API 文档 (spec_doc family)
4.4.1 典型文件
OpenAPI 2.0/3.0 (Swagger) YAML/JSON、Markdown API 文档、企业内部协议说明 PDF 摘要 (后者经格式转换)。
4.4.2 抽取算法
APIDocExtractor 用单一 regex 抓 endpoint 路径与 HTTP method 对应关系:
_ENDPOINT = re.compile(    r"^\s*(GET|POST|PUT|DELETE|PATCH)\s+(/[\w/{}-]+)",    re.MULTILINE,)# 每条命中产 1 个 ProtocolNorm (kind=api_endpoint, facets=[api_pattern, endpoint:<path>])
spec_doc 抽取只覆盖 HTTP-ish 协议端点;若协议是 RTSP 这种「自定义 method」,API 文档可能不适用,这时分类阶段会给出 spec_doc 但 extract 阶段返 [] (无害空集)。
4.5 专家注释 / 边缘用例 (expert_note family)
4.5.1 两种格式
expert_note family 涵盖两种典型格式:
Markdown `## hint: METHOD = ...` 模式 (ExpertNotesExtractor 处理)
CSV `code,meaning,when` 三列错误码表 (ErrorTableExtractor 处理)
4.5.2 ## hint: 抽取
ExpertNotesExtractor 用单一 regex 抽取 ## hint 块:
_HINT_PATTERN = re.compile(    r"^#+\s*hint[:\s]+([A-Z][A-Z0-9_]+)\s*\n(.*?)(?=^#|\Z)",    re.MULTILINE | re.DOTALL | re.IGNORECASE,)# 每个 ## hint 块产 1 个 ProtocolNorm (kind=method, name=<METHOD>, facets=[expert_hint])
4.5.3 错误码表抽取
ErrorTableExtractor 用 csv.DictReader 读三列:
# 期待列: code, meaning, when (大小写不敏感, 兼容 .tsv)code   = row.get("code") or row.get("Code") or row.get("CODE")meaning= row.get("meaning")when   = row.get("when")# 产 1 个 ProtocolNorm (kind=outcome, name=<code>, content=f"{meaning} ({when})")
4.5.4 角色定位
expert_note 段在 5 段 RAG 中位置最低,但承担「研究者补丁」作用:RFC 规范没说清楚的边界 case、错误码语义解释、跨 method 组合禁忌,这些往往只能靠 ## hint 块和错误码表来兜底。LLM prompt 中 edge 段虽然字符预算最少 (800),但命中率最高的反而是 edge 段 (因为 researcher 已经做了去噪)。
五、合成阶段:5 段 Layered RAG 拼装
5.1 入口函数
核心入口 rag/rag_context.py::build_layered_rag_context(spec_graph, method, state, *, max_chars_per_segment=800)。签名:
def build_layered_rag_context(    spec_graph,           # SpecKnowledgeGraph (含 source_layer / extracted_by facet)    method: str,          # 目标 method (如 "SETUP")    state: str,           # 目标 state  (如 "Init")    *, max_chars_per_segment: int = 800,   # 每段字符预算) -> dict[str, str]:    """Returns: {        'rfc':     str,    # 段 1: 协议规范主源        'source':  str,    # 段 2: 源码实现细节        'traffic': str,    # 段 3: 真实流量模式        'vuln':    str,    # 段 4: 历史漏洞        'edge':    str,    # 段 5: 边缘 case + 专家注释    }"""
5.2 _LAYERED_SEGMENTS 映射表
5 段与 9 类 source_layer 的映射 (registry-driven, fallback 写死):
_LAYERED_SEGMENTS = {    "rfc":     ["rfc"],    "source":  ["source", "header_def", "api_doc"],    "traffic": ["traffic_raw", "traffic_pcap"],    "vuln":    ["vuln"],    "edge":    ["expert_notes", "error_table"],}# 闭环反馈源 (不进 KB 5 段, 仅 stage4 重抽规范时使用):_FEEDBACK_SOURCES = ["fuzz_history", "log_file"]
5.3 段内检索与裁剪
每段独立走 _entities_by_layer + _format_entity_block 两步:
def _entities_by_layer(spec_graph, layers: list[str], method: str = "") -> list:    layer_set = {f"source_layer:{l}" for l in layers}    out = []    for e in spec_graph.all_entities():        if not (layer_set & set(e.facets or [])): continue        if method:            # 命中 method (entity.name == method 或 entity_id 含 method)            if e.name.upper() != method.upper() and method.lower() not in e.entity_id:                continue        out.append(e)    return outdef _format_entity_block(entities: list, max_chars: int = 800) -> str:    lines, total = [], 0    for e in entities:        # 截短 content 到 200 字符 (per entity), 留 token 给 prompt 主体        content = (e.content or "")[:200]        line = f"  [{e.entity_id}] {e.name}: {content}"        if total + len(line) > max_chars:            lines.append(f"  ... (and {len(entities) - len(lines)} more)")            break        lines.append(line); total += len(line)    return "\n".join(lines)

六、校验阶段:JointConstraint 协议无关联合校验
6.1 校验目标
5 段 RAG 拼装完成后,种子生成器把 RAG context 喂给 LLM,LLM 产出候选种子消息。JointConstraint (core/constraint.py) 在候选种子写入 KB 前做协议无关校验,确保 4 件事:
状态机合法性:消息 method × response code → to_state 是否在 spec_graph transitions_to 关系中
必填字段完整性:method 必填 header 列表是否齐备 (CSeq 通常豁免)
字段格式合法:header 值是否匹配 spec_graph 中定义的 value_pattern
历史漏洞规避:不要盲目复刻 VulnSeed 触发条件 (除非有意 fuzz 该漏洞)

6.3 字段必填 / 可选校验
required_fields(method, state) 返回 method 在 state 下的必填 header 列表。算法:
def required_fields(self, method, state):    spec = self.spec    required = []    mid = f"{spec.protocol.lower()}.method.{method.lower()}"    for r in spec.relations_of(mid, "out"):        if r.rel_type == "requires_field":            field_entity = spec.get(r.dst_id)            field = field_entity.name if field_entity else r.dst_id.split(".")[-1]            if field.upper() == "CSEQ": continue   # CSeq 总是自带, 豁免            required.append(field)    return required
字段必填信息来源于 source 段 (header_def 层 entity 的 requires_field 关系),不是 RFC 段直读。这是因为 RFC 章节中「MUST」关键字需要 LLM 推理才能映射到具体 header,header_def 层是 LLM 抽取后的结构化产物。
6.4 transition 合法性校验
is_valid_transition(from_state, method, response_code) 检查状态机是否允许该转换:
def is_valid_transition(self, from_state, method, response_code):    for r in self.spec.all_relations():        if r.rel_type != "transitions_to": continue        ev = r.evidence        # evidence 格式: "Init + SETUP(200) -> Ready"        if " + " not in ev or " -> " not in ev: continue        left, to_state = ev.split(" -> ", 1)        fs_part, rest = left.split(" + ", 1)        if fs_part.strip().lower() != from_state.lower(): continue        m = rest.split("(", 1)[0].strip().upper()        code = int(rest.split("(", 1)[1].split(")", 1)[0])        if m == method.upper() and code == response_code:            return to_state    return None   # 不在状态机内 = 非法
transition 关系来自 rfc 段 (transitions_to facet),RTSP 实测有 26 条 transitions,TCP 有 36 条 (state_machine.json 实测)。
6.5 协议特化兜底
JointConstraint 在协议未知时用 GenericAdapter 兜底,known_methods / required_headers / fallback_transitions 默认全部空。但对 RTSP/DNS/TCP 等已知协议,BaseProtocolAdapter.from_protocol(name) 自动加载对应 adapter:
RTS ProtocolAdapter:KNOWN_METHODS = [OPTIONS, DESCRIBE, SETUP, PLAY, PAUSE, TEARDOWN, ...]
DNS ProtocolAdapter:KNOWN_METHODS = [QUERY, UPDATE, NOTIFY, ...]
TCP ProtocolAdapter:无 method (TCP 是字节流),但提供 segment / flags 兜底
七、评估方法:5 段 RAG 的消融维度
7.1 评估目标

8.2 与 ChatAFL / AFLNet RAG 的差异
ChatAFL 是 LLM-guided 协议模糊测试的早期工作,但其 RAG 是「单段查询 + LLM prompt 拼接」,没有按 source 切分;AFLNet 是无 LLM 的协议模糊测试,无 RAG 概念。ProtoRAG 把 ChatAFL 的 LLM 能力与 RAG 检索结合,并显式做 5 段切分以解决「规范主源被噪声稀释」问题。
8.3 与通用 multi-source RAG 的差异
通用 multi-source RAG (LangChain / LlamaIndex multi-retriever) 是「多路 retriever 并行召回再 rerank」。ProtoRAG 的 5 段是「按 source_layer 语义优先级硬切 + per-segment 预算裁剪」,不需要 rerank,因为优先级是领域先验而非 learned ranking。
九、小结
ProtoRAG 的 RAG 模块在三个层面对 5 类源做了差异化处理:
分类层:5 类 source_family × 57 条证据规则 → 7 档决策;让 KB 文件按语义角色打标签
抽取层:8 个 per-format extractor × 各异抽取算法 → ProtocolNorm + VulnSeed 双写;让异构源统一为结构化知识
合成层:5 段 Layered RAG × 800 字符预算 → LLM prompt 拼装;让 LLM 在每次种子生成时看到规范 / 源码 / 流量 / 漏洞 / 边缘五类互补信号
5 段 RAG 是「分类」与「组装」的桥梁:5 类 family 提供分类标签,9 类 source_layer 提供组装标签,5 段 RAG 把后者映射为 5 个独立 retriever。这种设计让 ProtoRAG 在 RTSP 上实测得到 4 states / 26 transitions / 26420 norms,在 TCP 上得到 11 states / 36 transitions,可直接用于 JointConstraint 协议无关联合校验。
闭环反馈源 (fuzz_history / log_file) 不进 KB 5 段,而是在 stage4 重抽规范时由 build_feedback_rag_context 独立处理;这避免了「运行时的脏数据污染 boot 阶段的干净 KB」。
