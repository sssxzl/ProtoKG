一、设计哲学
ProtoRAG 的设计由四条原则统领,这四条原则是后续所有具体决策的根源。它们彼此之间有时会冲突——例如「协议无关」和「启发式抽取」就存在张力,遇到冲突时,我们优先回到这四条原则做判断。
1.1 协议无关优先
加新协议时,理想情况下不改 Python 代码,只往 kb/ 里塞规范原文。这条原则的代价是大量工程纪律(见 §1.3)和数据建模成本(见 §9 双层抽取),但收益是「协议迁移性」——这正是 ProtoRAG 区别于 ChatAFL / AFLNet 的核心卖点。我们把这个卖点放在所有其他目标之上。
原则:如果一个协议特定知识可以放 KB,就不放代码。如果一定要放代码,必须有不可替代的理由(性能 / schema 验证 / 跨协议通用机制)。
1.2 工程纪律优先
协议模糊测试工具链的核心资产是 KB 原文和抽取结果——一旦损坏,所有实验失效。因此 ProtoRAG 把「写入原子性 / 备份 / CHANGELOG / schema 校验」当作一等公民,由 scripts/check_discipline.py 自动化检查,而不是靠 review 时人工发现。
这条原则有时会让代码变长(KBWriter 比直接 open 多 ~150 行),但避免了「跑 24h fuzzing 后发现 KB 损坏 → 全部数据作废」的灾难。在长期项目中,这个权衡我们认为是值得的。
1.3 零硬编码协议知识
当前代码库 的 protocols/rtsp.py / tcp.py / dns.py 三个 adapter 已 KB 化(2026-09-22 完成):方法白名单 / REQUIRED_HEADERS / state machine / canonical_header (~215 行硬编码) 全部移到 kb/spec/<proto>/expert_note/*.json。 protocols/<proto>.py 现在只剩 parse_<proto>_frames 字节解析器 (~80 行/协议, RFC 字节格式必然协议特化) + KB-backed ProtocolAdapter class 框架 (从 KB 加载)。 详: docs/refactor_kb_protocol_adapter.md.
每个 adapter 都是技术债——它的存在是为了填 KB 没覆盖的空白。当 KB 覆盖率够 90%+,adapter 应该被替换为「KBReader 动态读」。
1.4 不为兼容性妥协纪律
我们拒绝「为了兼容旧代码保留 KB 直接写头」「为了减少迁移成本允许 derived/ 直接覆盖 KB」之类的妥协。理由:工程纪律的本质是「防呆」,一旦开了例外,纪律就形同虚设。新代码遇到问题应该改纪律的执行者,不是绕过纪律。
KBWriter 默认 create-only,要覆盖必须显式 overwrite=True
check_discipline.py 不会加「白名单文件」豁免——docstring/注释会被 AST 跳过,真实违规必然被抓
derived/ 永远可重建——下次 prefill 重跑即可,不会被任何代码保护
二、核心设计决策
本节解释 ProtoRAG 三大顶层架构决策的「为什么」,具体实现在 §5 权衡里逐条展开。
2.1 为什么是 5 段 Layered RAG
经过对 5 类外部 KB 源(RFC / SOURCE / TRAFFIC / VULN / EDGE)的功能分析,我们决定把它们分成 5 段独立 RAG,而不是合并成 1 段统一 RAG。理由有三条:
per-source ablation 友好——做 ablation 实验时,可以单独去掉某一段看 LLM 表现
每段可以独立 retriever / 独立排序——RFC 走 BM25 词法,TRAFFIC 可能走结构化查询
prompt 拼装时可控——LLM 看到的是「RFC §X」还是「CVE-2021-1234」,边界明确
代价是 prompt 模板变复杂(5 段 × 2-3 个字段 = ~15 个 slot),但我们认为 prompt 模板的复杂度可以通过 §4.3 的模板集中管理解决。如果合并成 1 段 RAG, ablation 实验就做不了——这跟我们的研究目标冲突。
2.2 为什么是双层抽取(章节 + 段落)
章节级抽取(method / state machine transition)需要完整 prose 上下文,段落级抽取(field / outcome / constraint)只需要局部上下文。强行混在一起会出现两种问题:
「用段落级 prompt 抽 transition」→ LLM 看不到完整状态机,漏抽关闭/异常路径
「用章节级 prompt 抽 field」→ 单次 LLM 调用成本高 10-20 倍,但质量并不好
所以我们坚持两层,即使 重构才完整实现段落级。详见 §9 的完整推理过程。
2.3 为什么 KBWriter 是单一入口
kb/ 目录的内容是 ProtoRAG 全部实验的基础——任何错误写入都会污染所有后续实验。我们决定:任何写入 kb/ 必须走 core/kb_writer.py::KBWriter,不允许 open('kb/...', 'w') 直接写。理由:
原子性:写入中途崩溃不能损坏 KB(用临时文件 + os.replace)
备份:覆盖前自动 .bak.<ns-timestamp>-<uuid8>
CHANGELOG:每次写都留审计追踪(actor / input_hash / output_path)
schema 校验:write_json / write_jsonl 时机一致,而不是散落在调用方
lock:防多进程并发写,虽然单进程跑但 multi-experiment 仍可能撞车
代价:写 KB 多 ~150 行代码(atomic + backup + changelog + lock + schema 五件套)。但 KBWriter 是项目最重要的基础设施——少这 150 行,换来 5 次 KB 损坏事故,哪个更贵?
三、关键设计原则
本节列出 6 条贯穿全项目的具体原则,每条都有简短理由。这些原则之间可能冲突,冲突时回到 §1 的四条哲学判断。
3.1 协议级隔离(共享)
kb/spec/<proto>/ 和 kb/vuln/<proto>/ 跨实验共享,不按 task_id 隔离。理由:协议知识(RFC、CVE)是不变量,不会随实验变化。100 次实验共享同一份 RFC 解析结果,避免「100 份 RFC 副本」。
3.2 启发式 + LLM 兜底(不纯 LLM)
method 名抽取用 5+1 启发式规则(H1-H6, 阈值 ≥2 命中),state machine transition / field / outcome 用 LLM 抽取。理由:method 名是协议表层符号,正则匹配已经够用,LLM 在这个层级反而失真(method 名需要严格规范化)。transition / field / outcome 需要理解 prose,LLM 在这个层级远胜规则。
3.3 KB 是 immutable source of truth
KB 一旦写入,下游(derived/)任何缓存都不能反向修改 KB。任何「根据运行反馈回写 KB」的需求应该走专门通道(例如 runtime_additions.jsonl append-only),而不是直接改 norms.jsonl。
3.4 canonical hash 不受格式影响
同一份 JSON 数据,无论 pretty-print 还是 compact,canonical hash 必须一致。实现见 core/json_utils.py::canonical_hash(stream)。理由:CHANGELOG 的 input_hash 必须能跨编辑器/工具稳定,否则 diff 噪声爆炸。
3.5 模块独立可替换
BM25 → embedding 只改 Index 实现;DeepSeek → OpenAI 只改 LLMClient 实现;JSONL → SQLite 只改 ProtocolNormStore 实现。测试时用 StubLLMClient 替代真实 LLM,无需 API key。Protocol 抽象层(8 个)在 core/interfaces.py 定义。
3.6 测试用 Stub LLM,生产用 DeepSeek opt-in
Workflow 默认 StubLLMClient(返回空 list / 占位数据),--use-llm 才切到 DeepSeekClient。理由:测试不需要 API key;dry-run 跑端到端流程;用户没配 DEEPSEEK_API_KEY 也不会崩。切换是显式 opt-in,不隐式。

全文 <10KB(RTSP 实测 4.8KB / TCP 实测 7.2KB),直接塞 prompt 性能 OK
LLM 看到约束表能「理解」,不需要「检索」
代价:prompt 长度变长(token 成本略增,但收益更高);状态机变更需要重新生成 JSON(不是动态追加 norms)。

五、显式不做
好的设计有一半功劳来自「显式不做」。本节列出我们反复考虑过、最终决定不做的方案,以及决定不做的理由——这些理由可能在未来某天被推翻,所以留着记录。
5.1 不写协议 adapter
我们反复考虑过「为每个协议写 adapter」(protocols/rtsp.py 这种),最终决定 移到 KB 而非 RD 代码硬编码,理由:
adapter 是技术债——一旦写,所有人都往里加逻辑,最后变成「什么都能往里塞」
迁移新协议要重写 adapter,违反 §1.1
测试时需要 mock adapter,降低测试保真度
代价:协议特定启发式(章节号映射、method 名规范化)需要改放 KB 或改放通用启发式。重构后,标题启发式 fallback 替代章节号映射——代价是首次抽取可能多花 1 次 LLM 调用。
5.2 KB 不能 append-only
考虑过:KBWriter 走 append-only,所有写都是 append,旧数据不删。决定不做,理由:
append-only 会让 norms.jsonl 越长越大,检索变慢
错误数据无法回滚——只能加「修正记录」,污染 KB
不符合工程直觉——实验做错了应该能改,不是只能加备注
我们用另一套方案解决「修改追踪」:CHANGELOG.jsonl 记录所有写操作(actor / input_hash / output_path),历史状态由 .bak.<ns-timestamp>-<uuid8> 保留。备份是 append 的「真·append-only」载体,但 KB 本身不是。
5.3 不用 embedding
理由见 §4.1。补充一条:如果某个 reviewer 说「你们的 RAG 没用 embedding,太老」,我们会说「协议术语是结构化符号,BM25 比 embedding 更准,而且论文不需要第三方服务依赖」。
5.4 不做多协议联合检索
考虑过:一次检索可以跨多个协议(rtsp + rtp 同时命中)。决定不做,理由:cross-protocol 误检率高(很多协议 method 名相似,但语义不同),而且实验设计上需要单协议 ablation。
代价:用户必须显式指定 protocol。这反而是好事——强制用户思考「我跑哪个协议」。
5.5 不做运行时自演化
考虑过:fuzzing 过程中根据 coverage 自演化 KB(添加新 norm)。决定不做(至少 不做),理由:
自演化会让「同一个 KB 不同实验跑出不同结果」——不可复现
需要复杂的反馈环路,工程成本极高
研究目标目前不需要——ablation 是单轮实验,不需要自演化
未来可考虑:runtime_additions.jsonl append-only,记录 fuzzing 中发现的新 transition,但不下次实验重放。这超出 范围。
5.6 不引入 pytest plugin 体系
考虑过:写一个 pytest-protorag plugin,提供 fixture / marker / parametrize 自动生成。决定不做,理由:项目只有 500 个测试,直接写 fixture 比学 plugin 体系快;新人接手 plugin 体系需要额外学习成本。
代价:conftest.py 可能膨胀,但目前 ~120 行,还 OK。
六、工程纪律决策
工程纪律是 ProtoRAG 的「隐性创新点」——论文不一定会大篇幅讲,但它是 24h fuzzing 实验能跑完、KB 不会突然损坏的根因。本节讲三大基础设施的设计推理。
6.1 KBWriter vs 直接 open("kb/...")
考虑过:让所有调用方直接 open("kb/..."),KBWriter 是多余的抽象层。决定不做,理由见 §2.3。补充一点:KBWriter 把 schema 校验上移到 write_json / write_jsonl 方法,而不是散落在每个调用方——这意味着「调用方忘了校验 schema」这种 bug 不存在。
验证:scripts/check_discipline.py 规则 1 自动拦截 open("kb/...", 'w'),违规时 pytest 失败。我们故意不收紧 pattern——只抓真实代码 token,docstring/注释自动跳过。
6.2 atomic_io vs 简单 write
考虑过:derived/ 用最朴素的 open(path, 'w'),坏了就重跑 prefill。决定不做完全朴素方案,理由:
简单 write 写入中途崩溃会留下半截文件,下次启动会误读
atomic_io 的成本极低(os.replace 跨平台 ~10 行代码),不值得省
具体实现:用临时文件 + os.replace(target, tmp)。Path.rename() 在 Windows 上不覆盖——所以必须用 os.replace。with open() 块内调用 fsync,句柄还活着——这是手册不强调的细节,踩过坑才知道。
6.3 canonical hash vs 普通 hash
考虑过:用 hashlib.sha256(json.dumps(data).encode()).hexdigest() 简单方案。决定不用,理由:
JSON pretty/compact 不同格式 → hash 不同 → CHANGELOG 噪声爆炸
dict 顺序非确定(Python 3.7+ 保证插入序,但跨进程仍可能不一致)
streaming SHA-256 对大文件(<10MB norms.jsonl)性能 OK
实现见 core/json_utils.py::canonical_hash(stream):sorted keys + compact + ensure_ascii=False + 显式 utf-8 编码。测试 test_canonical_hash.py 验证「同内容不同格式 hash 一致」。
七、跨协议可复用性
ProtoRAG 的核心卖点是「加新协议只改 KB 不改代码」。本节解释这个卖点是怎么落地的,以及它的真实成本。
7.1 为什么是 KB 而不是 adapter
传统做法:为每个协议写 adapter(protocols/<proto>.py),内含 method 白名单、章节号映射。我们的做法:把同样的信息塞进 KB,norms.jsonl 里有 method 名,state_machine.json 里有 transitions。运行时通过 KBReader 动态读。
理由:KB 是声明式数据(人类可读、可 git diff、可手工编辑),adapter 是命令式代码(需要写、需要测、需要 review)。迁移新协议时,前者成本是「更新一份 JSONL」,后者成本是「写 + 测 + review 一个新 .py」。

八、双层抽取的推理
双层抽取(章节锚点 + 段落细粒度)是 ProtoRAG 的核心方法论创新。本节完整推导为什么需要两层,以及两层之间如何连接。
8.1 为什么章节级不够
章节级抽取把 RFC §X 当作原子单位,LLM 一次性抽 method / field / outcome / constraint。问题:
章节 body 长达 12KB,LLM 容易「看完就忘」——field 名常常拼错
段落级语义(field 在哪一段出现)在章节级完全丢失
不同段落 field 之间的「关系」(如「Content-Length 必须在 Content-Type 之后」)无法表达
8.2 为什么段落级也不够
段落级抽取把每个段落当原子单位,LLM 抽当前段落的 field。问题:
state machine transition 需要「全局上下文」(关闭路径 + 异常路径)
method 名需要「跨段聚合」(method 定义可能在 5 个段落散布)
单段落 LLM 不知道全局 method 列表,容易重复命名
8.3 双层如何连接
连接方式:
章节层:抽 method 名 + state_machine.transitions(需要全局上下文)
段落层:抽 field / outcome / constraint(局部上下文)
段落层每个 norm 带 section_ref 字段,指向所属章节(method 锚点)
method 名跨段怎么解决:method 名规范化由章节层一次性完成,段落层 LLM 在 prompt 里看到「已知 method 列表」,直接引用
具体实现见 core/paragraph_splitter.py + core/paragraph_extractor.py(重构后落地)。method 锚点示例:
{  "norm_id": "norm:rtsp:field:content_length:7.2.1",  "kind": "field",  "method": "SETUP",  "field_name": "Content-Length",  "section_ref": "7.2.1",     # ← 锚点, 防止 norm 索引断链  "constraint": "required if Transport header present"}
九、闭源协议考虑
RFC 协议有规范的章节号(1. / 1.1 / A. / Appendix B),抽取相对容易。但闭源协议(私有协议、SDK 文档、RFC 衍生规范)往往章节号不规范、标题层级混乱、表格稀疏。本节讲 ProtoRAG 对闭源协议的应对策略。
9.1 章节号不规范
现象:闭源协议常用「§1 Message Format」这种标题,但没有 1.1 / 1.2 子层级。应对:corpus.py 的 _SECTION_RE 同时支持 [1. / 1.1.2 / A. / A.1 / Appendix A.1] 五种模式,并在 RfcSectionParser 解析失败时回退到 GenericSectionParser。
进一步问题:某些闭源协议完全没章节号,只有「一坨 prose + 几张表」。应对:的 title 启发式 fallback(按标题长度 + 关键词「Message / Format / State」切段),再不行就整篇作为 1 个「超级段落」让 LLM 自己分。
9.2 method 名不规范
现象:闭源协议 method 名可能是「login / LOGIN / LoginUser / login_user」四种风格混合。应对:启发式抽取后接规范化步骤(全大写 + 统一分隔符),重构后规范化规则放 KB(method_canon_rules.jsonl),不放代码。
9.3 缺 state machine
现象:某些闭源协议没有 RFC 那种 Appendix A 状态机。应对:LLM 兜底——给 LLM 看全篇 prose,让它自己推断状态机,再用 fuzzing 实测覆盖率验证。
代价:LLM 推断的状态机覆盖率低,实测时需要补 norm。这个补的过程可以半自动——LLM 提候选,人审核。
十、不确定项与待重新评估的设计
诚实记录本设计中「我(们)还不确定」的部分。这些决策可能在 24h fuzzing 实验后被推翻,所以提前标出来。
10.1 段落级抽取的成本
段落级 LLM 抽取的调用次数估算:RFC 2326(RTSP) ~80 个段落 → 80 次 LLM 调用。DeepSeek 单价约 ¥0.001/1K tokens,80 次调用如果每次 ~3K tokens(输入+输出)= ¥0.24。看起来不贵,但如果加上重试 / 错误恢复 / multi-section,实际可能是 3-5 倍。
未实测,24h fuzzing 后再验证。如果成本爆炸,可能改成「批量段落抽取」(一次 prompt 装 10 段,LLM 返回 10 个 result)。
10.2 path_enumerator max_paths=50 是否合理
BFS 状态机路径枚举默认 max_paths=50。这个数字是经验值——TCP 状态机 11 states / 36 transitions,如果全展开可能是几百条路径,50 是个折中(覆盖核心 + 不爆)。
未实测不同 max_paths 对最终种子质量的影响。24h fuzzing 后可能改成 100 或自适应。
10.3 启发式 method 抽取阈值 ≥2 是否合理
5+1 启发式(H1 关键字「method」/ H2 关键字「command」/ ... H6 大写动词)的阈值是 ≥2 命中。这个阈值在 RTSP 实测 11 个 method 全部命中,但 TCP(连接状态机的「SYN/SYN-ACK/ACK」)可能只命中 1 个就被错误过滤。
需要 24h fuzzing 后看 TCP 实验是否漏 method。如果漏,把阈值改成 ≥1 + LLM 复核。
10.4 LLM 抽取的缓存命中率
LLM 抽取按 run_id 分目录(derived/<proto>/llm_extracts/run_<ts>_<prompt_hash>/)。同 prompt 重复调用应该 100% 命中缓存——前提是 prompt hash 算法稳定。
未实测:如果 hash 算法有微小变化(例如 prompt 模板里加了一个空格),缓存命中率可能崩到 0%。解决:canonical prompt hash(类似 canonical JSON hash),具体见 core/json_utils.py。
十一、自我辩论
本节诚实记录「当时考虑不周」「备选方案没考虑」「可能错了」的决策。写在论文前不丢人——比发表后被 reviewer 抓出来好。
11.1 可能错了的决策
决策 1:KBWriter 抽象层是不是 over-engineering?
反方观点:500 行测试的项目,KBWriter 一个文件 150 行,值得吗?我们的回应:如果项目只跑 1 个实验、不需要复用,KBWriter 是 over-engineering。但 ProtoRAG 是研究项目,会跑 10+ 个 ablation × 3 协议 = 30+ 次实验,KBWriter 防呆价值远超 150 行成本。
如果 reviewer 质疑,我们会说「24h fuzzing 跑完 KB 没坏——这就是工程纪律」。ChAtomFL 类似的工具没有这套,跑 24h 后 KB 损坏重跑的案例我们见过。
决策 2:协议无关真的是「必要」吗?
反方观点:论文只需要 RTSP/TCP 实验,协议无关性是 nice-to-have,不是 must-have。我们的回应:论文核心贡献之一就是「协议无关」——没有这个,论文差异性减弱。工程成本 19-21 天,论文差异性 = 顶会 vs 二区,值得。
如果 reviewer 说「你们只是说协议无关,但还是测了 3 个,扩展性没证明」,我们的反驳:迁移 DNS 已经规划中,只要 KB 准备好不需要改 Python 代码。
决策 3:BM25 vs Embedding 真选对了吗?
反方观点:2026 年的 RAG 还用 BM25,out 了。我们的回应:协议术语是结构化符号,BM25 词法匹配天然合适。我们的 ablation 实验(knowledge_source 4 条件)会包含 BM25 vs Embedding 对比,用数据说话。
11.2 当时没考虑周全的备选方案
备选 1:RFC 解析用 docling / unstructured 而不是 regex
我们用的是 regex 章节切分(corpus.py::_SECTION_RE)。当时没考虑用 docling 这种 PDF/HTML 解析库——理由是 RFC 文本格式固定(纯 ASCII + 章节号规范),regex 足够。
但如果未来要处理 RFC 衍生(I-D, Internet Draft)或 闭源规范的 PDF/HTML,regex 就不够了。需要扩展点:corpus.py 已经是 Protocol 抽象,可以加 PdfSectionParser / HtmlSectionParser。
备选 2:norms.jsonl 不 append-only 但备份频率不够
KBWriter 现在每次写 1 个 .bak。<NS-timestamp>-<uuid8>。如果高频实验(每小时 1 次写)会生成几百个备份。没考虑过:备份自动 prune(只保留最近 10 个)。
未来加:KBWriter 增加 max_backups 参数,默认 10,超出时按 mtime 删旧。
备选 3:JointConstraint 校验时机太晚
现在 JointConstraint 在 path → seed 生成后校验。没考虑过:在 path_enumerator 阶段就校验(避免生成「已知违反约束」的路径)。
未来优化:path_enumerator 阶段注入 constraint filter,可能减少 LLM 调用 20-30%。
