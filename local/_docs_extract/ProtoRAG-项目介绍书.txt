ProtoRAG
Protocol-Aware Fuzzing with Retrieval-Augmented Generation
基于检索增强的协议模糊测试种子生成器
文档版本: v3 · 2026-09-22
本文档按当前项目实际情况重写, 不编造数字, 不把设计写成已实现.
一、项目定位
ProtoRAG 是一个面向协议模糊测试 (protocol fuzzing) 的种子生成器, 通过检索增强生成 (RAG) 把协议规范 (RFC) / 历史漏洞 / 真实流量 / 专家注释等异构知识库源转化为 AFLNet 可消费的初始种子, 让模糊测试从"碰运气"变成"按状态机走".
1.1 项目核心特征
协议无关 (Protocol-Agnostic): 加新协议不需要写 adapter, 章节号映射表, 或启发式规则, 只需提供 KB 原文.
零硬编码协议知识 (Zero Protocol-Specific Knowledge): 不维护 protocols/<proto>.py 这种手写 method 白名单, 全部从 KB 动态读取.
检索增强 (RAG-First): 5 段异构 Layered RAG, 每段独立 retriever, 支持 per-source ablation.
工程纪律 (Engineering Discipline): KBWriter / atomic_io / canonical_hash 三件套, scripts/check_discipline.py 自动化检查.

二、架构总览
ProtoRAG 的核心架构是 5 段 Layered RAG + 状态机引导的种子生成.RAG 负责把异构 KB 源拼装成 LLM-friendly context, 种子生成负责在状态机图上枚举合法路径, JointConstraint 负责校验生成的报文符合协议规范.
2.1 数据流总览
kb/spec/<proto>/rfc*.txt          ← 原料 (只读)        │        ↓ split_sections() 按章节切 (RFC 标准章节号)        │sections [{number, title, body, kind}, ...]        │        ↓ split_paragraphs() 章节内段落切分         │paragraphs [{section_ref, para_idx, body, method_context}, ...]        │        ↓ 双层抽取        ├─ 章节级: method 列表 (LLM 抽章节标题) + state_machine.transitions (LLM 抽章节 body)        └─ 段落级: field / outcome / constraint (LLM 抽每段, section_ref 做 method 锚点)        │        ↓ norms.jsonl (进 KB, KBWriter.write_jsonl)        │rag_context.build_layered_rag_context(sm, method, state)        │  5 段拼装 [RFC | SOURCE | TRAFFIC | VULN | EDGE]        ↓path_enumerator.enumerate_state_paths(sm, max_depth=4, max_paths=50)        │  BFS 在状态机图上枚举合法路径        ↓path_builder.build(path, sm, llm_client)        │  LLM 填充每条 transition 的具体 message        ↓.raw 种子 → seeds/<proto>/seedgen/<batch>/        │        ↓ChatAFL / AFLNet fuzzing

三、核心创新点
ProtoRAG 围绕"协议无关"和"工程纪律"两条主线, 形成 4 个核心创新点.前 3 个是学术贡献 (适合论文), 第 4 个是工程贡献 (适合工具论文).
3.1 协议感知 RAG 架构 (Protocol-Aware RAG)
ProtoRAG 用 5 段异构 Layered RAG 把协议知识喂给 LLM, 每段独立 retriever, 支持 per-source ablation. 相比 ChatAFL (无 RAG, 知识隐式在 LLM 权重里), ProtoRAG 把知识显式化, 可追溯, 可切片.
5 段: [RFC | SOURCE | TRAFFIC | VULN | EDGE]
7 档决策 (A1/A2/B1/B2/B3/C/D), 28 条分类规则 (16 支持 + 12 排斥)
per-source ablation 已实测 (knowledge_source 4 条件)
vs ChatAFL: 无 RAG, 不可按源切片
vs 现有 RAG-fuzzing: 一般 1-2 源, ProtoRAG 5 源异构
3.2 双层知识抽取 (Section Anchor + Paragraph Granularity)
章节做锚点 + 段落做细粒度. 章节级保留 method 名和 state_machine transition (需要完整 prose), 段落级抽取 field / outcome / constraint (每段独立). section_ref 给段落提供 method 上下文锚点, 解决 method 名跨段关联问题.
章节级: 5+1 启发式 method 抽取 (H1-H6, 阈值 ≥2 命中)
章节级: state_machine.transitions LLM 抽取 (章节 body ≤12KB)
段落级: 每段 LLM 抽 field / outcome / constraint
段落级: section_ref 做 method 锚点, 防止 norm 索引断链
vs ChatAFL grammar 派生: 经常产生非法序列, 服务端直接 400/454
vs AFLNet response replay: 不能探索未观察到的合法路径
3.3 协议无关 + 零硬编码 (设计目标, 重构后落地)
加新协议不需要写 protocols/<proto>.py adapter, 不需要章节号映射表, 不需要启发式正则. 所有协议特定逻辑通过 KB 原文 + LLM 抽取自动获得. JointConstraint 的 method 白名单从 KB 动态读取, 完全协议无关.
重构: 删 protocols/<proto>.py adapter, JointConstraint 从 KBReader 读 method 白名单
重构: 章节分类不再依赖硬编码 _classify_section, 改走 title 启发式 fallback
重构: 段落级 LLM 抽取, 不依赖任何协议特定规则
当前代码状态: 当前仍有 protocols/rtsp.py / tcp.py / dns.py (过渡期)
3.4 工程纪律基础设施 (Engineering Discipline)
KBWriter / atomic_io / canonical_hash 三件套, 保证 KB 内容不被破坏, 中间产物可重建, scripts/check_discipline.py 自动化检查.适合工具论文 §5 "Implementation & Engineering" 章节.
KBWriter: create-only 默认, 覆盖需显式 overwrite=True, atomic + 备份 + CHANGELOG + lock
atomic_io: os.replace 跨平台, with-open 内 fsync, 通用 derived/seeds 写入
canonical_hash: streaming SHA-256, 同内容不同格式 hash 一致
check_discipline.py: 2 条规则自动检查 (open("kb/") / KBWriter 越界 derived)
vs 现有 fuzzer 工具: 大多靠目录约定, 无 schema 校验, 无原子写入保证
四、5 类源处理方法
外部 KB 划分为 5 类 source_family, 每类承担互补的语义角色. 内容驱动分类器 (format probe + 内容打分 + 7 档决策) 自动识别每份 KB 文件的归属, 不依赖路径或扩展名.

4.1 内容驱动分类 (Content-Driven Classification)
format_type: 9 种 (pcap / jsonl / csv / markdown / pdf / html / json / txt / binary)
支持证据权重: 强 3.0 / 中 2.0 / 弱 1.0
排斥证据权重: 强 -2.5 / 中 -1.5 / 弱 -0.5 (严格小于支持权重)
