## 二、根因分析
### 2.1 表面数据
- 覆盖率几乎持平 (3.65% vs 3.63%)，说明双方最终探索广度接近；
- 但 ProtoRAG 执行量 +27%、周期数 +100%，说明它在"更忙"；
- 稳定度 -70.1%，说明反馈质量差。
### 2.2 核心问题
**ProtoRAG 生成的种子字段值过于标准化，导致 bit-flip 变异后语义大量丢失。**
具体现象：
ProtoRAG 种子:PING Id=1 Token=ping-token-abc123 Seq=1 Timestamp=1700000000
ChatAFL 原始种子:DESCRIBE rtsp://127.0.0.1:8554/test RTSP/1.0CSeq: 1User-Agent: LibVLC/3.0.18 (LIVE555 Streaming Media v2016.11.28)Accept: application/sdp
AFLNet bit-flip 变异对比：
| 变异对象 | ProtoRAG 种子 | ChatAFL 种子 |
|---|---|---|
| 改 Token 一个 bit | server 校验失败 → 拒绝 → 状态转移丢失 | — |
| 改 User-Agent 一个 bit | — | server 不校验 → 接受 → 状态转移保留 |
| 结果 | 大部分变异无效 | 部分变异有效 |
**稳定度指标 10.57% vs 3.16% 直接佐证这一判断。**
### 2.3 深层根因
**RFC 中定义的字段约束信息没有进入 RAG，LLM 无法区分字段的"可行值域"。**
RFC 2326 里每个字段都有明确约束，例如：
- `Content-Length`: MUST be the size of the body in bytes (数值)
- `CSeq`: MUST be incremented for each request (递增)
- `Session`: assigned by server in SETUP response (引用)
- `User-Agent`: 真实客户端各不相同 (枚举)
但当前 RAG 拼装的 [5. 协议约束] 段只列了"哪些字段必填"，没有列出"字段能取什么值"。

## 三、改进方案
### 3.1 核心思想
**将"字段约束"作为一等公民，从 KB 抽取、存储、渲染到 prompt，全程保原格式，让 LLM 生成具有约束多样性且 bit-flip 后语义稳定的种子。**
### 3.2 关键设计原则
1. **不预设约束类型**：不强行将约束分为 range/enum/pattern 等固定几类；
2. **保原格式**：`0-1000` 就是 `0-1000`，`张三、李四` 就是 `张三、李四`；
3. **不转义、不 lowercase、不类型转换**；
4. **JSON 存储用 `ensure_ascii=False`**；
5. **约束原文本 + 出处**：让 LLM 自己理解约束语义。

3.7 Prompt 引导
在 path_prompts.py 中新增生成要求:
text
[生成要求 - 字段]1. 对每个 header，先查 [5. 协议约束] 里的"字段约束":   - 有约束 → 按约束填   - 无约束 → 不填（不要凭想象加字段）2. 按约束填值:   - 数值范围 → 从区间内选   - 枚举列表 → 随机选一个   - 引用类型 → 用占位符 (如 {{session_id}})   - 固定值 → 精确填3. 不同种子的弱校验字段用不同值:   - 种子 A 用 User-Agent: LibVLC/3.0.18   - 种子 B 用 User-Agent: Lavf58.76.100   - 不要 N 个种子都用同一个 User-Agent4. 不要在 [字段约束] 未列出的 header 上填值,   避免引入 bit-flip 攻击面。

六、转义与数据完整性
为满足"不因转义问题导致信息出错"的要求,本方案执行以下规则:
JSON 写入: ensure_ascii=False (中文原样存储);
不 lowercase / trim: 保留原字段名和值的大小写与空格;
不类型转换: "0-1000" 保持字符串,不拆成 min/max 数值;
不 split 原文本: "张三、李四、王五" 保持一个字符串;
读取时: 直接 json.loads,不解码、不归一化;
渲染时: 直接把 constraint_raw 拼进 prompt,不做任何处理。
