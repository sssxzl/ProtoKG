## 一、根因分类（实测，非推测）

排查后确认**存在两类性质完全不同的编码问题**，必须区别对待：

| 类别 | 机制 | 是否本项目缺陷 | 处置 |
|---|---|---|---|
| **① 可逆 mojibake** | 文件以 **latin-1/cp1252 读入**、再以 **UTF-8 写出** ⇒ 字节层面被"双重编码" | **是**（拷贝 kb/ 第三方源码时弄坏的） | **还原**成上游原样 |
| **② 上游原生混合编码** | kamailio 是 2000 年代老代码库，源码/测试/文档本就是 **latin-1** | **否**（上游本来如此） | **登记豁免、只报告不改** |

### ① 的证据链

```
git 首次入库（c9295b4）就已损坏 ⇒ 不是本轮引入
  文件：kb/sip/协议实现源码/kamailio/src/modules/presence_profile/README
  字节：Mih \xc3\x83\xc2\xa1 ly      ← \xc3\x83 = UTF-8 的 U+00C3(Ã)，\xc2\xa1 = UTF-8 的 U+0081
  还原：Mih \xc3\xa1 ly             ← U+00C3 的 UTF-8 首字节 ⇒
        "Mihály Mészáros"（匈牙利人名，kamailio 作者）✓ 语义完全合理
```

⇒ **缺失的编码声明不是元凶**（第三方文件本来就没声明）。真正的元凶是
**「读时用错字符集 + 写时用对字符集」的往返**。

⚠ 受损文件经历过**两轮**往返（`Ã„` = U+00C3 + U+201E），单轮还原不彻底
⇒ 修复器必须**迭代到收敛**。

⚠ 往返字符集是 **cp1252 而非 latin-1**：latin-1 无法编码 U+201E(`„`) / U+20AC(`€`)
⇒ 纯 latin-1 还原会漏掉 `Ägypten` 这类词 ⇒ 必须 cp1252 优先、latin-1 兜底。

- 还原后全仓 mojibake 标记：**846 → 0**

### 2.2 统一行尾（54 个文件）

- 根因：跨平台换行不一致 —— Windows 上 `Path.write_text()` 写出的文件是 **CRLF**，
  而 git 仓库内统一是 **LF** ⇒ 工作区出现"纯 CRLF / 纯 LF / 混合"三态
- 混合行尾 1 个：`local/decisions_pending.md`（CRLF 143 / 裸 LF 206）
  ⇒ 成因是我此前用 Python 脚本改它时插入了 LF 行
- 处置：全部文本文件统一为 **LF**（与仓库一致）⇒ 混合行尾归零、Edit 工具可稳定匹配
- ⚠ **`.raw` 种子文件不在范围内** —— RTSP/SIP 协议语义要求 CRLF，保持不变

### 2.3 补齐缺失的 `encoding`（18 处）

- 根因：`open()` / `read_text()` / `write_text()` 未显式指定编码
  ⇒ 在 Windows 上默认走 **locale 编码 cp936** ⇒ 换台机器（CI / Linux）就炸
- 当前环境恰好是 UTF-8（`PYTHONUTF8=1`）⇒ 隐患**未暴露**，属"环境保证"而非"代码保证"
- 分布：`local/` 16 处（一次性脚本）、`tests/` 2 处
- **`core/` `scripts/` `tools/` 原本就是 0 处** ⇒ 生产链路本来就干净
