### 0-A.3 ★ 主理人提出的「坑 1」：结论需要修正 —— **不是并发竞态，是确定性源码 Bug**

主理人报告的报错：

```
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\app\Anaconda3\Lib\site-packages\docx\__init__.py'>'
```

主理人判断为「文件正被工程师改写 → 读到半成品 → 并发竞态」。

**QA 复验结论：该判断不成立。这是确定性缺陷，与并发无关。**

根因：`local/rq1_2_fill_docx.py` 的函数**形参名就叫 `docx`**，而函数体内又有 `import docx` → **`import` 语句把局部名 `docx` 绑定到模块对象**，形参被遮蔽 → `str(docx)` 实际是 `str(<module 'docx' ...>)` → python-docx 把它当文件路径去开 → 报出上面那个"文件名是模块 repr"的诡异错误。

**决定性证据**（QA 最小复现，同一段代码连跑 5 次）：

```python
def _read_body_tables(docx):        # ← 形参名 = docx
    try:
        import docx                 # ← 局部名 docx = 模块，遮蔽形参
    except ImportError as e:
        raise RuntimeError(...)
    d = docx.Document(str(docx))     # ← str(docx) 实为 str(模块)
```

```
$ for i in 1 2 3 4 5; do python repro2.py; done
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\\app\\Anaconda3\\Lib\\site-packages\\docx\\__init__.py'>'
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\\app\\Anaconda3\\Lib\\site-packages\\docx\\__init__.py'>'
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\\app\\Anaconda3\\Lib\\site-packages\\docx\\__init__.py'>'
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\\app\\Anaconda3\\Lib\\site-packages\\docx\\__init__.py'>'
PackageNotFoundError: Package not found at '<module 'docx' from 'E:\\app\\Anaconda3\\Lib\\site-packages\\docx\\__init__.py'>'
```

**5/5 完全相同、零抖动** → 确定性缺陷。**"重跑一次就正常"的原因是 QA 在 22:35 已把形参改名修掉了**（`docx_path` + `import docx as docx_mod`），主理人第二次跑到的已是修复后的代码 —— 看起来像"竞态自愈"，实则是**被修好了**。

> ★ **若不修，这个错会 100% 复现**（不是偶发），且错误信息极具误导性（把"我的代码有 bug"伪装成"环境有竞态"）。
> **修法**（已在 QA 侧落地）：形参改名 `docx_path`，`import docx as docx_mod`。

if [ "$DRY_RUN" != "1" ]; then
  case "$FUZZER" in
    chatafl|aflnet) ;;
    *) echo "!! 未知 fuzzer: $FUZZER（可选：chatafl | aflnet）" >&2; exit 2 ;;
  esac
  if ! docker image inspect "$IMG" >/dev/null 2>&1; then
    echo "!! 镜像不存在: $IMG" >&2; exit 2
  fi
  # 进容器内探测 fuzzer 二进制（镜像内路径）；只探一次，结果缓存

    if docker run --rm --network none --entrypoint test "$IMG" -x "${FUZZER_BIN[$FUZZER]}" >/dev/null 2>&1; then
      _FUZZER_OK=1
    else
      echo "!! 镜像内未找到 fuzzer: ${FUZZER_BIN[$FUZZER]}（$IMG）" >&2; exit 2

  fi

**建议修法**（技术方案 §5.2.2 已给出可直接编码的算法）

```python
def resolve_root_seeds(entry_id: int, orig_map: dict, src_map: dict) -> set:
    """沿 src: 链上溯，返回可达的根种子文件名集合（splice 可能有多父）。"""
    seen, stack, out = set(), [entry_id], set()
    while stack:
        x = stack.pop()
        if x in seen:            # 防环
            continue
        seen.add(x)
        if x in orig_map:
            out.add(orig_map[x]); continue
        for parent in src_map.get(x, []):   # splice 的两个父都要走
            stack.append(parent)
    return out
```

配套：`orig_map` / `src_map` 需由队列条目名批量构建；`kind` 判定应按 §5.3.1 改为**命名形式**（`orig:` = 初始 / `src:` = 派生），MD5 降为交叉校验；多父口径按「任一根属 ③ 层即计入」并报告 `multi_parent_ratio`。

> ★ **注意**：`MHR_A`（主口径）**不受本问题影响** —— 它只依赖内容判定，QA 已实测在真实崩溃上命中 14 次，**Wave 1 的表 18 主列可用**。受影响的是附录 R3-1 的口径 B/C 与 `unattributed_ratio`。

### Q-4 ★★ P1 · 源码 Bug · 归属：工程师

> **崩溃样本的线格式未做自适应 → 帧格式样本的模式判定会漏判。**

**问题描述**
技术方案 §M4 / §5.3.0 明确：`/out/queue/*` 与种子文件是纯文本 `\r\n\r\n`，但 **`/out/replayable-crashes/*` 是 4 字节长度前缀帧**；且 AFL 变异会破坏字段名（`SETUP`→`SETUdioTerack1`、`Transport`→`Trans\x7fort`）→ 判定必须**格式自适应 + 去噪 + 宽松匹配**，§5.3.2 原文写道"实测严格规则在真实崩溃上命中 0 → 宽松是必需的，不是可选优化"。

当前 `scripts/rq3_mhr_patterns.py`：

```python
def split_messages(content: bytes) -> list[bytes]:
    """按 RTSP 消息边界切分内容（\r\n\r\n）"""   # ← 无帧格式探测
```

**复现命令**（VM 侧，`qa_vm_mhr_diag.py`）

**期望输出**：崩溃样本应被识别为帧格式并按帧切分
**实际输出**

```
id:000000,sig:06,src:001325,op:havoc,rep:128
   size=15441  frame_exact=False frames=0 consumed=1195 crlf_msgs=69
   head=b'\x9d\x00\x00\x00TEAR'
id:000004,sig:06,src:001325,op:havoc,rep:2
   size=2118  frame_exact=True frames=11 consumed=2118 crlf_msgs=11
```

→ 7 个真实崩溃中 **6 个的帧解析不能精确消费文件**（只有 `id:000004` 是纯帧格式），说明**这些样本是"帧头 + 文本"混合**（首字节 `\x9d\x00\x00\x00` 即残留的长度前缀）。
后果：CRLF 切分后首条消息的请求行变成 `b'\x9d\x00\x00\x00TEARDOWN rtsp://127.0.0.1\xd5\xd5…'` —— **方法名前带 4 字节长度前缀**，严格的 `line.startswith(b"SETUP")` 判定会漏。

**实测漏判证据**：设计规格对照实现（自适应切分 + 去噪 + 宽松匹配）在 7 个样本上只命中 7 次，而当前实现命中 14 次 —— 差异说明**两者判定路径不同**，且当前实现的"P1 命中"来自 CRLF 切分后的宽松 track 匹配（靠 `/track(\d+)` 正则搜 URI，不依赖请求行前缀），因此**恰好**没漏；但这是**偶然正确**，不是设计正确 —— 一旦 AFL 变异破坏 `/track` 的斜杠形式（§5.3.2 明确点名 `SETUdioTerack1` 这类变异），当前实现的严格正则 `/track(\d+)` 就会漏判。

**建议修法**

1. 按 §5.3.0 实现自适应切分（长度前缀帧精确消费 → 否则回退 CRLF）；
2. 按 §5.3.2 把 P1 的正则从 `/track(\d+)` 放宽为 `track\s*(\d+)`，并做去噪（剔除控制字符与 `0xff`）；
3. P2 用 `extract_session_candidates()` 返回的**候选集合**（`['000022B8','107518505','7477886380351771441']`）而非硬编码单值。
