# 五源知识抽取 → 结构化知识中枢 → 种子生成 全链路代码审查

> 审查日期：2026-10-21
> 审查范围：`core/fused/`（五源抽取器 + 知识中枢模型）、`core/fused/downstream/`（组装 + 种子生成）、`core/models.py`、`core/raw_writers.py`、`core/paths.py`、`scripts/build_hub.py`、`scripts/seedgen.py`
> 审查维度：数据格式、字段映射、接口约定、状态流转、边界处理

---

## 结论摘要

整体架构清晰（五源抽取器 → dataclass Fact → `get_fact_view` 序列化 → `load_fact_views` 读回 → `assemble_bundle` 分桶 → 三层种子生成），**协议×源二维解耦的主干已基本打通**，全量 229 测试通过。但存在 **1 个实际影响字段级实例失效的 bug**、**5 个换协议时会暴露的接口/协议耦合问题**，以及若干脆弱设计与死代码。

---

## 一、高严重（实际影响，建议立即修复）

### 问题 1：`message_instance` 状态名未归一化，字段级实例全链路失效 ⭐

- **涉及文件**：
  - `core/fused/downstream/rag_seedgen.py` — `assemble_bundle()` 的 `relation` 分支（`aspect == "message_instance"`）
  - `core/fused/source_autoseeder.py` — `map_to_facts()`（产出 SST 字段级实例）
  - `core/fused/downstream/edge_cover.py` — `build_seed_from_edges()`
- **矛盾表现**：
  `assemble_bundle` 对 `transitions` 的 src/dst 做了 `_normalize_state`（`INIT→Init`、`READY→Ready`），但对 `message_instances` 的 key 用的是**未归一化**的原始状态名。实测数据：

  ```
  transitions 里：('Init', 'SETUP', 'Ready')    # 归一化后
  message_instances 里：('INIT', 'SETUP', 'READY')  # 未归一化
  ```

  而 `edge_cover.build_seed_from_edges` 用 `message_instances.get((_src, method, dst))`，其中 `_src/dst` 来自归一化后的 edges（`Init/Ready`）。**key 大小写不一致 → 永远查不到**。
- **实际后果**：AutoSeeder 精心设计的「字段级实例」（LLM 现场生成的合法字段模板）在 edge_cover / generic_danger 里**完全失效**，种子只能回退到「必填头 + 取值池默认值」，丢掉了 AutoSeeder 的核心卖点。
- **修复方向**：在 `assemble_bundle` 的 `message_instance` 分支里，对 src/dst 同样调 `_normalize_state`（与 `transitions` 分支一致），或统一把归一化提前到 `relation` 分支入口处做一次。

## 二、中严重（换协议时暴露，建议近期修复）

### 问题 2：`strategy.classify_vuln` 漏传 `protocol`，触发流提取退化为 RTSP 硬编码

- **涉及文件**：`core/fused/downstream/strategy.py`（`classify_vuln`）、`core/fused/vuln_pattern.py`（`extract_stream_hints(text, protocol="rtsp")`）
- **矛盾表现**：`vuln_pattern.extract_stream_hints` 已协议参数化（从 profile 读流名映射），但 `strategy.classify_vuln` 调用时写的是 `extract_stream_hints(text)`，**没传 protocol**，走默认 `rtsp`。
- **实际后果**：换协议（SMTP/FTP/SIP）时，`strategy` 层的漏洞触发流提取仍用 RTSP 流名映射（`matroskaFileTest` 等），触发流提取失效或错误。`classify_all`/`dedupe_reqs` 同样无 protocol 参数。
- **修复方向**：给 `classify_vuln`/`classify_all`/`dedupe_reqs` 补 `protocol` 参数并透传给 `extract_stream_hints`。

### 问题 3：`selector.select_seeds` 不传 `method_order`，P2b 拓扑序在该路径失效

- **涉及文件**：`core/fused/downstream/selector.py`（`select_seeds`）、`scripts/seedgen.py`、`core/fused/downstream/edge_cover.py`
- **矛盾表现**：`assemble_bundle` 产出了 `method_order`（traffic 推导的会话语序，P2b）；`scripts/seedgen.py` 调 `edge_cover(..., method_order=bundle.get("method_order"))` **传了**，但 `selector.select_seeds` 调 `edge_cover(transitions, required_headers, headers, message_instances, protocol=protocol)` **没传**。
- **实际后果**：两个种子生成入口行为不一致——seedgen 路径遵循会话语序，selector 路径回退字典序。edge_cover 覆盖边的顺序不同，产出的种子序列不同。
- **修复方向**：`select_seeds` 里补 `method_order=bundle.get("method_order")`。

### 问题 4：`resolver.py` 统一消解引擎未接入主链路（死代码）

- **涉及文件**：`core/fused/downstream/resolver.py`（`resolve_claims`）、`core/fused/downstream/rag_seedgen.py`（`assemble_bundle`）
- **矛盾表现**：`resolver.resolve_claims` **无任何调用点**（已 grep 确认）。`assemble_bundle` 仍手写消解：`header value_enum` 用自写 union 合并、`method.state_changing` 直接 `bool(val)`（覆盖而非按优先级消解）、其余取 `claims[0]`。
- **实际后果**：P2a「统一消解引擎」虽实现但未生效；多源对同一 fact 的冲突（precedence/union/consensus/conflict）从未按声明式优先级表执行，消解逻辑与 resolver 文档描述脱节。
- **修复方向**：二选一——(a) 让 `assemble_bundle` 对多 claim fact 调 `resolve_claims`，删掉手写消解；(b) 若维持现状，明确 resolver 是独立库并在 `assemble_bundle` 注释标注「消解在此处简化实现」，避免误导。

### 问题 5：`SOURCE_PRIORITY` 值域与实际 epistemic_type 不匹配

- **涉及文件**：`core/fused/downstream/resolver.py`、`core/fused/downstream/source_availability.py`（均 `SOURCE_PRIORITY={"observed":3,"normative":2,"descriptive":1}`）、`core/fused/norm.py`（rfc 产出 `normative_unspecified`/`must`）
- **矛盾表现**：优先级表用 `normative`，但 rfc 源（norm.py）实际产出的 epistemic 是 `normative_unspecified` 和 `must`（`_MODALITY_TO_EPISTEMIC` 映射），**没有 `normative` 这个值**。
- **实际后果**：`_priority("normative_unspecified")` / `_priority("must")` 返回 0，低于 `descriptive(1)`，导致 rfc 规范知识的优先级被错误降到最低。当前因 resolver 未接入（问题 4）暂不触发，一旦接入即暴露。
- **修复方向**：统一 epistemic 值域——要么 norm.py 产出 `normative`，要么在 `SOURCE_PRIORITY` 补 `normative_unspecified`/`must → 2`。

### 问题 6：`boundary_probe.generate_candidates`（序列型）RTSP 硬编码，与字段型不一致

- **涉及文件**：`core/fused/downstream/boundary_probe.py`（`generate_candidates`/`_describe_msg`/`_setup_msg`/`_TRIGGER_SESSION`）、`core/fused/downstream/selector.py`
- **矛盾表现**：`boundary_probe` 内 `_field_action_candidates` 已按 `profile.raw_format` 协议化（url vs argument 分支），但 `generate_candidates`（double_setup/uaf_seq/lifecycle_seq/interleave_seq）仍硬编码 RTSP：`rtsp://127.0.0.1:8554/`、`matroskaFileTest`、`track1/track2`、`SETUP/TEARDOWN/DESCRIBE`、`Transport/Session` 头、`_TRIGGER_SESSION="000022B8"`。且 `selector` 调 `derive_vuln_pattern_candidates` 未传 `stream`（默认 `matroskaFileTest`）。
- **实际后果**：这些序列型 action 恰好是 RTSP 特有漏洞模式，换协议时不会命中，故暂不触发；但这是隐式协议耦合，与同文件字段型的协议化形成不一致，后续加新协议的序列型漏洞会踩坑。
- **修复方向**：把序列型候选的消息构造也下沉到 profile（URL 模板、方法名、触发 Session 值从 profile/知识中枢取），`derive_vuln_pattern_candidates` 增加 stream 参数透传。

## 三、低严重（脆弱设计 / 孤儿代码 / 死代码）

### 问题 7：`relation + target_state` 复用同一 fact 形态，靠 `source.type` 隐式区分两种语义

- **涉及文件**：`core/fused/traffic.py`（`_state_machine_facts`，source/target `type="method"`）、`core/fused/norm.py`/`core/fused/source_autoseeder.py`（source/target `type="state"`）、`core/fused/downstream/rag_seedgen.py`（`assemble_bundle` relation 分支）
- **矛盾表现**：`Subject(type="relation", name="transitions_to") + aspect="target_state"` 这个形态同时承载两种完全不同语义——rfc/source 的「状态机边 `state--method-->state`」（source/target 是状态名，带 method qualifier）与 traffic 的「方法相邻对 `method→method`」（source/target 是方法名，无 method qualifier）。`assemble_bundle` 靠 `quals.source.type == "state"` 分流到 `transitions` vs `method_sequences`。
- **风险**：任一抽取器写错 `source.type`（state/method）会**静默**走错分支，无任何校验。
- **修复方向**：用不同 `aspect`（如 `target_state` vs `method_sequence`）或不同 `subject.name` 显式区分，去掉「靠 qualifier.type 隐式分流」。

### 问题 8：`source.py` 硬编码 `protocol="rtsp"` + 孤儿代码

- **涉及文件**：`core/fused/source.py`（`_make_fact` 第 50 行 `FactKey(protocol="rtsp")`、`extract_header_facts` 硬编码 `kb/协议实现源码` 旧路径）
- **矛盾表现**：`source_norm_to_facts` / `extract_header_facts` 均无调用点（source 源已改走 `source_autoseeder.infer_source_facts`），但 `source_fsm.py`（DEPRECATED）仍 `from core.fused.source import _make_fact`。其 `_make_fact` 硬编码 rtsp，与 memory 中「source 源已 protocol 参数化」的结论相悖（参数化只发生在 source_autoseeder.py，source.py 未改）。
- **修复方向**：删除 source.py / source_fsm.py / protocol_patterns.py 孤儿代码，或至少给 source.py 的 `_make_fact` 补 protocol 参数。

### 问题 9：rfc 源不产 transition，`norm.py` 的 transition 映射是死代码

- **涉及文件**：`core/fused/rfc_extractor.py`（注释明确「状态机不在此确定性抽取范围」）、`core/fused/norm.py`（`transition_norm_to_fact` + `RFC_KIND_MAP["transition"]`）
- **矛盾表现**：`norm.py` 保留了 `transition` kind 的映射函数，但 `rfc_extractor` 从不产 `kind="transition"` 的 norm，故 `transition_norm_to_fact` 永不执行。状态机**单点依赖 source 源**。
- **风险**：无源码（source 源缺失）时状态机缺失，种子生成直接返回空。
- **修复方向**：明确 transition 产出源（rfc 用 LLM 补，或删掉 norm.py 的 transition 映射避免误导），并在文档标注状态机对 source 源的单点依赖。

### 问题 10：`compat.py` 映射的 v1 aspect 在 `assemble_bundle` 无消费端

- **涉及文件**：`core/fused/compat.py`（`_PROPERTY_TO_ASPECT`）、`core/fused/downstream/rag_seedgen.py`
- **矛盾表现**：compat 把 v1 的 `value_type/value_range/default_value/case_sensitivity/observed_presence_rate/observed_co_occurrence/observed_occurrence_rate` 映射为 aspect，但 `assemble_bundle` 的 header 分支只处理 `syntax/definition/value_enum/occurrence/security_property/legal_boundary/response_expectation/vuln_pattern`，上述 aspect 会被静默丢弃。
- **修复方向**：确认这些 v1 字段是否还需要；不需要则从 compat 映射表删除，需要则补 assemble_bundle 消费分支。

### 问题 11：`rfc_extractor.infer_structures` 的 field norm 格式与 `_extract_rfc_file` 不统一

- **涉及文件**：`core/fused/rfc_extractor.py`（`infer_structures` vs `_extract_rfc_file`）、`core/fused/norm.py`（`parse_field_content`）
- **矛盾表现**：`_extract_rfc_file` 的 field norm content 是 `"Title | required: 语义"`（带 modality 分隔），`infer_structures` 的 field norm content 是纯语义文本（无 `| required:` 分隔）。`parse_field_content` 对后者找不到分隔 → 语义被当成 `syntax`（产出 aspect=syntax），而非 definition。
- **修复方向**：统一 `infer_structures` 的 field content 格式（加 `| required:` 或让 `parse_field_content` 兼容纯文本）。

### 问题 12：`export.py` 冗余死代码 + `scope` 字段名不一致

- **涉及文件**：`core/fused/export.py`
- **矛盾表现**：(a) `get_fact_view` 里 `res_view` 被赋值两次（第一个 `if fact.resolution` 块是冗余死代码）；(b) `_fact_from_json` 里两个完全相同的 `if isinstance(obj,dict) and "subject" in obj and "aspect" in obj` 判断；(c) `get_claim_view` 里 `scope` 用 `claim.scope.in_scope`，但 `Scope` dataclass 无 `in_scope` 字段 → 永远 None。
- **修复方向**：清理冗余块，修正 scope 字段访问（或删掉 scope 输出）。

### 问题 13：`strategy._data_root/_vuln_dir` 与新「协议×源」路径并存

- **涉及文件**：`core/fused/downstream/strategy.py`（`_data_root` 用 `here.parents[3]/"kb"`、`_vuln_dir` 用 `kb/历史漏洞`）、`core/paths.py`
- **矛盾表现**：`load_vuln_kb(protocol)` 走 `paths.kb_source_dir(protocol,"vuln")`（新结构 `kb/<protocol>/历史漏洞`），无 protocol 时回退 `_vuln_dir`（旧单协议 `kb/历史漏洞`）。两套路径解析并存，易混淆。
- **修复方向**：统一走 `paths`，废弃 `_data_root/_vuln_dir`。

### 问题 14：`source_probe.py` 硬编码 RTSP DESCRIBE 探测 + VM 地址

- **涉及文件**：`core/fused/source_probe.py`
- **矛盾表现**：`probe_streams` 硬编码 `VM="zxy@192.168.37.130"` + DESCRIBE 探测（RTSP 特定）。
- **修复方向**：探测逻辑协议参数化（或明确这是 RTSP 专用运行时辅助脚本，从协议无关层剥离）。
