## 四、结论

### 4.1 ★ 两条通道**各有胜负，没有单边优势**

| 协议 | 更好的通道 | 理由 |
|---|---|---|
| rtsp | **平** | 方法集完全一致（丢0增0），漏抽误抽都是 0 |
| sip | **config** | content 多出 `OK`/`TLS` 两个**误抽** |
| smtp | **平** | 方法集完全一致 |
| **dhcpv4** | **content** | config **漏抽 3 个**（`DHCPOFFER`/`DHCPACK`/`DHCPNAK`）；content 漏抽 0 误抽 0 |

### 4.2 差异的**根因**（都是可解释的，非随机）

| 差异 | 根因 |
|---|---|
| **config 漏抽 DHCP 的 3 个服务器消息** | RFC 2131 §4.3 **只有客户端消息的小节**；`DHCPOFFER`/`DHCPACK`/`DHCPNAK` 只在 **§3.1 散文 + Figure 3 时序图**里 ⇒ 标题式抽取拿不到 |
| **content 误抽 sip 的 `OK`/`TLS`** | 二者来自**示例块**（`SIP/2.0 200 OK`）与散文（`concern about TLS`）⇒ 窗口外通道（散文命令格式通道）产出，**与 `_section_kind` 无关** ⇒ 不是新通道引入的 |
| **content 字段集有增有减** | 增的是「章节标题形态的字段」（`Caching`/`Connections`/`Body`…）；减的是「CSeq」等 ⇒ 标题形态判据的边界不同 |

### 4.3 ★ 归因边界（**明确不能下的结论**）

✅ **可以**归因：「同一 kb + 同一抽取逻辑 + 只换判据来源」下的 fact 集合差异；

❌ **不能**归因：「内容判据更好」这个**总体结论** —— 只测了 4 个协议，
且其中 3 个是**已知正确**的（方法集已人工确认过），
而唯一体现 content 优势的 dhcpv4 **同时是新协议**（配置本身是手工打的补丁）。

### 4.4 对 S3（清除旧通道）的影响

★ **S3 的前置条件（新通道须覆盖旧通道全部 6 类）已满足**：
`method` / `field` / `status` / `transition` / `outcome` / `required_header` 六类均有判据；

★ 但 **S3 现在**不**该**执行 —— 因为 E-1 的结论是「各有胜负」：
  · 换成 content ⇒ DHCP 补全 3 个消息，但 sip 多 2 个误抽；
  · 保持 config ⇒ sip 干净，但 DHCP 永远缺服务器消息。

⇒ **建议 S3 暂缓**，先做「**两通道互补**」：
  · **config 优先**（人工配置是可靠的）；
  · **content 补漏**：仅当 config 判不出时，才用 content 判（= 现有 L-D 兜底的**反向用法**）；
  · 或者：为 content 通道补上「排除示例块/散文噪声」的判据，把 sip 的 2 个误抽消掉，
    再评估是否值得切换。
