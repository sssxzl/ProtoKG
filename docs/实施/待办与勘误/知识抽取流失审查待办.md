## 〇、审查范围与方法

**审查对象**：协议规范（RFC）作为知识源时，从正文到「后端消费」全链路上**被疏漏、被排除、被隔离、被静默丢弃**的知识。

**审查方法**：全部基于**实测数据**（只读统计，不改任何产物）——
`derived/per_source/<协议>/rfc/verify.jsonl`（479 条候选的逐条判定记录）、
`derived/per_source/<协议>/rfc/facts/*.jsonl`（抽取产物）、
`derived/hub/`（中枢事实）、`derived/seeds/`（种子产物），以及对应源码。

**审查的九道关卡**（按数据流顺序）：

```
①候选触发 → ②主体解析 → ③L1确定性校验 → ④L2语义核验 → ⑤发布闸
→ ⑥通道可见性 → ⑦中枢投影 → ⑧消费侧过滤 → ⑨种子产出
```

## 二、三条核心结论

### 结论一：★ 规范约束类知识几乎为零，而消费端恰恰只吃这一类

- 消费端 `core/fused/downstream/rule_store.py` 明确写着：**合格规则投影出 `legal_boundary` / `response_expectation`，消费端才有输入**。
- 而中枢里 `legal_boundary` 只有 **5 条（占 414 的 1.2%）**，`definition` + `syntax` 合计占 31%。
- ⇒ ⇒ **《设计思想与设计方案》§1.2 理念三「用图增强检索 + 大语言模型生成种子」所依赖的约束输入，在 rfc 单源场景下几乎不存在。**
- ⇒ ⇒ 知识分布偏向「协议是什么」，而非「协议要求什么」。

### 结论二：★ 规则通道的成果**没有进入中枢**，因而无法被消费

- 通道 J（段落级散文规则抽取）实测：L1 通过 **92** 条、L2 确认 **7** 条。
- 但通道 J 以**影子模式**运行（`core/fused/extraction/prose_semantics.py:547`：「影子模式（`shadow=True`）：只产出候选与统计，**不进 fact 空间**」）。
- ⇒ ⇒ **92 条通过确定性校验的规则成果，对后端消费完全不可见**；中枢里那 5 条 `legal_boundary` 来自通道 I（按文档抽取）。
- ⇒ ⇒ 这是**有意为之的隔离**（防止未验证规则污染事实库），但它同时意味着：**当前无法回答「规则通道的成果对种子生成有多少贡献」**，因为它的贡献恒为零。

### 结论三：★ 最危险的不是丢弃，是**静默失效**

三处「不报错、但知识等于没用上」的地方：

| #   | 位置                          | 现象                                                                                          |
| --- | --------------------------- | ------------------------------------------------------------------------------------------- |
| a   | `hub_view.py` 字段级实例对齐       | 状态机换源后，旧实例的键命中不了 ⇒ `edge_cover` 取不到字段模板 ⇒ 消息退回「必填头 + 取值池首值」⇒ **同一字段在所有方法上取值相同**，方法特有字段组合丢失  |
| b   | `hub_view.py:282` method 过滤 | LLM 腿抽的 method 可能是「provisional response」「Timer F」这类**触发事件**⇒ 必须过滤 ⇒ 被丢弃的 method **不进任何候选库** |
| c   | `hub_view.py` 注释            | 「**规范原生腿空 ⇒ 退回 LLM 腿**」⇒ 说明**规范原文原生抽出的方法-字段关系本身是空的**，才需要 LLM 兜底                             |

⇒ ⇒ 结论：a 与 c 指向同一个根因 —— **从规范文本里直接抽出「状态—方法—字段」关系的通道能力不足**，导致下游要么拿不到，要么拿到的是降级结果。

## 三、逐关卡分析：该拦的 vs 误伤的

| 关卡          | 拦下的主要是什么                                     | 判定                                             |
| ----------- | -------------------------------------------- | ---------------------------------------------- |
| ② 主体解析      | 描述性陈述（RFC 2119 关键词定义段、协议定义句）、无主语句、代词主体       | ★ **大部分拦对了**（250/341 不含 BCP14 等级词）；**91 条是误伤** |
| ③ L1 强度归一   | 小写 `must`/`may`/`should`（RFC 8174 规定小写不承载强度） | ★ **拦对了**（宁可强度未定，不可强度错）                        |
| ③ L1 极性一致性  | 抽成 negative 但原文无否定词                          | ★ 拦对了                                          |
| ③ L1 跨节引用   | 「described in Section 12」无法定位                | ✘ **误伤**（主体其实明确，缺的是跨节定位能力）⇒ **可补**             |
| ④ L2 确定性前置  | 原文未出现动作/对象（如对象「globally unique」）             | ★ 拦对了幻觉；但**对抽象化动作词过严** ⇒ **部分误伤**              |
| ④ L2 语义判定   | 条件/例外/作用域等字段「不确定」                            | ⚠ 机制对，但**判定不可复现**（同输入四次重跑 confirmed 数不同）       |
| ⑤ 发布闸       | 主体不可靠 / 强度未知 / 结论非已证实                        | ★ 拦对了（正是它挡住了不可复现的 L2 结论）                       |
| ⑥ 通道影子      | 全部未验证规则                                      | ★ **有意隔离**，但需评估放行条件                            |
| ⑧ method 过滤 | LLM 腿的触发事件型 method                           | ★ 拦对了污染，但**被丢弃者不留痕**                           |

## 四、主体缺口的专项分析（★ 用户要求记录）

### 4.1 「主体」指什么

**主体 = 这条规范要求由谁承担**（义务的承担者），落在 `fact_key.subject`。

必须区分两个字段：

| 字段                        | 含义                 | 例                 |
| ------------------------- | ------------------ | ----------------- |
| `mentioned_entity`（提及实体）  | 抽取时**在原文中识别到的实体名** | `server`          |
| `normative_subject`（义务主体） | **这条要求是谁必须做的**     | `client` 或 `None` |

实测：

```
RESOLVED    entity='client'            → subject='client'
RESOLVED    entity='RTSP servers'      → subject='RTSP servers'
UNRESOLVED  entity='server'            → subject=None
UNRESOLVED  entity='RTSP connection'   → subject=None
```

⇒ ⇒ **「无法解析」指义务主体定不下来，不是「没找到实体」。**

### 4.2 真实原文（rtsp，RFC 2326）

**主体可确定（行 326）**

```
the server. For audio/video feeds, this means that the client
may issue a single play or pause message to control both the
audio and video feeds.
```
⇒ ⇒ 「the client may issue …」⇒ 主体明确 ⇒ 正确判定。

**主体未定 · 描述性（行 247）**

```
There is no notion of an RTSP connection; instead, a server maintains
a session labeled by an identifier.
```
⇒ ⇒ 在解释 RTSP 是什么，**没有任何义务** ⇒ 拦对了。

**主体未定 · 省略主语（行 810）**

```
The use of IP addresses in URLs SHOULD be avoided whenever possible
```
⇒ ⇒ 有规范措辞，但**主语省略** ⇒ **真实缺口**。

**主体未定 · 跨节引用（行 580）**

```
A server SHOULD implement all header fields described in Section 12.
```
⇒ ⇒ **主体其实是明确的（server）**，失败原因是**跨节内容无法定位** ⇒ **可补**。

### 4.3 缺口的量与结构

| 指标 | 数值 |
|---|---|
| unresolved 总数 | 341 |
| 其中**含 BCP14 等级词**（疑似真义务） | **91**（27%） |
| 其中不含等级词（描述性，拦对了） | 250（73%） |
| 分协议分布 | rtsp 14 / sip 20 / smtp 21 / DHCPv4 36 |
| 这 91 条是否进过 L1 | **全部未进**（在主体这一步就被挡下） |

### 4.4 ★ 缺口的**级联效应**（比数量更严重）

```
主体未定 ⇒ aspect 无法归类 ⇒ 进不了 L1/L2 ⇒ 进不了发布闸 ⇒ 进不了中枢
```

⇒ ⇒ 这 91 条**在整条链路上不存在**：既不能被图检索，也不能被种子生成消费。
⇒ ⇒ **代价远大于 91/479 这个比例表面看起来的样子。**

### 4.5 ★ 不能把「主体解析率 29%」读作「准确率 29%」

341 条 unresolved 混着两类完全不同的东西：

| 类别 | 条数 | 排除是否正确 |
|---|---:|---|
| 本来就不该是规则（描述句、定义句、元规范段） | 250 | ✔ **排除正确** |
| 是真规范义务，但主体省略或跨节无法定位 | 91 | ✘ **保守隔离的代价** |

⇒ ⇒ 真正该跟踪的指标是：**unresolved 中含 BCP14 等级词的比例（当前 27%）**，而不是主体解析率本身。

## 五、补齐待办清单（★ 按性价比排序）

### P0 —— 阻塞「约束类知识进入消费端」

| # | 事项 | 目标 | 验收口径 | 成本 |
|---|---|---|---|---|
| **P0-1** | **通道 J 的受控发布决策** | 明确「影子」何时可转为发布；当前 92 条 L1 通过的成果对消费端贡献恒为零 | 若放行：rfc 单源中枢 `legal_boundary` ≥ 20 条，且种子数与 `legal_boundary` 数量**正相关**（当前 5 条 ⇒ 9~30 条，无相关性） | 需先解决 P1-2 |
| **P0-2** | **跨节引用定位** | 让「described in Section N」这类条目可定位 ⇒ 回收主体明确但跨节失败的一批 | P0-1 之前完成；预期把 91 条缺口里的跨节类清零 | 低（已有 `cross_ref` 字段与「无法定位」判定，只差定位能力） |
| **P0-3** | **省略主语的主语消解** | 按协议角色表回填隐含主体 | 用 RFC 2119 §主体惯例 + 协议档案已有角色信息 | 中 |

### P1 —— 提升规则通道的通过率与判定可靠性

| # | 事项 | 目标 | 验收口径 | 成本 |
|---|---|---|---|---|
| **P1-1** | **L2 确定性前置放宽** | 当前对「抽象化动作词」过严（原文无 "send" 也拒收）⇒ 误伤一部分真规则 | 拒收原因分类统计；「原文未出现动作/对象」类占比下降，且**误判率不上升**（需人工抽样 20~30 条复核） | 中 |
| **P1-2** | **L2 判定稳定性** | 同输入多次判定不一致（rtsp confirmed 1→2→1→0）⇒ 结论不可复现 | 同一批输入重复 5 次，**逐条判定一致率 ≥ 90%**；或改为「多次投票 + 分歧即降级为候选」 | 中高 |
| **P1-3** | **静默失效告警** | 字段级实例对齐失败、method 过滤丢弃等**不留痕**的流失要可观测 | 每次种子生成输出「知识降级统计」：多少字段退回默认值、多少 method 被过滤、多少实例未命中 | 低 |

### P2 —— 降噪与可观测

| # | 事项 | 目标 | 验收口径 | 成本 |
|---|---|---|---|---|
| **P2-1** | **元规范段识别** | 显式排除 RFC 2119 关键词解释段、目录段、术语定义段 | 这类条目占 unresolved 的比例被单列统计 | 低 |
| **P2-2** | **被过滤项回流** | method 过滤、跨节失败等被丢弃的条目**进候选库并带原因**，不静默丢 | 候选库条数 = 过滤丢弃条数（可对账） | 低 |
| **P2-3** | **跟踪指标固化** | 把「unresolved 中含 BCP14 等级词的比例」设为常规跟踪指标（当前 27%） | 每次构建产出该数字与历史对比 | 低 |

## 六、复算方法

本审查的全部数字均可用下列命令复算（**只读**）：

```bash
# 抽取与校验阶段（479 条候选的逐条判定）
python guard/_out/_audit_leakage.py

# 中枢 aspect 分布
python - <<'PY'
import json, pathlib, collections
c = collections.Counter()
for f in pathlib.Path('derived/hub').rglob('*.jsonl'):
    if 'index' in str(f) or 'order' in str(f):
        continue
    for ln in f.read_text(encoding='utf-8').splitlines():
        if ln.strip():
            c[(json.loads(ln).get('fact_key') or {}).get('aspect')] += 1
print(c.most_common())
PY

# 种子规模与来源
python - <<'PY'
import json, pathlib
for f in sorted(pathlib.Path('derived/seeds').rglob('manifest.json')):
    d = json.loads(f.read_text(encoding='utf-8'))
    print(f.parent, d.get('seed_count'), (d.get('provenance') or {}).get('source_set'))
PY
```

## 七、诚实声明

1. 本审查的「流失量」均为**候选条目计数**，不等于「丢失的协议知识量」—— 一条候选可能对应原文多处要求，反之亦然。
2. 「疑似真义务」的判定依据是**证据上下文含 BCP14 等级词**，这是**代理指标**，不排除仍有遗漏的描述性条目被计入。
3. 91 条缺口中「跨节引用」与「省略主语」两类占比**未经逐条人工确认**，仅从抽样原文推断 ⇒ ⇒ **P0-2 的收益需先做一次人工分类统计**。
4. 本文所有结论基于 2026-11-15 的代码与产物状态；通道 J 的发布策略一旦变更，关卡⑥的结论即需重估。
