### 1.3 第 10 种 normalizer（§6-Pre15 起）

`rate_normalize_v1` / `rate_relation_v1` 为**第 10 种** normalizer /
comparator，与现有 9 种**同属未排期 backlog**。

- **声明已落位**：`observed_presence_rate` 已加入
  `property_registry.json`（18 → 19 条），其 `normalizer` /
  `comparator` 字段已写入（§14 E15）
- **实现待排期**：该 pair 属 N-1 ~ N-5 序列，尚未启动
- 连带: §6.6-E 冻结的「outcome category 枚举由
  `temporal_normalize_v1` 判定」同样依赖本 backlog

### 1.4 当前比较语义的实际执行者

**关键事实**：Phase A 的比较（`compare_assertions`）当前走的是
`comparison_policy.json` 的 `decidable_subset_supported` 路径，
在 `phase_a.py` 中**硬编码**为 `{equal, disjoint}`，**不读** Registry 的
`comparator` 字段。

⟹ 因此「normalizer / comparator 未实现」**当前不产生可观测症状**：
已产出的 62 个 complete Facts 的比较判定走的是硬编码路径。

**但这是双轨**：

- 当前路径能产出 65 Facts，是因为 18 property 的值域足够简单
  （bool / str）
- 一旦出现 dict / set / range / condition 形态的 assertion
  （如 D9 的 rate 三元组、R2 value_range、R11–R14），
  现有硬编码比较路径**未必覆盖**

⟹ 本 backlog 的真正风险不是「现在会坏」，而是
**「结构化 value 一旦落地，比较语义可能不完整」**。

## 3. 待排期

### 3.1 待裁定问题

1. **normalizer 的语义边界**：各 property 的 `value_schema` 已声明
   结构，但「归一成什么 canonical 形态」无定义
   （例：`numeric_range_v1` 对 `0-255` / `[0,255]` / `min=0,max=255`
   的归一目标形态，`fused_canonical_spec.md:96` 有示例但无形式化定义）
2. **是否需要第 10 种 normalizer**：若 D9 的 rate 落地，
   需新增 1 种 rate normalizer（届时为 10 种）
3. **comparison_policy 与 comparator 的关系**：
   `comparison_policy.json` 的 `decidable_subset_supported`
   与 per-property `comparator` 如何分工
4. **与 `phase_a.py` 硬编码路径的迁移**：是否将 `compare_assertions`
   改为 Registry 驱动

### 3.2 建议排期单元

| 单元 | 内容 | 依赖 |
|---|---|---|
| N-1 | normalizer 语义的形式化定义（9 种） | 需先裁定 3.1.1 |
| N-2 | normalizer 实现（9 种） | N-1 |
| N-3 | comparator 实现（9 种） | N-1 + 3.1.3 |
| N-4 | `compare_assertions` 改为 Registry 驱动 | N-2 + N-3 |
| N-5 | 结构化 value 的比较覆盖验证 | N-4 |

### 3.3 优先触发条件

**不建议预先排期。** 建议在下列任一条件出现时启动：

- D9 的 rate property 落地（需 normalizer）
- R2 value_range 获得 producer（value 为 dict/range）
- R11–R14 任一获得 producer（value 为 dict，含 observation_scope）
- 出现 dict / set / range 形态的 assertion value
