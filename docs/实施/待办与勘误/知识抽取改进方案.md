## 一、改 1 · 主体归属三层增强（对应 P0-2 / P0-3）

### 1.1 根因（★ 已在代码中定位）

抽取 prompt **已经把两个概念分开了**（`core/fused/extraction/prose_semantics.py:56`）：

```
★ ★ `normative_subject`：**真正承担义务的主体**（★ **不是** `entity`！
★ ★ `subject_span`：`normative_subject` 在原文中的行号（★ 用于核对；不确定就留 0）。
```

⇒ ⇒ **问题不在「问错了」，而在三处**：

| # | 缺口 | 后果 |
|---|---|---|
| ① | prompt **没给候选域** ⇒ LLM 不知道该填什么，只能留空 | `normative_subject` 空 ⇒ 直接 unresolved |
| ② | 「不确定就留 0」的指引 ⇒ **留空被当作失败** | 明明可以靠候选域推断，也放弃了 |
| ③ | RFC 大量**省略主语**的规范句，prompt 无从判断 | 主体永远为空 |

### 1.2 改法：新增 `resolve_subject()` 三级判定

**新代码位置**：`core/fused/extraction/normative_rule.py`（与 `subject_resolvable` 同处）

```python
def resolve_subject(*, quote: str, stated: str = "",
                    candidates: Sequence[str] = (),
                    default_owner: str = "") -> tuple[str, str]:
    """义务主体三级消解 ⇒ 返回 (主体, 状态)。

    状态 ∈ resolved / inferred / unresolved
      · resolved  ⇒ 原文有显式主语且命中候选域（★ 唯一可进发布闸的状态）
      · inferred  ⇒ 由候选域/默认承担者推断（★ **只进候选，不进发布**）
      · unresolved ⇒ 候选域与默认承担者都无从判定
    """
    # L1 显式主语：stated 非空 ⇒ 在候选域内按规范化名/别名匹配
    #    · 命中 ⇒ (canonical_name, "resolved")
    #    · 未命中但 stated 本身是合法实体名 ⇒ (stated, "resolved")
    # L2 代词回指：stated 是代词 ⇒ 取 quote 中**最近的**候选域实体
    #    ⇒ (该实体, "inferred")            ★ 代词 ⇒ 不进发布
    # L3 无主语兜底：default_owner 非空 ⇒ (default_owner, "inferred")
    #    ⇒ ★ 无主语 ⇒ 不进发布（保守）
```

**候选域的构造（★ 不需要新数据源，现成）**：

| 候选域 | 来源 | 说明 |
|---|---|---|
| 协议角色与实体 | `derived/hub/index/entities.jsonl` | 字段 `{entity_id, protocol, type, name, canonical_name, aliases}` ⇒ **`aliases` 天然支持「client / user agent / UA」这类同指** |
| 方法与消息名 | `profiles/<协议>/profile.json` 的 `allowed_methods` | 用于「谁执行这个方法」这类判断 |

**调用点改造**：`prose_semantics.py` 中构造 norms 的位置（`:340` 附近，现为
`subject=str(item.get("normative_subject") or "").strip() or _ent`）⇒ ⇒ 改为：

```python
_subj, _sstat = resolve_subject(
    quote=quote, stated=item.get("normative_subject"),
    candidates=_entity_candidates(protocol), default_owner=_default_owner(protocol, aspect_hint))
```

⇒ ⇒ **`subject_status` 随之从二态变三态**（resolved / inferred / unresolved），
⇒ ⇒ verify.jsonl 与护栏基线需同步更新（★ 见 §八）。

**prompt 侧改造**：把候选域（截断到 **≤ 30 个**，按出现频次排序）注入 prompt，
并把指引从「不确定就留 0」改为：

> `normative_subject`：真正承担义务的主体。下列候选中若有合适者请直接选用；
> 若原文省略主语，请填**该句的默认承担者**（如 server / client）；
> 确实无法判定时留空串（留空会被系统按候选域兜底推断，但会标记为待审）。

### 1.3 验收口径

| 指标 | 当前 | 目标 |
|---|---:|---:|
| unresolved 中含 BCP14 等级词的比例（真实缺口率） | 27%（91/341） | **≤ 12%** |
| `subject_status=resolved` 占含等级词条目的比例 | 待测 | ≥ 80% |
| ★ **误配率**：人工抽 30 条 inferred 复核主体是否正确 | —— | **≥ 90% 正确**（错配比不填更危险 ⇒ 若 <90% 则 L3 兜底关闭） |

### 1.4 风险

- ★ **L2/L3 推断出的主体可能错配** ⇒ ⇒ 缓解：**inferred 一律不进发布闸**，只进候选
- `subject_status` 由二态变三态 ⇒ ⇒ **护栏期望集需更新**（★ 属口径变更，须先确认）

## 二、改 2 · 跨节引用定位（对应 P0-2）

### 2.1 根因

`cross_ref` 只有**字段与状态**（`normative_rule.py:132-147`，状态 ∈ none/present/unknown），
**代码里没有任何「定位被引节」的实现** ⇒ ⇒ 「存在跨节引用但无法定位 ⇒ 待审」是**判为 unknown**。

⇒ ⇒ 后果：像 `A server SHOULD implement all header fields described in Section 12.`
这类**主体其实明确**的条目，因内容在别节而定位不到 ⇒ ⇒ 落入缺口。

### 2.2 改法：证据跨度随跨节引用扩展

**已有能力**：`core/fused/extraction/doc_registry.py:parse_header(text, protocol=..., source=...)`
⇒ ⇒ **文档的章节树已经能解析出来** ⇒ ⇒ 不需要新建章节解析。

**改法**（`prose_semantics.py` 构造 quote 的位置）：

```
1. 从原文抽 cross_ref（现状已有）
2. 若 cross_ref_status == 'present'：
     a. 用 parse_header 得到的章节树，把「Section N」映射到被引节的起始行 _s
     b. quote 扩展为「本行 ± 2 行」+「被引节首行起 8 行」
     c. 同时把 entity_in_span 的窗口参数相应放大（当前 window=3）
3. 若映射失败 ⇒ 保持现状（unknown ⇒ 待审），但**把失败原因写进 reasons**
```

**为什么这样能救回主体**：主体（`A server`）**就在本行**⇒ ⇒ 现在的失败原因**不是主体定不下来**，
而是**对象/字段定位不到**（因为字段清单在 Section 12）⇒ ⇒ 扩展证据后，对象可定位 ⇒ ⇒ 主体随之可定。

### 2.3 验收口径

| 指标 | 当前 | 目标 |
|---|---:|---:|
| L1「存在跨节引用但无法定位」 | 5 条 | **0 条**（能定位的都定位） |
| 缺口 91 条中跨节类占比 | 未逐条确认 | **先人工分类统计**（★ 见 §九），再定目标 |
| 扩展证据后 L2 确认数 | 7 | 不下降（★ 若下降说明扩展引入了噪声） |

### 2.4 风险

- 证据跨度变长 ⇒ ⇒ **L2 的判定输入变复杂** ⇒ ⇒ 可能引入噪声 ⇒ ⇒ 需用「L2 确认数不下降」作为守门条件
- 章节号解析错误（RFC 里的节号写法五花八门）⇒ ⇒ 解析失败必须**优雅降级**回原逻辑

## 三、改 3 · L2 确定性前置放宽（对应 P1-1）★ M1 先做

### 3.1 根因（★ 代码已定位）

`core/fused/extraction/normative_extract.py:257-299` 的 `semantic_support`：

```python
if action:
    _a = _norm(action)
    if _a and _a not in _flat_n:
        # ★ 词根匹配（去掉常见的动词后缀）
        _stem = _a[:-1] if _a.endswith("e") else _a
        if _stem and _stem not in _flat_n:
            _reasons.append(f"原文未出现动作「{action}」")
```

⇒ ⇒ **只做「去掉末尾字母 e」这一种词根处理** ⇒ ⇒
`transmit`（LLM 抽）对上原文的 `send` ⇒ ⇒ 匹配失败 ⇒ ⇒ **直接判「不支持」⇒ 拒收**。

实测样本：`action="be"` / `object="globally unique"`（原文根本没这个词）⇒ 这是**真幻觉**，拒得对；
但 `action="transmit"` / 原文 `send` 这类**是误伤**。

### 3.2 改法：**不放宽判据，只降级结论**

★ **关键设计**：既不放宽成「支持」，也不直接拒收 ⇒ ⇒ **降级为「不确定」交 LLM 复核**。

```
改前：词根匹配不上 ⇒ 直接 "不支持" ⇒ 拒收（LLM 没有机会复核）
改后：词根匹配不上 ⇒ 判 "不确定" ⇒ 继续走 L2 的独立核验
```

具体三步：

| 步 | 改什么 | 怎么改 |
|---|---|---|
| ① | **词干处理升级** | `_stem` 由「去末尾 e」改为**多后缀剥离**（`-ing` / `-ed` / `-tion` / `-s` / `-e` 组合，取最长匹配）⇒ 例：`transmitting`→`transmit`、`generated`→`generat` |
| ② | **受控同义词表** | 新增模块级常量 `ACTION_SYNONYMS`：协议域常见同义对（`send`/`transmit`/`forward`；`receive`/`accept`；`include`/`contain`/`carry`；`respond`/`reply`；`terminate`/`close`/`teardown`）⇒ **只认表中列出的，不做通用同义扩展** |
| ③ | **三态降级** | ① 或 ② 命中 ⇒ 判「不确定」并记 reason「词干/同义命中 ⇒ 交 LLM 复核」；**两者都不命中 ⇒ 仍判「不支持」**（真幻觉照样拒收） |

**改点**：`normative_extract.semantic_support`（返回本已是三态 ⇒ ⇒ **函数签名与调用方都不用改**，
只需改内部判定）⇒ ⇒ `l2_deterministic_check` 的「不支持 ⇒ 立即 REJECTED」分支自然不再触发。

### 3.3 验收口径

| 指标 | 当前 | 目标 |
|---|---:|---:|
| L2 因「原文未出现动作/对象」而拒收的条数 | 67 中的多数 | **下降 ≥ 30%** |
| ★ **真幻觉仍被拦住** | —— | 抽样 20 条被放过的条目，**幻觉率 ≤ 5%**（★ 这是硬红线） |
| L2 确认数 | 7 | 上升（**但必须同时满足幻觉率红线**） |

### 3.4 风险

★ 这是**唯一会放松拒收条件**的改动 ⇒ ⇒ 必须配「放行样本人工抽检」作为守门；
若幻觉率超红线 ⇒ ⇒ 回退同义词表（只保留词干升级）。

## 四、改 4 · L2 判定稳定性（对应 P1-2）

### 4.1 根因

L2 用**带温度的 LLM 调用**做逐字段核验 ⇒ ⇒ 同输入不同判定。
实测：rtsp 的 confirmed 数在四次重跑中为 **1 → 2 → 1 → 0**。

⇒ ⇒ 后果：**任何以 L2 结论为依据的放行都不可复现** ⇒ ⇒ 这正是通道 J 不能发布的原因。

### 4.2 改法：多数决 + 分歧降级

| 步 | 改什么 | 怎么改 |
|---|---|---|
| ① | **温度归零** | L2 调用显式 `temperature=0`（若模型支持）⇒ 降低单次抖动 |
| ② | **同一候选多次调用取多数** | 每候选跑 **3 次**（★ L2 预算 ×3 ⇒ 需同步调大 `RunGuard(max_calls=20)`） |
| ③ | **分歧即降级** | 3 次判定不一致 ⇒ `verdict = pending`，reason 记「三次判定不一致」⇒ ⇒ **不进发布** |
| ④ | **一致性指标落盘** | verify.jsonl 增字段 `l2_agreement`（3 次中多数票占比）⇒ ⇒ 纳入跟踪 |

### 4.3 验收口径

| 指标 | 当前 | 目标 |
|---|---:|---:|
| 同输入重复 5 次，**逐条判定一致率** | 未测（confirmed 数已见漂移） | **≥ 90%** |
| `l2_agreement == 1.0`（三次全同）的 confirmed 条数占比 | —— | ≥ 70% |
| L2 调用预算 | 20/协议 | 60/协议（★ 成本上升 3 倍，需在报告中显式说明） |

## 五、改 5 · 通道 J 受控发布（对应 P0-1）★ 依赖改 4

### 5.1 根因（★ 开关已存在）

`core/fused/extraction/prose_semantics.py:547`：

```
★ **影子模式**（shadow=True）：★ 只产出候选与统计，**不进 fact 空间**
```

⇒ ⇒ `extract_window_norms(..., shadow=True)` 产出的 92 条 L1 通过、7 条 L2 确认，
**只落 verify.jsonl，不进 fact** ⇒ ⇒ 对后端消费贡献恒为零。

### 5.2 改法：受控发布（四道前置条件全过才发）

```
发布条件（全部满足才写入 fact 空间）：
  ① final_state == 'confirmed'
  ② subject_status == 'resolved'          ★ inferred / unresolved 一律不发
  ③ strength 已知（非空）
  ④ l2_agreement >= 2/3                    ★ 依赖改 4
发布去向：legal_boundary aspect（★ 语义约束类，与消费端 rule_store 的投影对齐）
```

**灰度顺序**：★ **先只对 rtsp 开启**，其余协议保持影子 ⇒ ⇒ 观察一轮再推广。

### 5.3 验收口径

| 指标 | 当前 | 目标（rtsp 灰度） |
|---|---:|---:|
| 中枢 `legal_boundary` 条数 | 5 | **≥ 20** |
| ★ **种子数与 legal_boundary 数量的相关性** | 无相关（5 条 ⇒ 30 条种子） | **正相关**（回归斜率 > 0） |
| 种子合法性（种子校验层通过率） | —— | **不下降** |
| 护栏 | —— | 新增 0 / 消失 0 |

### 5.4 风险

★ **这是唯一会改变正式知识库内容的改动** ⇒ ⇒ 必须：
- 灰度单协议
- 先跑改 4（判定稳定）
- 发布前后做**逐字节对比**，把新增 fact 逐条列出人工过一遍

## 六、改 6 · 静默失效可观测（对应 P1-3）★ M1 先做

### 6.1 根因（三处「不报错但知识没用上」）

| # | 位置 | 现象 |
|---|---|---|
| a | `hub_view.py` 字段级实例对齐 | 状态机换源 ⇒ 旧实例键命中不了 ⇒ `edge_cover` 退回「必填头 + 取值池首值」⇒ **同字段在所有方法上取值相同** |
| b | `hub_view.py:282` method 过滤 | LLM 腿的触发事件型 method 被丢弃 ⇒ **不留痕** |
| c | `hub_view.py` 注释 | 「**规范原生腿空 ⇒ 退回 LLM 腿**」⇒ 规范原生关系抽取不足 |

### 6.2 改法：产出「知识降级统计」

**新增**：`derived/seeds/<协议>/<组>/degradation.json`，每次种子生成写：

```json
{
  "instance_align": {"total": 0, "migrated": 0, "unmatched": 0},
  "method_filter": {"kept": 0, "dropped": 0, "dropped_samples": []},
  "field_fallback": {"fields_defaulted": 0, "fields_from_instance": 0},
  "rule_input": {"legal_boundary": 0, "response_expectation": 0}
}
```

⇒ ⇒ 落盘点：种子生成入口（`core/fused/downstream/rag_seedgen.py`）汇总
`hub_view` 与 `rule_store` 的中间计数。

### 6.3 验收口径

- 每次种子生成都有 `degradation.json` ⇒ ⇒ **降级不再静默**
- `method_filter.dropped` 与候选库条数**可对账**（★ 配合改 7）

## 七、改 7 · 元规范降噪 + 候选回流（对应 P2-1 / P2-2）★ M1 先做

### 7.1 元规范段识别

**典型文本**（实测见审查报告 §4.2）：

```
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", …
in this document are to be interpreted as described in RFC 2119 [4].
```

⇒ ⇒ 在抽取阶段识别并**显式排除**（不进候选，直接标 `non_normative`）
⇒ ⇒ 依据：**该段含 BCP14 等级词列表本身 + 「are to be interpreted as」类固定句式**。

⇒ ⇒ 收益：250 条描述性 unresolved 里的一部分被**正确归类**（不是被拦，而是被识别为非规范）
⇒ ⇒ 这**不增加召回**，但让「真实缺口率」的指标更准确。

### 7.2 被过滤项回流

| 丢弃点 | 改法 |
|---|---|
| method 过滤（`hub_view.py:282`） | 被丢弃的 method **写入候选库**，带 `reject_reason` |
| 跨节定位失败 | 同样入候选库，带原因 |

⇒ ⇒ 对齐已有的好做法：`rule_store.publish_rules` 已经是
「不合格 ⇒ 进 `candidates.jsonl` + 带 `reject_reason`，**不静默丢弃**」
⇒ ⇒ **把其它丢弃点也统一到这个模式**。

## 九、实施顺序与里程碑

| 里程碑 | 内容 | 出口判据 | 风险 |
|---|---|---|---|
| **M1**（可立即做） | 改 3 + 改 6 + 改 7 | 召回提升且**幻觉率红线不破**；降级统计可观测 | 低（不放宽放行条件） |
| **M2** | 改 1 + 改 2 | 真实缺口率 27% → ≤ 12% | 中（三态口径变更） |
| **M3** | 改 4 | 逐条一致率 ≥ 90% | 中（成本 ×3） |
| **M4** | 改 5（rtsp 灰度） | `legal_boundary` ≥ 20 且种子数与之正相关 | ★ 高（改正式库） |

★ **M2 启动前先做一次人工分类统计**（91 条逐条看，按「跨节 / 省略主语 / 代词 / 其它」分类）
⇒ ⇒ 这决定改 1 与改 2 哪个收益更大，避免做错方向。

## 十、明确**不做**的事（★ 防止走偏）

| 不做 | 理由 |
|---|---|
| 不让**小写等级词**赋强度 | RFC 8174 明确规定小写不承载 BCP 14 强度 |
| 不让 **inferred 主体**进发布闸 | 错配比不填更危险（会生成方向颠倒的种子且下游难发现） |
| 不为「让护栏变绿」而改期望集 | 期望集是验收口径，不是调试对象 |
| 不做**通用**语义同义扩展 | 只允许受控同义词表；通用扩展会掩盖真幻觉 |
| 不在 M4 之前动正式发布范围 | 判定不稳定 ⇒ 不可复现 ⇒ 不可发布 |
