## 一、总设计原则

> **新增抽取能力不能以牺牲已有事实的语义正确性为代价。**

⇒ ⇒ 抽取结果明确划分为**三类**，各有明确去向：

| 类别 | 定义 | 去向 |
|---|---|---|
| **已证实事实** | 证据支持**全部**关键语义字段，且**通过当前版本的自动证据校验** | ✔ **进入正式知识库**（现有 aspect） |
| **待审候选** | 有一定证据，但关键语义尚未确认（强度 / 极性 / 条件 / 例外任一不确定） | ★ **不进 fact 空间** ⇒ 写入**候选台账**（元数据）⇒ ⇒ 中枢零影响 |
| **拒收结果** | 无有效证据，或存在明确语义冲突 | ★ 只留**诊断记录**（含拒收原因） |

⇒ ⇒ ★ **规范强度、否定、条件、例外必须原样保留且可核查** ⇒ ⇒ **宁可零产出，不可产出反向语义**（禁止变强制、条件约束变无条件、例外条款被抹除）。

⇒ ⇒ ★ 「已证实事实」是**相对当前校验器版本**的结论 ⇒ ⇒ 事实记录里保留**校验器版本、判定结果与不确定性**。

## 二、事实表示契约（**准备阶段冻结**）

### 2.1 规范规则在 `definition` 内的表示

`definition` 的 `value_type` 保持 **text**（⇒ aspect 数量与类型面均不变），规则类事实用**带版本的 JSON 文本**承载：

```
[RULE:v1] {"schema_version":1,"kind":"normative_rule",
           "subject":"client","action":"send","object":"message_M",
           "strength":"MUST","polarity":"negative",
           "keyword_raw":"MUST NOT",
           "condition":"before authentication completes",
           "condition_status":"stated",
           "exception":null,"exception_status":"absent",
           "scope":"state_S",
           "evidence":[{"file":"rfcXXXX.txt","span":[1234,1236]}]}
```

| 字段 | 含义 | 硬要求 |
|---|---|---|
| `strength` | **要求等级**：`MUST` / `SHOULD` / `MAY`（**不含否定**） | ★ 只表达等级 |
| `polarity` | `positive` / `negative` | ★ 否定只在此表达 |
| `keyword_raw` | 原文措辞（如 `MUST NOT`） | 可选；★ **保留原文**以便核对 |
| `condition` + `condition_status` | 生效条件 | ★ `condition_status` ∈ `stated` / `absent` / `unknown` ⇒ ⇒ **区分「明确不存在」与「尚未识别」** |
| `exception` + `exception_status` | 例外 | ★ 同上三分 |
| `scope` | 作用域 | |
| `evidence` | **证据引用列表** | ★ 支持**多条独立跨度**（一条事实可有多条证据）<br>★ ★ **只存引用，不复制内容** ⇒ ⇒ 规则文本内保存 `evidence_refs`（指向 claim 层证据记录）⇒ ⇒ **避免维护两套证据源** |

⇒ ⇒ ★ **规范关键词归一化（RFC 2119 / RFC 8174）**

| 原文关键词 | `strength` | `polarity` |
|---|---|---|
| `MUST` / `REQUIRED` / `SHALL` | `MUST` | `positive` |
| `MUST NOT` / `SHALL NOT` | `MUST` | `negative` |
| `SHOULD` / `RECOMMENDED` | `SHOULD` | `positive` |
| `SHOULD NOT` / `NOT RECOMMENDED` | `SHOULD` | `negative` |
| `MAY` / `OPTIONAL` | `MAY` | `positive` |

⇒ ⇒ ★ `keyword_raw` 保留原文完整措辞（用于核对）⇒ ⇒ **强度等级**与**极性**分离 ⇒ ⇒ 避免双重否定。

⇒ ⇒ ★ **缺失值的严格解释（三分）**

| 取值 | 含义 |
|---|---|
| `stated` | 在**相关证据**中明确出现 |
| `absent` | ★ 在**明确限定的作用域内**，有**充分依据**确认不存在或不适用 |
| `unknown` | ★ 当前证据**无法确认** |

⇒ ⇒ ★ **「仅仅没抽到」⇒ 默认 `unknown`，不得记为 `absent`**（证据跨度没提到例外 ≠ 整个 RFC 里不存在例外）⇒ ⇒ `condition` 与 `exception` **同此原则**。

⇒ ⇒ ★ **规范强度的边界（RFC 8174 的澄清）**
· **「不含 BCP 14 关键词」≠「不具规范性」** ⇒ ⇒ L1 **不得**把「含关键词」当作所有规范性候选的**硬性必要条件**
· 对**无显式关键词**的散文约束 ⇒ ⇒ **不得凭模型推测**赋予具体 `MUST`/`SHOULD`/`MAY`
· 强度无法确定 ⇒ ⇒ 记 **`unknown`**（⇒ 归「待审」）⇒ ⇒ **宁可强度未定，不可强度错**

⇒ ⇒ ★ **强度与极性不得冗余** ⇒ ⇒ `strength="MUST NOT"` 与 `polarity="positive"` 这类组合**视为非法** ⇒ ⇒ 由 §3 的 L1 确定性检查拦截。

⇒ ⇒ ★ **普通定义与规范规则的隔离判据** = 前缀 `[RULE:v1]`（普通定义**无此前缀**）。

### 2.2 规范规则的**身份唯一性**：Rule Slot 与 Assertion 分离（★ 关键约束）

★ **问题一（身份碰撞）**：规范的**事实身份**由 `protocol + version + subject + aspect + condition` 决定
⇒ ⇒ 同一主体、同 aspect、同条件下的**多条行为规则会撞成同一身份**
（例：`MUST send ACK` 与 `MUST update timer`）⇒ ⇒ 质量闸判「重复身份」并 fail-closed
⇒ ⇒ **只能保留一条 ⇒ 义务丢失**。

★ **问题二（冲突不可见）**：若把 `strength` / `polarity` 也放进身份
⇒ ⇒ 同一行为位置上的**相反要求**会被拆成**两个不同身份**
（例：`MUST send ACK` 与 `MUST NOT send ACK`）
⇒ ⇒ 它们**永不进入同一事实槽位** ⇒ ⇒ **永不触发同槽位的冲突处理** ⇒ ⇒ **冲突不可见**。

⇒ ⇒ **解法：把「行为位置」与「规范内容」分开**

| | 组成 | 作用 |
|---|---|---|
| **Rule Slot（规则槽位）** ★ 进 **事实身份** | `protocol + version + subject + action + object + condition + scope` | 判定「**是不是同一个行为要求**」⇒ ⇒ **不含** `strength` / `polarity` / `exception` / `evidence` |
| **Assertion（规范声明）** ★ 进 **声明内容（claim 的值）** | `strength` + `polarity` + `exception` + `keyword_raw` + `evidence` + 来源 | 表达「**实际怎么规定**」⇒ ⇒ 同一槽位的**相反极性声明 ⇒ 同一事实槽位 ⇒ 冲突可发现** |

⇒ ⇒ ★ **落地方式（不扩契约）**：
· `action` / `object` ⇒ 进 `subject.qualifiers`（**既有契约字段**）
· `condition` / `scope` ⇒ 进 `condition`（**既有契约字段**）
· `strength` / `polarity` / `exception` / `keyword_raw` ⇒ 进 **claim 的值**（`value` 允许任意结构）
· `evidence` ⇒ 只存 **claim 层的证据记录**（见 §2.1）

⇒ ⇒ ★ **效果**：同一 Rule Slot 的 `MUST` 与 `MUST NOT` ⇒ **同一事实身份**
⇒ ⇒ 现有的**多声明共存 + 冲突标记保留**机制**直接生效** ⇒ ⇒ **不新增冲突机制**。

⇒ ⇒ ★ **配套要求**
| # | 要求 |
|---|---|
| 1 | 普通 `definition` 与 `normative_rule` **不得**仅因 aspect 相同而自动归并 ⇒ ⇒ 靠 Rule Slot 差异区分 |
| 2 | 只有**语义上可比较**的声明才进入冲突处理 |
| 3 | 描述「**应然**」与「**实然**」的声明**分别保留**（⇒ 供一致性检查用）⇒ ⇒ 不由一方覆盖另一方 |
| 4 | ★ **Rule Slot 只是「候选关联依据」**，**不是**无需语义判断的冲突结论 ⇒ ⇒ 条件 / 例外 / 版本 / 角色 / 来源效力都可能影响可比性 ⇒ ⇒ 冲突判定**必须带这些上下文** |
| 5 | 正式入库前跑**专项兼容验证**：身份唯一性 / 相反极性可关联 / 混装隔离 / 消解行为 / 消费端行为 |

### 2.3 契约稳定与**降级路径**

| # | 要求 |
|---|---|
| 1 | **不增加 aspect**，但**明确语义契约可能变化** ⇒ ⇒ 「21 个 aspect 不变」**只是类型面不变**，**不等于兼容性无问题** |
| 2 | **散文约束的最终映射冻结为 `definition`** ⇒ ⇒ 不先落 `legal_boundary` 再迁移 ⇒ ⇒ 消除中间态与重复迁移 |
| 3 | **消费端语义兼容检查**必须列入验收（见 §9 灰度门槛） |
| 4 | ★ **降级路径**：若核查发现消费端确实会把 `[RULE:v1]` 当作普通 `definition` 并错误处理（⇒ **结构性冲突**，不是回归测试能消的）⇒ ⇒ **重新评估约束**，改走：<br>① 扩展 `legal_boundary` 的 value 结构（**改 value、不改 aspect 数量**）或<br>② **新开一个 aspect**（契约面 21 → 22）⇒ ⇒ **两条路都要重新评估下游读端** |

## 三、抽取引擎的**三级语义校验**（可执行）

| 层级 | 机制 | 处理结果 |
|---|---|---|
| **L1 · 确定性检查** | 来源区间存在且可回溯 / 规范关键词与原文一致 / **否定与强度与原文一致** / 字段完整性 / 格式约束（JSON 可解析、`strength`×`polarity` 组合合法、`condition_status` 三分合法） | 不通过 ⇒ **拒收**或**待审** |
| **L2 · 语义支持检查** | ★ **独立**核验原文与事实字段的对应关系（主体 / 动作 / 对象 / 强度 / 极性 / 条件 / 例外 / 作用域）<br>★ **输入**：① 待校验规范事实及其结构化字段；② 原文证据跨度与**必要上下文**；③ 同 RFC 内已解析的引用信息<br>★ ★ **「独立」的三层含义要分开**：**独立调用** / **独立判断过程** / **独立事实证据** ⇒ ⇒ 即使调用两次 LLM，若依赖**相同模型或相同的错误文本解析结果**，仍会**相关性错误**<br>★ ★ **「独立上下文」≠「验证器必须看到不同的原文」** ⇒ ⇒ 验证器应看到**候选事实 + 能支持或反驳它的完整原始证据**<br>★ **不得**把抽取模型给出的理由直接当成验证结论<br>★ **输出**：逐字段的 `支持 / 不支持 / 不确定` ＋ 对应证据区间 ＋ 简明判定依据 ＋ 整体判定与待审原因<br>★ ★ **「模型说是」本身不构成证明** ⇒ ⇒ 可靠性仍须由 L3 与影子抽样验证 | 支持 ⇒ **已证实事实**；不支持 ⇒ **拒收**；不确定 ⇒ **待审** |
| **L3 · 人工确认的关键语义回归样本** | §8 的 8 类正反例 | 衡量 L1/L2 的可靠性，防止严重错误回归 |

⇒ ⇒ ★ **禁止**「因否定 / 条件未落在跨度内 ⇒ 丢掉极性 ⇒ 保留正面陈述」⇒ ⇒ 证据不足只能**拒收或待审**。

⇒ ⇒ ★ **跨章证据**：同一 RFC 内的章节引用**通常可离线定位**⇒ ⇒ 与「跨 RFC 外部依赖」**分开处理**：
· **同 RFC 跨节引用** ⇒ ⇒ 本轮支持定位（引用可解析 ⇒ 扩展证据跨度；不可解析 ⇒ **转待审**）
· **跨 RFC 引用 / IANA 注册表** ⇒ ⇒ 本轮**只记录引用**⇒ ⇒ 涉及外部证据的候选一律**转待审**

⇒ ⇒ ★ **「同一跨度内同时出现主体名与约束词」只是定位线索，不足以证明语义成立。**

## 四、覆盖台账：**两本分离 + 两项覆盖率**

### 4.1 两本台账

| 台账 | 回答的问题 | 记录内容 |
|---|---|---|
| **文本覆盖** | 原文是否**到达**了抽取输入？ | 三段映射：**原始输入（行号跨度）** →（清洗 / TOC 隔离，含 `excluded_reason`）→ **清洗后正文** →（窗口归属，含 `truncated_by_budget` / `dropped_by_dedup`）→ **抽取窗口** |
| **抽取覆盖** | 哪些知识**尝试抽过**、哪些**仍有候选**？ | 各通道执行情况、产出事实、LLM 触发原因、**拒收原因**、未处理候选 |

⇒ ⇒ ★ **结构化命中 ≠ 知识覆盖完整** ⇒ ⇒ 「某窗口的字段表解析成功」**不能**证明「该窗口里的条件性散文义务已被抽出」⇒ ⇒ 两本台账**不可互相替代**。

### 4.2 两项覆盖率指标（★ 不用单一分母）

| 指标 | 分母 | 回答 |
|---|---|---|
| **原始输入核算率** | **原始输入全部行** | 每个原文区间都有**明确去向**：保留 / **合理排除** / **待检查**（⇒ 清洗误删会暴露） |
| **有效正文窗口覆盖率** | **已确认属于抽取范围的正文** | 有效正文是否都进入了抽取窗口（⇒ 衡量窗口组织的完整性） |

⇒ ⇒ ★ 因为原始行里含目录、封面、页眉页脚等**合理排除**内容 ⇒ ⇒ 不能只用单一分母
⇒ ⇒ 对**排除项**做**抽样或规则校验** ⇒ ⇒ 防止真正的规范正文被误判为可删除内容。

## 五、LLM 补漏的触发、去重与运行保护

### 5.1 触发粒度与**漏检自查**

| 规则 | 内容 |
|---|---|
| **候选信号** | 规范性关键词 · 条件句式 · 异常/错误处理 · 跨节引用 ⇒ ★ **只是候选信号**，**不是**「存在未抽取知识」的证明 |
| **判定粒度** | ★ **先在段落 / 语义块上判候选**，再组织所需上下文窗口 ⇒ ⇒ 不让边缘词触发整个大窗口 |
| ★ **独立抽样漏检检查** | ★ 从**未触发 LLM 的段落**中**抽样** ⇒ ⇒ 检查是否含被触发策略漏掉的规范义务 ⇒ ⇒ 统计**漏检迹象** ⇒ ⇒ 用于调整触发规则<br>⇒ （**逻辑必然**：候选识别器从未识别过的文本 ⇒ 进不了「未处理候选」集合 ⇒ ⇒ 必须有独立抽样路径才能发现） |

### 5.2 **两级去重**（★ 修正）

| 级别 | 键 | 作用 |
|---|---|---|
| **声明级去重** | **规范化语义身份 + 证据区间** | 去掉同一声明经**重叠窗口**反复抽取的结果 |
| **事实级归并** | **规范化语义身份** | 识别同一事实，**允许其关联多条不同证据** |

⇒ ⇒ ★ **基本原则：一条证据可以支持多条事实；一条事实也可以拥有多条证据。**
⇒ ⇒ ⇒ 只按证据区间去重 ⇒ 会**误删同一行里的不同义务**；只按语义身份去重 ⇒ 会**丢掉跨章节的重复表述的多条证据**。

### 5.3 运行保护（★ 影子模式不是「零运行风险」）

| 保护项 | 内容 |
|---|---|
| **单请求超时** | 防止单次调用挂死 |
| **最大重试次数** | 防止失败重试风暴 |
| **并发限制** | 防止资源竞争 |
| **重复调用检测** | 防止同一输入被反复调用 |
| **异常熔断与失败日志** | 连续失败时快速失败，并保留诊断 |

⇒ ⇒ ★ 这些限制针对**失控调用**，**不针对**正常抽取覆盖率 ⇒ ⇒ 与「不设 LLM 硬成本上限」并存。

### 5.4 成本观测（每批构建必须记账）

`LLM 调用次数` · `处理窗口数` · `token` · `耗时` · `候选数` · `确认数` · `拒收数` · `重试次数` · `熔断次数`

## 七、文档级登记（**只标记，不拦截**）

| 项 | 内容 |
|---|---|
| **登记内容** | 从 RFC 头部抽：编号 / 标题 / **文档自述状态** / 日期 / `Updates` / `Obsoletes` / 规范性引用 |
| ★ **标签语义限定** | ★ 只能标「**该文档自身声明的信息**」⇒ ⇒ **单篇旧 RFC 的头部无法反映后来其他 RFC 对它的更新或废弃**⇒ ⇒ **不得**标「当前生效」 |
| **支持 `unknown`** | 无法从头部判定的 ⇒ 记 `unknown`（**不猜**） |
| **两级信息分开** | ① **文档类别**（如 Standards Track / Informational）<br>② **单条 claim 的规范强度**（`MUST` / `SHOULD` / …）⇒ ⇒ 二者**不可混用** |
| **不门禁** | ★ **不因状态是 Informational 或已被 Obsoletes 就拒抽** ⇒ ⇒ 只**标记**，让下游自行过滤 ⇒ ⇒ 避免误伤 |
| **产物去向** | 文档登记 ⇒ 写 `derived/per_source/<协议>/rfc/documents.json`；效力标签 ⇒ 作为 claim 的**元数据** ⇒ ★ **均不进 fact 空间** ⇒ ⇒ **中枢零影响 / 契约零变化** |

## 八、最小语义回归集（**本轮必须完成**）

> 完整 P/R/F1 评测需要人工标注基准集 ⇒ **另立项**（评测层，不属抽取层）
> ⇒ ⇒ 但**最小语义回归集不能省**（它是 L3 的验收依据）

| # | 样本类型 | 断言 |
|---|---|---|
| 1 | `MUST NOT` 否定性约束 | **不得**产出正面陈述 |
| 2 | `SHOULD` vs `MAY` | 强度**无损区分** |
| 3 | 条件 / 例外**跨行** | 条件**被保留或被拒收**（不可静默丢失） |
| 4 | 跨章节引用（同 RFC） | 定位成功**或**明确**待审** |
| 5 | 代词指代 | 主体无法定位 ⇒ **待审** |
| 6 | 非规范性示例 | **不产出**规则 |
| 7 | 实体名出现但**不支持结论** | **拒收** |
| 8 | 重叠窗口 / 多通道重复事实 | 对重叠窗口中「**相同语义身份 + 相同证据**」的声明去重；★ **不得误删不同规则**；★ 同一事实的**多条独立证据必须保留** |
| 13 | ★ **同一 Rule Slot 下的相反极性声明**（`MUST` 与 `MUST NOT`） | ★ **能够被关联**并进入冲突检查（不要求判定为真冲突） |
| 9 | ★ **同一行含两个独立 `MUST`** | ★ **不得误删**其中一条 |
| 10 | ★ **同一事实在不同章节重复表述** | ★ 归并为**同一语义事实**且**保留多条证据** |
| 11 | ★ **同主体两条不同行为规则** | ★ **身份不碰撞**（各自独立入库） |
| 12 | ★ **普通定义与规范规则同名** | ★ **不得**被错误归并 |

⇒ ⇒ 归层：`tests/extraction/`（**抽取层的测试**）⇒ ⇒ 不越界。

## 九、实施批次

| 阶段 | 工作项 | 目标 | 验收重点 |
|---|---|---|---|
| **准备阶段** | ★ **冻结**：规则表示契约 · **Rule Slot / Assertion 身份语义** · **关键词归一化表** · 三级校验语义 · 去重两级键 · 最小回归集 | 冻结事实契约 | ★ 强度 / 极性 / 条件 / 例外**可无损表达**；★ 同主体多规则**身份不碰撞**；★ 相反极性声明**可关联** |
| **第一批** | 覆盖台账（两本 + 两项覆盖率）· 缓存键扩展 | 输入完整性可观测 + 可复现 | 关闭开关时历史产物**逐字节不变**；覆盖缺口**可追踪**；排除项**可审计** |
| **第二批** | LLM 补漏 + 三级校验 ★ **影子模式**（**不正式入库**，只测量） | 测量新抽取效果 | 记录候选 / 误抽 / 拒收 / token / 调用成本 / 重复率 / 漏检迹象 |
| **第三批** | 规则正式发布 ★ **灰度**（逐协议开放） | 把**已验证**规则按约定格式发布 | ★ **灰度门槛 7 项全部满足**（见 §10）；定义 / 规则**隔离**；身份稳定；**下游行为回归** |
| **第四批** | 文档登记与标签 · 集成验收 | 来源可追溯 | 每条新增事实有来源与证据；未核验状态**明确** |

⇒ ⇒ ★ **影子模式的作用**：**隔离新增事实对正式知识库的影响**（只产出候选与统计，不进 fact 空间）⇒ ⇒ 用实测数据决定是否灰度。
⇒ ⇒ ★ **但它不是「零运行风险」**：仍存在 **LLM 成本、构建耗时、缓存写入、资源竞争与运行失败**风险 ⇒ ⇒ 须配合 §5.3 的超时 / 重试 / 并发限制 / 重复调用检测 / 熔断保护。

⇒ ⇒ **第四批与前面无严格前置依赖**，可并行开发；其**集成验收**放在最后。

## 十、灰度门槛（**不可妥协项**）

> ★ 不以「记账两轮后再定数值」代替正确性条件 ⇒ ⇒ 以下 7 项是**第三批灰度的前置门槛**

| # | 灰度验收项 | 最低要求 |
|---|---|---|
| 1 | **规范语义** | 人工标注回归集中**不得**出现「否定反转」「条件丢失后仍入库」等严重错误 |
| 2 | **事实唯一性** | 同一证据包含的**不同规则不得被错误合并**；同主体多规则**身份不碰撞** |
| 3 | **证据归属** | 每条规则均能定位**完整、真实**的原文证据 |
| 4 | **身份唯一性 + 冲突可发现性** | ★ 同一规则槽位的**相反规范声明能够被关联并报告**；★ 不同规则**不会**因共享主体 / 条件 / 证据而被错误合并；★ 不同语义类型（**应然 / 实然**）**不会**被错误覆盖；★ 同一语义事实**允许保留多个证据来源** |
| 5 | **旧消费者兼容** | 21 个 aspect 不变，且通过消费者既有行为的回归测试 |
| 6 | **语义准确性** | 对影子输出做**人工抽样确认** ⇒ ⇒ **不以模型自评代替真实误抽率** |
| 7 | **运行安全** | 调用 / token / 耗时 / 异常 / 重试 / 成本**可观测** |

⇒ ⇒ ★ **结构性冲突的处理**：若第 5 项发现消费端确实会**结构性误处理**规则 ⇒ ⇒ **「中枢读端零改动」与「新规则正式入库」不能同时满足** ⇒ ⇒ 此时**重新评估约束**（走 §2.3 的降级路径）⇒ ⇒ **不能指望增加回归测试消除结构性冲突**。

## 十一、通用验收口径

| # | 项 | 判据 |
|---|---|---|
| 1 | ★ **兼容性** | **开关关闭时，与基线产物逐字节一致**（这是唯一硬性兼容判据） |
| 2 | ★ **开关开启后** | 既有正确事实**不得**发生**未经解释**的回归；新增事实**必须**具备可核验证据；**错误事实不得进入正式产物** |
| 3 | **回归闸** | 护栏本身：新增 **0** / 消失 **0**（★ 这是**回归闸的判据**，**不是事实条数的判据** ⇒ 两件事**分开表述**） |
| 4 | **契约稳定** | aspect 数量 = **21**（不变）＋ **消费端语义兼容检查**通过 |
| 5 | **正确性** | ★ 不得为了提高通过率**删除否定、条件、例外或规范强度** |
| 6 | **可追溯** | 新增事实能定位原文证据，并能解释其**触发来源**与**验证结果** |
| 7 | **可复现** | 缓存命中、版本指纹、解析配置**可审计**（★ 只承诺「缓存命中可复现」，不承诺「重调同模型逐字节相同」） |
| 8 | **成本观测** | §5.4 的九项**齐全** |
| 9 | **回归检查** | 原有正确事实不得无故消失；新增事实不得造成已知下游行为回归 |
| 10 | **失败隔离** | ★ 不确定候选**不得**自动简化后进入正式事实库 |

## 十二、残余风险（**明确未关闭**）

| # | 风险 | 状态 |
|---|---|---|
| 1 | **全链路原子发布 / 失败回滚** | ★ **范围外且未关闭**：抽取层只能保证「闸不通过 ⇒ 不写盘」⇒ ⇒ **不能据此宣称生产发布安全** |
| 2 | **文本→XML/AST 统一文档模型** | 阶段外：当前输入为 TXT |
| 3 | **完整 ABNF 语义**（增量 / 递归 / 重复 / 大小写） | 阶段外 ⇒ 建议：抽到 ABNF 时标注「**语法完整性未知**」（元数据） |
| 4 | **跨 RFC 引用与 IANA 注册表快照** | ★ 阶段外（**确需外部数据源与网络**）⇒ ★ 与「同 RFC 跨节引用」**已分开**（后者本轮支持定位） |
| 5 | **状态机边的守卫条件 / 动作 / 角色** | 阶段外：`target_state` 现为「目标状态名」文本 ⇒ 扩展会改 value 结构 ⇒ **需单独决策** |
| 6 | **完整 P/R/F1 语义评测** | 另立项（评测层）⇒ ★ 本轮以**最小语义回归集**替代 |
| 7 | **规范时效性** | ★ 本轮只做「文档自述状态」登记 ⇒ **不声称**「当前生效」⇒ ⇒ 时效性仍**未关闭** |
| 8 | ★ **规则与普通定义同 aspect 的结构性风险** | 本轮以「身份唯一性 + 混装隔离 + 消费端兼容检查」三道闸覆盖 ⇒ ⇒ 若核查发现结构性冲突 ⇒ ⇒ 走 §2.3 降级路径 |

## 十四、附录 · 现有能力的实测证据

> ★ 用于支撑「不需要重复建设」的判断（**实测取自真实产物**）

| 能力 | 实测证据 |
|---|---|
| **三级标识** | 真实产物里同时存在：`fact_id: f2_bdbf66e03bb70258` / `claim_id: c2_c74e34fba97a4106` / `evidence_summary: ["rfc:rtsp.field.status-line@file:rfc2326.txt#@1233"]` |
| **多声明共存** | 事实结构含 `all_claims: [...]`（多条并存）＋ `resolution` 字段 |
| **冲突消解** | resolver 的 `SOURCE_PRIORITY`（`observed 3 > normative/must 2 > descriptive 1`）＋ `resolution`（winner / reason）；★ 被覆盖的 claim **不丢弃**，记入 `superseded` |
| **`definition` 的消解语义** | ★ **走默认 `consensus`**（多源一致取其一；值不同且同优先级 ⇒ **标记 conflict 保留**）⇒ ⇒ **不会**让观察结果覆盖规范要求（`precedence` 只作用于 `existence` / `state_changing` / `target_state`） |
| **身份计算** | `fact_id = sha256(canonical_serialize(fact_key))` ⇒ ⇒ **身份完全由 `fact_key` 决定** ⇒ ⇒ 规则语义必须进入 `fact_key` 的契约字段（见 §2.2） |
| **`subject.qualifiers` 的可用性** | ★ 已有先例：`origin` / `constraint_id`；导出时**遍历不硬编码键名**；**图投影不使用** ⇒ ⇒ 放规则语义**副作用可控** |
| **取值样本 vs 封闭取值域的区分** | 已在通道 D 与下游判定中区分 ⇒ 「取值合法性」因此只能作**统计**而非判违规 |
| **缓存可复现范式** | 已有「提示版本 + 输入指纹」磁盘缓存（状态机腿 / 散文语义腿各一份） |
| **身份的序列化稳定性** | `canonical_serialize` 用 `sort_keys=True` ⇒ ⇒ `qualifiers` 的键序**确定** ⇒ ⇒ 追加规则语义键**不引入不确定性** |
| **`qualifiers` 的读端影响面** | ★ 中枢组装只对 `subject.type == "relation"`（状态机边）读 `qualifiers`（`source`/`target`/`method`）⇒ ⇒ ★ **规则类（`header`）的 `qualifiers` 读端零影响** ⇒ ⇒ 放 `action`/`object` **副作用可控** |
| **声明值的承载能力** | `Claim.value` 声明为 `Any` ⇒ ⇒ 规范内容（强度 / 极性 / 例外）放声明值**无结构限制** |
| **多声明的冲突处理** | `consensus`：多源一致取其一；★ 值不同且同优先级 ⇒ **标记 conflict 保留**（不误判）；被覆盖的声明记入 `superseded`（不丢弃）⇒ ⇒ ★ 正是「相反声明可发现」的现成机制 |
