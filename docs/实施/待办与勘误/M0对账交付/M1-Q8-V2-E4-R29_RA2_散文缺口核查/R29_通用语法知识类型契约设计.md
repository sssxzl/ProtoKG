# 通用语法知识类型契约设计

## 一、三种方案比较

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 复用 syntax | ABNF 表达式塞进 `syntax` 的 pattern | 零改动 | subject 错（header）、语义被曲解为"字段模式" |
| B 扩展 syntax 语义 | 保留 aspect 名，明确"pattern 可为产生式" | 不动 aspects | 语义仍混淆：字段模式 ≠ 文法产生式 |
| C 新增 grammar_rule | 新 aspect：`grammar_rule` / `abnf_production` | 语义准确 | 破 21 aspects 冻结 |

## 二、推荐：C 的受限版本

不新增 aspect，而是**在 syntax 下增加 `value.type="grammar"`**：

```json
{"type": "grammar", "data": {"rule": "request-line",
  "expr": "method SP request-target SP HTTP-version CRLF",
  "deps": ["method", "request-target", "HTTP-version"]}}
```

- aspects 不变（仍是 21）；
- Value.type 是既有枚举的可扩展点（需确认是否封闭）；
- 与 `pattern`/`text` 并列，不污染字段语义。

## 三、必须回答的设计点

| 点 | 建议 |
|---|---|
| rule | 产生式名，原样保留大小写 |
| expression | 原样字符串，不做规范化 |
| dependency | 由表达式中的非终结符推导，保留出现顺序 |
| syntax order | 顺序即表达式顺序，不额外建模 |
| subject | 见下一份文档（protocol_rule 类） |

## 四、对 H1/H2/H3/H5 的适配

| Gold | 能否用 grammar 表达 |
|---|---|
| H1 HTTP-message | 能 |
| H2 request-line | 能 |
| H3 field-name | 能（表达式含 forbidden 字符集） |
| H5 chunked-body | 能（含多条产生式，需一规则一 Fact） |

## 五、边界

需要先确认 `Value.type` 是否封闭枚举；若封闭，C 方案也要走契约变更。
