# R29 RA-2 最小修复候选与审批建议

## 一、候选（按是否需 LLM 排序）

### F1 触发条件：让散文通道覆盖「有产出但仍有缺口」的文档

| 项 | 内容 |
|---|---|
| 位置 | `rfc_extractor.py:4162`，`if _unmatched_files and ...` |
| 现状 | 只喂零产出文档；rfc1542 / rfc2131 这类文档永不进入 |
| 改法 | 候选条件改为「有散文类缺口线索的文档」，如「该文档存在未被任何通道命中的章节」；具体判据需设计 |
| 影响 | 14 条 Gold 首次进入通道；但会显著增加 LLM 调用量（文档数从 12 升到 36） |
| 风险 | 成本与产出质量未知；可能引入重复知识 |
| 是否需 LLM 验证 | 是 |

### F2 缓存粒度：批次级 → 文档级

| 项 | 内容 |
|---|---|
| 位置 | `prose_semantics.py:888-891`（block_hash 与 cache_key） |
| 现状 | 整批一个键，输入集合一变全失效 |
| 改法 | 按 doc 分键，或多个条目存同一文件；需定义迁移（旧条目如何识别） |
| 影响 | 新增/删除文档不再使全部缓存失效；76 条历史条目可能被复用 |
| 风险 | 缓存语义变更，需回归；不得顺手改 `complete` 含义 |
| 是否需 LLM 验证 | 否（工程可验证键稳定性），但复用效果要 LLM 才能验证 |

### F3 部分缓存消费（谨慎）

| 项 | 内容 |
|---|---|
| 位置 | `_load_cache:619` |
| 现状 | `complete=false` 一律不命中 |
| 改法 | 新增「partial」状态，允许消费但标注来源不完整 |
| 风险 | 直接把未跑完的批次当知识入库，质量不可控；**不建议** |
| 结论 | 只登记，不推荐 |

### F4 打开 smtp / rtsp 开关

| 项 | 内容 |
|---|---|
| 位置 | `profiles/smtp/rfc_config.json`、`profiles/rtsp/rfc_config.json` |
| 影响 | 影响 31 条 Gold 的可能性，但需先有 F1（否则仅零产出文档才触发） |
| 成本 | 需要 LLM 预算 |
| 建议 | 与 F1 一起评估，不单独开 |

## 二、建议路径

1. 先做 **F2**（纯工程，不动产出，可离线验证）。
2. 再做 **F1** 的判据设计与影子验证（需要 LLM 预算）。
3. **F4** 跟随 F1，不单独开闸。
4. **F3 不做**。

## 三、必须项目方决定的事

| 编号 | 决定 |
|---|---|
| R1 | 是否接受「散文通道覆盖有产出文档」带来的调用量上升（12 → 36 份） |
| R2 | LLM 预算上限（次数、token、硬停止条件） |
| R3 | 76 条历史条目的处置：人工抽检 / 丢弃 / 保留待用 |
| R4 | 是否允许改缓存粒度（F2）——涉及缓存格式，需登记为变更 |

## 四、本轮不做的
