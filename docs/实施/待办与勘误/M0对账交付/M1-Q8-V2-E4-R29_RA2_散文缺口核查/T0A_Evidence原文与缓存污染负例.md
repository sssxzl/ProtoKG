# T0-A Evidence 原文与缓存污染负例

## 一、Evidence 原文真实性（补强断言）

| 检查 | 方法 | 结果 |
|---|---|---|
| 文档存在 | `document` 含 `rfc3207.txt` 且文件在 kb 内 | PASS |
| 行号可定位 | 取 `#@` 后缀为行号，落在 1..508 | PASS |
| 引用与原文一致 | 第 80 行文本含实体 `STARTTLS` | PASS |
| 不越块边界 | 行号 80 落在块 1（1-114） | PASS |
| 缺失即不采信 | 无 `document` 或无行号 ⇒ 断言直接失败 | 逻辑内建 |

`locator` 字段仍为空，因此回溯依赖 `document` 的行号后缀。这是既有数据模型的状态，本轮未改 Schema。

## 二、缓存污染（真负例）

上一轮的负例只构造了「外层 doc 错误 + items 为空」，太弱。本轮构造：

```json
{"doc": "rfc3207.txt", "doc_sha256": "<真实>", "key": "<合法>",
 "complete": true, "items": [{"doc": "rfc4954.txt"}]}
```

外层字段全部合法，只有内部 item 指向另一份 RFC。

结果：`_load_doc_caches` 判定该文档未命中（整条拒收），不是只检查外层。

## 三、为此做的最小修正

原加载器只校验外层 `doc`/`key`/`doc_sha256`，不校验内部 item 归属。已加一行判断：任一条目 `doc` 与文件名不一致 ⇒ 整条缓存拒收。

补丁：`T0A_缓存污染拒收最小修正.patch`（13 行）。

## 四、限制

- 未构造「item 缺 doc 字段」的旧格式缓存；按现行规则会被判污染并拒收，这是有意为之（宁可重跑）。
- 未验证跨协议的缓存目录混放情形。
