# R29 RA-2 F2 旧缓存读取策略一致性验证

## 一、现行策略（本轮落实）

| 规则 | 实现 | 证据 |
|---|---|---|
| 旧 `*.prose.json` 原件保留 | 不改名、不删除 | 文件 SHA256 未变 |
| `complete=false` 绝不消费 | 文档级路径根本不读旧文件 | 删除 `_load_cache` 兜底 |
| 不自动迁移 | 无迁移代码 | 代码审查 |
| 不赋予单文档完成资格 | 不拆 76 条 | 代码审查 |
| 文档级不回退旧批次 | 全 miss 时 `cached = None` | 代码路径 |

## 二、验证

| 场景 | 期望 | 实测 |
|---|---|---|
| 旧文件 `complete=true` | 仍不被消费，且不被改写 | PASS（旧文件哈希不变、调用次数 ≥1） |
| 旧文件 `complete=false` | 不被消费、不被改写 | PASS（上一轮已测，本轮回归） |
| 生成 `.prose.d/` 后旧文件是否被覆盖 | 不覆盖 | `_save_cache` 检测目录即返回 |

## 三、为什么连 `complete=true` 也不消费

旧文件的身份是「批次」，与本轮要求的「文档 + 原始哈希 + 选块指纹」不是同一空间。若消费它，等于用一种无法逐文档证明来源的缓存，绕过新的来源约束。保守做法是：只保留原件，不参与判定。

## 四、未来的合法迁移（未实施）

若项目方希望复用历史条目，需单独提交兼容设计，至少回答：

1. 如何证明某条目只来自单个文档；
2. 如何回填该文档的原始 SHA 与选块指纹；
3. 如何标注「来自旧批次、未经验证」。

本轮不出方案，避免变成事实上的自动迁移。

## 五、结论

策略已一致：**读旧文件的地方为 0 处**，写旧文件被 `_save_cache` 拦截。76 条记录保持隔离。
