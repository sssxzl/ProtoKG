# R29 RA-2 无需 LLM 与需 LLM 问题分离清单

## 一、45 条的断层分布

| 类别 | 条数 | 协议 | 是否需要 LLM 才能判明原因 |
|---|---|---|---|
| 通道未启用（profile 关闭） | 31 | smtp 26、rtsp 5 | 否 |
| 触发条件未满足（仅处理零产出文档） | 14 | DHCPv4 rfc1542 9、rfc2131 5 | 否 |
| 缓存存在但不完整 | 0（就这 45 条而言） | — | 否 |
| 合计 | 45 | — | 0 条需要 LLM 判原因 |

一个重要的口径更正：R28-C 把 14 条记成「有缓存未被接受」，本轮查调用链后发现它们根本没进入散文通道，`complete=false` 对它们不生效。原分类保留，新分类另列。

## 二、无需 LLM 就能做的事

| 事项 | 说明 |
|---|---|
| 打开 smtp/rtsp 的开关并复跑 | 会触发 LLM，因此「改配置」本身不需 LLM，但「验证」需要 |
| 让散文通道覆盖「有产出但仍有缺口」的文档 | 纯代码改动（触发条件），验证仍需要 LLM |
| 缓存改为文档级键 | 纯工程改动；可离线验证键的稳定性 |
| 人工抽检 76 条历史条目 | 不需要 LLM，但需要人 |
| 判断 `complete=false` 的历史原因 | 无日志，结论只能到「批次未完成」 |

## 三、必须 LLM 才能推进的部分

| 事项 | 理由 | 规模 |
|---|---|---|
| 补齐 12 份零产出文档的散文知识 | 唯一入口是 LLM；缓存不可用 | 约 7 次批量调用（沿用 R27C 估算） |
| 验证「打开开关后 smtp/rtsp 是否有散文知识」 | 需要真实调用才知道 | 取决于 smtp 4 份 + rtsp 1 份文档 |
| 判断 76 条历史条目质量 | 条目是 LLM 产出，需对照原文；可人工做，也可再调用对比 | 人工优先 |

## 四、结论

**45 条缺口的「原因」全部不需要 LLM 就能确定**（配置与触发条件），需要 LLM 的是「补齐内容」和「验证开关效果」这两件下游工作。

因此可以先把工程侧（触发条件、缓存粒度）改对，再一次性申请 LLM 预算，而不是现在就调用。
