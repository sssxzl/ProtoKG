# R29 RA-2 F2 定点核验与冻结

## 一、F2-A 跨批次完成状态

原实现 `_doc_ok[_d] = bool(ok)` 会让后一个成功批次覆盖先前失败。已改为「与」运算 + `_doc_seen` 记录实际处理的文档：

```python
_doc_seen.add(_d)
_doc_ok[_d] = _doc_ok[_d] and bool(ok)
```

| 用例 | 结果 |
|---|---|
| 两批均成功 ⇒ complete | PASS |
| 先失败后成功 ⇒ 不得标成功 | PASS |
| 先成功后失败 ⇒ 不得标成功 | PASS |
| A 部分失败 ⇒ 不缓存 A，但缓存 B | PASS |
| 各批成功且结果为空 ⇒ success_empty | PASS |

## 二、F2-B 来源身份拒收

原实现中，冲突后 `has_src=False`，但后续块若带 SHA 会让 `has_src` 重新变真——即「被后续块恢复」。已改为粘性 `conflict` 标记：

```python
if m.get("conflict"): continue
```

| 用例 | 结果 |
|---|---|
| SHA-A/B/A 冲突 ⇒ 来源不可用 | PASS |
| 部分块缺 SHA ⇒ 粘性不可用 | PASS |
| 来源一致 ⇒ 可用 | PASS |
| 来源缺失 ⇒ 不写缓存 | PASS |
| 缓存内 items 的 doc 与文件名一致 | PASS |

## 三、测试暴露的一个测试侧错误（记录）

首版测试给同一文档的不同块写了「块文本哈希」当 `src_sha256`，导致被正确判为来源冲突、全部用例失败。真实块携带的是**文件级** SHA。修正测试后 10/10 通过。实现无需为此改动——但它说明：来源字段必须由构建方统一提供，不能靠块内容猜。
