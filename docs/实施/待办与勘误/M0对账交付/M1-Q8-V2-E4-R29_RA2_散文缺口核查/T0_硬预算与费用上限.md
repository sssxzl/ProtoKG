# T0 硬预算与费用上限

## 一、参数（待项目方确认后冻结）

| 参数 | 值 | 说明 |
|---|---|---|
| 最大真实请求数 | 2 | 不自动重试 |
| 单次输出上限 | 2 000 token | `max_tokens` |
| 累计输入阈值 | 21 317 token | 每次调用前检查剩余额度 |
| 模型 | deepseek-flash | 与现有缓存 manifest 一致 |
| Prompt | prose-semantics-v2 | 不改内容 |
| 温度 | 0.1 | 与 cache_key 一致 |
| 货币上限 | **未确定** | 项目方未给单价 ⇒ 视为阻断项 |

## 二、规模实测（替代此前估算）

| 项 | 数值 |
|---|---|
| 文档 | rfc3207（6 块）、rfc4954（13 块） |
| 块数 | 19 |
| 字符 | 62 155 |
| 输入 token 估算 | 17 759（3.5 字符/token） |
| 输出上上限 | 4 000（2 次 ×2 000） |

## 三、与 2 次请求的冲突

默认每批 5 块 ⇒ 需要 ⌈19/5⌉ = 4 次调用，**超过 2 次上限**。两条出路：

| 方案 | 块 | 调用 | 输入 token | 说明 |
|---|---|---|---|---|
| T0-A 只跑 rfc3207 | 6 | 2（批 5+1） | 5 335 | 最省，仍可观察 2 条 Gold |
| T0-B 两份全跑 | 19 | 2（批 10+9） | 17 759 | 需把 `PROSE_BATCH_BLOCKS` 设为 10 |

建议先 T0-A：2 次调用、5.3k token，风险最低；T0-B 作为第二步。

## 四、调用前额度检查

每次调用前比较「已用输入 token + 本次预估」与 21 317：

```
if used + est > 21317: 停止并记录 stop_reason=budget_exhausted
```

预估方式：本批块字符合计 ÷3.5。

## 五、停止条件

1. 单文档失败重试 2 次即放弃该文档；
2. 累计失败 3 次停止整批；
3. 额度检查失败即停；
4. 输出连续 2 次为空即停并报「疑似模型不可用」；
5. 缓存写入异常即停（不静默降级）。

## 六、费用

仓库内没有任何单价信息。费用 = 输入 token × 输入单价 + 输出 token × 输出单价，**单价必须由项目方确认并写入审批单**，否则本项视为阻断（按任务要求：无法确认的计费信息即阻断）。

## 七、结论

除货币上限外，其余参数均可冻结；一旦项目方给出单价与上限，T0-A 即可执行。
