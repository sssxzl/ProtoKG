# R29 RA-2 F2 文档级缓存身份及完成状态设计

## 一、文件布局

```
derived/cache/source_blocks/
  <proto>.prose.json          ← 旧批次缓存：只读，不写，不消费（76 条历史记录留在此处）
  <proto>.prose.d/            ← 新：文档级缓存目录
      <doc>.json              ← 每份 RFC 一个文件
      <doc>.json.tmp          ← 写入中间态，不作缓存
```

旧文件保留原位，影子实现里 `_save_cache()` 一旦发现同协议已有 `.prose.d/` 目录就直接返回，避免覆盖历史。

## 二、单条缓存的身份字段

| 字段 | 内容 | 作用 |
|---|---|---|
| `schema` | `prose-cache-doc-v1` | 格式版本，旧格式自然不命中 |
| `doc` | RFC 文件名 | 命名与回溯 |
| `doc_sha256` | 原文 SHA256 | 内容版本，改一个字即失效 |
| `key` | `cache_key(prompt_version, sha256(doc+text), temperature, max_tokens, prompt_digest, parser_version, schema_version)` | 组合身份 |
| `complete` | 仅当该文档本次完整产出才为 true | 完成状态 |
| `status` | `success_nonempty` / `success_empty` | 区分「抽到空」与「没跑」 |
| `items` | 该文档的条目 | 来源可回溯 |

设计取舍：

- **不把文件名当身份**，只用它做命名；身份由 `key` 决定，`doc` 与 `doc_sha256` 双写便于人工核对。
- **不用时间戳/随机数**，保证同输入同键。
- **不把批次写进身份**，批次只是运行方式，不是知识来源。

## 三、完成状态机

| 状态 | 含义 | 是否可消费 |
|---|---|---|
| 文件不存在 | 未开始 | 否 |
| 存在 `.tmp` | 写入中断 | 否 |
| `complete=false` | 失败/中断 | 否 |
| `complete=true` + `success_empty` | 跑完但无知识 | 是（负结果可信） |
| `complete=true` + `success_nonempty` | 正常 | 是 |
| key 不匹配 | 输入或配置变了 | 否 |

旧批次的 `complete=false` 不拆分、不猜文档级完成状态；76 条记录维持不可消费。

## 四、失效规则

| 变化 | 失效范围 |
|---|---|
| 某份 RFC 原文变更 | 仅该文档 |
| 换 prompt 版本或内容 | 全部 |
| 换模型 | 全部 |
| 换 parser/schema 版本 | 全部 |
| 输入顺序变化 | 无影响 |
| 新增/删除其他文档 | 无影响 |

## 五、与正式契约的关系

缓存命名空间只存在于抽取侧（`derived/cache/`），不参与 NormID、FactID、EvidenceID 计算，也不进中枢。因此不触碰冻结契约。

## 六、已知限制

1. 批内部分命中时，仍会为未命中文档单独发起调用；这是「按文档补抽」，不是「按块补抽」。
2. `success_empty` 允许缓存负结果，但只在同一 key 下成立；换 prompt 会重跑。
3. 未做并发写保护（单进程假设），并发运行同一协议可能竞争同一文件。
