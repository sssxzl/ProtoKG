# 协议字段与语法主体建模方案

## 一、问题

现在所有结构性知识都被标成 `header`：

- DHCP 的 `siaddr` 是消息字段，不是邮件头；
- HTTP 的 `request-line` 是报文起始行，不是字段；
- ABNF 产生式是语法对象，不是任何实体。

## 二、候选类型

| 类型 | 适用 | 现状 |
|---|---|---|
| `header` | 邮件头字段 | 已存在 |
| `field` | 协议消息字段（siaddr、hlen） | **需新增** |
| `start_line` | 请求行/状态行 | **需新增** |
| `grammar_rule` | ABNF 产生式 | **需新增** |
| `bitfield` | flags 保留位等 | **需新增** |

## 三、对身份的影响

`Subject.type` 参与 FactID 计算。新增类型 ⇒ 新 FactID，**但与既有知识不冲突**（既有知识仍用 header/method/state 等旧类型，id 不变）。

风险在于：如果把既有 `header` 知识迁移到 `field`，历史 FactID 会变。所以建议：

- 新知识用新类型；
- 历史不动；
- 不做批量迁移。

## 四、最小方案

只新增两个类型：`field`、`grammar_rule`。`start_line` 与 `bitfield` 暂用 `field` + aspect 区分，避免一次扩太多。

## 五、影响

| 项 | 影响 |
|---|---|
| FactID | 新知识新 id；旧知识不变 |
| Hub 实体 | 会多出 `dhcpv4:field:siaddr` 之类实体，属新增 |
| 检索 | 需按 type 过滤时更新查询 |
