# T0 Gold 原文跨度核查

## 一、三条 Gold

| Gold ID | 文档 | 跨度 | 原文行（首 80 字） |
|---|---|---|---|
| GK-B-smtp-rfc3207.txt-404-1 | rfc3207 | 404 | 见 `t0_preflight.json` 的 `gold[].line_text` |
| GK-B-smtp-rfc3207.txt-405-1 | rfc3207 | 405 | 同上 |
| GK-B-smtp-rfc4954.txt-704-1 | rfc4954 | 704-708 | `auth-param = "AUTH=" xtext` |

## 二、与块的关系

三条均落在首块（起始行 1），因为两份文档的 ABNF/规范段都在前部，首块 3500 字符即覆盖。

这意味着：即使 T0 只跑首块，也能观察这 3 条是否命中；但只跑首块会漏掉文档其余部分，故 T0 仍建议切满。

## 三、核查方式

脚本用原始文件的 `split("\n")` 行号（与 `documents.json`、Gold 一致），逐条确认：

1. 文件存在、SHA256 与 R25 清单一致（R28-C 已核 121/121）；
2. 跨度可在原文重建；
3. 跨度落在某个候选块内。

## 四、命中判定口径（预先冻结）

| 结果 | 判据 |
|---|---|
| 命中 | 产出条目的 doc 与跨度所在块一致，且其 evidence span 与 Gold 跨度重叠 |
| 部分命中 | 跨度量级正确但语义只覆盖半句（需人工看） |
| 未命中 | 无对应条目 |
| 不计入 | 条目存在但 doc 不符（跨文档串号，属缺陷） |

本口径只用于观察，3 条不构成统计指标，也不能当作泛化证据。
