# R28-C R29 定点修复候选清单

## 一、原则

只登记有本轮证据支撑的候选，不重新设计系统。每条含证据、建议范围、前置条件、风险。R29 正式立项前不执行任何一条。

## 二、候选清单

### RA-1 syntax 类知识缺口（最高优先级）

| 项 | 内容 |
|---|---|
| 证据 | `protocol_syntax` 33 条可比、33 条缺口；其中 32 条所在文档**有** Norm（非零产出），说明文档被解析与抽取了，但这 32 条命题所在跨度无候选 |
| 典型 | rfc1542 的「报头按八位组顺序传输」「位图按 1..6 编号」两条，同跨度无任何 Norm |
| 判断 | 确定性通道当前只产出结构条目（字段/布局/方法），不产出「传输顺序/位序规则」这类语法描述 |
| 建议范围 | 先做零成本核查：这 32 条跨度是否落在 Chunk 内（读分块结果），再决定是「扩通道」还是「改分块」 |
| 前置 | 分块级日志或可复算 chunk 划分 |
| 风险 | 容易变成「为这 32 条写特例」，需先定义通用判据 |

### RA-2 散文通道与缓存（R29-C 主体）

| 项 | 内容 |
|---|---|
| 证据 | `normative_rule_candidate` 32 条、`protocol_descriptive_semantics` 33 条全部缺口；散文通道默认关闭；`DHCPv4.prose.json` 有 76 条但 `complete=false` 被判不命中 |
| 判断 | 这类知识本就不该由确定性通道产出，缺口属通道可用性问题，不是抽取算法缺陷 |
| 建议范围 | 先做「接受部分缓存」的可行性评估（不改代码），再决定是否申请 LLM 预算补齐 12 份 |
| 前置 | 缓存语义变更设计 或 LLM 预算审批 |
| 风险 | 把 `complete=false` 直接改成 true 会污染知识质量，禁止 |

### RA-3 零产出文档（28 条 Gold 落点）

| 项 | 内容 |
|---|---|
| 证据 | 28 条 Gold 落在零 Norm 文档；与 R27C 的 12 份零产出文档一致 |
| 判断 | 与 RA-2 高度重叠，应合并归因，不单独立项 |
| 建议范围 | 并入 RA-2 的逐文档归因 |
| 前置 | 同 RA-2 |

### RA-4 Evidence 支持（R29-B）

| 项 | 内容 |
|---|---|
| 证据 | 3 条 partial 的 Evidence 均不支持命题；91 条大偏移中 46 条落在章节标题 |
| 判断 | 当前是「行内有 token」级别，不是「句级支持」 |
| 建议范围 | 只处理与 Gold 有直接重合的少数条目，不扩大成人工复审 |
| 前置 | 需要少量人工判定（S3） |
| 风险 | 与 C-4 定位精修耦合，C-4 仍冻结 |

### RA-5 C-3 行号基准（延续）

| 项 | 内容 |
|---|---|
| 证据 | DHCPv4 曾有 5 条因 `splitlines`/`split` 不一致被误判目录行 |
| 判断 | 修复已存在但未合入；缺跨平台证据（CI 已无 Ubuntu） |
| 建议范围 | 先补一条按行切分基准的单元测试，再决定是否在无 Ubuntu 的情况下合入 |
| 前置 | 项目方接受「仅 Windows 验证」 |

## 三、不建议进入 R29 的项

| 项 | 原因 |
|---|---|
| 类型判别准确率修复 | 无当前身份的 Gold，改了也无法验证 |
| 字段保全修复 | R19 不可比，看不到基线 |
| 文档级召回补强 | 属输入范围问题，不是修复 |

## 四、排序建议

1. RA-1（零成本核查先行）
2. RA-2 + RA-3（合并，需预算或设计决策）
3. RA-5（小改动，但缺验证平台）
4. RA-4（依赖人工样本）

## 五、与 R28-D 的关系

RA-1 的第一步行不需要新人工；RA-4 需要 S3 的 20 条判定。可以先做 RA-1，再决定是否补人工。
