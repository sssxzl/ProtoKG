# R28 标注规范（试点版）

## 一、评审员看到什么、看不到什么

看到：RFC 原文（指定文件与行号范围）、系统产出的 Norm 列表（名称、kind、内容、source）。

看不到：系统内部判定过程、抽取器代码、其他评审员的结论。

不得查阅 R13/R19 的既有标注来「对齐答案」——那是独立性问题，须在评审记录里声明未接触。

## 二、五个维度的判据

### D1 原文知识识别完整性（按文档）

不看系统产出，先在原文上标出「该文档声明了哪些规范义务」，形成人工清单；再与系统产出对账。

判据：只要原文用 MUST / MUST NOT / SHALL / SHOULD / SHOULD NOT / REQUIRED / MAY 对实现方提出要求，就计入清单。纯描述性说明不计。

### D2 抽取准确性（按 Norm）

逐条判断：该条知识是否真实存在于原文、表述是否被曲解。

- 正确：语义与原文一致，允许措辞压缩。
- 部分正确：主体或取值正确，但条件/限定被丢掉。
- 错误：原文没有该要求，或语义相反。

### D3 类型判别（按 Norm）

按 kind 判定：method / field / field_value / transition / outcome / option_layout / binary_layout / state / required_header_*。

判据以「该知识在协议里扮演的角色」为准，不看字段名是否像。

### D4 语义保全（按 Fact）

四项逐一比对：

| 项 | 含义 | 反例 |
|---|---|---|
| strength | MUST/SHOULD/MAY 的强度 | 原文 SHOULD 被记成 MUST |
| polarity | 肯定/否定 | MUST NOT 被记成 MUST |
| condition | 生效条件 | 丢掉「if the server supports X」 |
| exception | 例外 | 丢掉「except when ...」 |

任一项丢失即记「不完整」，并在备注写明丢了哪项。

### D5 证据正确性（按 Evidence）

- 行号是否落在**支撑该命题的句子**上；
- 引用片段是否足以独立支撑该命题（不能只引到标题或半个从句）；
- 若同一行承载多条知识，允许共用行，但要确认该行确实同时支持这几条。

注意：**「行内有该名称」不等于「该行支持该命题」**。章节标题、目录、示例都属于高风险落点。

## 三、评分与分歧

- 每条记录：`正确 / 部分正确 / 错误` 三档，不用 1–5 分，避免尺度漂移。
- 两名评审员独立完成后比对：不一致的条目进入仲裁，由第三人裁。
- 记录一致性：对 D2/D3/D5 计算 Cohen's kappa；D1 是清单对账，用「双方清单的交集/并集」报告。

## 四、材料与命名

| 材料 | 文件 |
|---|---|
| 60 条抽样 | `R28_试点抽样_60条Norm.csv` |
| 6 份 RFC 清点 | `R28_RFC清点包_6份.csv` |
| 标注模板 | 上述 CSV 的空列（人工_* 前缀） |

填写约定：`正确` / `partial` / `wrong` / `unclear`；`unclear` 必须写理由。空白表示未评，不得默认算作正确。

## 五、禁止事项

1. 不得用系统产出反推「原文应该有这条」。
2. 不得因为 CI 绿色、Norm 数量对上就跳过阅读原文。
3. 不得把 91 条大偏移诊断集混入随机样本统计。
4. 不得在评审过程中修改抽取器或重跑抽取。
