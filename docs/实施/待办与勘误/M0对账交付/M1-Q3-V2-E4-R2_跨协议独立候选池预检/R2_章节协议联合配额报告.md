# R2 跨协议来源与容量报告

## 一、已验证事实

库内 42 份 RFC 的元数据从原文自带头部提取，零网络请求，可由 `guard/_out/_n1c_v2/r2/inventory.py` 复算。跨协议三协议共 6 份：

| 协议 | 文档 | RFC 号 | 正式标题 | Category | Obsoletes | Updates | 总行数 | 历史窗口覆盖 | 尚未暴露 |
|---|---|---|---|---|---|---|---:|---:|---:|
| rtsp | rfc2326.txt | 2326 | Real Time Streaming Protocol (RTSP) | Standards Track | 无 | 无 | 5156 | 703 | 4453 (86.4%) |
| sip | rfc3261.txt | 3261 | SIP: Session Initiation Protocol | Standards Track | 2543 | 无 | 15068 | 634 | 14434 (95.8%) |
| smtp | rfc3207.txt | 3207 | SMTP Service Extension for Secure SMTP over Transport Layer Security | Standards Track | 2487 | 无 | 508 | 155 | 353 (69.5%) |
| smtp | rfc4954.txt | 4954 | SMTP Service Extension for Authentication | Standards Track | 2554 | 3463 | 1124 | 132 | 992 (88.3%) |
| smtp | rfc5321.txt | 5321 | Simple Mail Transfer Protocol | Standards Track | 2821 | 1123 | 5324 | 191 | 5133 (96.4%) |
| smtp | rfc5322.txt | 5322 | Internet Message Format | Standards Track | 2822 | 4021 | 3196 | 149 | 3047 (95.3%) |

每份文档均登记了 source_sha256、字节数与行数映射，满足可复算要求。

## 二、独立性判定

三层隔离的实际归属：

| 层 | 集合 | 与库内跨协议 6 份的关系 |
|---|---|---|
| A 开发集 | N1-B、N1-C、V2 六轮调优 | 6 份全部落入 |
| B 历史独立 | H1 156 条、H2 52 条、H3 23 条、队列 B 54 片段 | 6 份全部落入 |
| C 新跨协议测试集 | 拟新增 RFC | 库内为 0 |

## 三、推论

1. 库内 SIP、RTSP、SMTP 全部 6 份不能作为 C 类来源，文档级独立数为 0。
2. 尚未暴露行数占比在 69.5% 到 96.4% 之间，行覆盖本身不构成容量瓶颈，瓶颈是独立性。
3. 若改为区段级隔离，可获得块容量，但独立性等级降级，不能声明文档级泛化。按用户要求，此降级须单独标记并另行审批。

## 四、限制

1. `Category`、`Obsoletes`、`Updates` 取自原文头部左对齐段。RFC Editor 的 info 页包含同一信息，本次未联网取证，两者若不一致以 info 页为准。
2. RFC 状态（是否被更新或取代）依据原文的 `Obsoletes` 与 `Updates` 字段判断，不覆盖后续的更新 RFC 列表。
3. 尚未暴露行数按历史 chunk 行覆盖计算，与实际抽取尝试记录无绑定关系。
