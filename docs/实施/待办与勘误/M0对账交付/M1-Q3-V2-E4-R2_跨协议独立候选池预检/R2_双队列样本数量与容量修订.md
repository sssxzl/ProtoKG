# R2 双队列样本数量与容量修订

## 一、已验证事实

队列 B 的冻结状态（本轮只读核对，未重新计算）：

| 项 | 数值 | 来源 |
|---|---|---|
| RFC 片段数 | 54 | `B1_人工真值冻结清单.jsonl` |
| valid_gold | 121 | 同上 |
| no_target_knowledge | 9 | 同上 |
| uncertain | 0 | 同上 |
| unresolved | 0 | 同上 |

队列 B 与 H1/H2/H3 的来源交集（`guard/_out/_n1c_v2/r1/r1_verification.json`）：

| 比较 | 文档交集数 | 判定 |
|---|---:|---|
| H1 与队列 B | 11 | 可比较 |
| H2 与队列 B | 0 | not_comparable |
| H3 与队列 B | 0 | not_comparable |

## 二、本轮新增的勘误：文档交集不等于原文已被处理

按用户要求逐片段核验 `source_sha256 -> chunk_id -> input_span -> actual_extraction_attempt -> candidate_output`：

| processing_status | 片段数 |
|---|---:|
| never_processed | 51 |
| processed_with_candidate | 3 |
| processed_without_candidate | 0 |

抽取窗口覆盖率 = 0.0556（3/54）。

证据：`guard/_out/_n1c_v2/r2/r2_queue_b_coverage.json` 的 `per_snippet`，逐条给出命中的 chunk_id、chunk 行范围与 chunk 内候选数。窗口范围来自 `M1-Q2证据冻结/frozen_blocks.jsonl` 的 `chunk_start` 与 `chunk_text` 行数。

## 三、推论

1. 11 份文档级交集不能证明这 54 个片段已被抽取。实际仅 3 个片段落在有候选产出的历史 chunk 内。
2. 51 个片段从未进入历史抽取窗口，属于输入覆盖缺口，不属于 LLM 未成功抽取。
3. 因此不得对 H1 计算这 54 个片段上的 LLM 知识召回率。队列 B 的可用结论范围是源头漏抽与输入覆盖缺口分析。

## 四、限制

1. `processing_status` 的判定依赖 `frozen_blocks.jsonl` 记录的 chunk 行覆盖范围。若历史运行实际处理过范围外的行（无记录），本核验无法发现，此时状态应为 `processing_status_unavailable` 而非 `never_processed`。现有证据不足以区分这两种情形。
2. 3 个 `processed_with_candidate` 片段尚未做 Gold 与候选的语义匹配，因此其条件召回率尚未计算。

## 五、下一步

1. 执行队列 B 匹配时，按 `never_processed` 与 `processed` 两组分别报告覆盖率与条件召回率。
2. 对 3 个 processed 片段单独核对：LLM 产出候选但人工判为无目标知识，属非目标知识误入规则通道的样本。

## 六、跨协议容量修订

| 协议 | 库内 RFC | 文档级独立 | 未暴露行 | 可选块容量 | 预计候选容量 |
|---|---:|---:|---:|---:|---:|
| sip | 1 | 0 | 14434 | 0 | 0 |
| rtsp | 1 | 0 | 4453 | 0 | 0 |
| smtp | 4 | 0 | 9525 | 0 | 0 |

三个协议的文档级独立数均为 0，原因是库内 SIP 1 份、RTSP 1 份、SMTP 4 份全部已参与既有集合（详见 `R2_跨协议RFC来源清单.xlsx` 与 `R2_独立性与泄漏排除台账.xlsx`）。

结论：跨协议独立候选池在现有 RFC 库内无法建立，必须引入新文档。这是本轮最重要的约束，直接决定后续所有容量数字。
