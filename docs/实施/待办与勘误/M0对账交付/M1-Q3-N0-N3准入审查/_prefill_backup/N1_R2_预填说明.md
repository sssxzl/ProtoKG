## 三、本次采用的判定口径（5 条，供人工复核时对照）

1. **规范义务 = 对协议实体行为的约束**（义务 / 禁止 / 许可），不是「谁是什么、为什么这么设计」。
   定义句、示例、状态码与 ABNF 枚举、章节标题、IPR 与致谢样板、历史沿革叙述 → `valid_rejection`。
2. **无 2119 关键词不等于无义务**：`has to be issued`、`is optional at the discretion of`、
   `If…, that server silently discards…` 这类「条件→行为」规则句按语义判为 MUST / MAY。
3. **字段缺失 ≠ 义务不存在**：主体为空、漏 condition、极性推导错，判 `valid_confirmed`
   但 `evidence_support=partially_supported`；**字段写错**（与原文不符）才判 `valid_rejection`。
4. **极性单独判**：`SHOULD NOT / MUST NOT` 一律 `polarity=negative`，不因 strength 是 SHOULD/MUST
   就推导为 positive。
5. **evidence_support 与 truth_label 一一配套**：confirmed → supported / partially_supported；
   rejection → contradicted（或 evidence_insufficient）；pending → evidence_insufficient。

## 五、顺带发现的两个数据/脚本问题（与本次标注无关，但会影响统计口径）

1. **`n1_汇总脚本.py` 的「原文支持率」恒为 0.0**：`field_support()` 里 `_supported = 0` 之后
   从未累加，`_pct(_supported, _nonempty)` 恒返回 `0.0`。本次运行可见每个字段都是
   `"★ ★ 原文支持率": 0.0`。该列在修好前不可作为证据引用。
2. **极性是机械推导的**：候选 CSV 头就写明 `polarity（LLM 候选，★ 原始无此字段）`，
   `推导 polarity` 由 strength 单值映射，`SHOULD NOT` 会被推成 `positive`（见
   `rfc5321.txt@5226#1`）。若要保留极性维度，应在抽取阶段单独判定否定词，而不是从 strength 推导。
3. **抽取阶段几乎没做条件/例外抽取**：50 条候选的 `condition`、`exception` **全部为空**，
   而 24 条 confirmed 里有 12 条原文带明确条件（When/If/Unless/For any…）。这是当前
   语义抽取最系统性的缺口，比「抽多抽少」更值得优先修。

## 七、人工复核建议

1. 先用 `N1_R2_预填对照表.md` 通读 50 条（约 10 分钟），标出你**第一反应**与预填不一致的条目，
   不要先看 A 的 review_note 详细理由，避免被锚定。
2. 再对不一致条目**只读 RFC 原文**独立判定，填入该表最后一列。
3. 最后才回看 `★ A:review_note` 逐条比对依据，把你的结论写进 `N1_盲审标注表_A.csv`
   （或另存 `N1_人工标注表.csv`，不要覆盖预填件，保留审计痕迹）。
4. 双方分歧处走 `N1_仲裁表.csv`，仲裁后才是可用于质量率的真值。
