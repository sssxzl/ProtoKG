## 四、★ 4 次 JSON 失败的具体归因

**结论：★ 原始记录已不可恢复 ⇒ 只能给出机制性归因 + 当前可复现的等价证据。**

| 项 | 说明 |
|---|---|
| 为何不可恢复 | 那 4 次发生在 **2026-11-15 02:11 的一次临时 dump 脚本**里（`guard/_out/_dump_norms_I.py`），★ **该脚本未启用本轮新增的诊断器** ⇒ ⇒ 当时**只有 stderr**，**无结构化记录** |
| 当时的 stderr | `[通道I] LLM 调用失败（第 1 次，JSONDecodeError: Expecting value: line 1 column 1 (char 0)）`（共 4 次：第 1 次 ×3、第 2 次 ×1） |
| **机制性归因** | `core/llm.py` 的 `_safe_json_parse` 对**空字符串**必抛 `JSONDecodeError("Expecting value: line 1 column 1")`（`json.loads("")`）⇒ ⇒ 与实测报错**完全吻合**<br>⇒ 空输出的**已知成因**（`core/llm.py:303` 注释的实测）：★ **推理模型 `deepseek-flash` 的 `reasoning_tokens` 先吃光 `max_tokens`** ⇒ `finish_reason="length"` ⇒ 正式输出为空串 ⇒ JSON 解析必失败 |

| 当前可复现性 | ★ **本轮真实运行未复现 JSON 失败**（`finish_reason="stop"`，解析成功）⇒ ⇒ **4 次失败的具体触发条件尚未确证**；机制推断见上，**需后续运行中出现同类失败时由诊断记录直接判定** |

## 五、★ 38 与 176 两批运行的配置差异

| 项 | 38 条那批 | 176 条那批 | 判定 |
|---|---|---|---|
| 入口 | 通道 I（按文档） | 通道 I（按文档） | 相同 |
| `_MAX_TOKENS` | 16000 | 16000 | 相同 |
| `temperature` | 0.1 | 0.1 | 相同 |
| 模型 | `deepseek-flash` | `deepseek-flash`（缓存 key 里记的是 `deepseek-chat`） | ★ **不一致**（缓存 manifest 记录的 model 与当前 env 不同） |
| 块切分 | `_collect_blocks`（按文档） | 同 | 相同 |
| LLM 调用 | **4 次 JSON 解析失败** | 无失败记录 | ★ **差异点 1** |
| **缓存状态** | ★ **缓存里 items=0 且 `complete=True`** ⇒ ⇒ `_load_cache` **仍判为命中** | items=176 | ★★ **差异点 2（关键）** |

### ★★ 差异点 2 的机制（★ 本轮实测确认）

`core/fused/extraction/prose_semantics.py::_load_cache` 的命中条件：

```python
if not isinstance(d, dict) or d.get("block_hash") != block_hash: return None
if d.get("complete") is False: return None      # ★ 只认 complete != False
```

⇒ ⇒ **「跑完但产出 0 条」会被写成 `complete=True` + `items=[]`** ⇒ ⇒
**后续运行永远命中这个空缓存 ⇒ ⇒ 永不重跑 ⇒ ⇒ 产出骤降且不自愈**
⇒ ⇒ ★ **这可解释「38 vs 176」的骤降**（一次失败/全拒的运行把空结果固化进缓存）。

★ **本轮不改缓存策略**（约束③）⇒ ⇒ 只记录 ⇒ ⇒ **列为 M1 待查项**。
