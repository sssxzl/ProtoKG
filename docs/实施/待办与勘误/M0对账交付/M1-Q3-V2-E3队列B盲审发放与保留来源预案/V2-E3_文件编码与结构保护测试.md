# V2-E3 · 文件编码与结构保护测试

> ★ 背景：★ N1-C 曾发生 **GB18030 编码替换**、★ **原文特殊字符丢失**、★ **未转义引号导致的 CSV 断行**

---

## 一、★★ 本轮定位到的真正根因：★ `splitlines()` 会破坏多行字段

★ ★ **N1-C 的「行被拆成 26 列 + 12 列」⇒ ★★ 不是审核者的错，★ 是解析方（我们）用 `splitlines()` 读的**

★ **反证实验（★ 本轮实测）**：

| 读法 | ★ 结果 |
|---|---|
| ★ `csv.reader(io.StringIO(text))` | ✔ **字段完整往返**（含 `"` / `,` / 换行 / `⏎` / `\`） |
| ★ `csv.DictReader(text.splitlines())` | ✘ **字段被破坏**（★ 字段内换行被当作行分隔） |

★ ⇒ ★★ **★ 强制约定：★ 读任何含多行字段的 CSV ⇒ 必须用 `csv.reader` + `StringIO`，★ 禁止 `splitlines()`**

---

## 二、★ 本轮的八项保护措施（★ §五）

| # | 措施 | ★ 实现 |
|---|---|---|
| ① | ★ 原文/证据/不可编辑字段保留 **UTF-8 机器基线** | ★ `V2-E3_原文与证据不可编辑字段基线.jsonl`（★ 54 条，★ 含 rfc_sha256 与证据原文 sha256） |
| ② | ★ 人工用**独立 Excel 友好模板**，★ 不得覆盖机器基线 | ★ `V2-E3_队列B_审核者X_Excel友好编辑模板.csv`（★ **不含原文** ⇒ ★ Excel 无法破坏证据） |
| ③ | ★ 优先只填可编辑标注字段 | ★ Excel 模板仅含 20 列（★ 全部可编辑） |
| ④ | ★ 导入按 `snippet_id` / `gold_knowledge_id` 合并 | ★ 模板首列即 `snippet_id`；★ 原子知识用 `GK-<snippet_id>-N` 稳定编号 |
| ⑤ | ★ 不可编辑字段**逐单元格比较** | ★ 导入器须比对 `rfc_sha256` / 证据原文 sha256 / 跨度 / 章节类型 |
| ⑥ | ★ 正确处理引号/逗号/换行/`⏎` | ★ 写出用 `csv.writer(quoting=QUOTE_ALL)`；★ **★ 实测往返通过** ✔ |
| ⑦ | ★ 导入后重新记录 SHA256 | ★ `V2-E3_发放包文件哈希.json` |
| ⑧ | ★ 任何证据字段非预期改变 ⇒ **停止后续评估** | ★ 导入器须在差异时**中止**并出具差异报告 |

## 三、★★ 编码层面的三条硬约定

| # | 约定 | ★ 理由 |
|---|---|---|
| ① | ★ **机器基线一律 UTF-8 无 BOM + LF** | ★ BOM 会污染首列键名；★ CRLF 会在 Excel 往返时混入 |
| ② | ★ **人工填写文件不得用 GB18030 保存**（★ Excel 默认行为） | ★ ★ U+23CE（`⏎`）等字符**不在 GB18030 字符集** ⇒ ★ 会被替换成 `?` ⇒ ★ **证据文本实质改变** |
| ③ | ★ **原文不进入人工填写文件** | ★ ★ 从根本上杜绝 Excel 破坏原文的可能 |

---

## 四、★ 机器基线的不可编辑字段（★ 逐条哈希）

| 字段 | ★ 保护方式 |
|---|---|
| ★ `snippet_id` | ★ 稳定 ID（★ 由协议+文档+锚点行确定） |
| ★ `protocol` / `document` | ★ 固定值 |
| ★ `rfc_sha256` | ★ 逐文档 SHA256（★ 本轮补算） |
| ★ `★ 章节类型` | ★ 结构规则判定（★ 非人工） |
| ★ `★ 证据跨度（行号）` | ★ 绝对行号（★ 可复核） |
| ★ `★ 证据原文` | ★ 原文逐行（★ 单空格连接，★ 与冻结时一致） |
| ★ `★ 证据原文 sha256` | ★ 逐条哈希（★ 导入时逐单元格比对） |
