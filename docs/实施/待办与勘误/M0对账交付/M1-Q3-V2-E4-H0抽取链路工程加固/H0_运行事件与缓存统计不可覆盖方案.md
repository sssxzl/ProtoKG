## 一、★ 三个概念的分离

| 概念 | ★ 计入请求数 | ★ 计入 token | ★ 计入费用 |
|---|:---:|:---:|:---:|
| ★ `actual_llm_request` | ✔ | ✔ | ✔ |
| ★ `cache_hit` | ✘ | ✘ | ✘ |
| ★ `local_replay` | ✘ | ✘ | ✘ |

## 二、★ 八条实现要求

| # | 要求 | ★ 实现 |
|---|---|---|
| ① | ★ 首次真实调用统计不可被后续复核覆盖 | ✔ **汇总由追加式事件重算**（★ `RunEventLog.summarize()`）⇒ ★ 复核只追加 `cache_hit`/`local_replay` 事件 ⇒ ★ **首次统计不变** |
| ② | ★ 缓存命中不计入真实请求数 | ✔ `event_kind=cache_hit` 不计入 `_actual` |
| ③ | ★ 离线重放不产生虚假 token 或费用 | ✔ `event_kind=local_replay` 不计入 |
| ④ | ★ 重试与首次请求分别记录 | ✔ 重试事件带 `is_retry=True`；★ 汇总分列「首请求数」与「retry_requests」 |
| ⑤ | ★ 一个请求处理多个块 ⇒ 请求数与块数独立 | ✔ 事件带 `block_ids[]`；★ 汇总中「涉及块数」独立统计 |
| ⑥ | ★ 解析失败后重试**保留首次失败证据** | ✔ `record_failure(attempt_of=...)` 单独写事件（★ 不被重试覆盖） |
| ⑦ | ★ 运行统计与产物统计可对账 | ✔ 汇总可与候选/块数对照（★ 本审计已用同一口径核对） |
| ⑧ | ★ 缺失的历史 token 标 **unavailable**，★ **不得估算后写成真实值** | ✔ 见 §三 |

## 三、★★★ §四 第 9 条：★ V2-E4 历史记录的可复算性结论

| 项 | ★ 声称值 | ★ 能否独立复算 |
|---|---|:---:|
| ★ H2：12 份 RFC / 24 块 / 24 请求 / 48,644 token / $0.0206 | ★ 见运行报告 | ★ **否** |
| ★ **H3：9 份 RFC / 18 块 / 4 请求 / 19,657 token / $0.009789** | ★ 见运行报告 | ★ **否** |

### 3.1 ★★ 为什么不可独立复算（★ 逐条证据）

| # | 证据 | ★ 结论 |
|---|---|---|
| ① | ★ 两次隔离试点的 `LLMDiagnostics.flush()` **从未被调用** | ★ 诊断目录 **0 个事件文件** |
| ② | ★ 生产诊断目录 `derived/diagnostics/llm_calls/` 有 **12** 个事件文件（★ 生产流程有 flush 调用） | ★ **但不含本项目两次试点**（★ 最新为 11-15，★ 本项目为 11-16） |
| ③ | ★ 汇总数字仅来自生产 `_extract_blocks` 的**内存 stats**（★ 该值**不落盘**） | ★ 无事件 ⇒ 无失败/截断/重试证据 |
| ④ | ★ H2 的缓存里**只剩 1 条** raw item（★ 被后续批次覆盖） | ★ **原始输出未完整留痕** |

⇒ ⇒ ★★★ **★ 结论：★ 「9 份 / 18 块 / 4 次请求 / 19,657 tokens / $0.009789」★
★ ★ ★ 这些数字【无法由底层事件独立复算】★ ★ ★**
⇒ ⇒ ★★ **★ 不得因摘要报告存在数字，就默认底层记录完整**

### 3.2 ★ 缺失数据的处置

★ 缺失的历史 token 数据标记 **unavailable**（★ **不估算后写成真实值**）
★ ⇒ ★★ **本轮以影子事件日志重建可复算链路**（★ `run_events.py`）
