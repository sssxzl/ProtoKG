## 五、★ 特别检查：canonical `definition` 规范规则为什么不能被部分消费路径识别

### 5.1 消费侧读的是什么

```python
# core/fused/hub/hub_view.py:375
def project_semantic_rules(bundle: dict) -> dict:
    """把 bundle["semantic_rules"] 投影进 legal_boundary / response_expectation 两个桶"""
# core/fused/hub/hub_view.py:761 / 789
elif aspect == "legal_boundary":        # ★ 只认 legal_boundary 这个 aspect
elif aspect == "response_expectation":
```

`bundle["semantic_rules"]` 来自 `hub_view._resolve_semantic_rules` ⇒ ⇒ **读 `profiles/<协议>/semantic_rules.jsonl`（人工资产）**。

### 5.2 三重断裂

| # | 断点 | 证据 |
|---|---|---|
| **1** | ★ **形态不匹配**：canonical 规范规则的 fact 是 `aspect=definition` + `value=[RULE:v1] {json}`；而消费侧只读 `legal_boundary` fact 或 `semantic_rules` 列表 ⇒ ⇒ **definition fact 不在任何一条消费通道上** | `hub_view.py:761/789` 的 aspect 分支 |
| **2** | ★ **数量为零**：能走路径③产出 canonical fact 的极少（中枢 rtsp **0 条**、DHCPv4 6 条）⇒ ⇒ 通道 J 的 130 条全在影子 | §四.2 实测 |
| **3** | ★ **反链缺失**：即便 canonical fact 进了中枢，种子侧也无 `fact_id/claim_id/source_span_id` ⇒ ⇒ **无法说明「哪条种子用了哪条知识」** | `manifest.json` 的 seed 键集 |

### 5.3 中枢现有 5 条 `legal_boundary` 的真实形态

```
Transport        {target_field: Transport,     operator: ...}
Content-Length   {target_field: Content-Length, operator: ...}
Public           {target_field: Public,        operator: pres...}
Session          {target_field: Session,       operator: ge...}
Content-Length   {target_field: Content-Length, operator: ...}
```

⇒ ⇒ ★ **是 `target_field + operator + operand` 的语义算子形态** ⇒ ⇒ 来自**人工语义四库**，**不是** RFC 散文规则
⇒ ⇒ ⇒ **「rfc 抽取的规范规则」与「消费端读到的 legal_boundary」在形态上就是两套东西**

### 5.4 结论（★ 对用户第 5 问的直接回答）

> **canonical `definition` 规范规则不能被消费路径识别，不是「识别逻辑写错了」，而是三重断裂叠加**：
> ① **形态**：规范规则的 canonical aspect 是 `definition`，消费侧只读 `legal_boundary`；
> ② **数量**：能产出 canonical fact 的规范规则目前几乎为 0（通道 J 的 130 条全在影子）；
> ③ **反链**：种子侧不携带知识溯源字段，即使进了中枢也说不清被谁消费。
>
> ⇒ ⇒ ★ **三者必须一起修**，只修①（加投影）不会有任何效果，因为②③仍然为 0。
