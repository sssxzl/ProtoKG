# R26 任务 B：field_value 合并的最小影子修复

## 一、缺陷

`core/fused/extraction/rfc_extractor.py` 的协议级去重循环里，`field_value` 类条目按 `norm_id` 合并取值时，合并结果写回 `norm["content"]`。而 `norm` 是**当前这条后续条目**，真正被保留在 `norms` 列表里的是**首次出现的那条**。于是：

- 首条永远只有自己的取值；
- 后续条目的取值被写进一个马上被丢弃的 dict；
- 结果是"合并执行了，但结果没人拿到"。

## 二、影子修复

影子副本里新增 `merged_anchor[key] = norm`（首次出现时记录实际保留者的引用），后续合并写回 `_anchor["content"]`，被丢弃条目的 content 不再改写。生产文件 SHA256 仍为 `7b91622987e8943866473325208ff8b1e0974b67ed93238427c0763d92c4eff0`，未改动。

## 三、合成用例（四项）

| 用例 | 输入 | 修复前 | 修复后 | 判定 |
|---|---|---|---|---|
| V1 三条同 norm_id | `a1` / `a2` / `a3` | 保留条只有 `a1` | `a1 \|~\| a2 \|~\| a3` | 通过（修复前丢失 2 个合法取值） |
| V2 不同 norm_id 负例 | `fvX:x1`、`fvY:y1`、`fvX:x2` | 两条各自独立 | `fvX = x1,x2`；`fvY = y1` | 通过（互不干扰） |
| V3 单条记录 | `Date: s1` | — | 内容完全相同 | 通过（完全不变） |
| V4 多取值 | `v1,v2,v3` | — | 三个取值全部保留 | 通过 |

第一轮判定曾出现"V1 需人工复核 / V2 未通过"，原因是验证脚本按 `;` 切分取值，而生产分隔符是 `VALUE_SAMPLE_SEP = " |~| "`（`rfc_extractor.py:1118`、`1279`）。修正验证脚本的切分口径后重跑，V1 与 V2 均通过。这是**验证脚本的判据错误**，不是修复本身的问题。

## 四、真实语料（三协议）

| 协议 | Norm 总数 | field_value 条数 | content 与生产不同 | source 与生产不同 |
|---|---|---|---|---|
| smtp | 63 | 8 | 0 | 27 |
| rtsp | 107 | 16 | 0 | 16 |
| DHCPv4 | 92 | 0 | 0 | 0 |
| 合计 | 262 | 24 | 0 | 43 |

逐条比对 262 条 Norm 的 content：262/262 完全相同，`field_value` 内容差异 0 条。source 的 43 条差异全部来自任务 A 的行号化，与任务 B 无关（已逐条核对：差异条目的 locator 均由锚点名变为行号，content 未变）。

## 五、结论与限制

**结论**：修复在合成用例上成立（合并值落到保留条目，负例不受影响）；对当前三协议真实语料**零影响**，因为真实语料中不存在"同 `norm_id` 的 `field_value` 多次出现"的情况。

**限制**：

1. 真实语料零触发意味着这个修复目前只有合成证据，没有生产语料的正面证据；不能据此宣称线上缺陷已被观测到。
2. 修复只处理 `field_value` 一类，其他 kind 的合并路径未检查。
3. 修复停留在影子副本，未进生产；入口条件（何时启用）需要与 EvidenceID 迁移一起排期。

## 六、下一步建议

1. 在真实语料上构造一次可控复现：把同一 `norm_id` 的两个样例段放进同一 RFC，验证合并值落到保留条目，并写入回归用例。
2. 若确认修复进生产，需要同步更新 `fv_*` 相关断言与基线。
