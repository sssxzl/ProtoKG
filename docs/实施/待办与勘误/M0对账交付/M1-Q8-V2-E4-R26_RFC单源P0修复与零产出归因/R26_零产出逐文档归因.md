# R26 任务 C：零产出文档逐文档归因

## 一、范围与总数

RFC-only 实验集共 41 份文档（smtp 4、rtsp 1、DHCPv4 36），全部登记编号、字节数与 SHA256。以影子抽取器（`llm=None`）跑完后按"是否产出至少一条 Norm"判定：

| 结果 | 文档数 | 说明 |
|---|---|---|
| 有产出 | 22 | smtp 4、rtsp 1、DHCPv4 17 |
| 零产出 | 19 | 全部为 DHCPv4 |
| 合计 | 41 | — |

逐文档指标与归因见 `R26_零产出逐文档归因.csv`（39 列，含 SHA256、行数、Chunk 有效行、目标 token 命中、通道命中、Norm 数、归因分类与归因证据）。

## 二、19 份零产出的两类原因

### 类别一：LLM 通道缓存与映射器契约不一致（12 份）

RFC 2939、3011、3046、3074、3495、3925、4361、4776、4833、5010、8357、9928。

事实：这些文档在冻结散文缓存 `derived/cache/source_blocks/DHCPv4.prose.json` 里**有条目**（该缓存 76 条、覆盖 28 份文档），但 76 条**全部缺 `name` 字段**，`map_norm_to_facts` 的入口检查直接丢弃，因此不落为 Norm。

证据：DHCPv4 缓存 76 条，含 `name` 的 0 条，`constraint` 非空的 22 条；把 22 条原样送进映射器可映射 **0 条**，补 `name=entity` 后可映射 **22 条**（三协议缓存合计 92 条，`constraint` 非空同为 22 条）。当前生产代码 `core/fused/extraction/prose_semantics.py:1206` 会写 `name`，说明这批缓存是**该字段写入修复之前**产生的历史缓存。

推论：这 12 份不是"抽不出来"，而是"抽出来了但进不了中枢"。修法有两条：重建这批缓存（会产生 LLM 调用），或在读取端对缺 `name` 的历史条目做补全。本轮 0 次新增 LLM 调用，两条都未执行。

### 类别二：确定性抽取器覆盖缺口（7 份）

RFC 3118、6607、6704、8910、2563、9463、951。

事实：7 份文档均解析成功（非空行 396 至 897），命中目标 token 3 至 10 种，命中 4 至 7 个通道，但产出 0 条 Norm。

推论：这些文档的正文结构（多为选项定义、扩展选项表）落在现有 ABNF / 状态表 / 消息清单 / 头表 / 选项表 / 样例六个通道的识别规则之外。属于抽取器覆盖问题，不是数据问题。

## 三、与"只看确定性抽取"口径的差别

若只看确定性通道（不认 LLM 缓存的产出可能），则零产出为 7 份、有产出 34 份。两个口径的差 12 份就是类别一。

R25 报告的"23 份零产出"用的是第三种口径（按文档级覆盖统计，包含 SIP 与未参与实验的文档），不能与 19 或 7 直接比较。三个数字的分母不同，引用时必须带口径。

## 四、限制

1. 类别一的结论依赖冻结缓存的状态：`DHCPv4.prose.json` 一旦被重建或裁剪，12 与 7 的划分会变。本轮已把该缓存恢复到提交态（`git checkout --`），重跑可复现 19。
2. 类别二只做了"没抽到"的归因，没有逐条给出"应该抽到什么"，因为没有人工真值。
3. 未评估补 `name` 后这 22 条 Rule Slot 的语义正确性，只验证了能进映射器。

## 五、下一步建议

1. 对类别一的 12 份，在读取端做 `name` 缺省补全（用 `original_record` 或首行字段名），补全后重跑，确认这 12 份转为有产出且不引入错误的 `norm_id`。
2. 对类别二的 7 份，逐份定位正文结构对应的 RFC 段落，判断是新增通道还是放宽现有通道的窗口。
3. 冻结缓存前先做一次 schema 校验（每条必须含 `name` 与 `constraint` 字段），避免同类问题再出现。
