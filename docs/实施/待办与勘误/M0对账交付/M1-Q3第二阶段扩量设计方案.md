## 〇、核心目标与可验收口径

> **在可控 LLM 成本下，提高 RFC 原文覆盖率、规范知识发现率和通过语义验证的有效知识数量。**

| 目标 | 可验收口径（★ 不得混为一谈） |
|---|---|
| 原文覆盖 | 字符覆盖率 / 行覆盖率 / **规范义务行覆盖率**（三者分别统计） |
| 知识发现 | raw item 数 → **映射通过 norm 数**（★ 候选数 ≠ 知识数） |
| 语义有效 | ★ **L1/L2 confirmed 数**（★ canonical 候选数 ≠ confirmed 数 ≠ 正式 fact 数） |

★ **三层口径恒定分离**：**映射通过（norms）｜canonical 候选（形态）｜published facts（正式）**

## 一、各协议 RFC 规模与未覆盖区域统计

### 1.1 规模（★ 全文可切块口径：`_MAX_BLOCK_CHARS=3500`）

| 协议 | 文件数 | 字符 | 行 | **可切块** | 章节 | **规范义务行** | 当前生产覆盖 |
|---|---:|---:|---:|---:|---:|---:|---:|
| rtsp | 1 | 195,011 | 5,156 | **56** | 156 | 120 | 1.8% |
| sip | 1 | 647,976 | 15,068 | **184** | 270 | 1,079 | 0.5% |
| smtp | 4 | 410,423 | 10,152 | **118** | 223 | 565 | 3.4% |

| **合计** | **42** | **2,275,197** | **56,452** | **665** | **1,387** | **2,813** | — |

### 1.2 ★ 未覆盖区域的结构性特征（★ 关键）

★ **「按前 N 块」会系统性漏掉规范义务**：rtsp 在 **字符覆盖 100%** 时，
**规范义务行覆盖仅 51.67%** ⇒ ⇒ **规范义务集中在文档中后段，而前 N 块覆盖的是开头**
⇒ ⇒ ⇒ **⇒ 预算分配必须按「规范义务密度」而非「字符长度」**

⇒ ⇒ **未覆盖区域的三个来源**（必须分别留痕）：

| 来源 | 判定 | 留痕字段 |
|---|---|---|
| ① 预算未用满 | `eligible_blocks > processed_blocks` 且预算未耗尽 | `budget_remaining` |
| ② 预算耗尽 | 达 `PROSE_MAX_CALLS` / `PROSE_MAX_TOKENS` | `reason=max_calls_reached` / `max_tokens_reached` |
| ③ 单文档块已用尽 | 该文档块数 < 其全文块数 | `doc_blocks_exhausted` |

★ **不得直接认定短 RFC 的第一个块已含全部有用知识** —— rtsp 的数据直接否证这一点。

## 二、三种预算策略的成本与覆盖率比较

### 2.1 策略定义

| 策略 | 规则 | 确定性 |
|---|---|---|
| **S1 `fixed_per_doc`** | 每文档固定 k 块（k = 预算 ÷ 文档数） | ✔ |
| **S2 `length_proportional`** | 按文档字符数比例分配（★ 至少 1 块保底） | ✔ |
| **S3 `floor_plus_incremental`** | ★ 保底（每文档 1 块）+ ★ 增量（按**规范义务密度**排序，**逐块贪心**） | ✔ |

★ S3 的增量分配：**每次给当前密度最高且未用尽的文档加 1 块**，直到预算耗尽
⇒ ⇒ **确定性**（同一输入必得同一分配）

### 2.2 比较结果（★ 离线模拟，token 用实测均值：sip 7,924/块、DHCPv4 9,247/块）

**DHCPv4（36 文件 · 307 块 · 1,049 规范义务行）**

| 预算 | 策略 | 块 | 字符覆盖 | 行覆盖 | ★ **规范义务覆盖** | 遗漏章节 | 估算 token |
|---:|---|---:|---:|---:|---:|---:|---:|
| 36 | S1 fixed | 36 | 12.33% | 8.15% | 0.38% | 716 | 332,892 |
| 36 | S2 length | 36 | 12.33% | 10.32% | 1.72% | 708 | 332,892 |
| 36 | **S3 floor+增量** | 36 | 12.33% | 8.15% | 0.38% | 716 | 332,892 |
| 100 | S1 fixed | 72 | 24.66% | 20.41% | 8.01% | 568 | 665,784 |
| 100 | S2 length | 99 | 33.91% | 28.70% | 15.35% | 526 | 915,453 |
| 100 | **S3 floor+增量** | 100 | 33.68% | 27.60% | **33.75%** | 607 | 924,700 |
| 200 | S1 fixed | 163 | 54.95% | 50.39% | 33.17% | 330 | 1,507,261 |
| 200 | S2 length | 200 | 68.51% | 60.28% | 53.57% | 279 | 1,849,400 |
| 200 | **S3 floor+增量** | 200 | 65.86% | 61.80% | **59.29%** | 309 | 1,849,400 |

### 2.3 ★ 结论与推荐配置

| 协议 | 文件形态 | ★ 推荐策略 | 建议预算（第一轮） | 预期规范义务覆盖 | 估算 token |
|---|---|---|---:|---:|---:|
| **rtsp** | 单文件长 | **S1 fixed**（三策略等价） | **56 块（全文）** | ~52% | ~448K |
| **sip** | 单文件长 | **S1 fixed**（三策略等价） | **184 块（全文）** | ~74% | ~1,458K |
| **smtp** | 4 文件 | ★ **S3 floor+增量** | **118 块（全文）** | ~75% | ~944K |
| **DHCPv4** | 36 文件 | ★ **S3 floor+增量** | **200 块**（★ 307 块需 307 预算） | ~59% | ~1,849K |

★ **总估算：≈ 4.7M token**（★ 单价未配置 ⇒ **费用记 null**）

### 2.4 ★ S3 的已知不足（★ 第二阶段必须细化）

★ S3 的密度是**文档级**（`normative_lines / blocks`）⇒ ⇒ **文档内部仍有盲区**
⇒ ⇒ ★ **第二阶段须细化到「块级密度」**：逐块估算该块覆盖的规范义务行数，按块级密度排序分配
⇒ ⇒ ★ 这一步能进一步把 rtsp 的 51.67% 提上去（★ rtsp 的规范义务集中在少数块）

## 三、SIP 指定块与 M1-Q2 冻结样本的回归设计

### 3.1 必测对象

| # | 对象 | 来源 | 必测项 |
|---|---|---|---|
| ① | `sip/rfc3261.txt@10452`（块起始行 10452） | M1-Q2 冻结 | 绝对/相对解析、锚点 vs 匹配证据行、quote 完整性、L1/L2 不被绕过 |
| ② | 冻结的 **6 条可恢复候选** | `M1-Q2证据冻结/frozen_recoverable_13.jsonl` | 离线重放，验证相对路径 |

| ④ | 「server MUST include」真误伤 | `test_span_anchor_alignment.py` | 锚点 10466 ≠ 匹配 10464；quote 含 MUST include |

### 3.2 回归口径（★ 四层都要验）

| 层 | 断言 |
|---|---|
| **离线重放**（★ 不调 LLM） | ★ `resolve_span_evidence` 对 6 条给出 `span_mode=relative`、`resolved_span` = 锚点、`matched_evidence_lines` 单列；29 条重评 ⇒ 恢复 6 / 仍拒 23；127 条绝对命中行为不变 |
| **单块输入下的解析** | ★ `PROSE_BATCH_BLOCKS=1` 且该批只有一个块 ⇒ `_chunk_start_of` 返回真实起始行 ⇒ ⇒ 相对换算基准唯一 |
| **锚点 vs 匹配证据行** | ★ 两者**必须分别记录**（`resolved_span` / `matched_evidence_lines`）⇒ ⇒ 禁止混用 |
| **L1/L2 的 quote** | ★ quote = `[min(anchor,matched) .. max(anchor,matched)]` ⇒ ⇒ **含「MUST include」**；★ **entity 校验窗口仍 ±3** |
| **语义不被绕过** | ★ 恢复的候选**仍须过 L1/L2** ⇒ ⇒ **不得因位置修正而直接 confirmed** |

### 3.3 ★ 真实 LLM 运行的判定口径

★ **若真实运行未再次产生相对行号，不视为修复失败** —— 因为：
① 相对行号是否出现取决于 **LLM 当时的输出形态**（M1-Q1 已证实同键不同结果）
② ⇒ ⇒ **离线回归覆盖该路径即可**（★ 冻结数据 + 确定性函数 ⇒ 可复算）
③ ⇒ ⇒ **真实运行只用于观察「本次输出形态」**，不作为修复成败判据

★ **扩量时必须显式纳入 `sip/rfc3261.txt@10452`**（★ 第一阶段的 B/C 块集合未覆盖它 ⇒ ⇒ 相对恢复能力未被激活）

## 四、B/C 组 confirmed 差异归因（★ 扩量前的可比性检查）

### 4.1 块集合与输入哈希比对

| 协议 | B 组块 | C 组块 | **共同块** | ★ C ⊇ B | B confirmed | C confirmed |
|---|---:|---:|---:|---|---:|---:|
| sip | 3 | 7 | **3** | ★ **True** | **1** | **0** |
| DHCPv4 | 3 | 7 | **3** | ★ **True** | 0 | 0 |

### 4.2 ★ 归因结论

★ **C 组的块集合是 B 组的超集** ⇒ ⇒ **B 组确认过的块在 C 组里也存在**
⇒ ⇒ ⇒ **⇒ 「confirmed 从 1 变成 0」不可能由「扩量」本身造成**
⇒ ⇒ ⇒ **⇒ 归因：★ LLM 输出的非确定性**（★ 与 M1-Q1「同键不同结果」的实测一致）

★ **且该条 confirmed 本身可疑**：其 quote 为
「**Figure 5**: INVITE client transaction If timer D fires while the client transaction is in the "Completed" state…」
⇒ ⇒ **是图注，不是规范义务** ⇒ ⇒ ★ **该条 confirmed 可能是「误确认」**
⇒ ⇒ ⇒ **⇒ ★★ 因此「confirmed 的绝对数」在本项目当前不可直接采信**（★ 必须人工复核）
⇒ ⇒ ⇒ **⇒ 这直接决定了 §六 的验收标准必须包含人工抽检**

### 4.3 DHCPv4 的归一化比较要求（★ 用户要求）

★ DHCPv4 的 A/B/C **块集合完全不同**（A=36 文档各 1 块；B=3 块；C=7 块）
⇒ ⇒ **不可直接比较 confirmed 数**
⇒ ⇒ **必须按「相同文档集合 + 相同调用预算 + 相同 token 预算」重新归一化**后再比较
⇒ ⇒ ★ 第二阶段的比较协议：★ **同一文档子集 + 同一预算 + 同一批次数** 三者齐备才可比

## 五、分批扩量计划与停止条件

### 5.1 分批计划（★ 逐批推进，每批独立评估）

| 批次 | 协议 | 块数 | 预算（calls） | 估算 token | 前置条件 |
|---|---|---:|---:|---:|---|
| **P0** | ★ **sip 单块回归** | 1（`@10452`） | 1 | ~8K | ★ 冻结回归全绿 |
| **P1** | **rtsp 全文** | 56 | 60 | ~448K | P0 通过 |
| **P2** | **smtp 全文** | 118 | 125 | ~944K | P1 通过且 confirmed 率未下降 |
| **P3** | **DHCPv4 前 100 块** | 100 | 105 | ~925K | P2 通过 |
| **P4** | **DHCPv4 剩余** | 207 | 215 | ~1,849K | P3 通过 |
| **P5** | **sip 全文** | 184 | 190 | ~1,458K | P4 通过（★ **sip 放在最后** ⇒ 因其单文件块最多、风险最大） |

### 5.2 ★ 停止条件（★ 任一触发即停并回滚）

| # | 条件 | 阈值 |
|---|---|---|
| 1 | ★ **护栏新增失败** | > 0 |
| 2 | ★ **正式产物变化** | 中枢/种子任一非逐字节一致 |
| 3 | ★ **不受控的调用增长** | 实际 calls > 预算 × 1.1 |
| 4 | ★ **token 超限** | 实际 tokens > 估算 × 1.3 |
| 5 | ★ **证据错配** | 出现「quote 不含锚点行」的候选 |
| 6 | ★ **confirmed 率下降** | 相对上一批下降 > 20% |
| 7 | ★ **解析失败率上升** | > 15%（★ 第一阶段实测 DHCPv4 为 2/38 ≈ 5%） |

### 5.3 预算耗尽行为（★ 明确）

| 情形 | 行为 | 留痕 |
|---|---|---|
| 达调用上限 | 停止该协议剩余块 | `reason=max_calls_reached` + 未处理块清单 |
| 达 token 上限 | 同上 | `reason=max_tokens_reached` |
| 预算未用满但块已用尽 | 正常结束 | `doc_blocks_exhausted` |
| 单块调用失败 | 重试 ≤ 2 次（★ **不改重试策略**）⇒ 仍失败 ⇒ 记 `failed_incomplete` ⇒ **不写缓存为成功** | 已在 M1-① 实现 |

## 六、语义质量验收标准（★ 覆盖率提高 ≠ 质量提高）

### 6.1 每份 RFC 必须记录（★ 用户指定清单）

| # | 指标 | 口径 |
|---|---|---|
| 1 | 字符 / 行 / 块覆盖率 | 三者分别统计 |
| 2 | ★ **规范义务行覆盖率** | ★ **与 M1-Q1 定义保持一致**（BCP14 大写等级词所在行） |
| 3 | LLM 原始候选数 / 映射通过数 | raw items / norms（★ 不混用） |
| 4 | ★ **L1/L2 confirmed / pending / rejected** | ★ confirmed 需人工抽检（★ 见 §4.2） |
| 5 | canonical 候选数 / **正式 fact 数** | ★ **正式 fact 本阶段恒为 0** |
| 6 | ★ **单位 token 的有效知识产出** | `confirmed 数 / 估算 token` |
| 7 | 未覆盖内容及原因 | 三类原因分别计数 |

### 6.2 ★ 质量门禁（★ 覆盖率提高但 confirmed 不增加 ⇒ 必须进入质量诊断）

| 门禁 | 判据 | 不达标时的动作 |
|---|---|---|
| **G1 覆盖增益** | 规范义务行覆盖率提升 ≥ 10 个百分点 | ⇒ 若不达标 ⇒ **不得进入下一批** |
| **G2 语义产出** | ★ confirmed 数**不低于**上一批（★ 同预算归一化后） | ⇒ **不达标 ⇒ 进入质量诊断**（★ **不得直接宣布抽取效果改善**） |
| **G3 确认质量** | 人工抽检 20 条 confirmed，★ **语义正确率 ≥ 85%** | ⇒ 不达标 ⇒ 停止扩量，先修 L1/L2 |
| **G4 拒绝合理** | 抽检 20 条 rejected，★ **误拒率 ≤ 15%** | ⇒ 不达标 ⇒ 优先修证据定位 |
| **G5 证据完整** | 100% 的候选 quote 含锚点行 | ⇒ 任一不满足 ⇒ 停 |
| **G6 成本效率** | 单位 token confirmed 数不低于基线的 80% | ⇒ 不达标 ⇒ 复核预算分配 |

★ **G2 的「不达标即质量诊断」是硬约束**：★ **覆盖率提高但 confirmed 不增加，必须进入质量诊断，
不得直接宣布抽取效果改善**（★ 用户明确要求）

## 八、推荐配置（★ 供审查）

```bash
# ── 单块调用（★ 激活 M1-Q2 相对行号能力）──
set PROSE_BATCH_BLOCKS=1

# ── 预算策略（★ 按协议分治）──
# 单文件协议（rtsp / sip）⇒ S1 fixed（三策略等价）
set PROSE_BLOCKS_PER_DOC=999      # ★ 由 PROSE_MAX_CALLS 控制总量
set PROSE_MAX_CALLS=60            # rtsp 第一轮：56 块 + 余量
# 多文件协议（smtp / DHCPv4）⇒ S3 floor+增量（★ 需实现块级密度细化）
set PROSE_MAX_CALLS=125           # smtp 第一轮：118 块 + 余量

# ── 成本闸（★ 单价须显式配置，否则费用记 null）──
set PROSE_MAX_TOKENS=1500000
set PROSE_COST_PER_1K=<显式单价>

# ── 块选择（★ 确定性）──
set PROSE_BLOCK_SELECTION=density_desc   # ★ 块级密度降序（★ 第二阶段实现项）
```
