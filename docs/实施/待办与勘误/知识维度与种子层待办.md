### 1.2 待办 T1 ·「全抽」：每个源都尝试抽所有维度

**方向**（用户 2026-11-11 提出）：不再「源 × 维度强绑定」，而是**每个源都跑一组通用抽取器**，
能抽到就产出对应 aspect。

**现状**：各维度**天然归属于某个源**（实测 rtsp）：

| 维度 | 产出源（实测条数） |
|---|---|
| `syntax` / `value_enum_spec` / `definition` / `target_state` | **rfc**（45 / 16 / 71 / 14） |
| `message_instance` / `target_state` / `definition` | **source**（42 / 42 / 15） |
| `existence` / `method_sequence` / `value_enum_observed` | **traffic**（10 / 5 / 30） |
| `precondition` / `session_header` / `url_template` | **expert_note**（6 / 6 / 8） |
| `security_property` / `vuln_pattern` | **vuln**（53 / 23）+ expert_note（8 / 0） |

**跨源可对齐的 3 个**（⇒ 对齐机制已有实际用例）：
`definition`（rfc 71 + source 15）· `security_property`（vuln 53 + expert_note 8）·
`target_state`（rfc 14 + source 42）

**方案要点**：
1. **抽取器与源解耦**：把「抽什么」从「哪个源」里抽出 ⇒ 每个源跑**一组**通用抽取器
2. **按可行性矩阵驱动**（不是无脑全跑）：每个「源 × 维度」组合标注
   `必抽 / 可抽 / 无意义` ⇒ 避免把无意义的维度硬凑出来
3. **产出去重**：同一 `(fact_key, aspect)` 被多源产出 ⇒ 走中枢 claim 级消解（`union`/`precedence`）

**待决**：
- [ ] 哪些「源 × 维度」组合是**可抽**的（逐组合判定，写成矩阵）
- [ ] 抽取器解耦的接口形态（统一 `Extractor` 协议 vs 每个源各自注册）
- [ ] 成本评估：每源多跑几个抽取器 ⇒ 抽取时间与 LLM 成本上升

**⚠️ 前置**：先做 T2（删除无意义维度），否则「全抽」会把垃圾维度一起扩散。

## 6. T6 · `response_expectation` 接入 ⑥ 层（**投影已存在，只差接入**）

### 是什么

> 「**违反某约束后接收方应给出的响应**」（SemFuzz 的处理期望 P：
> `{violation, expected_code, expected_behavior}`，如超长 label 应返回 RCODE=1 FORMERR）

| 维度 | `legal_boundary`（**已有 20 条**） | `response_expectation`（**0 条**） |
|---|---|---|
| 说什么 | **客户端的约束**：这个头**必须带**、这个值**必须在这个域内** | **服务端的期望**：客户端**违反了**它，服务端**应该回什么** |
| 方向 | 客户端 → 规范 | 服务端 → 客户端 |
| 用途 | 指导**种子怎么构造**（合法的） | 指导**「预期结果」** |

⇒ ★ **它是区分「正常的协议错误」与「真正的漏洞」的判据**：
输入被拒（400/500/错误码）⇒ 只是触发了输入校验；
输入让服务器**崩溃/挂死**⇒ 才是漏洞。
⇒ **没有「应该回什么」这个判据，就无法区分二者**。
