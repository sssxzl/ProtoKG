# 跨协议调通改进计划（E1~E6）

> ★ **来源**：2026-11-11 跨协议 rfc 源调通实测（`docs/实施/路线与里程碑/RFC源调通报告.md`）
> ★ **背景**：核心链路（抽取→中枢→图→种子→校验）在 **rtsp** 上跑通，但**换协议即各有各的问题**
> ★ **根因**：不是「rtsp 实现得好」，而是「**现有实现对 rtsp 的素材恰好适配**」⇒ **5 条隐含假设从未被写进契约**

---

## 〇、五条隐含假设（问题的共同根因）

| # | 隐含假设 | 违反者 | 后果 |
|---|---|---|---|
| **A1** | 协议有**可确定性抽取的状态转移表** | sip（散文态）、smtp（无状态机） | L1/L2 空 ⇒ 出不了种子 |
| **A2** | spec 是**少文档且以结构化形态为主** | DHCPv4（36 文档、散文为主） | 26 个散文 RFC 全丢 |
| **A3** | 协议是 **HTTP-like 文本消息** | DHCPv4（二进制） | 校验层 V1 判据不适用 |
| **A4** | **源码可抽出消息实例** | sip(1 文件)/dhcpv4(0) | 种子只有方法序列、没有头 |
| **A5** | **profile 填了 required_headers** | smtp、DHCPv4 | 必填头知识缺失 |

⇒ ⇒ **解法 = 把这 5 条假设显式化**（而不是给 rtsp 打补丁）

---

## 一、六个改进项（**按实施顺序**）

### E1 · 种子层按**协议类型分路**（解 A1）★ 最高优先

| 项 | 内容 |
|---|---|
| **问题** | `edge_cover`（状态机边）+ `generic_danger`（自环/生命周期）**都以状态机为骨架** ⇒ sip/smtp 的 rfc 单源 `!! 无状态机转移`（退出码 1）⇒ **到不了种子层** |
| **判据** | ★ `core.kinds.detect_protocol_kind(protocol)`（**数据驱动**：自动探测 + profile 声明，**不认协议名**）⇒ 实测 rtsp/sip/smtp=**text**、DHCPv4=**binary** |
| **落点** | `core/fused/downstream/rag_seedgen.py`（组装）+ `scripts/seedgen.py`（编排） |
| **做法** | ① `transitions` 为空 ⇒ **不再退出**，切「命令序列型」路线<br>② 新增 **L6「命令序列种子」**：以 `profile.seedgen.canonical_flow`（如 SMTP 的 EHLO→MAIL→RCPT→DATA→QUIT）+ `method_sequence`（traffic 源）为骨架<br>③ manifest 记 `seed_path: state_machine` / `command_sequence` ⇒ **可溯源、可归因** |
| **契约影响** | ★ **无新增 aspect**（L6 复用现有 `method`/`definition` 等 fact）⇒ 契约面不变 |
| **风险** | 低 ⇒ rtsp 走原路（**零影响**，既有语料不变） |
| **验收** | ① smtp 的 rfc 单源能出种子（不再退出码 1）<br>② rtsp 的 A 组种子**逐字节不变**<br>③ 护栏新增 0 / 消失 0 |

### E2 · 状态机「表格腿空 ⇒ 退回 LLM 腿」（解 A1 的另一半）

| 项 | 内容 |
|---|---|
| **问题** | LLM 状态机腿的产出**只停候选区**（`state_machines.json`）⇒ 消费端 `_select_active_transitions` 按规则选一套 ⇒ **sip 表格腿为空 ⇒ 选不出** ⇒ 状态机知识实际为空 |
| **落点** | `core/fused/downstream/rag_seedgen.py::_select_active_transitions` |
| **做法** | 选路规则补一条：**表格腿为空 ⇒ 退回 LLM 腿**（并在 manifest 标 `transition_source: rfc:llm`）<br>★ 兜底启用时**必须过「method ∈ 已知方法集」过滤**（LLM 抽的 method 可能是 `provisional response`/`Timer F` 这类触发事件 ⇒ 混进 facts 会污染语义） |
| **风险** | 低 |
| **验收** | sip 的 `transitions` 从 0 变为非 0；且 method 全部 ∈ 已知方法集 |

### E3 · 补 smtp / DHCPv4 的 **profile 必填头**（解 A5）

| 项 | 内容 |
|---|---|
| **问题** | `smtp profile.json 无 required_headers ⇒ 跳过`；DHCPv4 同 ⇒ **必填头知识完全缺失** ⇒ 种子不会带 CSeq 等 |
| **落点** | `profiles/smtp/profile.json` / `profiles/DHCPv4/profile.json` 的 `seedgen.required_headers`（**人工资产**） |
| **做法** | ① 从规范整理消息级必填头（SMTP：`HELO/EHLO`、`MAIL FROM`、`RCPT TO`、`DATA`…）<br>② **挂进 `onboard_protocol.py` 的接入 checklist** ⇒ 新协议接入时必填 |
| **注意** | ★ **不是**「rfc 源抽不出」⇒ sip 已证明能力存在（14 个方法全有）⇒ 是**规范里没有这种表述** ⇒ 所以正解是**补人工档案** |
| **风险** | 无（纯人工资产） |

### E4 · 警告文案**去具体化**（跨协议不误导）

| 项 | 内容 |
|---|---|
| **问题** | 「无字段级实例」警告写死了 **rtsp 的实测数字**（`missing_required_header 234 条 / 36 条种子全部越界`）⇒ 在 sip/smtp/DHCPv4 的语境下**误导** |
| **落点** | `scripts/seedgen.py` 的该警告 |
| **做法** | 改成**协议无关**表述 ⇒ 具体数字交给 ⑥ 层（`seedcheck`）去测 |

### E5 · seedcheck 的 V1 按**协议类型**分判据（解 A3）

| 项 | 内容 |
|---|---|
| **问题** | V1「首行 ≥2 空格」是**文本协议**判据 ⇒ 对 DHCPv4（二进制）**不适用** |
| **落点** | `seedcheck/v1_format.py` + `seedcheck/knowledge.py` |
| **做法** | seedcheck 读 `core.kinds.detect_protocol_kind()`<br>· **text** ⇒ 现有 5 条最小集<br>· **binary** ⇒ 改判「长度字段与最小报文长度一致」「opcode 合法」等 ⇒ **由 profile 的 `raw_format.binary_fields` 提供**（不硬编码） |
| **风险** | 低（rtsp 走 text 分支 ⇒ 零影响） |

### E6 · rfc 源加「**通道 G：LLM 语义切片**」（解 A2）★ 工作量最大

| 项 | 内容 |
|---|---|
| **问题** | DHCPv4 的 kb 有 **36 个 spec 文档**，rfc 源只触及 **11 个** ⇒ **26 个散文型扩展 RFC 全丢**（rfc3004 Lease Management / rfc3203 Reconfigure / rfc2939 选项定义流程…）⇒ ★ 定性：**不是解析失败，是「形态覆盖不足」**（10 个通道覆盖的全是结构化形态） |
| **落点** | `core/fused/extraction/rfc_extractor.py`（新增通道 G）+ `core/fused/extraction/norm.py`（新 kind 映射） |
| **做法** | ① **只喂「没有任何结构化形态命中」的文档/章节** ⇒ 不重复劳动、不增加已有文档的调用量<br>② 产出**已有 aspect**：散文语义 → `definition`；散文约束（"MUST NOT"「只在 X 情况下」）→ `legal_boundary` ⇒ ★ **不新增 aspect**<br>③ 新 kind `prose_semantics`（映射到 `definition`/`legal_boundary`）⇒ 与现有 11 个 kind 并列<br>④ **可复现**：沿用现成缓存范式 `derived/cache/source_blocks/<协议>.prose.json`（按 `block_hash` 命中 ⇒ 不调 LLM ⇒ 逐字节可复现）<br>⑤ **质量闸**：LLM 产的事实同样过 schema / dup_fact_ids / TOC 闸<br>⑥ **反幻觉约束**：**证据必须带 span**（`file:xxx#@行号`）⇒ **无 span 的产出直接拒收** |
| **风险** | ★ 中（LLM 幻觉 ⇒ 靠 span 约束 + 质量闸兜） |
| **前置** | ⇒ **E1~E5 做完、框架稳住后再动**（用户 2026-11-12 指示：结构可能要调整 ⇒ 先把框架稳） |

## 附录 · E4 + E3 结论（2026-11-12）

### E4 · 警告文案去具体化 ✅

★ 原文案写死了 **rtsp 的实测数字**（`missing_required_header 234 条 / 36 条种子全部越界`）
⇒ 在 sip / smtp / DHCPv4 的语境下**误导**
⇒ 改为**协议无关**表述，并把量化指标的职责**指给 ⑥ 层**
（`python seedcheck/run.py --protocol <协议>`）。

### E3 · ★ 前提**不成立** ⇒ 不补「必填头」，改为「交叉验证」

★ 用户提议：用 VM 端 `/home/zxy/target programs` 的协议对应程序补 smtp/dhcpv4 的
  profile 必填头 ⇒ **实测后判定：不需要补，而且补了也是错的**：

| 协议 | profile 现状（实测） | 判定 |
|---|---|---|
| **smtp** | `required_headers` **键都不存在**；`canonical_flow` = EHLO→MAIL→RCPT→DATA→QUIT ✔；`raw_format` 有 `entity_headers`（DATA 的邮件头）✔；**本地 kb 已有 `smtp_in.c`/`smtp_out.c`** ⇒ source 源**已能抽**（实测 382 条 fact） | ✔ **不缺** |
| **DHCPv4** | `required_headers` = `{}`；**二进制协议没有「头」概念** ✔；结构声明在 `raw_format.binary_fields` ⇒ **已完整**（op/htype/hlen/hops/xid/secs/flags/ciaddr…） | ✔ **不缺** |

⇒ ★ **SMTP 是命令协议**（`MAIL FROM:<addr>` 的地址是**命令参数**，不是「头」）
⇒ ★ **DHCPv4 是二进制协议**（结构在 `binary_fields`，不在「头」）
⇒ ⇒ ⇒ **E3 的正确形态是「按协议类型声明该声明的结构」**，而两者**各自已经正确**。

### ★ VM 目标程序的两个真实用途

| 用途 | 可行性 | 结论 |
