# RFC 单源知识抽取与知识流转补全改进方案（LLM 协同版）


> 文档性质：设计建议，供本地 Agent 落实前做源码核查；不是已经实施或通过验收的结论。
>
> 依据：《知识抽取流失审查待办》《知识抽取改进方案》以及此前四协议真实样本的核查记录。

## 一、核心决策：保留「切块 + LLM」，但不要让一次抽取直接产生正式 Fact

**推荐采用：分层切块 → 多类型候选抽取 → 跨段/跨节补全 → 独立语义核验 → Canonical 映射 → 消费视图适配 → 全链路对账。**

之前把 RFC 切成段落后交给 LLM 提取目标知识，仍然很有价值。LLM 擅长识别自然语言义务、条件、例外、被动语态、跨句主体，以及「方法—头字段—状态—响应」关系；但 LLM 不适合自行确定证据行号、FactID、原文完整性和正式发布资格。

| 任务 | 推荐责任方 |
|---|---|
| 章节树、行号、ABNF 原文、表格与引用索引 | 确定性解析 |
| 规范义务与描述性知识的候选发现 | LLM + 少量确定性触发 |
| 跨句主体、条件与关系链抽取 | LLM（仅提出有原文证据的候选） |
| 跨节引用 | 章节索引检索 + 定位结果核对 |
| 强度/极性校验、Schema、身份、去重 | 确定性程序 |
| 语义支持 | L1 确定性校验 + 独立 L2 逐字段检查 + 人工抽样 |
| 发布、中枢归并、下游消费和回滚 | 原有明确契约及可审计闸门 |

**禁止「chunk → LLM JSON → 正式 fact」的直接路径。**

## 二、先重定义「知识流失」

现有报告描述四协议共 **479 条候选**，其中主体已解析 138、进入 L2 为 92、最终 confirmed 7。它们是候选流转数据，不能推断「479 条有效知识有 472 条丢失」。通道 J 的影子模式也属于有意隔离，不是技术性丢失。

每个候选至少有一个互斥的 `primary_stop_reason`，并允许附加 `secondary_reasons`：

| 状态/原因 | 含义 |
|---|---|
| `not_extracted` | 原文有相关知识，但未形成候选；从未触发段落的独立抽样发现 |
| `non_target_kind` | 描述/定义/示例不属于当前规范规则，但可转其他知识类型 |
| `evidence_missing` | 无法建立足够的原文证据 |
| `pending_semantics` | 主体、条件、强度、引用等未能确定 |
| `rejected_unsupported` | 候选声明与原文实质不符 |
| `shadow_only` | 已验证但按策略只保留在影子候选 |
| `mapping_loss` | 无可用现有契约映射，或映射丢失字段 |
| `hub_or_consumer_invisible` | 已入中枢却未能在消费视图里看到 |
| `consumer_fallback` | 已进入消费者，但因字段/实例缺失退回默认值 |
| `used` | 已在种子生成中实际消费且可追溯 |

**当前所谓 91 条「疑似真义务」仅由规范关键词代理筛出，应先人工标注，不能当作已证明的误漏条数。**

## 三、整体流水线

```text
RFC TXT + 协议档案
  │ 保存 doc_hash / 章节 / 段落 / 真实行号
  ▼
A. 确定性解析与分层切块
  ├─ 结构化知识：ABNF、表格、格式、头字段等
  └─ LLM 第一遍：多类型知识候选
         ▼
B. 章节级第二遍：查漏、跨句关联、按需检索跨节原文
         ▼
C. L1 校验 + 独立 L2 逐字段语义支持检查
         ▼
D. 候选类型分流 + Canonical 映射 + 证据保留
  ├─ confirmed，待发布审批
  ├─ pending/rejected，入可审计候选池
  └─ shadow，记录但不进入正式 fact
         ▼
E. 既有中枢 Facts（21 aspects，不改变原身份契约）
         ▼
F. rule_store / hub_view 消费投影视图
         ▼
G. 种子生成 + 降级追踪 + 反向来源追溯
```

要求能够双向串联以下 ID：
`document_hash → source_span_id → chunk_id → candidate_id → norm_id → fact_id/claim_id → projection_id → seed_id`。
某层没有 ID 必须显式记录 `N/A`、原因和关卡状态，而不是跳过。

## 四、抽取与补全设计

### A. 分层语义切块，而非机械定长截断

1. 保留不可变 RFC 原文；以章节、段落、列表、ABNF 生产式和表格为基本单元。
2. 为模型组合若干语义单元，附上 section path、前后必要上下文、稳定 `span_id` 和原始行号。
3. 区分 `core_span` 与 `context_span`，避免重叠窗口被误认为重复知识。
4. 需要主体上文时检索相关前文；涉及 `Section N` 时定位目标章节的相关段落，而不是固定拼接章节前 8 行。
5. 对 `[BASE64] Section 4`、`[1] Section 8` 这类外部引用，必须先解析 `target_doc`；未定位时待审，不得当成本地章节。
6. JSON 解析失败、输出截断、重试耗尽必须有 `raw_response / finish_reason / token_usage / retry_count` 记录；可限制次数重试或拆小块，不得静默当作「无知识」。
7. 缓存键纳入 `document_hash / chunk_hash / prompt_digest / model_id / schema_version`。

建议先试每块 **600～1200 tokens**，上下文 **100～200 tokens**，作为实验起点而非固定产品标准；由真实漏抽、证据准确率、JSON 可靠性决定参数。按文档与按段落入口要用等价文档集合和明确定义的计数口径比较。

### B. LLM 多类型候选，不只抽 normative_rule

LLM 第一次抽取必须先区分 `candidate_kind`：

- `normative_rule`：义务、禁止、许可、建议及条件/例外。
- `definition_or_description`：协议定义、能力描述、术语、回复码含义。
- `syntax_or_abnf`：语法/格式原文（优先保留原始结构，完整 ABNF 语义另立项）。
- `method_field_relation`：方法、消息、字段、必填/可选、值约束。
- `state_transition`：状态、触发事件、守卫条件、动作、目标状态。
- `response_expectation`：请求及正常/错误响应的条件关系。
- `timer_or_security_constraint`：定时器或安全相关限制。
- `cross_reference`：用于解析对象/作用域的引用。

这些是**候选分类，不是新增 aspect**。实际映射须复用 21 个已注册 aspects；不适配就进入独立关系候选池，不得伪装成规范规则，也不得用实体名填空的 action/object。

规范候选至少保留 `mentioned_entity`、`normative_subject`、`subject_status`、`action`、`object`、`strength_raw`、`strength`、`polarity`、`condition`、`exception`、`scope`、`evidence_spans`、`cross_refs`。
原文没支持的字段填 `unknown` 并待审，不能猜测。

### C. 第二遍「章节级补漏」，不是整章重写

第一遍输出候选后，第二遍只针对同一章节做四类检查：

1. 哪些原文跨度表述了目标知识，却没有相应候选？
2. 是否丢失并列主体、跨句动作、前置条件、例外？
3. 哪些方法—消息—字段—状态关系应当组成关联，而不是离散定义？
4. 哪些引用关系需要检索被引段落才能完成对象或范围解释？

第二遍只能输出 `missing_span_candidates` / `link_requests`，并附**具体原文跨度**；不得直接生成正式 fact。新候选必须重新经过 L1/L2。

## 五、语义验证和规范映射

### D. L1 不做无法证明的词面语义否定

**L1 负责可确定的错误**：证据跨度不存在、字段非法、`MUST NOT` 极性翻转、原文与强度明显冲突、被引章节不在指定文档等。

当 `transmit` 与原文 `send` 词面不同，既不能靠同义词表直接认定“支持”，也不能仅凭不出现就认定“幻觉”。标记 `uncertain` 并交 L2。受控同义表只是辅助信息，不能作为正式语义证据。

RFC 8174 的大小写规则需要保留：小写 `must/should/may` 不得自动当作全大写 BCP14 的特殊强度，但小写散文也不等于没有规范含义，须按文档语境处理。

### E. L2 做独立的字段级证据核验

对 `subject / action / object / strength / polarity / condition / exception / scope / referenced_object`，分别输出：

- `supported`：引用的原文明确支持该字段及其关系；
- `unsupported`：与原文有实质矛盾或补造内容；
- `uncertain`：证据不足或无法可靠解释。

每项必须有 `evidence_span_ids` 和 `reason`。单次 LLM 的 verdict 不是事实证明；关键字段不确定则 pending，明确不支持则 rejected。重复调用或不同模型有助于观察稳定性，但多数票不能掩盖字段级不支持，也不能替代人工抽样。

**重点防错样本**：义务主体 S11/S23/S26/S33；并列主体 S21；`even if` 的让步语义 S16；主体修饰误做条件 S17；`in order to` 的目的误做条件 S27；`or` 的替代方案误做例外 S28。

### F. Canonical Fact 与消费视图解耦

现有 RFC 散文规范规则的 canonical 方案保持为：

- 已注册的 `definition` aspect；
- 由 Rule Slot 决定事实身份；
- `[RULE:v1]` 保存规范声明值；
- `strength / polarity / exception` 保存在 Assertion 而非身份；
- 同义证据可多源保留，相反规范声明可关联并保留为潜在冲突。

**不要**为满足消费端就把这些规范规则改写成另一套 `legal_boundary` FactID。

让 `rule_store` / `hub_view` 对**已确认的规范 Fact**生成它需要的 `legal_boundary / response_expectation` **消费投影视图**；投影记录携带原始 `fact_id`、`claim_id`、证据跨度和版本。这样中枢 canonical 身份不变，消费方能够读到合法约束。

另设「方法—字段—状态—响应」关系抽取与消费对账，不假定增加规范散文规则就能补齐原生状态机缺口。

### G. 防止证据和关系在归并中被截断

- 同一事实多处证据全部保留，`evidence_refs` 不参与语义身份；
- 同一主体但动作、对象、条件、版本不同，不得仅因主体相同而覆盖；
- 可靠归一前不强制合并同义改写；
- 归并前后的 claim 和证据来源都可审计；
- 映射失败的候选保存在 `unmapped_candidates.jsonl`，附具体失败原因；
- 抽取过程中原文不足以建立完整关系时，保存**部分关系候选**（未完成字段为 unknown），不得填造字段使其获得正式身份。

## 六、下游静默降级改为逐项可观测

当前审查指出 `hub_view` 的实例字段对齐失败会退回默认值、method 过滤不留痕、原生关系为空后退回 LLM 候选。这几类都不是 RFC 抽取漏召回，而是**中枢到消费侧的可用性问题**。

建议每次种子构建输出：

1. `knowledge_flow.jsonl`：每条候选的各阶段状态及关联 ID。
2. `degradation.json`：实例对齐失败、method 丢弃、字段退回默认值、规则投影命中率的汇总。
3. `unconsumed_facts.jsonl`：已入中枢但没有进入对应消费路径的候选/事实及原因。
4. `seed_provenance.jsonl`：`seed_id → projection_id → fact_id/claim_id → source_span_id`。

审计中至少能定位到 `method / field / seed_id / fact_id / fallback_reason`，不能只有总计数。被 method 过滤的触发事件保留在**审计隔离池**，不回流合法 method 列表。

## 七、实施里程碑

| 阶段 | 具体任务 | 退出条件 | 发布行为 |
|---|---|---|---|
| **M0：流转对账** | 审计 9 道关卡，串通原文/候选/fact/seed ID；记录所有拒收与兜底 | 样本可双向追踪，无静默漏账 | 不改变正式事实 |
| **M1：切块与抽取** | 语义切块、JSON 失败恢复、多类型候选、章节级二遍补漏 | 非规范文本不再伪装规范规则，新候选有精确证据 | 仍为影子 |
| **M2：语义验证** | 主体独立消解、准确跨节检索、L1/L2 分工、证据归并 | 已知严重语义错例不以 confirmed 发布 | 仍为影子 |
| **M3：中枢与消费适配** | 保留 canonical 定义，新增已确认规则的消费投影，模拟种子差异 | 能逐条说明哪些事实被消费、哪些仍被默认值替代 | 影子/隔离模拟 |
| **M4：受控灰度发布** | 小批量、单协议、原子提交、反向差异和失败回滚 | 经独立人工批准、无严重错配、无兼容退化 | 仅获批后开启 |

**实施顺序建议：先 M0，再做 M1 的完整性与可靠性，再做 M2；M3 可以与 M2 后期并行准备，但 M4 严格最后进行。**

M0 的首批对账至少各做 10 条正向 `source → seed` 和反向 `seed → source`；没有进入种子的知识须有清晰分类，而不是被视为“丢失”。

## 八、验收指标与护栏

| 维度 | 应测什么 | 不应如何误判 |
|---|---|---|
| 源端覆盖 | 正文窗口、未触发段落独立抽样、原文规范句金标召回 | 窗口覆盖 1.0 ≠ 语义召回 100% |
| 抽取完整 | 主体、动作、对象、条件、例外、并列义务、跨段关系缺失比例 | 不能只看 LLM 产出条数 |
| 验证精度 | confirmed 规则逐字段人工正确率、误拒收率 | L2 投票或词面命中 ≠ 人工语义正确 |
| 证据保真 | 正式知识原文跨度与 ID 可追溯，归并不丢证据 | 证据行存在 ≠ 结论被证据支持 |
| 流转可对账 | 所有审计对象均有阶段状态、首个终止原因、对应位置 | 不得把 pending/shadow 当丢失 |
| 消费端可用 | rule_store 投影、hub_view 映射、method 过滤及字段回退 | 种子数量增长不等于质量提升 |
| 安全兼容 | 注册 aspect 仍为 21，新功能关闭时原产物逐字节不变，护栏新增失败为 0 | 不得为让护栏变绿改期望集 |
| 发布可靠性 | 写入前后增量差异、事务失败/回滚、按协议关闭能力 | 抽取层“不写盘”不等于全链路原子性 |

**特别要求：** 当前样本数量较少，不以 `legal_boundary ≥ 20` 或种子数量正相关作为发布硬门槛。发布门槛应围绕证据真实性、人工复核正确性、可回滚性和消费者兼容性制定。

L2 重跑应固定输入、prompt/schema/model 指纹并区分缓存与新调用，记录**字段级一致率**。模型重复三次全同也不等于语义正确。

## 九、交付文件

- `知识流转对账报告.md`：多协议分通道、分知识类型、按互斥原因统计。
- `knowledge_flow.jsonl`：贯穿九关卡的追踪 ID、状态和原因。
- `extraction_candidates.jsonl`：原始 LLM 响应、多类型候选和证据。
- `validation_trace.jsonl`：L1/L2 逐字段 verdict、引用证据、拒收与待审原因。
- `unmapped_candidates.jsonl`：无法无损映射但不应丢失的知识。
- `unconsumed_facts.jsonl`：已入中枢但下游没有读取的事实及原因。
- `degradation.json`、`seed_provenance.jsonl`：下游退回默认值及种子来源链。
- 四协议独立抽样复核包：已知错例回归 + 未触发段落抽样 + 新 confirmed 随机抽样。
- 护栏/兼容性/发布回滚报告：实际测试命令、数据版本、失败基线、运行指纹。

## 十、给本地 Agent 的第一批执行指令

**先做 M0，不要立即修改正式规则发布范围。**

1. 打开源码确认每个关卡的真实函数、输入/输出、数据落盘点；表中的行号仅为原审查报告给出的定位线索。
2. 用当前 479 条候选做阶段互斥原因统计，核对 L1 的 46 条流失原因是否有重叠（原报告原因合计 53）。
3. 把 91 条「带等级词但在主体阶段停下」的候选进行独立分类，不能预先假定都是真义务。
4. 查 RTSP 中枢的 canonical `definition` 规则是否能被消费侧的 `rule_store` 识别；若不能，提出不改 FactID 的影子投影方案。
5. 分别给出 10 条真实的“上游存在、下游因过滤/对齐/兜底未用”的案例，附真实来源及种子影响；不得靠种子总数判断流失。
6. 交付 `knowledge_flow.jsonl`、20 条双向追踪样本与差异报告，供人工确认之后启动 M1/M2。

**最终目标：不是把更多 RFC 文本转成 JSON，而是让真实、有证据、语义正确的知识可追踪地进入中枢与消费端，并能解释每一次停留、转换、过滤和降级。**
