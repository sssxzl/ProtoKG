> 下文保留原任务描述作溯源。

### E1 · 删除无条件放行（**纯度闸形同虚设**）

| 项 | 内容 |
|---|---|
| 位置 | `core/fused/hub/hub_view.py`（原 `core/fused/hub/hub_view.py`）的 `_allowed.add(PROFILE_AUTHORITY)` |
| 问题 | 协议骨架（authority=`profile`）**恒被放行** ⇒ 纯度闸对骨架无效 ⇒ 台账数字与闸行为不一致 |
| 改法 | 删掉该行 ⇒ 骨架改为**按 `source_set` 显式纳入** |
| 验收 | 台账（`knowledge_ledger`）的 `pure` / `violations` 与闸行为**一致** |
| 风险 | 🔴 高（改变产物 ⇒ 种子可能变 ⇒ 需重跑护栏并核对 RQ3 语料） |

### E2 · profile 源消解 ✅ 已完成（2026-11-10）

| 项 | 内容 |
|---|---|
| 问题 | 骨架（`authority=profile`）**不是五源之一**，但它与五源知识混在同一中枢 ⇒ 「五源解耦」名不副实 |
| **实际改法** | **走 ②：骨架「消解 + 物理移除」** —— 把它的 6 个维度各自**迁回真正的源**（target_state / message_instance → source；existence / method_sequence / occurrence / value_enum → traffic；syntax → rfc），然后删掉 `profiles/*/skeleton.json` 与物化逻辑 |
| 依赖 | E1（先让闸真正生效，才谈得上消解）✔ 已完成 |
| **结果** | profile 现在**只承载 `required_headers`**（协议结构声明，由 `profile.json` 独立物化）⇒ 与其它源**一视同仁**（要它进中枢就显式写进 `source_set`） |
| **实测（rtsp）** | ★ 状态机 **52 → 14 条是「修正」不是「损失」**：骨架那 38 条用的是 **SIP 式状态名**（`Idle`/`Invited`/`Confirmed`/`Paused`/`Registered`/`Terminated`）⇒ **在 RFC 2326 里出现 0 次**；留下的 14 条才是 RFC 2326 **A.1/A.2 自己的状态机**（`Init`/`Ready`/`Playing`/`Recording`）⇒ **状态机正确性提升** |
| **实测（dhcpv4）** | ★ RFC 源直接抽出 **24 条 target_state**（`INIT→SELECTING` / `SELECTING→BOUND` 等，证据通道 `file:llm@state-machine`）⇒ 「LLM 状态机通道命中 0」「骨架是唯一来源」**已被推翻** |
| 决策 | **已定**：②（消解 + 物理移除） |
