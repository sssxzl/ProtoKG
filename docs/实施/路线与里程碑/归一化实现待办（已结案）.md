### 1.4 当前比较语义的实际执行者

**关键事实**：Phase A 的比较（`compare_assertions`）当前走的是
`comparison_policy.json` 的 `decidable_subset_supported` 路径，
在 `phase_a.py` 中**硬编码**为 `{equal, disjoint}`，**不读** Registry 的
`comparator` 字段。

⟹ 因此「normalizer / comparator 未实现」**当前不产生可观测症状**：
已产出的 62 个 complete Facts 的比较判定走的是硬编码路径。

**但这是双轨**：

- 当前路径能产出 65 Facts，是因为 18 property 的值域足够简单
  （bool / str）
- 一旦出现 dict / set / range / condition 形态的 assertion
  （如 D9 的 rate 三元组、R2 value_range、R11–R14），
  现有硬编码比较路径**未必覆盖**

⟹ 本 backlog 的真正风险不是「现在会坏」，而是
**「结构化 value 一旦落地，比较语义可能不完整」**。

## 7. 结案（2026-11-10）：现代等价落地

| 旧单元 | 现代等价 | 状态 |
|---|---|---|
| N-1 normalizer 语义的形式化定义（9 种） | **值形态 × 比较语义规范**（`docs/设计/顶层设计/值形态与比较语义.md`）⇒ 按**值形态**组织而非按 property | ✅ |
| N-2 normalizer 实现（9 种） | `resolver._normalize_value()`（set/list 无序 + struct 的 `fields`/`headers` 无序） | ✅ |
| N-3 comparator 实现（9 种） | `resolver._value_eq()` 改为「**先归一再比较**」 | ✅ |
| N-4 `compare_assertions` 改 Registry 驱动 | ★ **不适用**（`comparison_policy.json` 与 `phase_a.py` 已移除 ⇒ 无旧路径可迁移）⇒ 现行机制：`resolver._ASPECT_SEMANTICS`（按 aspect 的消解语义）+ 本规范 | ✅ 不适用 |
| N-5 结构化 value 的比较覆盖验证 | 覆盖验证（实测 278 struct / 117 set claim）+ `tests/hub/test_value_semantics.py` | ✅ |

### ★ 为什么「按值形态」比「按 property」更合适

- 旧方案按 **property**（18~19 条）声明 normalizer ⇒ 每个 property 一套 ⇒ 重复且易漏
- 现行方案按 **value.type**（text/pattern/scalar/set/struct）⇒ **5 种** ⇒
  比较语义只取决于**值的形态**，与它来自哪个 property 无关 ⇒ 更可组合、更少重复
- struct 内部的**字段顺序语义**逐字段声明（§三）⇒ 避免「整体当集合」破坏序列语义
