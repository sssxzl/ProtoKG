# 协议知识中枢架构调整方案

> 本文档整合两项架构调整：**「协议骨架清理」**（去污染）与**「状态机候选定位升级」**（强能力），并给出两者的关系与整体推进顺序。全文只到方案与分阶段步骤层面，不展开具体代码实现。

---

## 概述：两个问题，一个共同目标

近期架构审计发现两个相互关联的问题：

1. **骨架是跨源污染源**：所谓「协议骨架」实为 source+traffic 抽取结果的固化快照，以 `authority=profile` 之名在「RFC 单源态」下仍物化进中枢、且「恒允许」，使单源纯净度名不副实。
2. **状态机候选定位过窄**：RFC 状态机抽取仅靠「扫含 state machine 关键词的行、取前后 60 行」，对「状态机以命令序列/事务模型呈现、无 state machine 字样」的协议（如 SMTP）在第一步定位即失效。

**共同目标**：让「RFC 单源」既**真正纯净**（不靠骨架偷渡），又**足够健壮**（能靠自身抽到必需的状态机知识）。

**两者关系**：状态机（target_state）是「RFC 唯一能贡献、且下游真正必需的维度」。删掉骨架后，RFC 单源态将完全依靠自身，因此**必须先升级状态机抽取能力，再移除骨架兜底**——即「先增强、后移除」，过渡更平滑。

**总体推进顺序**：`第二部分（状态机升级）→ 第一部分（骨架清理）`。

# 第一部分：协议骨架清理方案

## 一、清理目标与原则

**目标**：移除「协议骨架」这一跨源污染通道，使「RFC 单源态」不再混入 source/traffic 的固化知识。

**原则**：
1. **删的是「偷渡通道」，不是「知识本身」**——source/traffic 知识在多源态下仍通过正常源通道进入中枢，只是不再以「骨架（profile）」名义绕过开关。
2. **接受质量下降，换取纯净**——删骨架后，RFC 单源态下 4 个维度（existence / message_instance / method_sequence / occurrence）走默认值兜底，种子变少、覆盖下降，这是「真单源」本应承担的代价。
3. **不破坏多源态**——多源态五源全开，删骨架不影响（骨架本就是冗余）。
4. **可回滚**——每阶段先记录基线，保证可回退。

## 二、清理范围

### 2.1 删除（骨架本体，全部移除）

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 骨架源资产 | `fused_hub/targets/<协议>/skeleton.json` | source+traffic 固化的 145 条 fact |
| 骨架物化逻辑 | 构建脚本的 `_materialize_skeleton` 及配套函数 | 把 skeleton.json 物化进中枢 profile/ 源 |
| 骨架来源维度表 | 构建脚本的 `_skeleton_aspect_origin` | 记录骨架 aspect 来自 source/traffic |
| 骨架源目录常量 | 构建脚本的骨架源目录定义 | 中枢里 profile/ 目录的定位 |
| 骨架消融开关 | 构建脚本的 `--exclude-skeleton-dims` | 骨架已删，开关失去意义 |
| 下游骨架特权 | 消费端的「骨架 authority=profile 恒允许」「骨架兜底」分支 | 删除对 profile 来源的特殊放行 |

### 2.2 保留（正常链路，不动）

- **RFC 抽取器**：syntax / definition / target_state / value_enum / transition 的正常产出；
- **状态机 LLM 抽取**（第二部分升级后）：正确的协议状态机；
- **种子生成核心**：edge_cover / generic_danger / vuln_boundary / canonical / action_seq，及其「缺维度走默认值」兜底；
- **profile.json 协议配置**：方法白名单、URL 模板、会话语义等（协议结构配置，非骨架，不删）；
- **五源抽取器、多源融合、GraphRAG 子图检索**：全部保留。

### 2.3 厘清（特殊项，单独处理）

- **required_headers（必填头）**：现标 `authority=profile`，但来源是 profile.json 的「必填头清单」（协议结构声明），非 source+traffic 固化。方案：与骨架「脱钩」，改走「从 RFC 抽取」或「显式标注为协议结构声明」。**此项不删，只改来源标注。**

## 三、清理后的模块划分与数据流

### 3.1 模块划分（清理后）

```
[五源抽取层]  rfc / source / traffic / expert_note / vuln
      ↓（各自独立抽取，产出带 authority 的结构化知识）
[知识中枢层]  五源知识原子 + 多源融合 + 溯源（无「骨架物化」特殊通道）
      ↓（分桶组装 + GraphRAG 子图检索）
[消费生成层]  规则式生成（缺维度走默认值兜底）+ LLM 生成
      ↓
[质量闸门层]  corpus_gate + 护栏
```

### 3.2 关键数据流变化

**删除前（现状）**：
```
source/traffic ──抽取──► 固化 ──► 骨架 skeleton.json ──物化──► 中枢(伪装 authority=profile) ──恒允许──► 种子生成
（这条「偷渡通道」让单源态混入 source/traffic 知识）
```

**删除后**：
```
source/traffic ──抽取──► 中枢(如实 authority=source/traffic)   ← 仅多源态存在
rfc           ──抽取──► 中枢(如实 authority=rfc)               ← 单源态唯一来源
（单源态 = 纯 rfc，无 source/traffic 残留；缺的维度由下游默认值兜底）
```

**authority 收敛**：清理后中枢 facts 的 authority 只保留真实来源 `rfc / source / traffic / expert_note / vuln`（外加 required_headers 单独标注），**彻底移除 `profile` 这一伪装来源**。

## 四、分阶段改动步骤

### 阶段 0：基线锁定（前置）

- **改动**：跑全量护栏，记录基线（41 failed / 1572 passed / 20 errors / 1 skipped）；记录三协议中枢 facts 权威分布快照。
- **依赖**：无。
- **验收**：基线数字落盘，作为后续每阶段回归对照。

### 阶段 1：关闭骨架物化（默认不物化）

- **改动位置**：构建脚本的骨架物化调用点。
- **改动要点**：将「骨架物化」从默认必做改为默认跳过（等价于现有 `--exclude-skeleton-dims` 排除全部维度，但作为默认态固化）。
- **依赖**：阶段 0。
- **验收**：纯 RFC 构建后，中枢 facts 里 `authority=profile` 只剩 required_headers（8 条），骨架 6 维度不再出现。

### 阶段 2：移除下游「骨架特权」

- **改动位置**：消费端（组装/分桶模块）的「骨架 authority=profile 恒允许」「否则用骨架兜底」分支。
- **改动要点**：删除对 profile 来源的特殊放行；缺维度时走下游既有「默认值兜底」（消息字段回退默认值、方法顺序回退字典序）。
- **依赖**：阶段 1。
- **验收**：纯 RFC 态下种子生成能跑通（靠 RFC 状态机 + 默认值兜底），护栏「新增失败」可控且可解释。

### 阶段 3：删除骨架源资产与物化逻辑（物理清除）

- **改动位置**：构建脚本的骨架物化函数、来源维度表、源目录常量、消融开关；`fused_hub/targets/<协议>/skeleton.json` 三份资产文件。
- **改动要点**：物理删除，保证 `grep skeleton` 全局无残留。
- **依赖**：阶段 1、2。
- **验收**：全局搜索无 skeleton/骨架物化残留；构建流程无骨架相关路径。

### 阶段 4：required_headers 来源厘清

- **改动位置**：必填头清单的物化与来源标注逻辑。
- **改动要点**：把 required_headers 从「authority=profile（与骨架混淆）」改为「协议结构声明」独立标注，或改由 RFC 抽取器产出。
- **依赖**：阶段 1。
- **验收**：required_headers 来源可审计、不再与骨架同名同标；下游消费不受影响。

### 阶段 5：重标定基线 + 全量验收

- **改动位置**：基线重标定脚本、护栏期望集、协议 profile 标定值。
- **改动要点**：因种子数量/内容变化，重标定种子 MD5 基线、护栏期望集、聚焦组种子数。
- **依赖**：阶段 1~4。
- **验收**：护栏回绿（新增 0 / 消失 0）；单源态纯净度审计通过（facts 无 source/traffic 残留）。

### 阶段 6：同步副本 + 更新文档

- **改动位置**：独立运行副本、设计文档。
- **改动要点**：副本同步清理后产物与代码；设计文档移除「骨架兜底」定位，改为「缺维度走默认值兜底、单源态纯净」表述。
- **依赖**：阶段 5。
- **验收**：副本 MD5 与主仓库一致；文档与实现一致。

# 第二部分：状态机候选定位升级方案

## 一、问题与依据

### 1.1 现状问题（实测）

当前状态机抽取的候选定位逻辑是「扫含 state machine 关键词的行、取前后 60 行」，实测结果：

| 协议 | 候选定位命中 | 状态机抽取结果 |
| --- | ---: | --- |
| RTSP | 命中（A.1/A.2 有明确 state machine 章节） | 14 条（正确，但恰好是「有明确表格」的易例） |
| SIP | 命中 7 段 | 14 条，但只覆盖 INVITE 客户端事务一张，状态名大小写不净 |
| SMTP | **命中 0 段** | **完全抽不出**（SMTP 状态机 = 事务模型/命令序列，全文无 state machine 字样） |

根因：候选定位「只扫 state machine 关键词」过窄，对「状态机以命令序列/事务模型呈现」的协议（SMTP）在第一步定位即失效；且**未复用项目已有的章节切分**。

### 1.2 文献依据（为什么要这样做）

已有工作对「从协议提取知识/状态机」的共识是「**分块（chunking）+ LLM 推断**」，没有一个用「扫关键词」：

| 工作 | 出处 | 依据 |
| --- | --- | --- |
| PROSPER | HotNets 2023 | 清洗 RFC + 切成 500 行块 + LLM 提 FSM，并强调去除 TOC |
| StatePre | MDPI Electronics 2025 | 区分「有状态表（表格解析）」与「无状态定义（LLM 从语义功能块推断）」，SMTP 属后者 |
| ProtocolGPT | arXiv 2405.00393 | 强调「语法感知分块」，批评字符切分破坏语义单元 |
| PSMBENCH / RFC2PSM | NeurIPS 2025 | 标准流程「chunked RFC → LLM → PSM → 语义模糊匹配」，并揭示「state-transition gap」 |
| RFCNLP | IEEE S&P 2022 | 用 NLP 语义解析（词表示学习 + 零样本映射），从不用扫关键词 |

## 二、改造目标与范围

**目标**：把状态机候选从「扫 state machine 关键词行」，改为「**复用现有章节切分，取状态/会话/事务相关章节的语义块**」，使 SMTP 这类「无明确状态表」的协议也能被定位并抽出状态机。

**改造范围**：
- 候选定位逻辑（扩展关键词 + 复用章节树）；
- 语义块构建（候选 = 语义完整的章节块，而非「关键词行前后 60 行」）；
- LLM 抽取 prompt（从「只抽明确写出的转移」升级为「允许从文本推断状态与转移」）；
- 评测口径（引入状态级 + 转移级的语义模糊匹配）。

**不动**：章节切分能力、五源抽取、种子生成链路。

## 三、改造后的候选定位逻辑

```
改造前：全文扫「state machine」行 → 取前后 60 行 → 喂 LLM
改造后：复用章节树 → 定位「状态/会话/事务/阶段」相关章节节点 → 取整个章节为语义块（附章节标题 + 关键动词元数据）→ 喂 LLM 推断
```

具体三个升级点：

1. **候选定位扩展**：关键词从单一「state machine」扩展为状态/会话/事务/阶段相关词集（state / session / transaction / phase / stage / machine / diagram 等），并**优先匹配章节标题**（复用章节树），而非正文行。
2. **语义块构建**：命中章节后，取**整个章节节点**（语义完整单元）作为候选，而非「关键词行前后 60 行」；候选块附带元数据（章节标题、协议版本、MUST/SHALL 等关键动词），参照 StatePre 的 functional units 做法。
3. **LLM 推断 prompt 升级**：从「只抽规范里明确写出的转移、不要推测」改为「从文本推断状态与转移」（参照 StatePre 的上下文增强 prompt、PSMBENCH 的 chunked-RFC prompt），因为 SMTP 这类协议本就没有「明确状态表」，必须靠推断。

## 四、分阶段改动步骤

### 阶段 A：候选定位扩展（关键词 + 章节树）

- **改动位置**：状态机候选定位函数（`extract_transition_candidates` 的定位逻辑与关键词正则）。
- **改动要点**：把「扫 state machine 行」改为「扫状态/会话/事务/阶段相关章节标题 + 关键词，命中后定位到章节树节点」。
- **依赖**：无。
- **验收**：SMTP 候选定位从 0 段变为命中 Transaction Model / Session Initiation / Mail Transactions 等章节；RTSP/SIP 候选不减少。

### 阶段 B：语义块构建 + 元数据

- **改动位置**：候选块的结构与生成逻辑。
- **改动要点**：候选 = 整个章节节点（语义完整），附带章节标题、协议版本、关键动词元数据，替代「前后 60 行」。
- **依赖**：阶段 A。
- **验收**：候选块是语义完整的章节；同一章节不重复产候选；候选大小受控（不超过 LLM 上下文）。

### 阶段 C：LLM prompt 升级（允许推断）

- **改动位置**：状态机抽取的 prompt 定义。
- **改动要点**：从「只抽明确写出的转移、不要推测」改为「从文本推断状态与转移」，并约束输出格式（状态唯一标识 / 触发命令 / 下一状态），参照 StatePre。
- **依赖**：阶段 B。
- **验收**：SMTP 能抽出会话状态机（如 HELO → MAIL → RCPT → DATA 的阶段推进）；RTSP/SIP 抽取结果不回退。

### 阶段 D：评测口径（状态级 + 转移级语义匹配）

- **改动位置**：新增评测脚本。
- **改动要点**：引入「状态级 + 转移级」的语义模糊匹配（参照 PSMBENCH 的 cosine 语义匹配），量化改进前后的状态/转移 F1。
- **依赖**：阶段 C。
- **验收**：SMTP 状态级 F1 > 0（从 0 到可用）、转移级 F1 量化；与改进前基线对比产出报告。

### 阶段 E：缓存失效 + 三协议重抽 + 回归

- **改动位置**：状态机磁盘缓存（候选定位变了，需更新 block_hash 使缓存失效）。
- **改动要点**：缓存失效后重抽三协议状态机；跑护栏确认无回归。
- **依赖**：阶段 D。
- **验收**：三协议状态机重抽完成，缓存更新；护栏「新增失败」可控；SMTP 首次拥有状态机。

# 第三部分：两方案的关系与整体推进顺序

## 一、关系

| | 骨架清理 | 状态机升级 |
| --- | --- | --- |
| 性质 | 去污染 | 强能力 |
| 解决的问题 | 单源态混入 source/traffic 知识 | RFC 状态机抽取定位过窄 |
| 对 RFC 单源的影响 | 使其「真纯净」 | 使其「够健壮」 |
| 关键依赖维度 | existence/message_instance/method_sequence/occurrence 走默认值 | target_state（RFC 唯一能贡献的必需维度） |

## 二、推进顺序：先强能力，后去兜底

**总体顺序：第二部分（状态机升级）在前，第一部分（骨架清理）在后。**

理由：状态机是「RFC 唯一能贡献、且下游真正必需的维度」。若先删骨架，RFC 单源态会立刻因「状态机不全（SMTP 为 0）+ 其余维度默认值」而质量骤降；若先升级状态机抽取，RFC 能抽到更全的状态机（SMTP 从 0 到有），再删骨架时过渡更平滑。

## 三、合并后的整体阶段序

```
状态机升级  阶段 A（定位扩展）→ B（语义块）→ C（prompt 升级）→ D（评测）→ E（缓存重抽）
        ↓（完成后再开始）
骨架清理    阶段 0（基线）→ 1（关物化）→ 2（移除特权）→ 3（物理清除）→ 4（厘清必填头）→ 5（重标定）→ 6（同步文档）
```

## 四、风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 状态机升级引入 LLM 幻觉（推断出错误状态） | 阶段 D 用语义模糊匹配 + 一致性校验兜底；参照 StatePre 的 cross-validation |
| 纯 RFC 态种子质量下降 | 预期代价，用阶段 0 基线量化，供「纯净度 vs 覆盖」取舍 |
| required_headers 与骨架脱钩后必填头来源变弱 | 骨架阶段 4 单独处理，优先「从 RFC 抽取」，抽不到再「显式协议声明」 |
| 多源态回归 | 两方案末尾均跑全量护栏 + 多源态冒烟 |
| 误删 profile.json 协议配置 | 明确「profile.json 不删」，仅删 skeleton.json |
