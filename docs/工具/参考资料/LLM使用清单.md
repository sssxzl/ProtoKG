# 全流程 LLM 使用清单（批次 2.5）

> 原则（用户 2026-11-04 明确）：**调试过程中，该用 LLM 就用 LLM；调用 LLM 能让效果更好就结合 LLM。**
> 本文档把这条原则落成**逐环节的决策表**，避免两种偏差：
> ① 该用不用（怕 token / 怕不 reproducible 而回避 LLM）；
> ② 不该用乱用（把 LLM 用在「判定/度量」环节 ⇒ 指标不可审计、论文不可复现）。

---

## 0. 一条判据：**LLM 用在「理解规范」，不用在「度量效果」**

| 环节性质 | 是否用 LLM | 理由 |
|---|---|---|
| **理解规范文本**（散文状态机、约束语义、字段含义） | ✅ **必须用** | 确定性规则做不了；这正是 LLM 的强项 |
| **结构化/枚举化**（状态转移表、ABNF 字段、示例头值） | ⚠ **确定性优先，LLM 兜底** | 确定性可逐字节复现、可审计；LLM 只补剩下的 |
| **判定/度量**（种子是否合法、是否可发送、漏洞是否成立、覆盖是否达标） | ❌ **不用** | 指标必须**可复现、可审计**；用 LLM 判定 = 论文数字不可信 |

⚠ 项目现状偏「确定性优先」是**对的**（可审计是论文的卖点），但**不该因此回避 LLM** ——
凡「确定性做不到」的环节（散文状态机、约束语义），必须让 LLM 上。

## 2. ★ 该用 LLM 但**还没用**的环节（按价值排序）

| # | 环节 | 为什么需要 LLM | 预期收益 | 状态 |
|---|---|---|---|---|
| **L1** | **P1：RFC 源贡献完整状态机**（服务端散文状态机 + SIP ASCII 图） | 散文与 ASCII 图**无法用确定性规则抽取**（批次 2.1 已证：确定性表抽取只覆盖 RFC 2326 附录 A.1 的 14 条） | 纯 RFC 档的 transitions 从 12 → 数十 ⇒ **直接决定「规范单源能覆盖多少」这个核心结论** | ⬜ 待做（已批准） |
| **L2** | **语义规则覆盖扩充**（RTSP 现在**只有 2 条**规则） | 需要更宽的候选句来源（示例报文 / ABNF / 散文 / 附录表）⇒ 判定「这句是不是 MUST 约束」需要语义理解 | ③ 层从 2 条 → 数十条 ⇒ 恢复「源 A 第四类」的价值 | ⬜ 待做（依赖 L1 的候选句扩充） |
| **L3** | 通道 E 补 SMTP 取值（RFC 5322 §3.4 示例邮件报文） | 示例报文解析是结构化问题 ⇒ **确定性够**；LLM 只兜底异常形态 | smtp 取值池空值率下降 | ⬜ 待做（确定性优先） |
| **L4** | ⑤ 层动作序列规划（生产路径启用 LLM 兜底） | 规则给不出动作时，LLM 能给出语义合理的动作序列 | 直接对应 SemFuzz 的「w/oAction 87%→36%」那个消融 ⇒ **我们那条消融目前只测了规则通道** | ⬜ 待做（**评测阶段前必须做**，否则 E3 消融不公平） |

## 3. ★ 明确**不该用** LLM 的环节（评测与判定）

| 环节 | 为什么不用 |
|---|---|
| E1 抽取准确率的真值构建 | **确定性抽取做初稿 + 人工复核**更准、更省（1–3 人时 vs SpecGPT 210+ 人时）⇒ 用 LLM 反而引入噪声 |
| E2 test-case validity（可编码 + 可发送） | 是**执行判定** ⇒ 确定性、可复现 |
| E3 消融的两组对比 | 配置差异 ⇒ 必须是确定性开关（`--layers`） |
| E5 覆盖广度 | 真值来自 RFC 原文 ⇒ 机器可建 ⇒ 零人工 |
| E4 漏洞预言机 | SemFuzz 本身就是**规则驱动**（实际响应 ≠ 预期响应），**不是 LLM 判定** ⇒ 我们也应如此 |

## 4. 用 LLM 的三条纪律（可复现性）

| 纪律 | 做法 | 现状 |
|---|---|---|
| **① 缓存必须留** | 缓存键 = `sha256(候选句 + prompt版本 + 模型)` ⇒ 同输入只调一次；缓存文件**不含凭据**，可入库 | ✅ `（已随论文实验层移除）semantic_gain/llm_cache.jsonl` 已入库 |
| **② 冻结产物不动，生产库可演进** | 论文实验的 `group_E{1,2}/rules.jsonl` 是**可审计依据** ⇒ 冻结；生产库 `derived/per_source/<协议>/rfc/semantic/` 随能力演进 | ✅ 已用 `PROTORAG_RULE_SOURCES` 支持从新批次发布 |
| **③ 换模型/换 prompt ⇒ 缓存失效 ⇒ 结果变** | ⇒ 论文里的模型名、prompt 版本、缓存文件**三者必须一起固定** | ⚠ 论文写作时须显式声明 |

## 5. 对 D20 的影响（**需要调整**）

### 5.1 D20 的问题**变了**
原本问「semantic/ 保不保留」⇒ 实测证明它**可再生**（删除后重发布逐字节一致、零 LLM 成本）
⇒ 「保不保」已不是真问题。

**在你「该用 LLM 就用」的补充下，真问题是**：
> **semantic/ 的内容能否随「抽取能力」一起演进？**
>
> 因为当前生产库里的规则是**批次 2.0 之前**的抽取能力产物（14 条、跨协议混合、
> RTSP 过滤后只剩 2 条）⇒ **内容落后于当前能力**。

### 5.2 调整后的方案：**「丁+」= 丁（自动重发布）+ 规则源可配置 + 按协议过滤**

| 组成 | 状态 | 作用 |
|---|---|---|
| `--auto-republish-rules` | ✅ 已实现 | purge 后自动重发布（零成本、逐字节可复现）⇒ 语义规则**永不丢失** |
| `PROTORAG_RULE_SOURCES` 环境变量 | ✅ 已实现 | 规则源可指向**重抽后的新批次** ⇒ 内容可演进，**不必改代码** |
| `publish_semantic_rules.py` 默认按 `spec_version` 过滤 | ✅ 已实现 | 任何发布路径都不会再引入跨协议规则 |
| `exp_semantic_gain.py --out-dir` | ✅ 已有 | 重抽到新批次，**不覆盖冻结产物** |

⇒ **不需要新造「重抽」机制**：重抽 = 跑 B-10 实验到新批次 → 指定发布源 → 重发布。

### 5.3 ★ 关键结论：**「重抽」的最大杠杆是「扩大候选句集合」，而那就是 L1（P1）**
- `candidates_frozen.jsonl` 是**冻结的候选句集** ⇒ 在它之上重跑，规则**不会变**
  （转换逻辑没改）⇒ **重抽本身没有价值**
- ⇒ 真正的杠杆 = **新增候选句来源**（服务端散文 / ASCII 图 / 示例报文 / ABNF / 附录表）
  ⇒ **必须用 LLM**（散文语义理解）⇒ **这就是 L1**
- ⇒ **D20-丁+ 与批次 P1 是同一件事的两面**：
  - P1 扩大候选句集合（**LLM 出力**）
  - D20-丁+ 让生产库跟着候选句集合演进（**机制已就位**）

⇒ **执行顺序**：D21（架构级修复）→ **P1/L1（LLM 扩候选句）** → 重抽新批次 →
按协议过滤发布 → ③ 层覆盖提升 → 再做 E1–E5 评测。

---

## 6. 一句话总结

> **LLM 要用在「让规范知识更全」的地方（散文状态机、约束语义、动作序列兜底），
> 不要用在「让指标好看」的地方（真值、判定、度量）。**
> D20 因此从「保不保留」变成「**能不能随能力演进**」—— 机制已就位
> （自动重发布 + 规则源可配置 + 按协议过滤），而真正的内容增量来自 **P1 用 LLM 扩候选句**。
