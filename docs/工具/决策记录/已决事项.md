提出 agent 与 Step：Step 4 总指挥 / 阶段 4.1
问题描述：契约 §1.10 要求 Candidate.origin.source_id 存在于 PipelineBuildContext.input_entries，且 EvidenceCandidate.source_id == Candidate.origin.source_id、EvidenceCandidate.source_type == InputEntry.source_type。但 ProtocolNorm 的 11 个字段中没有任何字段能承载 InputEntry.source_id：
  证据一：字段为 norm_id / protocol / kind / facets / name / content / related_norms / source / kb_source_type / extraction_method / added_at，无 source_id 及其等价物。
  证据二：kb_source_type 是「类型」不是「标识符」，26135 条分布为 traffic_pcap 17998 / traffic_raw 8000 / expert_note 85 / vuln 37 / rfc 11 / expert_notes 4，一个 type 对应上万个 norm。
  证据三：source 是自由文本且 1:N，traffic_raw 形如 tcp_0260（每值恰好 8 条 norm，约 2500 个不同值），expert_note 形如 expert_note/body_format.json。
  证据四：同一概念同时存在 expert_note(85) 与 expert_notes(4) 两种拼写。
  证据五：全 core/（core/fused 之外）搜 source_id 零命中，无既有约定可继承。

最终决策：方案甲 —— source_id 在 Hub 侧 build 编排层构造，不改 ProtocolNorm 结构，不改任何 frozen 契约。
  命名格式：`<归一化后的 kb_source_type>:<source 字段值>`
  归一化规则：expert_notes 归一到 expert_note，其余五值（rfc / vuln / traffic_pcap / traffic_raw / expert_note）不变。
  input_entries 构造：build 编排层扫描全部 ProtocolNorm，收集 (归一化 kb_source_type, source) 唯一对，每对生成一个 InputEntry。
  唯一性：同一对在同一 build 内必须对应同一 InputEntry；若两个不同物理源产生相同对，停下汇报，不自行合并。
  派生：Candidate 与 EvidenceCandidate 的 source_id 从同一对派生，值相同；source_type 为归一化 kb_source_type。
  阶段分工：阶段 4.1 不落实际映射表，input_entries 的实际构造留阶段 4.7 或 4.8。

决策理由：契约未禁止 Hub 侧自建映射表；InputEntry 本身就是 Hub 侧概念（fused_canonical_spec.md §9 定义），由 build 编排层显式声明「哪个 input artifact 对应哪些 source_type 与路径」是自然边界，且不动任何 frozen 契约与既有代码。方案乙代价过高（动 core/ 既有模块 + 重跑 kb/ 派生链）；方案丙要改 frozen 契约；方案丁是降级实现。

决策影响：
  - 阶段 4.1 的 §1.10 Input Closure 检查可在阶段 4.7/4.8 拿到真实 input_entries 后完整启用
  - 命名规则「归一 kb_source_type : source 值」同时消解了 expert_note / expert_notes 的拼写不一致
  - 唯一性冲突时必须停下汇报，该行为已写入 build 编排层实现要求

提出 agent 与 Step：Step 4 总指挥 / 阶段 4.8a（第三批）
问题描述：basis 的定义来源在阶段 4.5（phase_b.py:94 读 PhaseAResult.basis_claim_ids）与 core/fused/validation.py 的 Invariant 22（读 Resolution.basis_claim_ids）之间不一致，且两边都有存量测试锁死。直接后果：write_facts → validate_fact 失败，任何 peer_conflict 的 Fact 都无法落盘。影响面精确等于「peer_conflict 的 Fact 有哪些 alignment」—— resolved 分支下两字段同值无分歧，insufficient_evidence / unsupported_assertion_type 两个 unresolved 分支下两边都空，唯一分歧点是 peer_conflict。

契约裁定（用户授权后 agent 回原文复核，这是 D8 的决定性依据，不是偏好选择）：
  - fused_canonical_spec.md §5.3 原文：「unresolved：peer_conflict 时 basis_claim_ids **包含参与冲突的 Claims**；insufficient_evidence 时可为空。」
  - fused_canonical_spec.md 条款 12 原文：「**alignments 必须覆盖所有非 basis claim**。参与 Phase A 但未进 basis_claim_ids 的 claim 必须有 alignment entry。未参与 Phase A 的 claim 也必须有 alignment entry。」
  - fused_canonical_spec.md §6.2 原文：「basis claim **不得**产生 alignment entry。」
  → basis 只有一个定义，即 Resolution.basis_claim_ids；参与冲突的 claim 就是 basis claim，不得有 alignment。方案甲是契约强制。

复核过程中发现的**第四个成因**（D8 报告时未预见，修 D8 后立刻会暴露）：
  phase_a 的 peer_conflict 分支把 **tuple** 传进 Resolution.basis_claim_ids（声明为 list[str]）。canonical.py §4.1 明确 tuple 不在 Canonical JSON Domain，models._to_jsonable 只处理 _Model/list/dict 不转换 tuple，_copy_mutable_fields 也不做 tuple→list。因此 tuple 会原样穿透 to_dict()，让整条 Resolution 序列化失败：
      Resolution(basis_claim_ids=('c1_aaa',)).to_dict()['basis_claim_ids']  -> tuple
      canonicalize_bytes(...)  ->  FusedSchemaError: tuple is not in the Canonical JSON Domain
  即：只修 basis 分叉的话，peer_conflict 的 Fact 仍会落不了盘，只是失败点从 validate_fact 移到序列化。

最终决策：方案甲，且按「根治」而非「补现象」实施 —— 四处改动一起做：
  1. phase_a.py peer_conflict 分支：PhaseAResult.basis_claim_ids 由 () 改为 competing，
     使其成为 Resolution.basis_claim_ids 的**真镜像**（不再是第二个定义）。
  2. phase_a.py 同一处：Resolution.basis_claim_ids 传 list(competing) 而非 tuple，
     修第四个成因。
  3. phase_a.py 的 PhaseAResult.validate_domains 新增 BASIS_MIRROR_MISMATCH 断言：
     basis_claim_ids 必须逐元素等于 resolution.basis_claim_ids；
     并新增 field_basis_on_unresolved 断言（field_basis 只在 resolved 时使用，契约 §5.3）。
     → 任何未来新分支若忘记同步，构造期立即抛错，整类 bug 结构上不可能再发生。
  4. phase_b.py 显式改读 phase_a.resolution.basis_claim_ids（契约权威字段），
     docstring 写明为什么读契约字段而非镜像。
  5. 同步修正 4.5 的 test_unresolved_gives_not_comparable：peer_conflict 下两条 claim
     全是 basis → alignments 应为空（原断言 len(b)==2 与 Invariant 22 对撞）。

决策理由：契约 §5.3 与 policy 条款 12 是明文，方案甲是唯一符合冻结契约的读法；validation.py 是 Final Frozen 且已被 4.4 测试锁死方向；改 1 行 + 加构造期断言的收益远大于逐个补分支。

## D24 — 问题1 裁定：source 走「混合」（候选丙）

**提出时间**：2026-10-05（步骤 B）
**依据**：`local/backup/step_source_a/step_a_measurement.txt` 的 A1/A2/A3 实测。

### 实测值

| 量 | 值 |
|---|---|
| A1a 方法级对齐率 | **0.90**（9/10） |
| A1b 全量口径对齐率 | 0.47（9/19） |
| A2 独立实现选择数 | **2** |

### 判定原则代入

原则原文：
- `对齐率 ≥ 0.7 且 独立选择数 = 0 且 形态 = 规范性` → 乙
- `对齐率 < 0.3 或 独立选择数 > 3 或 形态 = 观察性` → 甲

代入：0.90 ≥ 0.7 ✓；独立选择 = 2（既非 0 也非 >3）✗；形态 = 规范性 ✓
⟹ **不满足乙，也不满足甲，判定为丙（混合）**。

### 最终决策

**source 走混合双轨：**

1. **能归到 rfc fact 的实现 ⟹ provenance-only**
   - 9 个方法中 6 个（DESCRIBE / GET_PARAMETER / OPTIONS / PAUSE /
     PLAY / REDIRECT / SET_PARAMETER / SETUP / TEARDOWN 中的对齐部分）
     其代码处理归为 provenance，附着到既有 rfc method fact。
2. **不能归到 rfc fact 的实现 ⟹ 独立 Hub fact**
   - REGISTER（RFC 2326 外的方法，成体系实现 59 处）
   - 状态码 454（RFC 2326 未定义，语义与 455 分歧）

### 决策理由

- 对齐率高（0.90）说明**大部分**代码行为是 RFC 2326 的实现，
  把它们当 protocol knowledge 会重复 rfc 源已有的事实 ⟹ 归 provenance。
- 但独立选择数 = 2 证明**并非全部**可归入 RFC：
  REGISTER 是 liveMedia 独有的一整套能力（7 文件 / 完整类层次），
  454 是与 RFC 语义分歧的响应。这些**无处可附着**，因为
  rfc fact 池里没有对应 subject ⟹ 必须独立成 fact，
  否则这 2 项信息会被丢弃。

### 反证与为何不选其他候选

**为何不选甲（纯 provenance-only）**：
- 独立选择 = 2 且都是成体系的（REGISTER 59 处 / 454 完整 handler）。
- 若走纯 provenance，这 2 项无 target 可附着（rfc fact 无 REGISTER subject、
  无 454 status fact）⟹ 只能记 `relation = no_target`，等于**丢弃真实信息**。
- 这违反 traffic 侧已确立的原则：**「0 facts ≠ 语义不存在」**
  的镜像形式 ——「无 target ≠ 无知识」。

**为何不选乙（纯产 Hub fact）**：
- 对齐率 0.90 意味着 90% 的方法处理是 RFC 2326 的实现。
- 若全产 Hub fact，则 liveMedia 的 DESCRIBE/SETUP 等会与 rfc 源的
  同名 method fact 产生**大量重复 fact** ⟹ 触发冲突检测，
  且重演 traffic/vuln 侧已暴露过的 subject 分裂问题
  （见 hub_contract_errata_backlog §10.1 authorization 三分裂）。
- 单一实现产出的「事实」被当作 protocol knowledge，
  会把实现选择污染成规范 —— 这正是 traffic D9 全文在防的失效模式。

**候选丙的已知代价（明确承担）**：
- 分流判据需要精确定义，否则每次抽取都要重新裁定。
- 分流本身可能退化为甲或乙，需在 Rule Set 阶段用 Freeze Criteria 锁定。

### 决策影响

- 问题 3（代码包）按原则须「分两包」⟹ 见 D26。
- 问题 2（D9）实现数 = 1，默认不需要独立 D9，见 D25。
- 设计方向见 `docs/设计/各源设计/第五源设计.md`（草案，步骤 C）。

## D27 — source/traffic 同源的战略影响：独立信息增量分析

**提出时间**：2026-10-05

### 已知前提

- source = LIVE555 liveMedia；traffic 的 client.log =
  `openRTSP (LIVE555 Streaming Media v2026.04.01)`
- ⟹ **同源**。traffic D9 §4.5 P8-1 已冻结「同源生成器非独立证人」。
- 本条**不重复测量同源**（用户指令明示），直接引用既有结论。

### 核心问题

五源综合的目标是「多源知识 union」。但 source + traffic =
**同一实体的两个视图**。问：source 相对 traffic 的**独立信息增量**是什么？

### 增量分解

按知识类型逐类比：

| 知识类型 | traffic 提供 | source 独有增量 | 增量大小 |
|---|---|---|---|
| 报文**实际内容**（method/header/CSeq/URI 实际值） | ✅ 25000 observation | ✗ 无 | **0** |
| 报文**边界与顺序** | ✅ G1 重建 + C17 贡献集 | ✗ 无 | **0** |
| 实现**允许集**（Public 字段声明哪些方法可用） | ✗ 无 | ✅ `allowedCommandNames()` | **小但实** |
| 实现的**拒绝行为**（哪些输入被拒、返回何码） | ✗ 无 | ✅ 6 条错误路径 + 454 | **中** |
| RFC 外**扩展方法**（REGISTER 全套） | ✗ 无 | ✅ 59 处 / 7 文件 | **大** |
| 非 RFC **状态码**（454） | ✗ 无 | ✅ 1 条，但语义与 455 分歧 | **小但关键** |
| 规范**要求**（协议应该怎样） | ✗ 无 | ✗ 无（source 也不是规范） | **0** |

### 结论

**source 的独立增量不在「报文内容」，而在「实现的行为边界」。**

具体地，traffic 能告诉你「liveMedia **实际发了**什么」，
source 能告诉你「liveMedia **声明支持**什么、**拒绝**什么、
**额外支持**什么」。

这两类**不重叠**：
- traffic 观测不到「未被触发」的行为（语料里只有 5 消息会话，
  OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN，status 全 200）
- source 能看到 ANNOUNCE/RECORD **未实现**、455→454 **语义替换**、
  REGISTER **完全超出**语料范围

### 战略限制（须登记）

1. **source 不能为 traffic 的观测提供独立印证。**
   若两者结论一致，只说明**代码与它的行为自洽**，不说明协议正确。
2. **五源「union」在 source+traffic 这一对上退化为「同一实体的两个视图」**，
   不是两个独立知识源的交叉验证。
   真正提供交叉验证的是 rfc（规范）↔ source/traffic（实现）这一对。
3. **traffic 语料的形状限制被 source 反向照亮**：
   traffic 只有 5 消息 / 全 200，若无 source，
   无法判断这是 liveMedia 的能力边界还是语料采样artifact。
   ⟹ **source 恰恰能补上 traffic 无法自证的那部分**。

### 反证与为何不选其他结论

**为何不选「source 无独立价值」**：
- 违反用户明示原则「不得把『同源』等同『无独立价值』」。
- 实测 REGISTER 59 处 / 454 分歧 / allowedCommandNames
  都是 traffic 语料**结构上无法提供**的信息。

**为何不选「source 是 traffic 的冗余副本」**：
- 实测二者知识类型**不重叠**（见上表）。
- traffic 是「实际发生」，source 是「声明与边界」。

### 决策影响

- 五源融合的**独立性论证**须以 rfc ↔ source/traffic 为主轴，
  而非五源两两交叉。
- source 的价值主张应表述为「补齐实现行为边界」，
  而非「提供第二份协议知识」。
- 登记到 `docs/实施/待办与勘误/中枢契约勘误待办.md` §11（战略限制）。

## D29 — 战略理解更新：同源 ≠ 无独立价值（L3 的展开）

**提出时间**：2026-10-05（步骤 D）
**背景**：D27 登记了 L1/L2/L3 三条战略限制。本条**更新理解，不改契约**。

### 理解的转变

| 阶段 | 表述 | 依据 |
|---|---|---|
| 勘察初判 | 「同源 → 可能无独立价值」 | 只看了「同源生成器非独立证人」这一条 |
| D27 登记 | 「同源，独立性论证应以 rfc 为主轴」 | 已完成增量分解 |
| **D29（本条）** | **「同源但视图不同 → 有互补价值」** | A3 补样给出了结构性证据 |

### 为什么理解需要更新

D27 说「source 的增量在实现的行为边界」，但**没有解释为什么 traffic
无法自己提供这些信息**。A3 补样给出了答案：

traffic 语料实测：**5 消息会话 / status 全 200 / 覆盖 5 个方法**
（OPTIONS / DESCRIBE / SETUP / PLAY / TEARDOWN）

⟹ traffic **结构上无法观察**：
- `allowedCommandNames()` 声明的完整允许集（traffic 只触达 5 个）
- ANNOUNCE / RECORD **未实现**这件事（没有报文 = 没有 handler）
- 454 与 455 的**语义分歧**（traffic 全是 200，看不到错误路径）
- REGISTER **完全超出**语料范围（client.log 里一次都没出现）

**若没有 source，traffic 语料的这些限制无法被区分**：
是「liveMedia 只能这样」还是「语料恰好只采了这些」？

### 因此 source 的价值主张（更新后）

**不是**「第二份协议知识」（那是 rfc 源的事）。
**而是**：**「回答 traffic 语料无法回答的问题 —— 这个实现的能力边界在哪，
哪些是 RFC 没要求但它做了，哪些是 RFC 要求了但它没做。」**

这是 traffic 语料**不可替代**的补充，因为 traffic 只能看到
「实际发生过的」，看不到「声明支持的」与「拒绝处理的」。

### 对 traffic D9 §4.5 P8-1 的处理

P8-1 冻结的是「同源生成器非独立证人」—— **该结论完全正确，不改**。

本条更新的是**理解**，不是契约：
- P8-1 说的是「不能用 traffic 验证 traffic」
- 本条补充的是「可以用 source 回答 traffic 答不了的问题」

⟹ **不修改 `设计/traffic_d9_design.md` 任何内容。**
仅在本条与 `实施/待办与勘误/中枢契约勘误待办.md` §11 登记理解更新。

### 决策影响

- 五源综合的**问题分工**应表述为：
  - rfc = 规范要求
  - source = 实现的能力边界（含 RFC 外的扩展）
  - traffic = 实际行为（受语料采样限制）
- 三者**互补而非冗余**，但只有 rfc ↔ (source, traffic) 构成交叉验证
## D30 — 重大更正：454 是 RFC 2326 §11.3.5 合法码，不是独立实现选择

**提出时间**：2026-10-05（步骤 B）
**性质**：**纠正前序判定错误**（D24 / step_source_a 的 A2）

### 被更正的结论

`local/backup/step_source_a/step_a_measurement.txt` 的 A2 记载：

> ★ 发现 2：状态码 454 —— RFC 2326 未定义
>   代码响应串中实际出现：200 401 404 451 454 461
>   差集：**454**
>   代码位置：RTSPServer.cpp:509
>     setRTSPResponse("454 Session Not Found");

并据此得出「独立实现选择 = 2（REGISTER + 454）」。

### 该结论错误

RFC 2326 §11.3.5（L2331）明确定义：

```
11.3.5 454 Session Not Found

   The RTSP session identifier in the Session header is missing,
   invalid, or has timed out.
```

liveMedia 的 `setRTSPResponse("454 Session Not Found")`
**完全遵循 RFC 2326**。

### 错误来源

上一批构造的「RFC 2326 定义集」是
`200 400 401 404 405 451 455 459 461 500 503 505 551 553`
—— 这是**凭记忆写的常量**，**未从 `kb/spec/rfc2326.txt` 原文抽取**。

违反的原则（本批指令明示）：
> 「RFC 基准从原文抽取，不凭记忆」
> 「不得凭名称推测」

量具缺陷模式与 agent_rules 第四章一致：探针结果与预期不符时

## D35 — observation 粒度与 anchor 裁定（Rule Set §9 问题 1 / 2）

**提出时间**：2026-10-05（步骤 C / D）
**产物**：`设计/source_lane_a_rule_set_design.md` §4.1

### 问题 1 裁定：**函数级，一条分支一条 observation**

依据（三条独立来源）：
1. **分流判据已是函数级**（D28）：SETUP 有 3 个函数、DESCRIBE 有 2 个，
   方法级粒度无法区分它们 ⟹ observation 粒度须与之一致
2. **形态实测**（A3）：第 1/2 档函数分支 0–5 条，整函数一条会丢信息；
   第 3 档（PLAY）50 条分支，整函数一条无法定位
3. **R-1 原则**：「看分支条件不看分支体」—— 条件是规则的判据，
   故**分支**是自然单位

### 问题 2 裁定：`file:line` + 分支序号，**不沿用 traffic 的帧区间**

```
anchor = {
  "locator":    "RTSPServer.cpp:1772",   // 函数起点
  "branch_ord": 12,                        // 该函数内第 N 条 if 分支
  "symbol":     "handleCmd_PLAY"
}
```

**为何不沿用 traffic 的 `(capture_unit, frame_from, frame_to)`**：

traffic 的 anchor 是**帧区间**，理由是接口文档 §2.3
「契约不能假设一条 message 恒等于一个 frame」。
source 的观测单位是**代码位置**，**不存在「区间」语义** ——
函数起点 + 分支序号是代码位置的自然表达。

**反证（为何不用行号区间）**：
若用 `line_from`/`line_to` 表示一个函数体，
则一条 observation 会覆盖多个分支 ⟹ 退回方法级粒度，与裁定 1 冲突。

⚠ **禁止伪造 `frame_from` / `frame_to`**：
   source observation **没有帧概念**，编造帧号会污染 reader 语义，
   并使 source 与 traffic 的 anchor schema 语义混淆（§0.3 的核心区分）。

### relation 四值逐值判据（§6.1.1）

**判据基准的选择是本判定的关键**：

| | traffic | source |
|---|---|---|
| relation 表达 | 观察值 ↔ **既有 fact 的 assertion** | 实现选择 ↔ **RFC 2326 条款** |
| 客体 | Hub 内已存在 | 规范原文（**语料之外**） |

⟹ traffic 比「两个数据」，source 比「语料内的代码」与「语料外的规范」。

**四值判据**（均基于 RFC 2326 原文全文检索，可机械化）：

| relation | 判据 |
|---|---|
| `conforms_to_spec` | X ∈ RFC 定义域 **且** 行为与规范条款一致 |
| `deviates_from_spec` | RFC 规定值 A ≠ 分支返回值 B，且 B 在 RFC 中未定义 |
| `unspecified` | X ∉ RFC 定义域（全文检索 0 命中）且为实现自主选择 |
| `no_target` | 按 D28 L1/L2 判定无 Hub target（**正交维度**） |

⚠ 这是**推导结果不是设计偏好**。

## D40 — REGISTER 是 implementation extension，走 provenance 轨（D32 前提被推翻）

**提出时间**：2026-10-06（步骤 A / B / C）
**产物**：`local/backup/step_source_a7/stage_a_semantic_verify/register_semantic_verdict.txt`
**回答**：REGISTER 是 protocol-semantic fact 还是 implementation extension？

### 判定

**implementation extension（私有实现），非 protocol-semantic。**

### 依据（五条独立证据，方向完全一致）

| # | 来源 | 结果 |
|---|---|---|
| 1 | **RFC 2326 全文**检索 REGISTER | **6 次命中全为否定证据**：L70 / L994 是「Registering New Option Tags with IANA」小节标题与目录项；L991 / L996 / L4519 是「register the new option」/「register new encodings」**动词**；L1356 是「registered status codes」**形容词**。**无一处作为方法定义** |
| 2 | **RFC 2326 §10 Methods 小节清单** | 10.1 OPTIONS / 10.2 DESCRIBE / 10.3 ANNOUNCE / 10.4 SETUP / 10.5 PLAY / 10.6 PAUSE / 10.7 TEARDOWN / 10.8 GET_PARAMETER / 10.9 SET_PARAMETER / 10.10 REDIRECT / 10.11 RECORD —— **共 11 个方法，无 REGISTER 小节** |
| 3 | 与 `subject_registry` 差集 | 差集恰为 `REGISTER`（D34 新增那条）；原 11 条与 §10 **完全一致** |
| 4 | **IANA「RTSP 2.0 Methods」注册表（RFC 7826）** | 列举 DESCRIBE / GET_PARAMETER / OPTIONS / PAUSE / PLAY / PLAY_NOTIFY / REDIRECT / SETUP / SET_PARAMETER / TEARDOWN，**无 REGISTER**。RFC 7826 是 RTSP 2.0 后续标准，方法集为 RFC 2326 的演进 ⟹ REGISTER **未被任何 IANA 标准纳入** |
| 5 | 专利文献旁证（CN102761550B） | 「表 2 为本发明实施例**增加的** RTSP 方法：REGISTER / POUR」——业界实践视为私有扩展，需自行「增加」而非引用标准 |

### 对 D32 的推翻（显式登记，不静默改写）

D32 裁定「REGISTER 沿用 method kind，只加 subject」，

## D42 — S-PH 遍历入口补齐采用方案乙（独立正则 + 独立遍历路径）

**日期**：2026-10-06　**范围**：`core/source_a/segments.py`、`observation.py`

### 问题定位

`parseRangeHeader` / `parseScaleHeader` / `parseTransportParams` 是**自由函数**

### 候选方案对比

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|

| **乙** | **独立正则 + 独立遍历路径**，共用 body 扫描 helper | 新增代码不触碰既有路径 |
| 丙 | 正则工程化（多行签名 / 返回类型） | 复杂度最高，收益与乙相同 |

### 裁定：方案乙

**依据**：
1. 「不改 `handleCmd_*` 的现有匹配」是本批硬约束 —— **甲直接违反**。
2. S-PH 符号取自**白名单常量** `SPH_SYMBOLS`，非字符串切分
   ⟹ **天然满足 C-2 / I-6**（AST 测试 `test_i6_no_generic_underscore_split.py` 不受影响）。
3. 乙把 S-PH 视为**独立遍历入口**，与 Rule Set §3.0「S-PH 是独立组」结构对齐。

**反证（为何不选甲）**：`handleCmd_*` 已产出 12 个函数单元且被 41 项测试锁定行为；
为加一条路径而改动其正则，收益（少写一个正则）远小于回归风险。

**为何不选丙**：多行签名支持是**通用能力**，而 S-PH 只需 3 个已知符号；
用白名单换掉通用性，符合 YAGNI。

**实测结果**：函数单元 19 → **22**（S-M 12 / S-E 6 / S-PH 3 / S-EX 1）。
补 R-3 模式前 S-PH 的 10 条中 **9 条误标 `NEEDS_REVIEW`**，补后全 `EMIT`。

## D55 — 判据体系缺「不适用」态：三次同型判据错误的共同根因

**日期**：2026-10-06

### 三次同型错误

| # | 判据 | 错误形态 |
|---|---|---|
| 1 | **L2**（D52） | 用三元组检验契约定义的五元组 ⟹ 误判 FAIL |
| 2 | **L3**（D49 / D53） | 检验一个**尚未实现**的机制 ⟹ 把「不适用」判成「未达标」 |
| 3 | **L5-Q4** | 假设「所有 Hub 变化都应改变产物」⟹ 把「理应不改变」判成 FAIL |

> **PASS / FAIL / N-A（不适用）/ 判据失效**

并要求每条判据显式声明其**前提条件**：
前提未成立时输出 N/A，不得输出 FAIL。

⚠ 本条是**方法论级**裁定，适用范围不限于本框架。

## D56 — 判据四态落地：PASS / FAIL / N-A / PENDING

**日期**：2026-10-06　**承接**：D55

### 定义

| 状态 | 含义 | 使用条件 |
|---|---|---|
| **PASS** | 前提成立且达标 | — |
| **FAIL** | 前提成立但未达标 | — |
| **N/A** | **判据前提未成立**（不适用） | 前提未成立时**必须**用 N/A |
| **PENDING** | 前提成立，但因未实现或未测量而无法判定 | 前提成立却测不了 |

**强制要求**：每条判据必须显式声明**前提条件**。

### 逐条前提声明

| 判据 | 前提 | 当前 |
|---|---|---|
| L1 事实层 | build 已执行 | ✅ PASS |
| L2 身份层 | canonical fact_key 已按契约定义为五元组 | ✅ PASS |
| L3-A 契约落地 | **无**（判契约是否落地本身不需前提） | ❌ FAIL |
| L3-B 已落地合规 | **L3-A = PASS** | 🚫 **N/A** |
| L3-C 未落地标记 | **无** | 🚫 **PENDING** |
| L4 挂载层 | 存在「不产 fact 的源」 | ✅ PASS |
| L5 传导层 | 三项（P1/P2/P3，见 D57） | ❌ FAIL |

### 为何要区分 N/A 与 PENDING

- **N/A**：连判据对象都不存在（前提未成立）⟹ 谈不上达标与否
- **PENDING**：判据对象存在，但**测量手段缺失** ⟹ 结论未知

把二者混为一谈，会让「无法测量」看起来像「测了没达标」。

⚠ L3-B 的实际形态正是 N/A 的典型：
L3-A 为 FAIL ⟹ 没有任何已落地域 ⟹ **无 fact 可检验合规性**。
此前把它写成 FAIL 或「未实现」都是**误判**。

## D68 — `constraint` 通道：**语义不明，登记不硬塞**

⚠ 硬塞的两种伪做法及其问题：

| Hub 的 21 条 indexed 边 vs spec 的 21 条 indexed | **双向差集为空** —— 完全一致 |
| Hub 缺失的边 | 6 条，**全部是 wildcard**（`from="*"` / `to="$current"`） |

⟹ **纯 Hub 规划会丢 6 条 wildcard 边**，导致路径覆盖下降 = **负价值**。

### 裁定：Hub 优先 + spec 兜底（两层边集）

| 层 | 来源 | 数量 | 理由 |
|---|---|---|---|
| indexed | **Hub transition Fact** | 21 | 中枢 resolve 了就以中枢为准 |
| wildcard | spec state_machine | 6 | 中枢**未建模**（端点非注册状态） |
| `initial_state` | spec | 1 | 中枢未建模，且无法反推 |

### 实现要点

1. `HubInventory` 新增 `transitions` 字段（`(from, method, to)` frozenset），
   从 `facts/transition.jsonl` 读取，subject 按 `A->B` 拆分、method 取 `condition.field.name`
2. `_plan_paths()` 改签名接收 `hub_transitions`，wildcard 边在 BFS 时按**当前状态展开**
3. `HubInventory` 为空时**退化为纯 spec 行为**（向后兼容）
4. manifest 新增 `hub.state_graph` 记录两层边数与来源

### ★ 顺带修掉一个潜在缺陷

旧 `_plan_paths` 把 wildcard 边放进 `by_from["*"]`，
而 BFS 查 `by_from.get(states[-1])` —— `states[-1]` **永远不是 `"*"`**

## D75 — 第 0 步：bridge 种子保真度（对准 3.16% 那次的失败归因）

**日期**：2026-10-07　**范围**：同上

### 依据

`docs/step7_series_summary.md`：2026-09 的 12h AFLNet 实测
**ProtoKG 3.16% vs ChatAFL 10.57%**，根因归因为
「**Accept / User-Agent / URL 多样性不足 → server 频繁 reject**」。

实测桥接产物（修复前）：User-Agent **0**、Accept **1**、
URL **1 且为 `rtsp://localhost/seed`**（step7 原话「host 不存在, server 立刻 404」）。

⟹ Step 7a-d 的多样性修复全在 **LLM pathgen 链路**，
桥接是**另一条独立实现**，从未继承任何修复。

### 根因

| header | value_pool 候选数 | required_headers 是否声明 | 桥接产物 |
|---|---|---|---|
| `User-Agent` | **6** | ❌ **未声明** | **0**（根本没有） |
| `URL` | **3** | ❌ **未声明**（它是 request line） | 1 且 localhost |
| `Accept` | **3** | ✅ 仅 DESCRIBE | 1 |

### 修法（只动这三项）

1. **URL 轮转**：`_url_for(index, pools)` 从 `pools["URL"]` 的 3 个候选里轮转；
   候选含 `{{target_host}}:{{target_port}}` 占位符，交给
   `seedcorpus_to_raw` 既有的 `_resolve_all_placeholders` 解析
2. **User-Agent 注入**：`BASELINE_HEADERS` —— `required_headers.json` 未声明，
   故作为 baseline 注入每条 message
3. **Accept 轮转**：`ROTATED_HEADERS`

### ⚠ 刻意不动的三项

`Transport` / `Session` / `CSeq` / `Content-Type` **保持 `pool[0]`**：

- 它们是**协议结构性**的（Transport 决定传输层、CSeq 必须递增）
- 既有测试 `test_seedgen_uses_required_headers_from_kb` **钉死** `Transport: RTP/AVP`
  （value_pool 首个候选），轮转会打破它

⟹ 多样性收益集中在「客户端身份类」header 上，这是有依据的取舍，
不是遗漏。

### 轮转索引

用 **path 序号**（确定性，非随机），使同一批次可复现。
