## 二、方向 A：RFC 源抽取改造

### A1 候选定位换判据（解 DHCP 的实际卡点）

**现状**：`extract_transition_candidates()` 全文扫 `state\s+machines?` 字样
⇒ rtsp 7 处 ✅ / sip 15 处 ✅ / **DHCPv4 0 处 ❌**
⇒ DHCP 的 LLM 状态机通道**从未被调用**。

**新判据（协议无关，用「已识别的实体」而非英文措辞）**：

| 级 | 判据 | 命中 |
|---|---|---|
| **L1** | 段落含**已识别消息名**（N2 消息集）**且**含迁移动词（`respond`/`send`/`receive`/`enter`/`allocate`/`transition`） | DHCPv4 §3.1 |
| **L2** | 段落含**状态名**（N1 状态集）**且**含 ≥2 个不同消息名 | DHCPv4 §4.4 |
| **L3** | 同时含 ≥1 状态名与 ≥1 消息名（兜底） | — |
| 旧 | `state machine` 字样 | rtsp/sip ✅ |

★ **新旧并集**（不替换）⇒ rtsp/sip 的候选块**只增不减**。

### A2 ★「从内容判定类别」（本轮最重要的新增）

#### A2.1 为什么必须做

现状：类别判定**完全依赖 `rfc_config` 的章节号声明**
（`method_sections` / `field_sections` / …）。

**实测的脆弱性**（DHCPv4）：
- 36 份 RFC 章节号 **229 个里有 80 个重号**（每份都有 §1–§8，语义各异）；
- 全局配置必然误伤（`NVT` 来自 rfc6607 的 §4.3）；
- 只能靠新增 `sections_by_file` 逐文件声明来打补丁（36 份文件逐个配）；
- ⇒ **章节号是「位置」，而我们要判的是「语义」**；位置会撞车，语义不会。

#### A2.2 判据设计：四层判据链（优先级从高到低）

| 层 | 判据 | 依据 | 例子 |
|---|---|---|---|
| **L-A 形态层** | 块形态（`rfc_forms` 的 8 类） | 已有能力 | `table` ⇒ field/transition；`abnf` ⇒ field；`diagram` ⇒ transition |
| **L-B 标题形态** | 标题的**词形** | 已有部分能力 | PascalCase（`Content-Length`）⇒ field；全大写（`OPTIONS`）⇒ method；`N.N.N 数字码` ⇒ status |
| **L-C 正文句式** | 规范句式 | 已有形态 E 可扩展 | 「the format of the X command is」⇒ method（已有）；「X MUST be included in」⇒ required_header |
| **L-D 章节号配置** | `rfc_config` 的声明 | **降级为兜底 + 校验** | 仅在 L-A/B/C 都判不出时使用 |

★ **关键变化**：章节号从「**唯一判据**」降为「**兜底**」。
⇒ 新协议接入**不需要手工配章节号**；
⇒ 多 RFC 协议**不再有撞车问题**（内容判据与文件无关）；
⇒ 手工配置仍保留，用来**纠正**误判（人工干预能力不丢）。

#### A2.3 与现有 `_infer_kind_from_content` 的关系

现状：`_infer_kind_from_content()` 只在 `_section_kind()` 判不出时兜底，
且**已被实测证伪过两次**（「全大写 ⇒ method」被移除；「正文含 ABNF ⇒ method」被移除）。

⇒ **不能简单地把它的判据加回来**，必须：
- **先做对照实验**（见 §五）：把 A2 的判据做成**独立通道**，
  与现有章节号通道**并行运行**，在三个文本协议 + DHCPv4 上产出**逐条差集**；
- 只有当「内容版」在**不损失真知识**的前提下**显著减少误抽**，才切换默认口径。

#### A2.4 节点抽取规则（Phase A 的确定性部分）

| 规则 | 判据 | 产出 | 置信度 |
|---|---|---|---|
| **N1 状态节点** | 全大写术语 `\b[A-Z][A-Z-]{2,}\b`，排除消息名/缩写表/虚词；**与图形块出现的词取交集校验** | `state` | 图中出现=high；仅正文=medium |
| **N2 消息节点** | 协议名+消息后缀（`DHCP`+`DISCOVER`）或 ABNF 方法枚举（通道 A0 已有） | `message` | high |
| **N3 定时器节点** | `T1`/`T2` 式短标识，或「<名词> expiration/timeout」 | `timer` | medium |
| **N4 字段约束节点** | 表格块**首列**与已知状态集有交集 ⇒ 该表是「状态 × 字段」约束表 | `constraint` | high |
| **E1 图形边** | `diagram` 形态块内 `状态 --标签--> 状态` | `transitions_to`+`triggers` | **high** |
| **E2 表格边** | 表头列角色匹配（**已有 `_match_roles`**：from/trigger/to） | `transitions_to`+`triggers` | **high** |
| **E3 消息枚举** | 「can receive the following messages: X, Y, Z」枚举句 | `sends`/`receives` | medium |
| **E4 定时器共现** | 「T1 … expires … RENEWING」共现句 | `triggers` | medium |

★ **E1 是核心增量**（现状完全没有）：
箭头形态需覆盖 `-->` / `--->` / `==>` / `──>` / `->`，以及**标签在箭头上方/下方两行**；
图形块边界复用**已有的 `_merge_diagram_groups`**；
状态名要与 N1 状态集匹配（图中文字带对齐空格，需归一化）。

#### A2.5 ★ 一次性替换策略（D5：独立通道 → 验证 → **清除旧通道**）

**用户决策**：A2 做成**独立通道**；新通道建立并验证后，**把旧通道（章节号判据）清除掉**，
避免两条判据长期并存造成**判据分裂**（本项目已踩过：norm 侧与候选侧判据不一致 ⇒ 污染）。

**为什么不是长期并行**：
长期并行的最大风险不是「多花一次判定」，而是**两套判据在同一份产物里混用**
⇒ 出了错**无法归因**（是 config 判的还是 content 判的？）。

**执行序列**（三步，临时并行 → 验证 → 清除）：

| 步 | 动作 | 出口条件 |
|---|---|---|
| **S1** | 新增 `core/fused/rfc_classifier.py`（**独立通道**），与旧通道**临时并行**产出两份结果 | 两份结果都能产出（不崩） |
| **S2** | ★ **E-1 对照实验**：同一 kb + 同一 LLM 缓存下，逐条比对两通道的 fact 集合 | ① 真知识**净不减少**（漏抽 ≤ 误抽修复）<br>② 三协议方法集/字段集**逐条列出差异**并人工确认每条差异的方向<br>③ 报告归档到 `local/` |
| **S3** | ★ **清除旧通道**：删除章节号判据逻辑（`_section_kind` 的查表分支 + `_infer_kind_from_content` 的旧启发式）<br>⇒ **新通道成为唯一判据** | 现有护栏 **新增 0 / 消失 0**<br>+ 三协议 fact 集合与 S2 结论一致 |

★ **清除的范围界定（关键，避免误删）**：

| 对象 | S3 后的处置 | 理由 |
|---|---|---|
| **章节号 → 类别的判据逻辑**（`_section_kind` 的查表、`sections_by_file` 分支） | ❌ **删除** | 它就是「旧通道」本体 |
| **`rfc_config.json` 里的章节号配置数据** | ✅ **保留**（降级为**兜底 + 人工纠正入口**） | 数据不是判据；新通道判不出时仍可兜底；且保留人工干预能力 |
| **`_infer_kind_from_content` 的旧启发式**（已被证伪过两次的那两条） | ❌ **删除** | 新通道会**重写**这个函数（含更强的判据），而不是并列 |
| **A1 的候选定位判据**（`state machine` 字样） | ⏸ **暂不动**（阶段 3） | 它是**候选定位**，不是**类别判定** ⇒ 与 S3 正交 |

★ **S3 的前置条件（新通道必须覆盖旧通道的全部类别）**：
旧通道能判 6 类（`method`/`field`/`status`/`transition`/`outcome`/`required_header`）
⇒ **新通道必须能判全这 6 类**，否则删了旧通道就没有分类依据。
⇒ 这是 S2 的**硬性检查项**（逐类核对覆盖表）。

★ **S3 后的回退方式**：因为 `rfc_config` 的配置数据**保留**，
且旧逻辑在 git 历史里 ⇒ 回退 = 切 commit（不是靠开关）。

## 三、方向 B：中枢的 GraphRAG 组织（定位 = 检索层）

### B0 实体图投影（确定性，零 LLM）

**起点事实**（代码勘察结论）：中枢的 16 个桶**几乎全部**已可映射成图节点/边：

| 中枢桶 | 图中表示 |
|---|---|
| `methods` | 节点 `message` |
| `headers` | 节点 `entity` |
| `transitions` | **边** `transitions_to` + `triggers`（三元组拆两条） |
| `required_headers` | 边 `required_by`（method → header） |
| `message_instances` | 边 `instance_of` |
| `statuses` | 节点 `entity` |
| `precondition`/`session_header`/`url_template` | 边 `constrained_by` |
| `legal_boundary`/`response_expectation` | 边 `bounded_by` |
| `method_sequences` | 边 `followed_by` |
| `security`/`vuln_pattern` | 节点 `entity` + 边 `marked_by` |
| `protocol`/`actors` | 节点 `entity` |
| （A2 新增） | 节点 `state`/`timer`/`constraint` |

★ **关系的来源已存在**：`relation` 类 fact 的 `qualifiers` 里嵌着 Subject
（rtsp 实测 95/95 条全嵌）⇒ 图的原料齐备，**不需要 LLM 抽实体/关系**
（这是我们相对原始 GraphRAG 的结构性优势）。

**产物**（新增第 17 类维度）：
```
derived/per_source/<协议>/graph/
├── nodes.jsonl        {node_id, type, name, aliases[], source_owner, confidence, defined_in{}}
├── edges.jsonl        {edge_id, type, from, to, label, condition, source_owner, confidence, defined_in{}}
├── communities.json   {community_id, members[], summary, owner_mix, class}
└── graph_meta.json    {protocol, node_count, edge_count, isolated_node_ratio, largest_cc_ratio}
```

★ **每个节点/边带三个正交标注**（台账 × 置信度 × 溯源）：
```
{source_owner: "rfc", confidence: "high", defined_in: "file:rfc2131.txt#@1467"}
```
⇒ 论文可写「**high 置信度的迁移边全部来自 RFC §4.3，无一条来自 L2 实现层**」
—— 纯度证据在**图层面**的形态。

### B1 ★ 图分层（D2：两类知识分开）

**问题**：GraphRAG 的社区是「局部性」机制（社区内强相关、跨社区弱相关）
⇒ 对**弱结构**知识合适，对**强结构**知识（状态机）**会打散精确边**。

**实测的中枢构成**（rtsp 302 facts）：

| 知识类型 | 占比 | 性质 | 归属 |
|---|---:|---|---|
| `relation/target_state` | 17% | **强结构** | 精确图 |
| `relation/message_instance` | 13% | 强结构 | 精确图 |
| `header/*` | 52% | 弱结构 | 社区 |
| `status/definition` | 5% | 中等 | 社区 |
| `method/*` | 4% | 中等 | 社区 |

⇒ **建两张图（或一张图两个子图）**：

```
图 ① 精确图（结构图谱）
   节点：state / message / timer
   边：transitions_to / triggers / sends / receives / instance_of
   用途：邻域查询、路径枚举、状态机合成
   ★ 不做社区切分（会打散精确边）

图 ② 社区图（语义图谱）
   节点：header / status / method / constraint / entity
   边：constrained_by / required_by / marked_by / followed_by
        + **同 aspect 共现边**（弱连接，权重低）
   用途：Leiden 社区 + 社区报告 + 语义检索
```

★ **关键约束**：社区**不跨图** ⇒ 状态机的精确边不会被社区切分破坏。

### B2 完整 GraphRAG（D3：直接上完整版）

| 步骤 | 做法 | 产出 |
|---|---|---|
| **B2.1 合并** | 图 ② 的多 DiGraph（同对节点允许多条不同 `condition` 的边） | — |
| **B2.2 剪枝** | 度为 0 的孤立节点：**只标记 `pending_review`，不删除** | `isolated_node_ratio` |
| **B2.3 指标** | `isolated_node_ratio` / `largest_connected_component_ratio` | 参照区间（RFC-RAG-Agent）：0.1408 / 0.8002 |
| **B2.4 社区** | **Leiden** 社区检测（`python-igraph`）；不可用时**降级为连通分量** | `communities.json` 的 members |
| **B2.5 报告** | 每个社区一段 LLM 摘要：「含哪些实体、哪些关系、边界条件是什么」+ **`owner_mix`**（各源贡献几条） | `communities.json` 的 summary |

★ **规模优势**：我们的图规模是**几百 fact**（rtsp 302 / sip 361 / smtp 450）
⇒ 社区数量预计 **5–20 个** ⇒ 报告成本仅几十次 LLM 调用
（微软 GraphRAG 在百万 chunk 上要几万次）。

★ **社区报告带通道标注**（融合带来的新能力）：
```json
{"community_id":"c1", "summary":"客户端初始化与地址获取…",
 "owner_mix":{"rfc":6,"profile":0}, "class":"L1"}
```
⇒ 论文可用「**按知识层分层的社区视图**」：L1 社区是规范定义，L2 社区是实现观测。

### B3 检索层（D1：GraphRAG 的落点）

**三种检索模式并存**：

| 模式 | 入口 | 实现 | 状态 |
|---|---|---|---|
| **M1 状态邻域** | 给状态 S，返回一跳邻居 | 改造 `retrieve_subgraph`（读图、6 种边） | **已有雏形**，需扩边 |
| **M2 路径查询** | 给 (from,to)，枚举所有简单路径 + 边条件 | 新增 `retrieve_paths` | 新增 |
| **M3 社区报告** | 给查询，返回相关社区的报告 | 新增 | 新增 |

**混合排序**（检索层的实际用法）：
```
粗排：社区报告的相关性（LLM 生成的摘要 ⇒ 可用 embedding 或关键词匹配）
细排：子图内的精确事实
⇒ 上下文 = 相关社区报告 + 精确子图（而非原始 chunk 向量 top-k）
```

★ **`retrieve_subgraph` 改造的关键**：边类型从**代码硬编码**变**数据驱动**
```json
"traversal": {
  "method_to_header": ["required_by"],
  "state_to_state":   ["transitions_to"],
  "method_to_transition": ["triggers"],
  "state_to_message": ["sends","receives"],
  "message_to_constraint": ["constrained_by"]
}
```
⇒ 加边类型**不改这个函数**；三协议行为**必须逐字段不变**（硬护栏）。

★ **M2 与已有 `target_state_path` 的关系**：
`generate_seeds_react(bundle, ..., target_state_path=[...])` 已支持「按给定状态路径生成种子」，
但路径是**人工给的** ⇒ 有了图 ⇒ **路径可自动枚举** ⇒ 路径式种子。

## 四、两个方向的实施顺序（**含依赖**）

```
① G0  图模式注册表 graph_schema.json        ← 纯新增，零依赖
② A2.1 节点抽取 N1/N2/N3                     ← 零 LLM，是 A1/B0 的前置
③ A2.2 图形边 E1 + 表格边 E2                 ← 零 LLM（复用 _match_roles）
④ B0  实体图投影（图 ← 中枢 16 桶）          ← 零 LLM，中枢不动
⑤ B1  图分层（精确图 / 社区图）              ← 零 LLM
⑥ A2.3 ★ 内容判据通道（与章节号通道并行）      ← ★ 必须先做对照实验
⑦ A1  候选定位换判据（L1/L2/L3 ∪ 旧）        ← 依赖 ② 的实体集
⑧ B2  完整 GraphRAG（Leiden + 社区报告）      ← 依赖 ④⑤
⑨ B3.1 retrieve_subgraph 改造（读图）          ← 依赖 ④
⑩ B3.2 路径查询 + 路径式种子                  ← 依赖 ⑧⑨
⑪ B3.3 图级纯度闸                            ← 依赖 ⑩
```

## 五、★ 对照实验设计（归因边界必须干净）

按专家工作流「对照实验必须标注混杂变量与归因边界」：

### E-1：内容判据 vs 章节号配置（A2 的核心实验）

| 项 | 设计 |
|---|---|
| **自变量** | 类别判据来源：`config`（旧）vs `content`（新）vs `both` |
| **因变量** | ① 抽出的 fact 集合（逐条差集）② 方法集 ③ 字段集 ④ 误抽数 ⑤ 漏抽数 |
| **协议** | rtsp / sip / smtp（回归）+ DHCPv4（新协议） |
| **混杂变量** | ① LLM 通道的随机性（⇒ **必须用同一磁盘缓存**，缓存键含 prompt_version）② 章节号配置本身的正确性（⇒ 逐协议标注「配置是作者手工确认过的」） |
| **归因边界** | ✅ 可干净归因：「同一 kb + 同一缓存 + 只换判据来源」下的 fact 集合差异<br>❌ **不能**归因：「内容判据更好」这一**总体结论** —— 因为只在 4 个协议上测，且其中 3 个是**已知正确**的（它们的方法集已人工确认） |
| **失败判据** | 任何协议的真知识**净减少**（漏抽 > 误抽修复）⇒ 判据不合格，不切换默认 |

### E-2：候选定位换判据（A1 的实验）

| 项 | 设计 |
|---|---|
| **自变量** | 候选定位判据：`old`（`state machine` 字样）vs `new`（L1/L2/L3 ∪ old） |
| **因变量** | ① 候选块数量 ② LLM 调用的候选文本 ③ 抽出的迁移边集合（逐条差集） |
| **控制** | **LLM 缓存必须重置**（候选文本变了 ⇒ 缓存键变 ⇒ 这是被测机制的一部分，不是混杂） |
| **归因边界** | ✅ 可归因：「同一 LLM、同一 prompt，换候选定位 ⇒ 迁移边差异」<br>⚠️ **注意**：候选变多 ⇒ LLM 调用变多 ⇒ **成本上升**要单独报 |

### E-3：图组织 vs 无图（B 的实验）

| 项 | 设计 |
|---|---|
| **自变量** | 检索层：现有（扁桶 + 手写 BFS）vs 图（社区报告 + 子图） |
| **因变量** | ① 检索命中的知识覆盖率 ② 社区报告的 LLM 成本 ③ **种子质量**（最终指标） |
| **归因边界** | ⚠️ **种子质量的变化不能直接归因给「GraphRAG」** —— 因为同时改了「路径式种子」这个**产出形态**（种子数变了）⇒ 必须**分开做两个对照**：<br>① 只换检索层（种子形态不变）② 只加路径式种子（检索层不变） |

★ **E-3 的②很重要**：路径式种子会改变**种子数量** ⇒ 影响论文口径 ⇒
建议路径式种子**独立开关、默认关闭**，先在实验分支上量出影响再决定。

### ★ 实测得到的三条「形态事实」（修正了原设计假设）

1. **RFC 2131 没有 ASCII 状态迁移图** —— 只有 **Figure 3 消息时序图**
   （client/server 两列，含 DISCOVER/OFFER/REQUEST/ACK/RELEASE）；
2. **状态名只在散文里**（"the client reverts to INIT state"）；
3. **RFC 2326 的状态机不是图形**，而是「`Init:` + 描述」的**定义列表**
   ⇒ 形态层的 diagram 判据识别不出 ⇒ 只靠图形块收状态会**漏掉 rtsp 全部状态**。

⇒ 原方案里「E1：从图形箭头解析迁移」**不适用于 DHCP** ⇒ 改为
**E1'：图形内的消息序列**（时序图/迁移图通用）+ **E3：散文迁移句**。

### ★ 调试中修掉的 6 个判据缺陷（都是实测发现）

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | 位域图/报文图被当状态图 | 8 个真状态抽成 **76** 个 | 「状态图」判据：含迁移语义 ∧ 不含 octet/bit/field 语义 |
| 2 | 消息名本身是全大写 | DHCPOFFER 被当状态 | 抽取顺序：**先消息后状态** + 显式排除集 |
| 3 | RFC 折行截断 | `DHCPREQU`+`EST` 被当术语 | 「拼接后是否是本文件出现过的更长词」判据 |
| 4 | 术语/方法定义与状态定义**形态同构** | rtsp 19 个状态里 15 个误抽 | **迁移语义交叉校验** |
| 5 | 迁移语义判据里裸 `in\|to\|from` 太宽 | Conference/SETUP 被放行 | 收紧为「state 邻近」+「迁移动词+状态名」+「同段落共现」 |
| 6 | 折行判据把「与上一行末词相同」误判 | DHCPREQUEST 本身被当碎片 | 显式排除同词 |

## 附：让 RFC 通道的状态机真正生效（2026-11-08，`838d935`）

★ **起因**：用户质疑「阶段 3 已改过 ``state machine`` 候选定位，
为什么骨架还在用手工抄？」⇒ 核实发现**改造做了，但通道没真生效**。

### ★ 核心教训：「改进了候选定位」≠「通道真的生效」

LLM 其实**抽到了 24 条迁移**（磁盘缓存里有，质量也不差），但被**质量闸全拦下**：

```json
// derived/per_source/dhcpv4/transition_quality_gate.json
{"total": 24, "kept": 0, "dropped_method_not_a_method": 24}
```

⇒ 中枢只能用**手工骨架**（6 条，owner=profile）
⇒ 纯度闸把骨架边也拦掉 ⇒ **纯 RFC 单源下路径式种子 = 0 条**。

### 根因：两处**判据分裂**（同一形态两处实现）

| # | 分裂点 | 现象 | 修法 |
|---|---|---|---|
| ① | `_rfc_source_methods` **不支持 `sections_by_file`** | DHCPv4 全局清单为空（配置在文件专属里）⇒「已知方法集」**恒空** ⇒ 闸的判据②全拦 | 按**当前文件**取清单（全局+专属并集）；**保留「无配置⇒空集」契约** |
| ② | 缺「消息清单表」形态（阶段 3 有「通道 A0d」但这里没有） | 同一形态两处实现 ⇒ 又被拦 | 补**形态 F** + **协议名前缀判据**（消息名=协议名词干+后缀） |
| ③ | 图投影 owner **写死 `profile`** | 消解是 RFC 优先 ⇒ 迁移边可能来自 LLM(rfc) ⇒ 纯度闸误拦 | 用 `bundle["transitions_by_source"]` 取**真实 owner** |

★ 形态 F 的细节：
· 词干归一：`DHCPv4` ⇒ 去尾部数字 ⇒ 去尾部 `V` ⇒ `DHCP`（否则匹配失败）；
· **排除「已知头字段」这条路线不可行**（实测）：消息名在 headers 桶里
  **也带 definition/syntax** ⇒ 会被误排除（DHCPv4 方法集 9 → 2）。
