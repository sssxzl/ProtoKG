# ProtoKG 中枢 —— 四类规则集设计

阶段 4.8b 第一段产出。本文件是 `core/fused/pipeline/rules/` 的设计真源，
契约依据为 `fused_hub/docs/fused_canonical_spec.md`（Final Frozen）与
`fused_hub/docs/fused_canonical_spec.md`。

## 0. 设计约束（本设计的硬边界）

以下 6 条来自 4.8b 指令，逐条落到实现：

| # | 约束 | 落地方式 |
|---|---|---|
| C1 | 只处理现有 ProtocolNorm 能**明确识别**的知识 | 每条规则的 `eligibility_predicate` 必须能从 norm 的**结构化字段**或**固定格式**判定；判不出 → 投影返回 `None` → 契约 §2.3 规定 emit 0，**不是** violation |
| C2 | property 名取自 property_registry 的 18 个受控 property | 每条规则声明的 property 必须 `index.property_rule(p) is not None`，实现里有断言测试逐条钉死 |
| C3 | condition 取自 condition_schema 的 8 类 AST | 每条规则产出的 condition 必须是 8 类之一（`always` / `unknown` / `state` / `direction` / `field` / `numerical` / `temporal` / `packet_position`），实现里同样有断言测试 |
| C4 | 不发明新 kind | `fact_key.kind` 只取 `KIND_DOMAIN` 的 5 值；`actor` 只取 `ACTOR_DOMAIN` 的 5 值 |
| C5 | `emit_kind` 只能用 `entity` 或 `relation` | GraphCandidate.kind 只取 `GRAPH_ENTITY` / `GRAPH_RELATION` |
| C6 | rule 字段按契约 §2.2 与 §8.x | Candidateization 8 字段见 §2.2；Graph MappingRecord 字段见 §8.4.1 |

## 2. 受控域（全部实测自 `fused_hub/schema`）

```
condition_schema.anyOf type（8 类）:
    always / unknown / state / direction / field / numerical / temporal / packet_position
condition_schema.definitions.predicate:
    { lhs: {type: ref|literal, ref: str}, op: <15 个比较算子>,
      rhs: {type: literal|ref|range|set, value: any} }
condition_schema.definitions.composite:
    { type: "composite", operator: AND|OR|NOT, children: [<完整 condition>…] }

fact_key.kind    : method / header / constraint / state / transition
fact_key.actor   : client / server / both / not_applicable / unknown
assertion.type   : enum / bool / number / range / set / regex / condition / relation / ref / text
assertion.modality: must / must_not / should / should_not / may /
                    normative_unspecified / descriptive / observed / unknown
scope.type       : unrestricted / bounded / unknown
evidence.locator : { type: <str>, value: <any> }
```

`property_registry` 的 18 个受控 property 与其
`allowed_kinds` / `allowed_assertion_types` / `eligible_claim_classes` 见

## 3. Candidateization Rules（契约 §2.2 的 8 字段）

规则字段：`rule_id` / `applicable_protocol_norm_type` /
`eligibility_predicate` / `fact_key_projection` / `assertion_projection` /
`scope_projection` / `evidence_projection` / `emit_cardinality`。

### CR-1 `cand.rfc.method_existence` ← **kb/spec/rfc2326.txt 的主力规则**

| 字段 | 值 |
|---|---|
| `rule_id` | `cand.rfc.method_existence` |
| `applicable_protocol_norm_type` | `method` |
| `eligibility_predicate` | `norm.kind == "method"` ∧ `norm.name` 非空 ∧ `norm.kb_source_type == "rfc"` ∧ `modal(norm.content) is not None` |
| `fact_key_projection` | `RawFactKeyCandidate(kind="method", actor="client", subject=norm.name, property="existence", condition={"type":"unknown"})` |
| `assertion_projection` | `AssertionCandidate(value=True, type_hint="bool", modality_hint=modal(norm.content))` |
| `scope_projection` | `ScopeCandidate(type_hint="unrestricted", constraints={})` |
| `evidence_projection` | 1 条 `EvidenceCandidate`，`locator={"type":"section","value":{"source":norm.source,"norm_id":norm.norm_id}}` |
| `emit_cardinality` | `one` |

**`modal()` 的确定性提取**（C1 的核心，判不出就 emit 0）：

    MUST | SHALL            -> "must"
    SHOULD                -> "should"
    MAY                   -> "may"
    以上都没有，且 kb_source_type == "rfc"  -> "normative_unspecified"
    其余                                     -> None（emit 0）

`normative_unspecified` 的依据是 `phase_a.py` 步骤 7 的注释与契约 §7：
「已确定属规范性陈述但无法安全映射到 must/should/may，属**已确定**」。
它落在 `assertion.modality` 的受控域内，且被
`claim_classification_rules.cc.rfc.normative_unspecified`
（`{"modality": "normative_unspecified", "source_type": "rfc"}`）命中 →
`claim_class = "normative"`。

**实测结果**（11 条 rfc method norm）：7 条 `must`，
4 条（OPTIONS / ANNOUNCE / TEARDOWN / GET_PARAMETER）`normative_unspecified`。
**11 条全部可识别，0 条 emit 0** —— 这是把 `normative_unspecified` 用对的结果；
若只认 must/should/may，4 条会被丢掉，违反 C1 的「明确识别」。

**为什么 `actor="client"`**：RTSP 是 client 驱动的，11 条 method norm 的正文
示例一律是 `C->S:`。`existence` 问的是「这个方法存在且必须被支持」，其
责任方是发起方即 client。`ANNOUNCE` 的 server→client 方向属已知简化，
记为范围声明（§5.1）。

**为什么 `condition={"type":"unknown"}`**：契约 §7.6 规定
「condition 必填 —— 抽不到时必须为 `{"type": "unknown"}`」。
method norm 不携带任何状态前置条件，不编造 `state` 类 AST。

### CR-2 `cand.traffic.method_occurrence`

| 字段 | 值 |
|---|---|
| `rule_id` | `cand.traffic.method_occurrence` |
| `applicable_protocol_norm_type` | `message` |
| `eligibility_predicate` | `kind=="message"` ∧ content 完全匹配 `^method=(\S+) occurrences=(\d+) protocol=(\S+)$` |
| `fact_key_projection` | `(kind="method", actor="client", subject=<METHOD 大写>, property="occurrence", condition={"type":"unknown"})` |
| `assertion_projection` | `(value=<int occurrences>, type_hint="number", modality_hint="observed")` |
| `scope_projection` | `unrestricted` + `{}` |
| `evidence_projection` | 1 条，`locator={"type":"capture","value":{"source":norm.source,"norm_id":norm.norm_id}}` |
| `emit_cardinality` | `one` |

选 `occurrence` 而非 `observed_occurrence_rate` 的理由：
`observed_occurrence_rate` 的 `resolution_required_fields` 是
`["value","observation_scope"]`，而 `_completeness` 查的是 assertion 的
**顶层 view key**，`observation_scope` 永远取不到 → 该 property 的 Fact
**永远 partial**。`occurrence` 的 required 是 `["value","modality"]`，
两者都能确定 → `completeness="complete"`。选能让 Phase A 给出
`complete` 的那个 property，是有依据的选型而非偏好。

`modality_hint="observed"` 落在受控域内，且
`claim_classification_rules.cc.traffic.observational`
（`{"source_type": ["traffic_pcap","traffic_raw"]}`）命中 →
`claim_class="observational"`；`occurrence` 的
`eligible_claim_classes` 含 `observational` ✓。

### CR-3 `cand.traffic.header_occurrence`

同 CR-2，正则改为 `^(.+?) header occurrences=(\d+) protocol=(\S+)$`，
`fact_key` 改 `(kind="header", actor="client", subject=<Header 名原样>, property="occurrence", …)`。
实测只会命中 `CSeq`（`field.cseq`）与 `rtsp_url`（后者格式不同，不匹配 → emit 0）。

### CR-4 `cand.expert.error_code_value_type`

| 字段 | 值 |
|---|---|
| `applicable_protocol_norm_type` | `error_code` |
| `eligibility_predicate` | `kind=="error_code"` ∧ content 可 `json.loads` ∧ 具 `class` / `code` / `reason` 三键 |
| `fact_key_projection` | `(kind="constraint", actor="server", subject=f"status.{code}", property="value_type", condition={"type":"always"})` |
| `assertion_projection` | `(value=<class>, type_hint="enum", modality_hint="descriptive")` |
| `emit_cardinality` | `one` |

`kind="constraint"`：`KIND_DOMAIN` 没有 `status_code`，而 `value_type` 的
`allowed_kinds` 是 `[header, constraint]`。`subject` 取
`status.<code>` 使其成为一个可被 subject_registry 归一的 subject。
`condition={"type":"always"}`：error code 表是**无条件**成立的静态事实，
这是 8 类 AST 里唯一表达「无条件」的取值，且比 `unknown` 语义更强。

`modality_hint="descriptive"`：error code 表是描述性的，不是规范性要求。
`claim_class` 由 `cc.expert_note.default_interpretive` 判定为 `interpretive`，
而 `value_type` 的 `eligible_claim_classes` 含 `interpretive` ✓。

### CR-5 `cand.expert.security_note_condition`

| 字段 | 值 |
|---|---|
| `applicable_protocol_norm_type` | `security_note` |
| `eligibility_predicate` | `kind=="security_note"` ∧ JSON 可解析 ∧ 具 `note_id` / `category` / `trigger_method`（非空数组） |
| `fact_key_projection` | `(kind="method", actor="client", subject=<trigger_method[0]>, property="security_condition", condition=<§2 predicate 构造>)` |
| `assertion_projection` | `(value=<note 文本>, type_hint="text", modality_hint="must")` |
| `emit_cardinality` | `many`（一条 note 的 `trigger_method` 有多个时逐个 emit） |

condition 用 `field` 类 AST，predicate 按
`condition_schema.definitions.predicate` 精确构造：

    {"type": "field",
     "field": {"name": <trigger_field>,
               "predicate": {"lhs": {"type": "ref", "ref": <trigger_field>},
                             "op": "eq",
                             "rhs": {"type": "literal", "value": ""}}}}

只有 `trigger_field` 非空时才构造 `field` 类；否则退回 `{"type":"unknown"}`。

**只取 `trigger_method[0]`**：多个 trigger method 会产生**不同 subject**的
Fact（同一条 note 在两个方法下都成立），语义正确；但本设计只对
`trigger_method` 的**第一个**元素 emit，避免为同一 note 生成语义重叠的多条
Candidate。记为范围声明（§5.1）。

`security_condition` 的 `allowed_kinds` 含 `method` ✓，
`allowed_assertion_types` 是 `[condition, text]`，此处取 `text` ✓。
`eligible_claim_classes = [security, normative, observational]`；
`security_note` 源的 claim_class 由
`cc.security_notes.security_hint`（`file_or_path_hint: "kb/expert_note/security_notes.json"`，
实测该 source 正是 `expert_note/security_notes.json`）判定为 `security` ✓，
是 `security` tier 的**第一优先级**。

### CR-6 `cand.traffic.server_method_capability`（2026-10-08 新增）

| 字段 | 值 |
|---|---|
| `rule_id` | `cand.traffic.server_method_capability` |
| `applicable_protocol_norm_type` | `protocol` |
| `eligibility_predicate` | `kind=="protocol"` ∧ `parse_public_methods(norm)` 可识别 |
| `fact_key_projection` | **N 条** `(kind="method", actor="server", subject=<每个方法名>, property="existence", condition={"type":"unknown"})` |
| `assertion_projection` | **N 条** `(value=True, type_hint="bool", modality_hint="observed")`，与 fact_key 按位置配对 |
| `scope_projection` | `ScopeCandidate(type_hint="unrestricted", constraints={})` |
| `evidence_projection` | 1 条 `EvidenceCandidate`，`locator={"type":"capture", ...}`（与 CR-2/CR-3 同级） |
| `emit_cardinality` | `many`（一条 norm 的 N 个方法逐个 emit；**依赖 D61 的 0..N 实现修复**） |

content 固定格式（`core/extractors/traffic_session_log.py` 产出）：

    server-advertised methods (8): ['DESCRIBE', 'GET_PARAMETER', ...]

**计数自校验（C1 的落地）**：content 里声明的数量与实际解析出的数量不一致时，
返回 `None` ⟹ emit 0。**不**静默取前 N 个 —— 那会把「解析不可信」伪装成
「server 只支持这几个方法」。同理空列表、非匹配前缀均为 emit 0。

**为什么 protocol kind 里只有这一类被消费（§8 的部分推翻）**：
§8 把 `protocol` / `actor` 整个 kind 列为「刻意不实现」，理由是「部署事实，
不是协议**问题**」。该理由对 `protocol.rtsp_transport`
（`transport distribution: {'TCP': 20}`）与 `actor.rtsp_server`
（`RTSP server observed on ports [8554]`）**仍然成立** —— 二者是抓包部署画像。

但 `protocol.rtsp_public_methods` 不同：RTSP 响应头 `Public:` 是 server
**自述能力声明**（"我实现了哪些方法"），且可无损映射到既有受控件，不发明语义：

- `kind="method"` —— `property_registry.existence.allowed_kinds` 含之
- `property="existence"` —— CR-1 已在用，`allowed_assertion_types=["bool"]`
- `actor="server"` —— `ACTOR_DOMAIN` 内；与 CR-1 的 `"client"` 相对
- `assertion=bool(True)` + `modality="observed"`

**与 CR-1 各自独立（不是互相依赖）**：CR-1 是 rfc 源独立声明的规范事实
（actor=client, modality=normative/must），CR-6 是 traffic 源独立观测到的
实现事实（actor=server, modality=observed）。actor 不同 ⟹ fact_key 不同 ⟹
不误合并。★ **CR-6 不以「与 CR-1 的差集」为价值** —— 见 §8.1.1 的定位修正。

**CR-6 的独立价值**：对 fuzzer，「server 声明支持什么」决定
「哪些 method 值得构造测试」，这在完全没有 rfc 源参与时照样成立。

实测产出：3000 条 `protocol` norm 中 1000 条 eligible
（其余 2000 条是 `protocol.rtsp_transport`，正确被排除），
发出 8000 条 CandidateProposal，去重后 8 个 distinct server 方法。

⚠ 本 KB 上这 8 个方法**全部 ⊆ RFC 的 11 个**，故对 `HubInventory.methods`
净增量为 0（实测）。若换一个 KB（server 支持 RFC 之外的方法），
才会有净增量 —— 但那仍不应成为 CR-6 存在的理由。

### CR-7 `cand.source.method_definition`（2026-10-08 新增，让第五源进 Hub）

| 字段 | 值 |
|---|---|
| `rule_id` | `cand.source.method_definition` |
| `applicable_protocol_norm_type` | `method` |
| `eligibility_predicate` | `kind=="method"` ∧ `kb_source_type=="source"` ∧ `name` 非空。★ **不依赖任何 modality** |
| `fact_key_projection` | `(kind="method", actor="server", subject=<norm.name>, property="existence", condition={"type":"unknown"})` |
| `assertion_projection` | `(value=True, type_hint="bool", modality_hint="observed")` |
| `scope_projection` | `ScopeCandidate(type_hint="unrestricted", constraints={})` |
| `evidence_projection` | 1 条，`locator={"type":"code_branch", ...}`，`source_type="source"` |
| `emit_cardinality` | `one` |

**修复的断点（实测，非推断）**：修复前 source 源抽取正常（产出 1 条
`method.REGISTER`），但 **11 条规则逐条试无一产出 Candidate** ——
Hub 里 0 条 source fact。根因是唯一的 `kind="method"` 消费方 CR-1 的
eligibility 依赖 `extract_rfc_modality()`，该函数要么在正文找
MUST/SHOULD/MAY，要么要求 `kb_source_type=="rfc"`；源码正文两者皆无 ⟹
恒 `None`。**这不是抽取缺陷，是缺一条面向 source 源的 CR。**

#### ★ 五源 actor 语义统一（本规则的 actor 不是「为了跟谁融合」而选的）

契约对 actor 的定义是 `fact.schema.json:34` **"Actor this fact applies to"**
（这条事实适用于**谁**），**不是**「谁声明的」，更**不是**「跟谁融合」。
因此填法只能由**事实本身**推出，不能从融合目标倒推：

| 源 | norm 形态 | 该 fact 陈述的是 | actor |
|---|---|---|---|
| rfc | `method` | 规范定义该方法，应由 client 使用 | `client` |
| traffic | `message` | 观测到 **client** 发出该方法 N 次 | `client` |
| traffic | `public_methods` | **server** 自述支持该方法 | `server` |
| traffic | `field`/header | 该头在 client 请求中出现 N 次 | `client` |
| **source** | `handleCmd_X` | **server** 代码实现了该方法处理 | `server` |
| source | 客户端发出侧 | → `core/source_a` provenance 轨，**不进 Hub** | — |

**融合是结果而非目的**：CR-6（traffic 自述）与 CR-7（source 实现）陈述的
是同一件事（server 提供此方法）⟹ actor 同为 `server` ⟹ fact_key 相同 ⟹
Claim 聚合为 1 Fact 2 Claims（声明 + 实现，双源印证）。这是两者**碰巧在
陈述同一件事**的自然结果，不是刻意对齐。rfc 侧（actor=client）说的是
「规范要求 client 能用」，属另一个事实，独立成立。

#### C-1 边界（纵深防御）

只消费**服务端定义**。客户端发出侧（`RTSPClient` / `RTSPRegisterSender`）
在 extractor 层被 `_CLIENT_SIDE_FILES` 挡掉，CR-7 再加一道
`kind` / `name` / `kb_source_type` 三重校验作纵深防御。
理由（`core/source_a/__init__.py` C-1）：**发出是使用，服务端能处理才是提供** ——
把客户端调用抽成「liveMedia 支持 REGISTER」是语义错误。

## 4. Pair-Generation Rules（契约 §3.4.2 的 4 字段）

字段：`rule_id` / `applicable_fact_kinds` / `eligibility_predicate` / `pair_emit`。

### PG-1 `pair.same_element`

    rule_id                = "pair.same_element"
    applicable_fact_kinds  = ()                      # 不限制
    eligibility_predicate  = 两端 canonical fact_key 同 kind
    pair_emit              = 两端 canonical fact_key 同 subject

**设计取舍（重要）**：契约 §3.4.1 允许任何 rule 组合进入 pair universe。
本设计**只**生成「同一协议元素的不同侧面」的 pair，**刻意不**生成
「同 property 跨 subject」的 pair。理由：契约的
`comparison_policy.comparison_algorithm_reference` 明确
「Never let LLM guess logical relations」，其
`decidable_subset_supported` 只有 `{equal, disjoint}`。
两个**不同协议元素**的 existence 断言（DESCRIBE 存在 vs PLAY 存在）之间，
唯一可判定的结论永远是 `insufficient_evidence` —— 零信息量。
若启用同 property 跨 subject 规则，11 个 method 会立刻产生
C(11,2)=55 个全 `insufficient_evidence` 的 Match Audit，纯粹的噪声。

「同 subject 不同侧面」才是有信息量的：`method/DESCRIBE/existence`
（rfc 规范：存在）与 `method/DESCRIBE/occurrence`（traffic 观测：出现 1 次）
描述同一元素的不同侧面，`related` 是**可判定的**真实结论。

**实测**：真实数据下 PG-1 命中 5 个 pair
（DESCRIBE / OPTIONS / PLAY / SETUP / TEARDOWN 各一个
existence × occurrence）。

## 5. SemanticRelationEvaluationRule（契约 §3.4.4 的 4 字段）

字段：`rule_id` / `applicable_fact_kinds` / `eligibility_predicate` / `relation`。
求值是 **ordered first-match-wins**（§3.4.5），最后一条必须是
`semantic_relation_fallback` / 恒 true / `insufficient_evidence`。

### SR-1 `sem.same_subject_refinement` → `refinement`

    eligibility: 两端 canonical fact_key 同 subject ∧ 两端 Fact 的
                 resolved assertion 完全 canonical equal
    relation:    refinement

同 subject + 同 assertion 意味着两条记录说的是同一件事的两种来源表述，
后者是对前者的细化。

### SR-2 `sem.same_subject_related` → `related`

    eligibility: 两端 canonical fact_key 同 subject
                 ∧ (两端 resolved assertion 不同 ∧ 不是 disjoint)
    relation:    related

覆盖实测的 existence × occurrence 场景：同 subject、断言不同
（`true` vs `1`）、类型不同（bool vs number）故非 disjoint → `related`。

### SR-3 `semantic_relation_fallback` → `insufficient_evidence`

契约 §3.4.5 强制的兜底，`applicable_fact_kinds=()`，
`eligibility_predicate` 恒 true。`build_fallback_evaluation_rule()` 已提供，
规则集构造时**自动追加**，调用方不得自行拼。

> **实现纪律**：本规则集**刻意只提供 SR-1 / SR-2 / fallback 三条**。
> `different` 与 `insufficient_evidence` 的主动判定需要比较 policy 未覆盖的
> 语义（如「一个 claim 显式否定另一个」），当前无可执行规则，故不发明。

## 6. Fact 与 Claim Graph Derivation Rules

契约 §8.14.1 / §8.14.5 定义的是 **GraphCandidate 序列**，
不是 `graph_registry.derived_field_mapping` 里的 MappingRecord
（后者是 upstream spec graph 专用，阶段 4.6 已实现）。因此本类规则的形态是：

    rule_id / emit_kind / applicable_predicate / build(facts, claims_by_fact)

`emit_kind` 只取 `entity` / `relation`（C5）。
`GraphCandidate.fields` 的键沿用阶段 4.6 已实现的 7 个受控 target_field：
`/entity_type` `/canonical_name` `/derived_from` `/from` `/to` `/relation_type`。

### GR-1 `graph.rfc.method_entity`（emit_kind = **entity**）

    applicable: Fact.fact_key.kind == "method"
    build:      每个 method Fact 产出一条 GraphCandidate
                {"kind": "entity",
                 "fields": {"/entity_type": "method",
                            "/canonical_name": fact.fact_key.subject,
                            "/derived_from": {"fact_ids": [fact.fact_id],
                                             "claim_ids": []}}}

`entity_type="method"` 在 `graph_registry.entity_types` 的 18 个受控值内 ✓。

### GR-2 `graph.rfc.state_entity`（emit_kind = **entity**）

    applicable: Fact.fact_key.kind == "state"
    build:      {"kind": "entity",
                 "fields": {"/entity_type": "state",
                            "/canonical_name": fact.fact_key.subject,
                            "/derived_from": {...}}}

`state` 同样在 entity_types 内。本设计不消费 `state_machine` kind 的
ProtocolNorm（§5.2），因此真实数据下 GR-2 命中 0 条；
保留该规则是为了 4.9 接上 state_machine 后无需改规则集。

### GR-3 `graph.method_valid_in_state`（emit_kind = **relation**）

    applicable: 存在两个 method Fact，其 resolved assertion 的
                condition 为 {"type": "state", "state": {...}} 且 state 名相同
    build:      {"kind": "relation",
                 "fields": {"/relation_type": "valid_in_state",
                            "/from": GraphRef("fact", <A.fact_id>),
                            "/to":   GraphRef("fact", <B.fact_id>),
                            "/derived_from": {"fact_ids": [A,B], "claim_ids": []}}}

`relation_type="valid_in_state"` 在
`graph_registry.relation_types` 的 3 个受控值内 ✓。
`/from` `/to` 必须是显式 `GraphRef`（契约 §8.11 禁止靠字符串形态猜 type）。
真实数据下 11 个 method Fact 的 condition 全是 `{"type":"unknown"}`
（CR-1 的设计选择），故 GR-3 命中 0 条 —— 记为已知空转，
不为了让它「有产出」而编造 state 条件。

### GR-4 `graph.method_returns_code`（emit_kind = **relation**）

    applicable: 存在 kind="constraint" 的 Fact（CR-4 产的 status.NNN）
                且其 subject 形如 status.<code>
    build:      {"kind": "relation",
                 "fields": {"/relation_type": "returns_code",
                            "/from": GraphRef("fact", <method fact_id>),
                            "/to":   GraphRef("fact", <error_code fact_id>),
                            "/derived_from": {...}}}

`returns_code` 同样在 relation_types 内。
实测：CR-4 从 43 条 error_code norm 产出 Fact 后，本规则可把
method Fact 与 status fact 连起来，是**真实可判定**的结构关系
（method 存在且 status.<code> 存在 ⇒ 该 method 可返回该 code 类别）。
不判定「哪个 method 返回哪个具体 code」——那需要 state_machine，
当前无可执行规则，不发明。

## 8. §5.2 刻意不实现的 kind 及理由

这些 kind 的 content **可解析**，但解析后**无法映射到 18 个受控 property
中的任何一个而不发明语义**。按 C1「只处理能明确识别的知识」全部不实现，
并在此记录理由，避免后续误以为是遗漏：

| kind | 为什么不做 |
|---|---|
| `state_machine` | content 是方法**序列**。契约的 fact_key 是「一个协议问题的完整记录」，把序列塞进 assertion 需要定义新的 assertion 形态（既非标量也非受控 set 语义）——见 §8.3 的查证与结论 |
| `outcome` | `status code distribution: {'200': 5}` 是分布。`observed_occurrence_rate` 需要 `observation_scope` 才能 complete（见 §3 CR-2 的选型理由），而 content 里没有 scope 信息——见 §8.3 |
| `field_constraint` | content 有 `constraint_raw`（ABNF 文本）。18 个 property 里没有「值的语法约束」这一项；塞进 `value_range` 会把 ABNF 伪装成数值区间 |
| `value_pool` | `candidates` 是集合。`value_type` 只能取单值，`observed_co_occurrence` 语义是共现而非取值域。归约为任一单值都是发明 |
| `actor` / `protocol` | 「RTSP server 出现在 8554 端口」是部署事实，不是协议**问题**（fact_key 问的是协议要求什么）。无对应 property —— ★ **但 2026-10-08 起 `protocol` 有一个例外**，见下表 |
| `vuln_seed` | 关键字段大面积为空（`CVE=` `expected=`），无法稳定判定 |
| `body_format` / `constraint` / `sample` / `session_rule` / `timing` | content 完整但描述的是 MIME/命名约定/示例报文/会话生命周期/超时，18 个受控 property 无一对应 |

### 8.1 ★ 例外：`protocol` kind 下的 `rtsp_public_methods`（2026-10-08）

上表把 `protocol` 与 `actor` 并列为「不消费」。该判断对
`protocol.rtsp_transport` 成立（`transport distribution: {'TCP': 20, 'UDP': 35}`
是传输层抓包统计，与协议要求无关），**但对 `protocol.rtsp_public_methods`
不成立**。

区分依据不是「它是不是 traffic」，而是**它回答的是不是协议问题**：

| norm | 回答的问题 | 性质 | 判定 |
|---|---|---|---|
| `protocol.rtsp_transport` | 这批抓包走了多少 TCP / UDP | 部署画像 | 不消费 |
| `actor.rtsp_server` | server 监听哪些端口 | 部署画像 | 不消费 |
| `protocol.rtsp_public_methods` | **这个 server 实现了哪些 RTSP 方法** | **协议能力声明** | **消费（CR-6）** |

`Public:` 是 RTSP 响应头里 server 对 client 的**自述能力声明**（RFC 2326
规定该响应头用于列出支持的方法）。它不是「抓到了什么」，而是「协议参与方
声明自己是什么」，与 RFC 规范声明处于同一层级。

因此 CR-6 的每个字段都能落到既有受控件上，无一需要发明
（详见 §3 CR-6）。**本次只推翻 `protocol` 下这一个 norm_id，
其余 `protocol` / `actor` 仍按上表不消费。**

### 8.1.1 ★ 修正：「与 RFC 的差集」**不是** CR-6 的价值主张

初版本文档把 CR-6 的意义写成「与 CR-1 形成可判定对比」，
这是**定位错误**，2026-10-08 修正。

**错在哪**：那个说法暗示 traffic 知识要靠 rfc 源才能显出价值，
违背「五类知识源相对独立」这一基本原则 —— 每类源都该能独立成立。

**正确关系**：两侧产出**并列**且**各自独立成立**的 Fact。

| | 产出方 | actor | modality | 语义 |
|---|---|---|---|---|
| 规范事实 | CR-1（**rfc 源**） | `client` | `normative` / `must` | rfc 源独立声明的规范要求 |
| 实现事实 | CR-6（**traffic 源**） | `server` | `observed` | traffic 源独立观测到的能力声明 |

actor 不同 ⟹ fact_key 不同 ⟹ 不误合并；两者只是恰好同处一个 Hub，
各自可独立检索、独立缺失。**CR-6 的代码不读任何 rfc 数据**
（只解析自己 norm 的 content），`tests/…/test_candidateization_cr6.py::
TestSourceIndependence` 用**零 rfc 输入**的 build_context 断言了这一点。

**CR-6 的独立价值**：对 fuzzer 而言，「server 声明支持什么」决定
「哪些 method 值得构造测试」。这在完全没有 rfc 源参与时照样成立。

差集（哪些「被规范要求但该 server 未声明」）是**两侧都存在时**的附带
可观察现象，不是任何一条规则的职责，也不该写进任何一条规则的价值主张。
⚠ 另需注意：本 KB 上 server 声明的 8 个方法**全部 ⊆ RFC 的 11 个**，
故对 `HubInventory.methods` 净增量为 0（实测）—— 这进一步说明
CR-6 的价值不能建立在「与 RFC 比」上。

### 8.3.1 ★ `field` kind 内部格式不同质 —— URL 不是 header

（2026-10-08。⚠ 本节澄清一个容易误判的现象：**不要**照搬
「2026-10-07 统一 message content 格式」的做法去"修"它。）

`field` kind 5000 条里其实混了**两种不同语义**：

| producer | 条数 | content | CR-3 可解析 |
|---|---|---|---|
| `scapy_pcap_parse` | 2000 | `CSeq header occurrences=10 protocol=rtsp` | **100%** |
| `csv_wireshark_parse` | 1000 | `unique URLs=3 samples=['rtsp://…']` | 0% |
| `ndjson_wireshark_parse` | 1000 | 同上 | 0% |
| `rtsp_session_log_parse` | 1000 | 同上 | 0% |

**这与 message 的情况本质不同**：

- message 曾经的 `method_or_status=` vs `method=` 是**同一语义**（请求方法
  观测计数）的两种写法 ⟹ 统一格式即可，两者都是「方法计数」。
- field 这边，`CSeq header occurrences=N` 表达的是**消息头的观测频次**；
  `unique URLs=N samples=[…]` 表达的是**请求 URI 的集合**。
  **URL 不是 header。** 把 `unique URLs=3 …` 改写成能被 `HEADER_PATTERN`
  匹配的样子（如 `URL header occurrences=3 protocol=rtsp`）就是
  **把请求 URI 伪装成消息头** —— 那是发明语义，不是统一格式。

**契约侧确认无槽位**：`property_registry.json` 的 18 个 property 里，
凡 `allowed_kinds` 含 `header` 的（`value_type` / `value_range` /
`case_sensitivity` / `default_value` / `occurrence` /
`observed_co_occurrence` / `security_boundary` / `observed_presence_rate`）
**全部是关于消息头的**；其余 property 的 `allowed_kinds` 不含任何能承载
「请求 URI」的 kind（6 值枚举：method/header/constraint/state/transition/
packet_role_pair）。

⟹ **3000 条 URL 观测在当前契约下无法被诚实表达**，属契约层边界，
与 §8.3 的 `state_machine` / `outcome` 同类。

⚠ 但**信息价值不为零**：对 fuzzer 而言「server 响应过哪些资源路径」
正是构造种子 URI 的直接依据。若将来解锁 `fused_hub/`，优先级应为
**新增 kind**（如 `resource` / `uri`）而非硬塞进 `header` —— 后者会污染
header 通道，让 `HEADER_PATTERN` 的语义失效。

### 8.3 ★ 查证：为什么 `state_machine` / `outcome` 在**不改契约**的前提下进不了 Hub

（2026-10-08。在提出「改走 graph 关系」这条替代方案后被查证推翻，
故记录在此，避免后续重复讨论。）

**曾提出的替代方案**：既然 Fact 装不下序列，是否改用 graph 关系表达
「方法调用顺序」，从而绕开 `fact_key` 的槽位限制？

**查证结论：不可行。**

`fused_hub/schema/graph_registry.json` 的 `relation_types` 只有 3 个：

    returns_code / transitions_to / valid_in_state

其中唯一看似相关的是 `transitions_to`。但实测
`derived/model/spec/rtsp/graph/relations.jsonl` 表明它的既有语义是
**method → state**：

    {"src_id": "rtsp.method.setup",     "rel_type": "transitions_to",
     "dst_id": "rtsp.state.ready"}
    {"src_id": "rtsp.method.options",   "rel_type": "transitions_to",
     "dst_id": "rtsp.state.init"}

即「**某 method 触发状态转移**」。而 traffic 的
`observed methods: OPTIONS → DESCRIBE → SETUP` 只有方法**顺序**，
**从未观测到 state**（RTSP 状态机的 Init/Ready/Playing/Recording 不出现在
任何 traffic 观测里）。

若强行映射成 `OPTIONS --transitions_to--> DESCRIBE`，就是
「method → method」与既有「method → state」**同名不同义** ——
下游查这条关系时无法区分「SETUP 使状态变 Ready」与「OPTIONS 之后是
DESCRIBE」。这是制造歧义，不是复用词表。⟹ 方案不成立。

**`outcome` 同理**：唯一可能承载分布的 `observed_occurrence_rate`
要求 `observation_scope` 才能 complete，而 `status code distribution: {...}`
里没有任何 scope 信息（哪次会话？哪个状态？哪个抓包单元？）。

**剩余选项（全部需要动 schema，故未实施）**：

| 选项 | 代价 | 是否受阻于 `fused_hub/` 禁改 |
|---|---|---|
| 甲. 扩 `assertion.type`（加 `sequence` / `distribution`） | 改 `fact.schema.json` + `property_registry.json` | **是** |
| 丙. 新增 `relation_type`（如 `precedes`） | 改 `graph_registry.json`。且该文件 notes 明确写：「若未来出现新 relation_type, 按 §5.2 走 **Schema Version Upgrade**, 不在本文件**静默追加**」 | **是** |

⟹ **在 `fused_hub/` 禁改的当前约束下，这 7000 条（`state_machine` 5000 +
`outcome` 2000）无法进入 Hub。** 这是契约层的边界，不是抽取或分类的缺陷。
若将来解锁 schema，应优先走丙（新增 `precedes` relation）而非甲：
顺序关系本质是**边**而非**属性**，用关系表达比塞进 assertion 更贴合语义，
且不需要为 distribution 单独发明一种 assertion 形态。

### 8.2 ★ `build_fingerprint` 现在绑定规则集身份（2026-10-08）

**发现的问题（实测，非推断）**：加完 CR-6 重建 Hub，Facts 从 96 变成 104，
而 `build_fingerprint` 仍是 `sha256:e2c2b0fd…`，与加规则之前**一模一样**。

根因在 `build_inputs.py` 构造 `PipelineBuildContext` 时，三个版本号是
硬编码字面量：

    schema_version=当前, normalization_version="norm_v1",
    fusion_version="fusion_v3",

而 `build_fingerprint` 的 payload 只含 target_scope + aggregate_input_fingerprint
+ schema/registry + 这三个常量 —— **规则集根本不在指纹里**。
于是任何 CR / VR / SR / GR 的增删改都不会改变指纹。

**为什么这不只是「不严谨」而是缺陷**：`core/lane_a/attachment.py` 拿
`target_source_build_fingerprint` 判断「Hub 是否已重建」，不一致即报
`Hub 可能已重建`。指纹不变 ⟹ **漏报**：Hub 内容明明变了，下游却判为未重建。
（反向情形——内容等价而指纹变——只是误报，代价低得多。所以方向上宁可误报。）

**修法：只改 `fusion_version` 的值来源，不动 fingerprint 的 payload 结构**：

    fusion_version = f"fusion_v3+rules.{rules_digest()}"

`rules_digest()` 是五个规则模块（`candidateization` / `state_rules` /
`vuln_rules` / `semantic_relation` / `graph`）**规范化源码**的 sha256 前 16 hex。

⚠ **为什么不改 payload 结构**：`core/fused/pipeline/pipeline.py`
（`_compute_fingerprints`）与 `core/fused/validation.py`（Invariant 21）各有一份
**逐字相同**的 fingerprint 重算，两处注释都警告过「双实现漂移」风险 ——
改一边不改另一边，`validate_build` 会直接失败。
而 `validation.py` 的 `expected_build` 读的是 `meta.fusion_version` 这个**值**，
不是硬编码，所以只改「值的来源」时，两处自动保持一致，**零漂移风险**。

**摘要口径**（`_normalize_source`，经 `ast.parse` + `ast.unparse`）：

| 改动 | digest | 理由 |
|---|---|---|
| 改 eligibility / assertion / 加删规则 | **变** | 正是漏报的那一类 |
| 只改注释或 docstring | 不变 | 避免 provenance 信号被噪声淹没 |
| 只改缩进 / 换行 / 引号风格 | 不变 | 同上 |
| 字符串字面量里的 `#` | **完整保留** | ast 方案的关键收益；正则方案会误截断 |

⚠ 实现期踩过的坑：剥离 docstring 时**不能用 `ast.Pass()` 占位**，
否则「有 docstring 的函数」比「没有的」多出一个 `pass`，
于是**给函数补一段 docstring 也会改指纹** —— 正是本节要消除的噪声。
正确做法是直接删除 docstring 节点，仅当删完 body 为空时才退回 `Pass`
（`unparse` 需要非空体）。`tests/…/test_rules_digest.py::
TestNormalizeSource.test_semantically_identical_sources_match` 钉死了这条。

**当前基线**（RTSP/live555，4 源构建，2026-10-08）：
`build_fingerprint = sha256:cc6438b429f55631405…`，
产物 `104 Facts / 58 entities / 473 relations / 61 audits / 34100 lineage`。

⟹ 改规则 ⟹ 指纹变；规则不变 ⟹ 连跑两次指纹一致（两者均已实测）。

⚠ 规则文件语法错误时 `rules_digest()` **显式抛 `FusedSchemaError`**，
不静默降级成固定值——静默降级恰好会把本节要修的漏报又装回去。

## 10. 与编排层的接口（一处必要的扩展）

阶段 4.8a 的 `run_pipeline(..., fact_rule_candidates, ...)` 把
Fact/Claim graph rules 的产物当**入参**接收。但契约 §8.14.1/§8.14.5 定义的
graph rule 是「Fact 与 Claim graph rules 中 emit_kind=X 的 candidates」——
**规则本身需要看到 Fact 与 Claim**（`/derived_from` 要填 fact_id/claim_id），
而 Fact 在编排链的第 2 步才产出，早于第 4 步的 Graph Derivation。

因此 `fact_rule_candidates` 需要接受两种形态：

* `Sequence[GraphCandidate]` —— 阶段 4.8a 的既有形态，调用方自行预计算
  （`compute_fact_id` 是 §8.2 的确定性函数，预计算值必然一致）；
* `Callable[[tuple[Fact, ...]], Sequence[GraphCandidate]]` —— **新增**，
  在 §8.14 执行点（即 Facts 已产出之后）现场求值。

这是向后兼容的增量扩展（序列形态行为完全不变），且是唯一能让 graph rule
「基于真实 Fact」而非「基于预计算猜测」的顺序正确解法。已记入 audit.txt。
