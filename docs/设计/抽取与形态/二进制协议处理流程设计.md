# 二进制协议处理流程设计（2026-11-07）

> ★ **2026-11-10 状态**：`skeleton.json → profile 源` 这一环节已**移除**（骨架消解）；
> `profile/facts/profile.jsonl` 现在**只含 required_headers**（协议结构声明，独立物化）。

> 目标：让 **DHCPv4**（UDP 二进制）能像 rtsp/sip/smtp 一样走
> 「RFC 源 → 知识中枢 → 初始种子」全流程，**复用现有模型**（不新增/不重训模型）。
> 关键设计：**在流程最前面加一个「协议类型判断阶段」**，由它决定后续走哪条路径。

---

## 一、现状：文本协议的全流程（复用目标）

```
kb/<协议>/spec/*.txt
   │
   ▼  ① 抽取（core/fused/rfc_extractor.py，8 个通道 A0/A0b/A0c/E/F/D/G/H/H′）
   │     · 形态层 core/fused/rfc_forms.py（8 类形态：table/normative/example/prose/…）
   │     · 质量闸：dup_fact_ids / toc_pollution
   ▼  ② 映射（core/fused/norm.py：RFC_KIND_MAP）
   │     · kind=method/field/outcome/field_value/transition/… → aspect
   ▼  ③ 物化（scripts/build_hub.py）
   │     ③'  （★ 2026-11-10 已移除）协议骨架 skeleton.json → profile 源
   │     ③'' 会话语义三段 / ③''' 必填头清单（authority=expert_note/profile）
   ▼  ④ 按 aspect 落盘 → derived/per_source/<协议>/facts/*.jsonl
   ▼  ⑤ 组装 bundle（core/fused/downstream/rag_seedgen.py：assemble_bundle）
   │     · 16 个桶：methods/headers/required_headers/transitions/…
   ▼  ⑥ 生成种子（core/fused/downstream/edge_cover.py + core/raw_writers.py）
         · 文本：request_line/header_line 两个行模板
```

**DHCP 走不通的 3 个点**（实测）：
1. 抽取层：位域表/选项表**没有对应通道** ⇒ 抽不出字段布局
2. 中枢：字段的**布局信息（offset/length/endian）无处安放** ⇒ 骨架只能存「名字+值」
   （★ 2026-11-10：骨架已消解 ⇒ 该缺口由 `binary_layout` aspect 承担）
3. 渲染层：`raw_format` 只有**文本行模板** ⇒ `.raw` 是 `DHCPDISCOVER\r\n`（14 字节）
   而不是 236 字节 BOOTP 二进制

## 二、核心设计：**协议类型判断阶段**（新增，最前面）

### 位置

```
scripts/build_hub.py  main()
   │
   ▼  ★ 新增 ⓪ 协议类型判断（ProtocolKindStage）
   │     输入：kb/<协议>/spec/*.txt  +  profile.json（可选的显式声明）
   │     输出：ProtocolKind（text / binary）+ 判定证据（可审计、可落盘）
   │
   ▼  ① 抽取：按 kind 选通道
   │     text   → 现有 8 通道（**零改动**）
   │     binary → 新增二进制通道（位域表/定长字段/选项表）
   ▼  ... 后续流程**完全复用**（②映射 ③物化 ④落盘 ⑤bundle ⑥种子）
   ▼  ⑥ 渲染：按 kind 选 writer
         text   → 现有 _render_from_profile（**零改动**）
         binary → 新增 _render_binary_from_profile
```

### 判据（**协议无关**，不认协议名）

| 判据 | 含义 | rtsp | sip | smtp | **dhcpv4** |
|---|---|---:|---:|---:|---:|
| B1 位域图行 | `\|  op (1)  \|` 形态 | 0 | 0 | 0 | **21** |
| B2 `octet` 密度 | 字节单位的用法 | 10 | 4 | 18 | **185** |
| B3 网络字节序 | `network byte order` | 1 | 0 | 0 | **5** |
| B4 `0x` 魔数 | magic cookie | 0 | 0 | 0 | **18** |

**判定规则**（配置优先 + 自动探测兜底）：
1. `profile.json` 的 `protocol_kind` 字段**显式声明** ⇒ 直接采信（人的判断优先）
2. 未声明 ⇒ **自动探测**：
   - `B1 > 0` ⇒ binary（位域图是二进制协议的**结构签名**）
   - `B2 ≥ 阈值` **且**（`B3 > 0` **或** `B4 > 0`）⇒ binary
   - 否则 ⇒ text
3. 判定结果**落盘到中枢**（`derived/per_source/<协议>/protocol_kind.json`）
   ⇒ **可审计**：论文里能说「本协议经自动判定为 binary，依据 B1=21 行位域图」

### 为什么用「阶段」而不是「配置字段」

- 判定**发生在抽取之前** ⇒ 决定走哪些通道（省掉无效工作）
- 判定**结果落盘** ⇒ 后续每个阶段都能读到，不必各自判断
- 判定**可被人工覆盖**（profile 里写 `protocol_kind`）⇒ 探测失误时能救

## 三、二进制协议需要的新增能力（4 处）

### ① 形态层：`core/fused/rfc_forms_binary.py`（新增）

文本形态层（`rfc_forms.py`）按**行**分类；二进制协议需要按**表块**分类：

| 新形态 | 识别 | 产出 |
|---|---|---|
| `bitfield` | 位域图块（`+---+` 框线 + `\| name (N) \|`） | 字段名 + 长度 + 顺序 |
| `fixed_field` | 定长字段表（`XID  4 octets`） | 字段名 + 长度 |
| `option_table` | 选项表（`Code / Name / Length`） | 选项 code + 名称 + 长度 |

### ② 抽取层：`core/fused/rfc_extractor_binary.py`（新增）

新增 2 个通道（对应文本侧的 A/E/D）：

| 通道 | 抽什么 | 产出 aspect |
|---|---|---|
| **通道 B1** | 位域图 → 字段**布局**（名/长度/顺序） | `header/binary_layout` |
| **通道 B2** | 选项表 → 选项 code/名称/长度 | `header/option_layout` |

★ **复用现有模型**：布局抽取是**纯确定性**的（不需要 LLM）；
若某协议的布局只有散文描述，才走 LLM 兜底（复用 `infer_*` 的缓存机制）。

### ③ 中枢层：新增 2 个 aspect

| aspect | 含义 | 桶 |
|---|---|---|
| `header/binary_layout` | 字段的**布局**（名/长度/偏移/字节序） | `headers`（与现有头字段同桶） |
| `header/option_layout` | 选项的 **TLV 布局**（code/长度） | `headers` |

★ 放在 `headers` 桶 ⇒ **下游零改动**（`_known` 认识这些字段名 ⇒
实例字段不再被当「未知字段」—— 这正是上一轮实测到的坑）。

### ④ 渲染层：`core/raw_writers_binary.py`（新增）

`raw_format` 新增**二进制布局段**（协议无关，纯数据）：

```json
"raw_format": {
  "byte_order": "network",
  "binary_fields": [
    {"name": "op",      "offset": 0,  "length": 1, "type": "uint8"},
    {"name": "htype",   "offset": 1,  "length": 1, "type": "uint8"},
    {"name": "xid",     "offset": 4,  "length": 4, "type": "uint32"},
    {"name": "chaddr",  "offset": 28, "length": 6, "type": "mac"},
    {"name": "magic_cookie", "offset": 236, "length": 4, "type": "uint32"}
  ],
  "binary_options": [
    {"name": "subnet_mask", "code": 1, "type": "ipv4"}
  ]
}
```

支持的 `type`：`uint8/16/32`、`ipv4`、`mac`、`bytes`、`string`（NVT）、
`ipv4_list`、`uint8_list`。

★ **不硬编码协议**：DNS、QUIC 等将来的二进制协议都能用同一套。

## 四、文件夹结构（整理后的合理布局）

### 现状问题

- `core/fused/rfc_extractor.py` **5351 行**（8 个通道挤在一个文件）
- 文本与二进制的知识**混在同一套抽象**里（形态层、通道、writer）
- 「协议类型」这个**横切关注点**无处安放

### 建议布局

```
core/
├── kinds/                          ← ★ 新增：协议类型体系（横切层）
│   ├── __init__.py                 ← 公共 API：detect_protocol_kind()
│   ├── detector.py                 ← ★ 协议类型判断阶段（配置优先 + 自动探测）
│   └── evidence.py                 ← 判定证据的结构化表示（可审计）
│
├── fused/
│   ├── rfc_forms.py                ← 保留：文本形态层（8 类形态）
│   ├── rfc_forms_binary.py         ← ★ 新增：二进制形态层（位域/定长/选项表）
│   ├── rfc_extractor.py            ← 保留：文本抽取（8 通道，零改动）
│   ├── rfc_extractor_binary.py     ← ★ 新增：二进制抽取（2 通道）
│   ├── ...（其余不动）
│
├── raw_writers.py                  ← 保留：文本渲染
├── raw_writers_binary.py           ← ★ 新增：二进制渲染
└── paths.py                        ← 保留（加 protocol_kind 产物路径）
```

**为什么这样分**：
1. `core/kinds/` 是**横切层** —— 抽取、渲染、中枢三处都要读它 ⇒ 独立成目录，
   不塞进 `fused/`（那里是「知识抽取」专用）。
2. 文本/二进制**并列**（`rfc_forms` ↔ `rfc_forms_binary`）⇒ 差异一目了然，
   且**不破坏**现有 import 路径（零回归风险）。
3. `rfc_extractor.py` 已经 5351 行 ⇒ 二进制通道**另起文件**，
   不再往里塞（否则下一个协议又膨胀）。

### 产物目录（derived）

```
derived/per_source/<协议>/
├── facts/*.jsonl                    ← 现有（按 aspect）
├── protocol_kind.json               ← ★ 新增：协议类型判定结果（可审计）
└── profile/facts/profile.jsonl      ← 现有（★ 2026-11-10：只含 required_headers，独立物化）
```

## 五、实施顺序（每步独立可验收）

| 步 | 内容 | 验收 | 风险 |
|---|---|---|---|
| **1** | `core/kinds/`：判定阶段 + 证据落盘 | 4 协议判定正确（3 text / 1 binary） | 低（纯新增） |
| **2** | `raw_format.binary_fields` + `core/raw_writers_binary.py` | DHCP `.raw` 是 **236+ 字节 BOOTP** | 中（新增分支，不改文本路径） |
| **3** | `core/fused/rfc_forms_binary.py`（位域/定长/选项表形态） | 能从 RFC 2131/2132 抽出布局 | 中 |
| **4** | `core/fused/rfc_extractor_binary.py`（2 通道）+ 2 个新 aspect | 中枢里有 `binary_layout` | 中 |
| **5** | 骨架生成器改用**抽出的布局**（不再手写 offset） | 骨架的 offset 来自 RFC | 中 |
| **6** | 端到端：DHCP 全流程 + 护栏 | `.raw` 可被真实 DHCP server 接受 | — |

★ **步 2 单独就能解决「.raw 不是 DHCP 报文」这个阻塞项**（用现有骨架里的字段名+值 +
   profile 里的布局段即可渲染），步 3-4 再把布局**来源**从「手写」换成「RFC 抽取」。
