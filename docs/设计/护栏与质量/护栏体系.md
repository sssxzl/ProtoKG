# 护栏体系设计（guard）

> ★ **定位**：护栏**不是「测试」**，是「**判定这次改动是否可接受**」的机制。
> ★ **归属**：模型流水线**之外**的工程设施（与 `seedcheck/` 产物审查**刻意分开**）。
> ★ 代码落点：`guard/`（11 个脚本 + `baseline/` 期望集）

---

## 一、它解决什么问题

一个长期项目里，最贵的不是「写错」，而是「**不知道有没有写坏**」。护栏把这件事变成**可机械判定**的问题：

| 没有护栏 | 有护栏 |
|---|---|
| 改完跑一下 ⇒「好像没问题」 | 改完跑护栏 ⇒ **红灯/绿灯** |
| 回归被「顺手洗基线」掩盖 | **失败集合不许漂移** ⇒ 洗不掉 |
| 文档/schema 不同步 ⇒ CI 静默指向已删目录 | 文档-机器一致性闸 ⇒ 直接判红 |
| 编码乱码悄悄扩散 | 编码卫生闸 + **豁免名单**（只报告不改） |
| LLM 每次输出不同 ⇒ 语料每次变 ⇒ 无法判断「变好还是变坏」 | **缓存 + block_hash** ⇒ 逐字节可复现 |

## 二、体系的三个部分

### ① 回归闸（`guard/run_guarded_pytest.py`）

**核心机制：失败集合不漂移**

```
基线（guard/baseline/）：
  expected_b_class_failed_ids.txt        10 条   本机
  ci_expected_failed_ids_ubuntu.txt      70 条   CI(ubuntu)
  ci_expected_failed_ids_windows.txt     67 条   CI(windows)
  env_variant_failed_ids.txt             26 条   环境变体
  ci_expected_errors.txt                  0 条
```

| 情况 | 含义 | 判定 |
|---|---|---|
| 基线 = 实测（逐条相同） | 没引入回归 | 🟢 |
| 实测 **+1** | ★ 引入了**新回归** | 🔴 |
| 实测 **−1** | ★ 有人**从基线里删了一条**来「修绿」 | 🔴 |
| 基线 ≠ 实测但**平台不同** | 平台差异 ⇒ **两平台必须用各自基线** | 按平台基线判 |

⇒ ★ **为什么「消失」也判红**：防止**为了让 CI 绿而偷偷洗基线** ⇒ 基线的每次变化都必须**显式、有意识**地做。

⇒ ★ **为什么有「已知失败」**：有些用例依赖外部条件（真实服务器 / LLM key / 真实 SIP 行为）⇒ CI 环境必然失败 ⇒ **登记**成「已知失败」而不是删掉。

**护栏 1/2/4（跑测试本身的三道保险）**

| 闸 | 查什么 | 不通过 ⇒ |
|---|---|---|
| **护栏1** | 跑前/跑后各存一次**源码 mtime 快照** ⇒ diff 非空 | 「本次结果不可采信」⇒ **测试期间有人改了代码** |
| **护栏2** | **summary 行必须存在** | 「本次运行无效」（可能被 kill/超时）⇒ **不得当成「0 失败」** |
| **护栏4** | **抽取口径自检**（FAILED/ERROR 抽取口径自校验） | 抽取口径错了 ⇒ 比对结果无意义 |

⇒ ★ 护栏2 是典型的**「防自欺」**：没有 summary 行时判「无效」而不是「0 失败」。

### ② 契约闸（10 个 `verify_*.py`）

| 护栏 | 查什么 |
|---|---|
| `verify_aspect_layout` | 中枢**落位布局**（aspect→桶）★ 不能用 `sort_keys=True` ⇒ 会掩盖 dict **键插入序**差异（会改变种子编号） |
| `verify_source_filter` | 源过滤口径（按 `source_set` 过滤 claim） |
| `verify_provenance` | **溯源完整性**（每条 claim 能指回来源） |
| `verify_required_headers` | 必填头事实（逐协议核对） |
| `verify_rfc_field_values` | RFC 字段取值抽取（批次 2.0 P0） |
| `verify_consumer_wiring` | 消费端接线（**只认中枢，不碰知识源**） |
| `verify_single_source_e2e` | **单源端到端**（产物目录必须在仓库外，否则破坏护栏1） |
| `verify_seedcheck_wiring` | ★ 种子校验层架构（**不得反向依赖 downstream** / 不直读知识源 / 不写回中枢与种子） |
| `verify_docs_consistency` | **文档-机器一致性** ★ 「schema 变更后文档陈旧是**结构性必然**，不是偶然」 |
| `verify_encoding` | **编码卫生**（UTF-8 统一、防乱码）★ 已知乱码登记豁免、**只报告不改**（不是我们的 mojibake，改它反而偏离上游） |

### ③ 缓存范式（**不是护栏文件，但是护栏能成立的前提**）

| 机制 | 作用 |
|---|---|
| `block_hash = sha256(PROMPT_VERSION + 各候选块 hash)` | LLM 通道的**输入指纹** |
| 命中 ⇒ **不调 LLM** ⇒ 产物逐字节可复现 | ★ 否则每次构建语料都变 ⇒ **护栏基线必然漂移** ⇒ 整个护栏体系失效 |
| 指纹含 `PROMPT_VERSION` ⇒ 改 prompt 自动失效 | 「换 prompt 就重跑」白送 |

现有三处实例（都在 `derived/cache/source_blocks/`）：
`<协议>.transitions.json`（状态机 LLM 腿）· `<协议>.method_required_headers.json` · `<协议>.state.json`

⇒ ⇒ **护栏的「不漂移」要求 与 LLM 的「不确定性」是死对头** ⇒ ⇒ 缓存是它们之间的桥。

## 三、边界：**管什么 / 不管什么**

| | 护栏管 | 护栏**不**管 |
|---|---|---|
| 代码 | 回归（失败集合）、契约形状、架构约束 | 代码好不好、功能对不对 |
| 知识 | 落位/溯源/过滤口径、必填头抽取 | 知识**对不对**（⇒ 那是 `kb/<协议>/rfc_truth.json` 真值集的事） |
| 文档 | 文档与机器一致、命令路径有效 | 文档写得好不好 |
| **产物** | **不查** | 种子能不能投（⇒ **V1~V6**） |
| 平台 | 两平台各用自己的基线 | 跨平台一致（⇒ 靠基线分离） |

⇒ ⇒ ★ **两类审查刻意分开**

| | `guard/`（代码审查） | `seedcheck/`（产物审查） |
|---|---|---|
| 回答 | 「这次改动有没有引入回归？」 | 「这批种子**能不能用**？」 |
| 查 | 代码 / 契约 / 文档 | 种子质量 |
| 判据 | pytest 失败集合 + 契约 | 中枢知识 + 本次运行统计 |
| 目录 | `guard/` | `seedcheck/` |

## 四、三条设计原则（从代码里读出来的）

| # | 原则 | 体现 |
|---|---|---|
| 1 | **失败不是「红」，而是「不可采信」** | 护栏1/2：源码被改 / summary 缺失 ⇒ 判「本次结果无效」⇒ **不与「有回归」混为一谈** |
| 2 | **闸门自己必须 100% 干净** | CI 的 ruff **只查 `guard/`**（注释：「闸门自己有 lint 债很荒唐」）⇒ 全仓 114 个既存告警不纳入 |
| 3 | **豁免要显式登记，而不是「改对」** | 编码护栏：已知乱码进 `encoding_known_issues.txt` ⇒ **只报告不改** |

## 五、★ 红灯的哲学

> **红灯不一定是「你错了」，但一定是「这次结果不可采信」。**

⇒ ⇒ 遇到红灯**先分类**，**只有第一类才该改代码**：

| 类别 | 判别方式 | 处置 |
|---|---|---|
| **代码回归** | 失败断言指向**本次改动的代码路径** | ★ 改代码 |
| **数据状态** | 失败断言依赖**中枢/语料的当前内容**（如「五源齐全」） | ⇒ **不据此改代码**、**不洗基线**；按需重建产物后再判 |
| **闸门自身** | 护栏1/2/4 触发（源码被改 / summary 缺失 / 口径自检失败） | ⇒ 重跑，**不接受本次结果** |

⇒ ★ **绝不为「变绿」而改判据或洗基线** —— 那正是「失败集合不漂移」要防的事。
