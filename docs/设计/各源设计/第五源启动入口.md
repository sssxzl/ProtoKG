## 2. 为什么 source 源不能照抄 traffic 的路径

traffic 走的是「语料观测 → 判定能不能进 Hub → 裁定口径 → 落地」。
source 源的**观测性质不同**，不能直接套用：

| 维度 | traffic | source（预期，待勘察确认） |
|---|---|---|
| 观测对象 | 运行时报文（客观记录） | 实现代码（**有作者意图**，非纯观测） |
| cross-capture independence | 需判定（实测 NOT ESTABLISHED） | 不适用（不是多份独立捕获） |
| 群体性聚合（Lane B 类） | 需 population provenance | **可能天然不需要** |
| 观测独立性 | log 与 pcap 同源，非独立证人 | 代码与其产出可能循环论证 |

**关键提醒**：source 源最容易踩的坑是**把代码作者的意图当成协议事实**。
traffic 的 D9 花了大量篇幅处理「同源生成器不是独立证人」，
source 源在这一点上**风险更高**。

以上是**待勘察验证的假设**，不是结论。勘察后若与实际不符，应据实修订本表。

## 3. 启动前置（按顺序）

### 3.1 第一步：语料勘察（Corpus Recon）

参照 `设计/traffic_corpus_capability_profile.md` 的结构产出 source 侧的
Capability Profile，至少回答：

- 有多少代码单元？（traffic 是 1000 nominal / 500 effective 双层计数）
- 覆盖哪些协议版本 / 语言 / 组件？
- 语料能否区分「实现选择」与「协议要求」？
- 有无 external artifact 需排除？（traffic 排除了 tcp 侧 `client.log`）

**不预设立场**：traffic 的 `1000/500` 双层计数是 traffic 语料特有的，
source 语料**不得**沿用同一数字。

### 3.2 第二步：判定 D9 式口径问题

traffic 的 D9 解决的核心问题是「观测独立性口径」。source 源需先回答：

- 观测单位是什么？（文件 / 函数 / commit / 版本？）
- 「独立」如何定义？（不同文件 ≠ 独立观测）
- 代码与其测试/文档是否算同一观测源？

### 3.3 第三步：Candidateization Rule Set

结构完全可复用 traffic 的（§0.1 → §3.2 emission class → §4.x Primitive
Contract → §10 Freeze Criteria）。**但裁定内容不能照抄**。

### 3.4 第四步：实现与 Attachment

`core/lane_a/` 的 11 个模块可直接复用（见 §4.1）。
若 source 也走 provenance-only，可新建 `core/source_a/` 或复用 lane_a
框架 —— **该选择需在 source 设计阶段裁定**，本文件不预设。
