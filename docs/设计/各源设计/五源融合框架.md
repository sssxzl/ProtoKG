## 2. 融合的定义

### 2.1 「融合」有三种含义，必须先澄清

本节是本框架的**核心** —— 不澄清「融合」就无法判断成败。

| 含义 | 定义 | 当前状态 |
|---|---|---|
| **F-1 Hub facts union** | 多源的抽取结果合并进统一事实库，去重 / 对齐 / 记录冲突 | ✅ **已完成**（3 源 65 facts，`fusion_v3`，layout 0 violation） |
| **F-2 provenance 全挂** | 不产 fact 的源的观察，以**单向引用**挂到已有 fact 上 | ⚠ **一半**（traffic 已挂 11000；source 未挂） |
| **F-3 驱动 seedgen** | 中枢知识**改变**下游种子生成行为 | ❌ **未达成**（见 §2.3） |

### 2.2 三种含义的关系

```
F-1 (事实并集)  ──产生──>  F-3 (驱动下游)
      │                          ▲
      │ 挂载目标                  │ 方法词表
      ↓                          │
F-2 (provenance 挂载) ───────────┘
```

- **F-1 是 F-3 的前置**：没有统一事实库，下游无从消费
- **F-2 是 F-1 的旁证**：provenance 不改变 fact，但为 fact 提供观察支撑
- **F-3 是唯一能证明「融合发生了」的含义** —— 见下

### 2.3 关键实测：F-1 已完成，但对下游零增量

2026-09-30 实测（`pipeline_progress.log` Step 4.8d 动作 4）：

| 对照 | Hub | seedgen 产出 |
|---|---|---|
| 组甲 rfc 单源 | 11 facts | 26 个 `.raw` |
| 组乙 rfc + expert_note 双源 | 60 facts | 26 个 `.raw` |

**26 / 26 字节级完全相同。**

根因：桥接只用 `inventory.methods` 一个通道，而两 Hub 的 method 集合
完全相同（都是 11 个 RFC 方法）。Hub 侧 `fact_count` 11→60、
`headers` []→4、`security_flagged_methods` []→[SETUP] **全都没有传导到产物**。

⟹ **这不是 bug，是「融合」当前定义的必然结果**：F-1 产出的增量信息，
在现有单通道桥接下**无法到达下游**。

### 2.4 本框架的融合目标

> **融合 = 让五源的差异化信息改变下游行为，而非仅仅汇总入库。**

三条可检验的推论：

1. 若某源的全部信息都能被下游单通道消费，则它是**冗余源**
2. 若某源的信息无法被任何通道消费，则它是**未接通源**
3. **融合成功的判据必须包含「下游产出发生变化」** —— 否则 F-1 完成即自证成功

⚠ 这**不否定** F-1 的价值：它是 F-3 的必要前置。但**不得**把
「65 facts 落库」当作融合成功的证据。

## 4. 融合的判据

> 判据必须**可机器检验**，且**覆盖全部三种含义**，否则无法区分
> 「汇总完成」与「融合完成」。

### 4.0 判据四态

> 2026-10-06 引入（D55 落地）。此前只有 PASS / FAIL 两态，
> 导致「前提未成立」被系统性误判为「未达标」（见 §4.2）。

| 状态 | 含义 | 使用条件 |
|---|---|---|
| **PASS** | 前提成立且达标 | — |
| **FAIL** | 前提成立但未达标 | — |
| **N/A** | **判据前提未成立**（不适用） | 前提未成立时**必须**用 N/A，不得用 FAIL |
| **PENDING** | 前提成立，但因未实现或未测量而无法判定 | 前提成立却测不了 |

**强制要求**：每条判据必须显式声明其**前提条件**。
前提未成立 → 输出 N/A；前提成立但测不了 → 输出 PENDING。

⚠ 该规则的作用是**防止假信号**：
「不适用」被写成 FAIL，会让未完成的工作看起来像失败的实现，
进而误导优先级排序（本项目已因此误排过优先级）。

> 前一版两条判据检验的对象与契约实际定义不一致。

### 4.1.1 L3 的三分定义

**原判据**：「Hub facts subject 是否合规」—— **失效**。

**失效原因**：它混淆了两个不同问题。
原判据在问「当前 fact 是否合规」，
但合规性**依赖契约是否落地**；契约未落地时，
「合规」与「不合规」**都无意义**（`_normalize_subject` 原样透传，无从判断）。

**修订**：L3 拆为三项，各自可独立判定。

| 子项 | 判据 | 现状 |
|---|---|---|
| **L3-A 契约落地状态** | `normalization` 层是否已实现各 kind 的 lexical normalizer？ | ❌ **FAIL** —— lexical normalizer 属 Phase 4.4/4.6，`normalization.py:127` 明写「不实现」 |
| **L3-B 已落地域合规性** | **仅对已落地**的归一域，检验 fact 是否合规（前提：L3-A = PASS） | 🚫 **N/A** —— L3-A 为 FAIL ⟹ 前提不成立 |
| **L3-C 未落地域标记** | 未落地域的 fact 应被显式标记为「契约待落地」 | 🚫 **PENDING** —— 无此机制，无法测量 |

**L3 完整通过 = Phase 4.4 / 4.6 完成。**
在此之前 L3-A 恒为 FAIL，而 L3-B / L3-C 无判据对象。

⚠ 本次修订**不否认** header 存在 Title-Case 事实（4 条），
只是拒绝把「不符合某个未实现的词法描述」当作 FAIL 判据。

#### 4.2.1 L2：判据用了错误的三元组

**原判据**：「无同 `(kind, subject, property)` 重复」⟹ 测得 63 唯一 / 1 重复 ×3，

| 三元组 `(kind, subject, property)` | 63 | 1 项 ×3 |

**结论：L2 = PASS。`fact_identity.py` 无缺陷。**

### 4.4 L5 目标定义（2026-10-07 修正，D70）

> **L5 的目标不是「接通更多通道」**，
> 而是：**让 Hub 中的 protocol-semantic 知识传导到 seedgen 产物。**

#### 4.4.1 ★ 瓶颈诊断的更正

⟹ 把响应写进 `.raw` 不仅破坏 ProFuzzBench 格式，

### 4.5 判据的分层理由

单层判据会给出**误导性绿灯**：L1 单独看是完全通过的（0 violation、
65 facts、fingerprint 稳定），若以其为「融合完成」的判据，
就会掩盖 L2–L5 的四个 FAIL。

分层使「哪一层没通」成为**可定位的事实**，而非「差一点点」。

## 5. 融合的边界

### 5.1 融合**不做**什么

| 不做 | 依据 |
|---|---|
| 不让 traffic / source 产 Hub fact | D17 / D40 |
| 不把 provenance 写进 Hub 产物 | Rule Set §5.1；attachment 是**单向引用** |
| 不为「凑数」注入 fact | D40 明文禁止 |
| 不在 fact 中伪造帧字段 | C-3 |
| 不因实现落后就改冻结契约 | §2.3 授权等级 |

### 5.2 融合**做**什么

| 做 | 依据 |
|---|---|
| 跨源去重与冲突记录 | audit matches / conflicts |
| subject 归一 | `subject_registry.lexical_normalization` |
| provenance 单向挂载 | D9 §5.4 attachment |
| 把中枢知识传导至下游 | F-3 |

### 5.3 边界上的既有张力

**traffic ↔ source 同源（D27）**：两者语料同为 LIVE555。
「五源」在**语料**上是 4 源而非 5 源。
⟹ 融合框架必须区分「**语料源**」与「**视角源**」：

- **语料源**：rfc（规范）、expert_note（解释）、vuln（安全）、
  LIVE555（实现/观测，被 traffic 与 source **共享**）
- **视角源**：traffic（观测视角）、source（实现视角）

⚠ 这一点在 §1.4 矩阵中以「同源」标注，**不得**把 traffic 与 source
计为两个独立信源来论证「多源交叉验证」。

## 6.4 战略建议（2026-10-06 新增）

### 6.4.1 暂停第五源融合投入

在 L5 通道打通之前，**不再投入新的知识源融合**。

**理由**：当前架构下新增源的边际收益在下游为**零**（§2.3 实测）。
继续投入等于把工作量沉淀在**无出口的管道**里。

**具体暂停范围**：

| 项 | 处置 |
|---|---|
| 第六源 / 更多 expert_note 规范 | **暂停** |
| traffic 接入 Hub fact（D17 之外的新提案） | **暂停**（且 D17 已定 PROVENANCE-ONLY） |
| source 进一步抽取（Rule Set 扩展） | **暂停**（含 D44 的客户端侧符号表） |
| Q5 state/transition 规则补齐 | **暂缓** —— 补了也需先有 L5 通道才有下游价值 |

⚠ 「暂停」≠「取消」。Q5 与 D44 都仍有效，只是**优先级后移**。

### 6.4.2 优先级重排

```
P0  L5 通道扩展（含判据修订 L5-Q4）   ← 一切的前置
P1  L5 接线（G-2）
P2  Q5 state/transition 规则          ← 需挂载授权
P3  lexical normalizer（Phase 4.4/4.6）← L3-A
P4  任何新增知识源                      ← 当前暂停
```

**关键倒置**：此前隐含的顺序是「先把五源都接进来，再打通传导」。
实测表明这个顺序**从一开始就不产生下游价值** ——
正确顺序是**先打通传导，再加源**，因为只有打通后加源才有边际收益。

### 6.4.3 L5 判据必须先于 L5 实现修订

当前 L5 判据隐含「所有 Hub 变化都应改变产物」，
但加 traffic / source 源时 Hub facts **本就不变**（D17 / D40），
会被**误判为 FAIL**。

⟹ **不先修订判据，L5 实现无法被正确验收。**
详见 `docs/实施/立项提案/L5种子生成贯通立项.md` §5（L5-Q4）。
