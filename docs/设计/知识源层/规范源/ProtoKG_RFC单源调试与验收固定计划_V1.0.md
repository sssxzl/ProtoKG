# ProtoKG RFC 单源知识抽取研发总计划 V1.0（正式冻结版）

> 冻结日期：2026-11-19
> 适用仓库：`sssxzl/ProtoKG`，main 唯一长期分支
> 本文件为 V1.0 原件；任何修订须另发 V1.1，不得覆盖本文件。

## 一、任务性质

本任务是研发计划冻结与已有成果继承，不是新的功能开发轮次。

现根据 ProtoKG 历史 N1、V2-E4、H3、R13～R19、R25～R27C 的工作，正式建立 RFC 单源抽取研发总计划 V1.0。

本计划一经登记，作为以后所有 RFC 抽取调试任务的统一依据。

不得由于局部缺陷、新的审计发现或某次测试失败，未经审批重新规划整个研发流程。

必须严格区分：已完成、已冻结、本地影子验证通过、已批准但尚未执行、待审批、尚未解决、未执行、不适用。

Agent 的执行建议不等于项目方审批。

## 二、冻结架构与研发边界

正式保持七阶段：

1. RFC 原始文档。
2. 文档解析与分块。
3. 知识识别与抽取。
4. 知识类型判别与路由。
5. Norm 规范化。
6. Canonical Fact 构建。
7. 现有结构化知识中枢接入。

第四阶段与第五阶段之间保留原有验证门禁。

不得改变：Canonical Schema；21 aspects；FactID、NormID、EvidenceID 正式身份契约；Claim / Assertion 既有结构；正式中枢发布机制；Seed 与 Seedcheck 业务逻辑；GraphRAG；已冻结的 V2/V2-next 及 Gold 历史版本。

研究范围继续限定为 RFC 知识抽取至现有 Canonical 中枢。FTP、流量、源码、漏洞及专家知识正式扩展，必须等待 RFC 阶段验收后另行审批。

## 三、建立历史成果唯一登记册

首先只读核查仓库中现有的全部正式交付件。重点包括：

- N1-B 50 条人工审核。
- N1-C 50 条独立评估。
- V2-E4 队列 B：54 个片段、121 条有效知识及 9 个无目标知识片段。
- H3：23 条候选及 5 条补充知识。
- R13 的 57 条候选级分类 Gold。
- R14 一次性事后分类评估结果。
- R19 的 6 条最终原子 Gold v5。
- R25～R27B 的全部冻结报告。
- R27C 的 field_value、缓存隔离、Evidence 相关影子成果。

对每份人工 Gold 登记：原始任务与审核对象；样本 ID 与 RFC 来源；文件真实路径及 SHA256；原始人工标注；仲裁记录；最终 Gold 版本；适用指标；是否已用于开发或调优；是否曾作为独立评估样本；与其他 Gold 的重复关系；尚未裁定的字段；能否与当前正式基线比较。

规则：

- 不得将不同历史 Gold 的数量直接相加。
- 不得重做已有正式人工裁定。
- 不得把已揭盲或已参与调优的样本重新作为全新独立测试集。
- 原始人工记录、仲裁记录及版本差异必须全部保留。
- 历史文件缺失时先排查 Git 历史、交付索引与归档；确认无法恢复后才登记阻断，不得因一份文件暂不可读就重新发起人工审核。

## 四、固定 G0：已有批准修复的阶段性交付

当前只批准以下三项：Windows 单平台 CI；C-1 测试缓存隔离；C-2 field_value 真实抽取器修复。

首先检查 main 是否已完成上次授权的集成。已完成则直接核验 GitHub main 提交、四个 Windows job 真实结果及受保护文件哈希，不重复推送；未完成则继续执行此前已批准的独立集成任务。

不得直接合并整个 r27-shadow。

本阶段禁止纳入：C-3 行号基准候选；C-4 Evidence 精修；V2-next；散文缓存机制重构；其他未经批准的影子修改。

完成后冻结 main 完整 SHA 及相应输入、缓存、配置、版本哈希。集成失败则停在 G0，报告阻断项，不得用未经验证的版本冒充 R28 正式基线。

## 五、固定 R28：历史 Gold 复用与当前质量对账

R28 不再从零组织人工审核。执行顺序固定如下。

### R28-A Gold 资产核验

用第三节登记册确认所有可用真值，区分：历史开发样本；当时独立、后来已揭盲的评估样本；已冻结的人工仲裁 Gold；原始片段级知识清点结果；字段级真值；不在当前 RFC 输入范围内的历史样本。

### R28-B 历史 Gold 与当前知识对齐

建立链路：RFC 原文 → Gold → Raw Extraction → Norm → Canonical Fact → Evidence。

逐条区分：exact_match、semantic_equivalent、partial_match、missing_extraction、incorrect_extraction、duplicate_knowledge、incompatible_version、outside_current_scope、unresolved。

同一 Gold 不得重复计成功。跨协议、跨 RFC、不同版本须先确认可比较性。不能把 SIP 历史样本未出现在当前 SMTP/RTSP/DHCPv4 构建结果中当作漏抽。

### R28-C 复用现有真值计算质量指标

分别报告：已有人工范围内的知识识别覆盖；已抽取知识准确性；类型判别正确性；规范规则资格及语义字段正确性；Norm → Canonical 语义保全；Evidence 对命题的实际支持程度；文档、片段、知识命题三层覆盖差异。

每个指标须含分子、分母、适用范围、Gold 来源、冻结模型版本、是否历史回归、能否独立泛化推断、不可计算原因。

先用 V2-E4 队列 B 的 121 条原子知识分析其实际可比片段内的漏抽情况；不得把片段级召回推广为 41 份 RFC 的文档级或知识级召回。保留 R14 原始评估结果，不因判据变化而覆盖。

### R28-D 只输出新增人工真值缺口

仅在以下情况提出新人工审核：原审核未覆盖某必要知识类型；无独立原文清点无法形成召回率分母；当前修复需要未接触样本验证泛化；Evidence 是否支持命题存在无法由已有 Gold 解决的实质歧义。

必须先给出最小补充数量、样本来源、理由、人工工作量与预算。未经项目方单独批准，不得发放新审核表。

R28 结束后必须明确哪些指标可计算、哪些不可计算，不得为追求报告完整而编造指标。

## 六、固定 R29：基于 R28 结果的定点修复

R29 只修复有明确证据的实际缺陷。

### R29-A 已有抽取层缺陷收口

核对 C-3 行号基准统一的必要性及测试状态。继续保持 P-5 EvidenceID 迁移任务取消。不得重新宣称 231 条 locator 变化会导致 231 条 EvidenceID 变化。

### R29-B Evidence 证据正确性

91 条大偏移记录继续保留为专项诊断集。已自动识别的 46 条章节标题、32 条定义型行、13 条未判定记录，均不得直接当作人工正确性结论。C-4 定位精修继续冻结。

结合已有人工记录开展证据支持核验，必要时提出最小人工补充申请。修复应证明：新证据真实支持 Norm 命题；不只是 token 匹配；不错误定位其他章节同名字段；不伪造生成来源的 RFC 行号；EvidenceID 正式契约不变；旧中枢引用保持兼容。

### R29-C 零产出 RFC 与散文抽取缺口

保持 R25 的 41 份 RFC 输入基线，对 23 份零产出 RFC 逐文档归因。重点核查：原文是否有目标知识；解析与分块是否覆盖目标段落；确定性抽取器是否支持目标结构；散文通道是否被关闭；complete=false 缓存为何被拒收；缓存键与输入集合是否一致；LLM 客户端缺失时为何整批放弃；是否存在合法过滤；是否存在真正漏抽。

DHCPv4 继续遵守已证实的缓存结论：19 条状态机转移依赖 dhcpv4.transitions.json；不得再把 92→73 归因于 DHCPv4.prose.json；DHCPv4.prose.json 已有历史条目但 complete=false 的原因必须核查；不得直接把 complete=false 改为 true 来恢复数量。

如需新 LLM 调用，必须先报请求数、Token、预算、硬停止条件及可复算方案，等待审批。

### R29-D 分类与规范知识质量修复

优先参考 R14～R19 已有归因及 Gold。保持 V2/V2-next 已冻结版本，不根据旧 Gold 反复调参后再宣称独立验证通过。

必须区分：描述性知识；规范规则；语法知识；枚举或元数据；strength=unknown；规范资格不确定；合法缺省字段；真正的字段丢失。

每项修复先做正向、反向、旧 Gold 回归与影子整链验证，证明有效且无不可接受反向误判后才申请正式合入。

## 七、固定 R30：RFC 单源最终验收

R30 不重新设计系统，只验证经批准修复后的最终链路。必须完成：

1. RFC 原始输入、版本与哈希对账。
2. 文档解析与 Chunk 可复算。
3. 原始知识识别与丢失归因。
4. 知识类型与路由正确性验收。
5. L4→L5 验证门禁。
6. Norm 字段、知识身份与来源保全。
7. Canonical Fact/Claim/Assertion/Evidence 兼容性。
8. RFC-only 现有知识中枢影子构建。
9. 从最终知识反查 RFC 原文。
10. 已有人工 Gold 覆盖范围内的知识质量验收。
11. 必要的新增独立评估（仅限事先批准部分）。
12. 正式产物保护、版本冻结与回滚验证。

三协议 SMTP、RTSP、DHCPv4 作为既有整链回归基线。逐阶段报告输入、输出、知识身份、语义保全与问题原因。

不能以 262/262 映射成功代替知识质量通过；不能以 CI success 代替语义质量通过；不能以 18/41 文档有产出代替召回率。

未解决的关键缺口必须阻断正式接入，不得强行宣布 RFC 单源完成。R30 通过并经项目方审批后，才允许启动下一知识源扩展。

## 八、固定版本管理方式

GitHub 继续使用 main 作为唯一长期正式分支。本地可保留实验分支、独立 worktree 与补丁。只在明确的阶段性交付节点集成获批准的代码，未批准的影子代码不得混入 main。

每个正式阶段记录：完整 Git SHA；输入 SHA256；Gold 版本与哈希；抽取配置与模型版本；测试结果及统计口径；审批状态；回滚方法。

Windows CI 仅承担工程回归保护，不再为 Ubuntu 单独开展调试。除非未来正式提出跨平台运行需求，否则不重新开启 Linux CI 专项。

## 十、固定变更控制规则

本计划版本为 V1.0。除非项目方明确批准，不允许改变：七阶段架构；现有中枢冻结范围；R28 → R29 → R30 顺序；历史 Gold 复用原则；0 次未经批准的 LLM 调用；RFC 先于其他知识源的顺序；Windows 单平台 CI 决策。

确需修改时只允许提交正式变更申请，说明：哪条冻结规定需要变更；原计划为何无法继续；新证据是什么；对已有成果的影响；是否要求重新人工审核；是否修改已有 Gold；版本、成本与回滚影响。获批准后发布 V1.1，保留 V1.0 原件。

不得直接覆盖原计划，不得因一次局部调试失败重新制定整条路线。
