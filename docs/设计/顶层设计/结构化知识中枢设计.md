# 结构化知识中枢：重新设计（v2 · 按知识分类存储）

> 2026-11-08 · 设计稿（未实施）
> **定位（用户 v2 修正）**：
> 「我这个结构化知识中枢**针对目标协议的知识分类进行存储**，
> 后续对多个异构的知识源中提取里面关于协议的知识并**存入对应的位置**。」
>
> v1 的五层设计里 **L4（视图层）被否决** —— 视图不该是中枢的一层。
> 本版按「**知识分类 × 知识源**」二维重构。

---

## 〇、定位的精确化：三个可执行规则

把用户那句话拆成中枢必须满足的**硬规则**：

| # | 规则 | 含义 | 对设计的后果 |
|---|---|---|---|
| **R1** | **按「目标协议的知识分类」存储** | 中枢的**主结构 = 知识分类**（不是 aspect、不是源、不是文档） | 顶层目录 = 分类；每个分类有**槽位契约** |
| **R2** | **异构知识源抽出的协议知识汇入中枢** | 源是**输入方**，多个源都往同一批分类里写 | 源**不决定存放位置**，只作为 provenance |
| **R3** | **存入对应的位置** | 每条知识有**唯一确定的落点** | 需要一个**从「知识形态」到「分类槽位」的确定性映射** |

★ **R1 + R2 合起来的结构就是一张二维矩阵**：

```
                    知识分类（中枢的存放位置）
              ┌──────────┬──────────┬──────────┬──────────┐
              │ 结构     │ 交互     │ 约束     │ 构造     │
  知识源  ────┼──────────┼──────────┼──────────┼──────────┤
  rfc         │  A1 A2   │  B1 B2   │  C1 C2   │  D1 D2   │
  traffic    │  A3      │  B3      │  C3      │  D3      │
  source     │  A4      │  B4      │  C4      │  D4      │
  expert_note│  A5      │  B5      │  C5      │  D5      │
  vuln       │  A6      │  B6      │  C6      │  D6      │
              └──────────┴──────────┴──────────┴──────────┘
   ↑ 源不决定位置；同一格子里不同源的 claim 汇聚到同一个知识条目
```

★ **与现状的根本差别**：
- 现状：中枢按 **aspect**（= 某个实体的某个属性）分文件 ⇒ **一个实体散在多桶**；
- 本设计：中枢按 **知识分类**（= 一类知识的语义）分文件 ⇒ **一个分类里的知识聚在一起**，
  实体作为**分类内的分组键**。

## 一、知识分类体系（中枢的顶层结构）

分类的依据：**「这条知识回答了关于协议的什么问题」**（而不是「哪个源抽出来的」）。

### A 类 · 协议结构（Protocol Structure）
> 「这个协议**由什么构成**」—— 客观存在的东西清单

| 槽位 | 装什么 | 挂到哪类实体 | 现成的 aspect |
|---|---|---|---|
| `A1_methods` | 请求/方法及其定义 | method | `definition`(method) `existence` |
| `A2_headers` | 头字段/选项及其定义、语法 | header | `definition`(header) `syntax` |
| `A3_statuses` | 状态码及其含义 | status | `definition`(status) `value_type` |
| `A4_states` | 协议状态 | state | `existence`(state) |
| `A5_timers_params` | 定时器、协议参数 | timer/param | （缺，需扩展） |
| `A6_roles` | 参与者/角色 | actor | （缺，需扩展） |

### B 类 · 交互行为（Interaction Semantics）
> 「协议**怎么用**」—— 东西之间怎么连

| 槽位 | 装什么 | 现成的 aspect |
|---|---|---|
| `B1_transitions` | 状态迁移（源状态 → 方法 → 目标状态） | `target_state` |
| `B2_sequences` | 方法先后配对 | `method_sequence` |
| `B3_message_instances` | 一次交互的具体报文（含字段取值） | `message_instance` |

### C 类 · 约束规则（Constraints）
> 「协议**规定了什么必须/不许**」—— 规范性知识

| 槽位 | 装什么 | 现成的 aspect |
|---|---|---|
| `C1_required_headers` | 必带的头（全局 / 按方法） | `required_header_global` `required_header_by_method` `required_headers` |
| `C2_value_constraints` | 取值范围、长度上限、格式边界 | `legal_boundary` |
| `C3_preconditions` | 前置条件 | `precondition` |
| `C4_session_semantics` | 会话级头的语义 | `session_header` |
| `C5_url_templates` | URL 模板 | `url_template` |
| `C6_response_expectations` | 期望的响应 | `response_expectation` |

### D 类 · 构造与渲染（Construction）
> 「一条合法报文**怎么写出来**」—— 面向 fuzzer 的可用形态

| 槽位 | 装什么 | 现成的 aspect |
|---|---|---|
| `D1_syntax` | 字段语法（pattern / 顺序） | `syntax` |
| `D2_value_samples` | 合法取值样本 | `value_enum` |
| `D3_binary_layout` | 二进制布局（offset/length/顺序） | `binary_layout` `option_layout` |
| `D4_case_rules` | 大小写敏感规则 | `case_sensitivity` |

### E 类 · 观测与实现（Observation）
> 「实际跑出来**是什么样**」—— 经验性知识（★ 这一类天然多源）

| 槽位 | 装什么 | 现成的 aspect |
|---|---|---|
| `E1_frequency` | 出现频次 | `occurrence` |
| `E2_observed_samples` | 实测取值样本 | （现混在 `value_enum` 里，★ 应分开） |

### F 类 · 安全与漏洞（Security）
| 槽位 | 装什么 | 现成的 aspect |
|---|---|---|
| `F1_security_properties` | 安全属性 | `security_property` |
| `F2_vuln_patterns` | 漏洞模式 | `vuln_pattern` |
| `F3_field_guidance` | 字段级漏洞引导 | （现只在 profile.json 里） |

★ **六个分类的判据（可测试）**：
| 分类 | 判据 |
|---|---|
| A | 回答「**有什么**」 |
| B | 回答「**怎么连**」 |
| C | 回答「**必须/不许怎样**」 |
| D | 回答「**怎么写出来**」 |
| E | 回答「**实际什么样**」 |
| F | 回答「**哪里可能出错**」 |

## 二、存储布局

```
derived/per_source/<协议>/
├── index/
│   ├── entities.jsonl          ← ★ 全局实体主表（跨分类的唯一实体索引）
│   └── slots.json              ← ★ 槽位填充统计（每个槽位多少条/哪些源）
├── A_structure/
│   ├── methods.jsonl
│   ├── headers.jsonl
│   ├── statuses.jsonl
│   ├── states.jsonl
│   ├── timers.jsonl
│   └── roles.jsonl
├── B_interaction/
│   ├── transitions.jsonl
│   ├── sequences.jsonl
│   └── message_instances.jsonl
├── C_constraints/
│   ├── required_headers.jsonl
│   ├── value_constraints.jsonl
│   ├── preconditions.jsonl
│   ├── session_semantics.jsonl
│   ├── url_templates.jsonl
│   └── response_expectations.jsonl
├── D_construction/
│   ├── syntax.jsonl
│   ├── value_samples.jsonl
│   ├── binary_layout.jsonl
│   └── case_rules.jsonl
├── E_observation/
│   ├── frequency.jsonl
│   └── observed_samples.jsonl
├── F_security/
│   ├── security_properties.jsonl
│   ├── vuln_patterns.jsonl
│   └── field_guidance.jsonl
└── ledger.json                 ← ★ 纯度台账（分类 × 源 × 允许状态）
```

★ **实体主表在 `index/` 而不是某个分类里** —— 因为实体**跨分类**（`INVITE` 同时出现在 A1/B1/C1）。
分类内的组织方式是 **entity 分组**：

```jsonl
// A_structure/methods.jsonl
{"entity_id":"sip:method:invite",
 "entity":{"type":"method","name":"INVITE","canonical_name":"INVITE","aliases":["invite"]},
 "claims":[
   {"slot":"definition","owner":"rfc","value":{"type":"text","data":"..."},
    "epistemic":"normative","evidence":"file:rfc3261.txt#@1562","confidence":"high"},
   {"slot":"existence","owner":"traffic","value":{"type":"scalar","data":true},
    "epistemic":"observed","evidence":"traffic_raw:traffic.method.INVITE","confidence":"medium"}
 ],
 "resolution":{"definition":{"winner":"rfc","reason":"higher authority"},
               "existence":{"winner":"rfc","reason":"consensus"}}}
```

★ **一次读取 = 一个分类的全部知识**，按 entity 分组 ⇒ 「INVITE 在中枢里有什么」一次查询搞定。
★ **多源竞争显式化**：同一 `slot` 下多个 claim 并列 + `resolution` 记录裁决。

## 三、源如何汇入（**对齐的写入协议**）

★ 本节就是**对齐层的写入协议**：每个源抽取器产出**候选 claim**（源隔离），
由中枢按**确定性规则**把它们对齐到统一事实空间并落位：

```
① 源抽取器产出 claim：
   {slot_kind, entity_ref, value, epistemic, evidence, confidence}

② 中枢按 slot_kind → 分类槽位 的**映射表**落位（确定性，无歧义）：
   "definition"@method   → A_structure/methods.jsonl     slot="definition"
   "target_state"         → B_interaction/transitions.jsonl
   "legal_boundary"       → C_constraints/value_constraints.jsonl
   ...

③ 同一 (entity_id, slot) 已有其它源的 claim ⇒ **并入 claims 数组**（★ 不合并丢弃），
   按 resolution_semantics 裁决（默认 consensus），
   ★ **裁决结果写进 resolution**（谁说的 / 谁赢了 / 为什么 ⇒ 可审计）

④ 落盘后更新：
   - index/entities.jsonl（新增实体则登记）
   - index/slots.json（各槽位计数 + 源分布）
   - ledger.json（各分类 × 各源的 claim 数 + allowed 状态）
```

★ **关键**：源**不写目录**，只写**槽位**。⇒
- 加一个新源 ⇒ 只改抽取器，**中枢结构不动**；
- 换协议 ⇒ 只换 kb，**分类与槽位契约不动**；
- ★ **异构被对齐掉的地方就在 ②③ 之间**：不同源、不同形态、不同证据强度的知识，
  在此收敛为同一 `(entity_id, slot)` 下的多条 claim，**并留下消解痕迹**。

## 四、槽位契约（中枢的 schema）

新增 `core/fused/hub/knowledge_slots.json`：

```json
{
  "version": "1.0",
  "categories": [
    {"id":"A_structure","name":"协议结构",
     "question":"这个协议由什么构成",
     "slots":[
       {"name":"methods","aspect":"definition",
        "entity_types":["method"],"value_type":"text",
        "resolution":"consensus","cardinality":"one"},
       {"name":"methods","aspect":"existence",
        "entity_types":["method"],"value_type":"scalar",
        "resolution":"consensus","cardinality":"one"}
     ]},
    {"id":"B_interaction","name":"交互行为",
     "question":"协议怎么用",
     "slots":[
       {"name":"transitions","aspect":"target_state",
        "entity_types":["relation"],"value_type":"text",
        "resolution":"consensus","cardinality":"one"}
     ]}
  ]
}
```

★ **与现有 `aspect_registry.json` 的关系**：
`aspect_registry` 定义「**一个实体有哪些属性**」（23 个 aspect）；
`knowledge_slots` 定义「**这些属性归到哪个知识分类**」（分类 + 槽位）。
⇒ **两者正交**，前者是「属性清单」，后者是「存放位置」。
⇒ 迁移时：`aspect → (category, slot)` 的映射表**一次性生成**，
现有抽取器**几乎不用改**（只改落盘位置）。

## 五、纯度台账（在这个结构下如何自证）

`ledger.json` —— **分类 × 源 × 允许状态**：

```json
{
  "protocol": "sip",
  "source_set": ["rfc"],
  "by_category": {
    "A_structure": {"rfc": 168, "profile": 0, "allowed": {"rfc": true, "profile": false},
                     "total": 168, "pure_ratio": 1.0},
    "B_interaction": {"rfc": 12, "profile": 107, "allowed": {...},
                      "total": 119, "pure_ratio": 0.10},
    "E_observation": {"traffic": 12, "allowed": {"traffic": false},
                      "total": 12, "pure_ratio": 0.0}
  }
}
```

★ **这才是「RFC 单源」的准确表达**：
不是笼统地说「这次只用 rfc」，而是
**「在 A 类（结构）上纯度 100%，在 B 类（交互）上纯度 10%（其余来自骨架）」**。

⇒ 论文可以**逐类声明**纯度，而不是一刀切。
⇒ 也**暴露了真正的短板**：SIP 的状态机（B 类）现在 90% 靠骨架。

## 六、早期 → 当前 的差异

| | （原两版对照） × 源） |
|---|---|---|
| 顶层结构 | L0 实体 / L1 属性 / L2 关系 / L3 规则 / L4 视图 | **A~F 六个知识分类**（+ `index/` 与 `ledger.json`） |
| 实体位置 | L0 独立层 | `index/entities.jsonl`（跨分类索引） |
| 关系 | L2 独立层 | 归入 B 类（`transitions`/`sequences`/`instances` 三个槽位） |
| 规则 | L3 独立层 | 归入 C 类 |
| 视图 | L4 独立层 | ❌ **取消** —— 视图是消费端的事，不进中枢 |
| 源 | 记录内 authority | 记录内 authority（不变）+ **台账按分类统计** |
| 落位规则 | 无显式规则 | **slot → (category, slot) 映射表**（确定性） |

★ **L4 取消后，「16 桶」怎么办**：
`bundle` 的 16 桶是**消费端契约**，改成「**从中枢按分类聚合**」即可
⇒ 消费端不用改，只是聚合源变了（从 `facts/<aspect>.jsonl` 改成 `A_*/`、`B_*/`…）。

## 七、现状 → v2 的差距（以 SIP 为例，361 条 fact）

| 分类 | 现状条数 | 落位 | 备注 |
|---|---:|---|---|
| A 结构 | ~230 | `A_structure/*` | definition 101 + existence 8 + syntax 45 + value_enum 62 + … |
| B 交互 | ~119 | `B_interaction/*` | target_state 51 + method_sequence 17 + message_instance 51 |
| C 约束 | ~14 | `C_constraints/*` | required_headers 14 + required_header_global 6 + by_method 1 |
| D 构造 | （与 A 重叠） | `D_construction/*` | ⚠️ `syntax`/`value_enum` 现在**同时**属于「结构」和「构造」⇒ 需**二选一** |
| E 观测 | ~5 | `E_observation/*` | occurrence 5；★ `value_enum` 里的实测样本应拆出来 |
| F 安全 | 0 | `F_security/*` | ★ 空类（vuln/security 只在 profile.json） |

★ **两处必须裁决**：
1. `syntax` / `value_enum` 归 A 还是 D？
   ⇒ 建议 **A（结构）**：它们描述「字段长什么样」= 协议结构；
   ⇒ D 类只留 `binary_layout`（二进制协议特有）+ 未来新增的渲染相关 slot。
2. `value_enum` 里**混了两种东西**：RFC 规定的取值（normative）与抓包实测的样本（observed）
   ⇒ **必须拆开**（这正是 E 类存在的意义）。

| # | 问题 | 选项 | 我的建议 |

再**按类逐个迁**（每迁一类验一次纯度数字）。

## 附：与《架构调整方案》的关系

《架构调整方案》第一部分是「协议骨架清理」（去污染），其阶段 2「移除下游骨架特权」
正好对应本设计的**台账**：`ledger.json` 一旦按分类统计，
「profile 是否被放行」就变成**可审计的数字**，而不是代码里的无条件 `_allowed.add`。

⇒ **本设计与架构调整方案可以合并推进**：先建分类与台账（看清每个分类的纯度），
再按台账数字决定哪些分类该清骨架、哪些该保留。
